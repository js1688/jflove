# v1.1.2 项目管理记录

## 一、版本目标与范围概述

**版本目标**：让 v1.1.1 引入的"登录有效期"下拉选项**真正生效**——打通从桌面端选择 → 请求 body 注入 → 服务端 JWT 签发 → 响应 `expires_in` 回写的完整链路。

**用户痛点（v1.1.1 遗留）**：v1.1.1 已提供"登录有效期"下拉 UI（30分/1h/2h/4h/8h）并记忆上次选择，但选 4h/8h 后 JWT 仍按默认 1h 签发，选项形同摆设。

**范围**：

- **服务端 `jflove-server`（核心改动）**
  - `jwt_utils.create_token` 新增 `ttl_seconds` 参数并做 clamp（60s ~ 28800s），返回 `(token, effective_ttl)` 二元组；
  - `auth_service.login()` 传入 `requested_ttl_seconds`，用同一个 `effective_ttl` 计算 JWT exp 与响应 `expires_in`（消除两边计算偏差）；
  - `auth_controller.login` 从加密 body 中读取 `requested_ttl_seconds`，非法值容错（try/except）不报错走默认值；
  - 向后兼容：不带字段的旧客户端签发默认 1h。
- **桌面端 `jflove-desktop`（配合改动）**
  - `auth_service.login()` 在 `local_max_seconds is not None` 时注入 `requested_ttl_seconds`；
  - 登录页布局重排：`QHBoxLayout` 让"有效期标签+下拉"同行、"返回+登录"同行（Material Design）。
- **数据库**：无表结构变更。
- **加密协议**：无变更（沿用 ChaCha20-Poly1305 信封 + v2 帧格式）。

**版本策略**：补丁版本（PATCH），服务端 + 桌面端双端同步升级。

## 四、风险与应对

| 风险 | 影响 | 状态 | 处置结果 |
|---|---|---|---|
| `expires_in` 与 JWT `exp` 两边分别计算导致毫秒级偏差 | 客户端本地会话定时器提前/延后触发 | ✅ 已闭环 | `create_token` 返回 `(token, effective_ttl)` 二元组，`auth_service.login` 同一个值两用，无偏差 |
| 恶意客户端传 `requested_ttl_seconds=99999999`（无上限） | 签发超长有效期 JWT，增大令牌泄漏窗口 | ✅ 已闭环 | 服务端 `JWT_EXPIRE_MAX_SECONDS = 28800`（8h）硬 clamp，超界直接压到 28800，不报错不给攻击面 |
| 传负数/0 或字符串导致服务端报错 500 | 恶意/老客户端可能导致登录接口抛异常 | ✅ 已闭环 | `try/except (TypeError, ValueError)` 容错，非法值视为 `None` → 默认 1h；0/负数 → clamp 到 60s |
| v1.1.1 客户端连接 v1.1.2 服务端时兼容性 | 不传字段时服务端应保持 1h 默认行为 | ✅ 已闭环 | `requested_ttl_seconds is None` → `JWT_EXPIRE_DEFAULT_SECONDS = 3600`，行为与 v1.1.1 完全一致 |
| 登录页布局重排影响既有用例 | v1.1.1 登录页测试用例可能失效 | ✅ 已闭环 | 测试报告：v1.1.1 回归 46 用例全部通过；新增 3 个布局专项用例覆盖 AC-1/AC-2 |
| 双端同步升级（服务端 + 桌面端），比 v1.1.1（仅桌面端）发布复杂度高 | 版本号 5 处需同步，任一遗漏阻塞发布 | ✅ 已闭环 | devops 逐项核查全部 5 处版本号；代码审查报告已在发布前核对一轮 |
