# v1.1.3 项目管理记录

## 一、版本目标与范围概述

**版本目标**：为文档管理页面新增常规写操作——**重命名**与**移动到…**，并实现磁盘级写权限感知，使不同权限的用户在操作层面得到精确控制。

**用户痛点（v1.1.2 遗留）**：文件/目录只能删除，缺少重命名与移动能力，整理文档需手动删除后重建，体验差。

**范围**：

- **服务端 `jflove-server`（核心新接口）**
  - 新增 `POST /api/v1/files/rename`：重命名文件/目录，路径穿越防护 + 磁盘权限校验；
  - 新增 `POST /api/v1/files/move`：移动文件/目录（同磁盘），目标冲突 409 + 来源不存在 400 + 权限校验；
  - `GET /api/v1/files/disks` 响应新增 `can_write` 字段（向后兼容，原字段不变）；
  - `file_service.py` 新增 `rename_file()` / `move_file()` 方法及 `_safe_join()` 路径防护工具。
- **桌面端 `jflove-desktop`（交互扩展）**
  - `file_service.py` 新增 `rename_file()` / `move_file()` 服务方法；
  - `file_page.py` 新增 `MoveTargetDialog`（懒加载目录树选择弹窗）；
  - `FilePage` 右键菜单扩展：文件 7 项 / 目录 4 项；新增 `_rename_item()`、`_move_item()` 方法；
  - `_can_write` 状态随磁盘切换实时更新，无写权限时重命名/移动/删除均禁用。
- **数据库**：无表结构变更。
- **加密协议**：无变更（沿用 ChaCha20-Poly1305 信封 + v2 帧格式）。

**版本策略**：补丁版本（PATCH），服务端 + 桌面端双端同步升级。

## 四、风险与应对

| 风险 | 影响 | 状态 | 处置结果 |
|---|---|---|---|
| **M-1（中等）rename/move 路径不存在时返回 400 而非设计约定的 404** | 客户端错误处理逻辑不能按 HTTP 语义区分"参数错误"与"资源不存在"，调试体验略差 | ⚠️ 接受，列 v1.1.4 | 本版本 `ValueError` 统一被 controller 捕获为 400；不影响功能正确性与安全性；测试报告已标注；devops 发布记录已说明；v1.1.4 改用 `FileNotFoundError` → 404 修复 |
| `MoveTargetDialog.currentItemChanged` 信号连接时机 | 若在 `_setup_ui()` 中连接，`addTopLevelItem` 自动选中根节点会立即启用确认按钮，与设计（未选时禁用）矛盾 | ✅ 已闭环 | 信号连接移到 `__init__` 中 `_load_root()` 之后，确保根节点添加时信号尚未连接；对应测试用例从"show 后检查"改为"show 前检查"避免 Qt 自动选中干扰 |
| `sqlite3.Row` 对象不支持 `.get()` 方法 | `permission_service.check_disk_permission` 若直接 `.get()` 会抛 `AttributeError` | ✅ 已闭环 | 服务端已在查询后 `dict(p)` 转换，`check_disk_permission` 返回普通 dict，`can_write` 字段正常访问 |
| 懒加载目录树首屏大磁盘性能 | 磁盘根目录子目录极多时，懒加载也会有一定延迟 | 可接受 | 设计已约定懒加载（仅拉取当前层子目录）；Worker 线程异步，UI 不阻塞；本版本不做进一步优化 |
| 双端同步升级发布复杂度 | 版本号 5 处需同步，任一遗漏阻塞发布 | ✅ 已闭环 | devops 逐项核查全部 5 处版本号，均已对齐 "1.1.3" |

## 六、§9 安全宪法专项核验

| 条款 | 核验结论 |
|---|---|
| §9.1 加密通道：rename/move 接口走加密信封，路径不在 URL | ✅ 合规 |
| §9.1 明文白名单仍 3 项（/health / key-exchange / admin-exists） | ✅ 合规，未扩大 |
| §9.1 错误响应（400/401/403/409）均走加密 handler | ✅ 合规，测试专项验证 |
| §9.2 PFS 保持：session_key 仍仅内存，不引入长期密钥 | ✅ 合规 |
| §9.3 鉴权：JWT 仍只走加密 body 的 `token` 字段；新接口无 Authorization header | ✅ 合规 |
| §9.3 路径参数权限：disk_id 路由做磁盘权限校验（`check_disk_permission`）；无写权限 → 403 | ✅ 合规 |
| §9.4 响应头：rename/move 响应不含 filename/path 等敏感元数据 | ✅ 合规 |
| §9.4 日志：file_service 日志仅记录 disk_id 和路径长度，不含明文路径内容 | ✅ 合规 |
| §9.5 加密原语：复用现有 `decrypt_request_body` / `encrypt_response`，未引入新算法 | ✅ 合规 |
| §9.6 桌面端：HTTP 调用全走 `http_client`，无 `import requests` | ✅ 合规（grep 0 命中） |
| §9.7 自查：新接口有路径参数校验；body 走 decrypt；成功/错误均走加密响应 | ✅ 全部勾选 |
| 代码审查报告安全宪法各条款对照核查：无未解决严重项 | ✅ 全部通过 |
