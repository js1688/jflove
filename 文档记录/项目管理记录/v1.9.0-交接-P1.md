## 4. 现状取证（设计阶段直接引用，不必重新翻代码）

### 4.1 分片/临时文件固定位置

| 类型 | 固定位置 | 命名 |
|---|---|---|
| 上传分片 | `jflove-server/build/upload_tmp/<upload_id>/`（`settings.py:7` `UPLOAD_TEMP_DIR`） | `000000.chunk` … |
| 合并临时文件 | **目标文件同目录**（保证 `os.replace` 原子） | `.<文件名>.jflove-upload-<upload_id>.part`（`file_service.py:501-508`） |
| 上传会话元数据 | 现状只在内存 `_upload_sessions`（`file_service.py:37`） | — |
| 离线下载临时 | `<目标目录>/.jflove-download/<task_id>/`（`settings.py:66`；`media_fetcher_service.py:432`） | 完成后清理子目录，父目录残留 |
| 媒体修复产物 | `<原文件目录>/.jflove-repair/`（`settings.py:48`；`repair_task_service.py:65`） | 任务产物 |

### 4.2 问题根因（已在需求文档 §0.3 / §0.5 写清）

1. **相册同步走通用上传接口**：`album_backup_service.dart:950` → `transfer_service.dart:239`。
2. **合并同步长请求**：`complete` 在请求内逐片读 → 写临时文件 → SHA256 → 原子替换（`file_service.py:435-596`）；
   App `receiveTimeout=120s`（`app_config.dart:18-20`），3GB 合并必然超时。
3. **失败即删分片**：App 上传失败主动 `DELETE /upload/{id}`（`transfer_service.dart:306-311`）。
4. **服务端会话只在内存、无状态查询、init 不复用指纹**（`file_service.py:37/370-394`）；
   服务端重启/清理后旧 `upload_id` 直接失效。
5. **progress 在合并完成、会话删除后 403**（`file_controller.py:249-258`）。
6. **清理不一致**：TTL 24h（`file_service.py:40`）vs 启动首轮 1h（`main.py:36-41`）。
7. **`.jflove-download` 会显示**：`list_files` 只过滤 `.jflove-repair`（`file_service.py:322`）；
   `/scan` 的 `_collect_tree` 不过滤隐藏（`file_service.py:115-149`）。
8. **内存误解**：分片逐片写盘（`upload_chunk`），合并逐片读盘；内存峰值 = 并发请求 × 单请求几 MB
   （`middleware.py:15-54` 的整包读 + 解密 + JSON + base64 副本），**不随 3GB 线性增长**。
   「上传时播放卡」的真实原因是：合并的 `sha256.update` 跑在事件循环线程、**无全局合并并发上限**
   （`file_service.py:455-466`；App 同时 3 个传输任务）、播放流式帧与合并共用事件循环/线程池、
   1MB 分片在弱 CPU 上放大分配/GC。`N2840 + 8GB` 下多文件并发合并会打满 CPU/IO。
9. **桌面端已有客户端侧上传续传**（`jflove-desktop/src/services/file_service.py:246-380`，本地
   `upload_resume.json` + 分片级重试 + complete 子线程 + 远端核验），App 没有；设计可参考它。
10. **下载无 Range**：`file_controller.py:322-361`；桌面 `http_client.py:519-590`；Web `file-service.ts:108`。
11. **合并生成器可复用**：`_build_range_stream_generator`（`file_controller.py:534-584`）已支持任意字节区间；
    `file_service.get_stream_range`（`file_service.py:911-971`）已做 range 规范化，可复用于 `/download`。

## 5. Phase 2 设计要求（下个会话必须覆盖）

设计文档 `文档记录/设计文档/v1.9.0.md` 至少包含：

1. **协议/接口表**：`init`（新增 `client_type`、指纹复用、返回 `received_chunks/resumed/expires_at`）、
   新增 `upload/status`、`complete` 异步（`merging` + 轮询）、`progress` 扩展（done/path/failed/排队状态）、
   `download` 的 `range_start` 与响应头；逐接口标注鉴权、加密信封、错误码。
2. **会话持久化**：`session.json` 字段、启动恢复、以磁盘分片为准重建 `received`、TTL 读取、并发锁。
3. **合并异步 + 线程化**：`asyncio.to_thread` 的边界、进度更新方式、全局合并信号量（默认 1、可配）、
   排队状态、失败语义（缺片/hash/IO）、重启兜底。
4. **统一临时根**：每磁盘根一个隐藏根（建议 `.jflove-tmp`）及其分类子目录；
   旧 `.jflove-download` / `.jflove-repair` 迁移算法与失败兜底；合并 `.part` 例外说明。
5. **隐藏项过滤**：`list` / `scan` / `journal` 过滤规则；程序保留目录路径段拒绝清单
   （统一根 + 旧目录）；用户 `.` 文件精确路径兼容策略。
6. **清理算法**：TTL 单一来源、客户端类型过滤、启动首轮、孤儿目录、`.part` 精确匹配、
   真实路径校验、跳过告警、清理统计；「只删自产」的判据与测试设计。
7. **配置**：键名/默认/边界/校验（`config_controller` 钩子）、三端设置页字段与文案、
   配置缓存失效、立即清理。
8. **客户端**：三端续传记录格式、失败不删会话、分片级重试、异步 complete 轮询、
   下载 part/meta（App/桌面）、Web OPFS/IndexedDB 选型与降级、弱服务端模式预设、
   「检测到未完成上传 / 原分片已过期」提示。
9. **资源隔离**：上传并发信号量、分片 ≤1MB 校验、分片 512KB、合并并发 1、
   播放接口 P95 判据、可观测字段。
10. **数据库**：确认无 DDL；若设计改变结论，必须补 `jflove-db/migrate-1.9.0.sql` /
    `rollback-1.9.0.sql`（AGENTS.md §5.1.2）。
11. **测试设计**：AC-321~AC-365 逐条映射到用例（后端 pytest / 三端单测 / 实机证据）。
12. **安全对照**：逐接口标注 §9 检查项；清理误删安全用例单独列。

## 9. 风险提示（已写进需求文档 §9）

- **三端同步升级**：强制异步协议，任一端漏升级会导致上传失败；发布/UAT 记录必须写明同版本。
- **弱服务端 N2840/8GB**：合并并发 1、分片 512KB、上传并发 2 是默认建议；播放与上传同时进行仍可能有残余卡顿，
  需实机录像判据（AC-359）。
- **统一目录迁移**：旧 `.jflove-download` / `.jflove-repair` 迁移失败不得阻塞启动；旧残留按固定命名 TTL 清理。
- **隐藏过滤**：用户已有 `.` 文件不显示但可精确路径访问；新建 `.` 名称需提示「隐藏文件」。
