## 2. R1：磁盘四项

**模型**：`VirtualDisk` 的 `totalSize` / `usedSize` 原来用 `?? 0` 解析 —— 服务端不下发时恒为 0，
界面显示 `0 B`，会被误解成"真的没空间"。改为 `int?`，并新增 `freeSize` / `diskType`：

```dart
// 改前
totalSize: json['total_size'] as int? ?? 0,     // null → 0（错）
// 改后
totalSize: _toIntOrNull(json['total_size']),    // null → null → 渲染 —
```

同时补 `usedRatio` getter（总容量缺失或 ≤0 时返回 `null`，不画进度条）。

**格式化**：新增 `lib/utils/size_format.dart`，统一三端口径
（`B / KB / MB / GB / TB`，1024 进制，1 位小数），与 Web `format.ts::formatSize` 一致。
`formatSize(int?)` 传 `null` 返回 `—`；`orDash(String?)` 处理 `disk_type` 空值。

**渲染**：

| 位置 | 改后形态 |
| --- | --- |
| 文件管理 · 磁盘卡片 | `最大 951.6 GB · 已用 242.2 GB · 可用 708.7 GB · btrfs` + 容量进度条 |
| 管理 → 磁盘管理 · 列表项 | 同上（`最大 … · 已用 … · 可用 … · 类型`） |

## 3. P4：损坏媒体的中文引导 + 修复入口

### 3.1 两个独立缺陷

1. **文案**：界面上直接显示 `PlatformException(VideoError, Video player had error
   androidx.media3.exoplayer.ExoPlaybackException: Source error, null, null)` 原始英文。
2. **修复入口缺失**：服务端 415 带了 `[MEDIA_NEEDS_REPAIR]`，但 `_needsRepair` 永远是 `false`
   → 「立即修复」按钮不出现。

### 3.2 根因（第二点绕了两层）

**第一层**：ExoPlayer 抛的 `PlatformException` 里**不含**服务端 detail，detail 在 `_proxy.lastError`。
原实现只看 `e.toString()`，所以永远匹配不到。

**第二层（真凶）**：`stream_proxy.dart` 里解 415 信封的代码按 `Map` 判断：

```dart
final raw = resp.data;                          // ⚠ 这里是 ResponseBody（流）
final body = raw is String ? jsonDecode(raw) : raw;
if (body is Map<String, dynamic> && ...)        // 永远不成立
```

因为该请求用了 `ResponseType.stream`，`resp.data` 是 **`ResponseBody` 字节流**，不是 Map/String
→ 解密分支永不执行 → detail 恒为兜底串 `"服务端返回错误: 415"` → 页面识别不出
`[MEDIA_NEEDS_REPAIR]` → 修复入口不出现。

**第三层（竞态）**：`_server.listen` 里的 `_handleRequest` 不 await，而 ExoPlayer 收到代理的 500
会**立刻**抛异常 —— 页面 `catch` 读 detail 时，代理协程可能还没写完。

### 3.3 修复

1. `stream_proxy.dart`：按 `ResponseBody` 正确读流再解密
   （`raw.stream.toList()` → 拼字节 → utf8 → jsonDecode → 解密信封 → 取 `detail`）。
2. 新增 `lastServiceDetail`（只放服务端 detail 原文）+ `serviceError`（`Completer`），
   在拿到 4xx/5xx 时 complete。页面先 `await serviceError.future`（1.5s 上限）再读，消除竞态。
3. 页面按两种 415 语义分流（与 Web 同一口径）：

| 服务端 detail | 界面文案 |
| --- | --- |
| 含「已损坏」 | 「该文件已损坏，无法在线播放」 |
| 含「无法在线边下边播」 | 「该格式不支持在线播放，可修复为 MP4 后重试（桌面端可直接播放）」 |
| 其它（非 415） | `_humanizeMediaError()` 收敛为中文（解码/连接/会话类各给一句） |

两种 415 都显示「立即修复」按钮。

### 3.4 实测（真机）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| `broken_truncated.mp4` | `播放失败` + `PlatformException(VideoError, …)` 原始堆栈，**无**修复入口 | 「该文件已损坏，无法在线播放」+ **「立即修复」按钮**，无英文堆栈 |
| `good.mp4`（健康） | 正常播放 | 正常播放（`00:02 / 100%`，未回归） |

## 4. P5：服务器地址自动补协议

新增 `normalizeServerUrl()`（静态方法，便于单测）：

| 输入 | 归一化结果 |
| --- | --- |
| `10.0.2.2:8989` | `http://10.0.2.2:8989` |
| `http://127.0.0.1:8989` | 原样 |
| `HTTPS://host` | 原样（大小写不敏感） |
| `//host:8989` | `http://host:8989`（去前导斜杠） |

归一化结果**回写输入框**，让用户看见实际连接的地址。
改前填 `10.0.2.2:8989` 会抛 `FormatException: Scheme not starting with alphabetic character`
+ `DioException`；改后直接登录成功。

## 6. 排查过程中的一条重要发现（不是产品 bug，但影响取证）

媒体播放门禁（`/files/stream` 的 415 判定）依赖服务端能拿到 ffmpeg。本机 ffmpeg 不在默认 `PATH`，
我手工起的服务端实例没带 `PATH=/tmp/jfqa-bin:$PATH` 时 `probe_media` 会降级为
`available=False` → **门禁放行一切文件**（损坏文件也返 200）。

这不是 v1.10.26 引入的问题，但取证时若不注意会把"门禁没生效"误判成"移动端 P4 没修好"。
已记录：本地验证服务端必须让 ffmpeg 在 `PATH` 上，否则媒体相关用例无效。
