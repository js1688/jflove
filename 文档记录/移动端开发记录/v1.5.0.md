## 三、关键设计取舍

1. **颜色只允许出现在 4 个白名单文件**：`design_tokens.dart`（令牌本体）、`theme.dart`（Material 角色派生）、`mermaid_theme.dart`（mermaid 要求字面量）、`markdown_builder.dart`（高亮配色需与三端统一）。`Colors.transparent` / `Colors.white` 作为「无颜色」与渐变前景色豁免。由 `test/design_tokens_test.dart` 静态扫描强制。
2. **加载态用骨架屏而不是转圈**：骨架屏提前占住最终布局高度，内容到达时无跳动。`LoadingIndicator` 已无引用并标注 `@Deprecated`。
3. **主题偏好走 `flutter_secure_storage`**：移动端当前只有这一条已接入的持久化通道（`SessionManager` 复用），为不引入新依赖与新的存储原语而沿用；写入的是模式字符串，不涉及任何密钥内容。参考桌面端 `theme.json` 的语义。
4. **主题在 `runApp` 之前恢复**：否则首帧是默认跟随系统、下一帧才切成用户选的暗色，出现明显闪烁。
5. **图表缓存键 =「源码 + 主题 + 引擎版本」哈希**：日志只记哈希，不记图表源码（安全宪法 §9.4 第 14 条）。命中时不创建 WebView，二次打开秒开。
6. **关闭 Riverpod 自动重试**：见第五节，这是本轮发现的**真实体验缺陷**。

## 五、实现期发现并修正的缺陷（均非纸面推演，均已回归锁定）

1. **【真 bug】缓存命中的图表在重建时反复新建原生 WebView**
   `_StaticSvgView` 原本是 `StatelessWidget`，却在 `build()` 里 `WebViewController()`。
   主题切换、列表滚动、父级 `setState` 都会触发重建 → 每次都新建一个原生 WebView，
   旧控制器没有任何地方释放。→ 改为 `StatefulWidget`，`initState` 建一次，
   `didUpdateWidget` 仅在 SVG 变化时重载。

2. **【真 bug / 体验缺陷】Riverpod 3 默认自动重试让错误态 30 秒后才出现**
   实测：`t=0/100/300/1000/3000/10000ms` 时 `ErrorState` 出现次数恒为 0、骨架屏为 1；
   直到 `t≈30000ms` 才出现 `ErrorState`。根因是 `ProviderContainer.defaultRetry`
   （最多 10 次、指数退避 200ms→6.4s），期间 `AsyncValue` 处于「loading + 已有 error」，
   `AsyncValue.when` 一直走 loading 分支。**网络不通时用户看到的是永远转圈的骨架屏**，
   而不是「加载失败 + 重试」。→ `main.dart` 显式 `ProviderContainer(retry: (_, _) => null)`，
   失败立即呈现 `ErrorState`，由用户点「重试」再发起请求。回归用例
   `test/async_error_state_test.dart`（含「不应有自动重试，第一次失败后就停」断言）。

3. **【真 bug / 会让主题切换后图表不可读】已渲染的图表不随主题刷新**
   mermaid 的颜色是渲染时**烘焙进 SVG** 的（不是 SVG 内 CSS 变量），而
   `didUpdateWidget` 不感知主题变化 → 切到暗色后深色底上留着一整块亮色图表。
   → 补 `didChangeDependencies` 侦测 `brightness` 变化并重渲染。

4. **【框架断言】`ListTile` 放进带底色的容器会触发 Flutter 断言**
   `ListTile background color or ink splashes may be invisible`（debug 下报错、
   widget 测试直接判失败）。→ 在带底色容器内包一层
   `Material(type: MaterialType.transparency)`。

5. **【测试陷阱，已写成用例】换主题后立刻断言 `context.tokens` 拿到的是旧主题**
   `MaterialApp` 用 `AnimatedTheme`（200ms）包住子树，换主题后首帧动画 `t=0`，
   `ThemeData.lerp → _lerpThemeExtensions` 仍返回上一个主题的令牌。
   这条对**任何把颜色烘焙进产物**的组件都成立（Mermaid 正是），已写成
   `test/theme_test.dart` 的显式用例，避免后来者误判为 bug。

## 七、反馈修复第二轮（用户报「无法预览甘特图 / 图的显示面板有问题」）

### 1.【真 bug / 用户可见】尺寸归一化用了整图 `getBBox()`，被引擎的辅助线污染

`assets/mermaid/renderer.html` 里 v3 版本的尺寸归一化是：

```js
var bb = svgEl.getBBox();          // 把整张图的 bbox 当"内容尺寸"
if (bw > 0 && bw > w) { w = bw; }  // 并据此放大 viewBox
if (bh > 0 && bh > h) { h = bh; }
```

而 mermaid 会**故意**画一些远超图幅、靠视口裁掉的辅助图形：

- 时序图 `line.actor-line` 画到 y=2000（视口约 234）
- 甘特图 `line.today` 落在 x=28399（视口约 980）

于是 `getBBox()` 返回被这些线撑大的范围，并被**写进回传给 Flutter 的 SVG 字符串**。
实测（`设计预览/probe_app_renderer.mjs`，真 bundle + 真浏览器）：

| 图 | 引擎原始 viewBox | 回传串（APP 显示的那份） | 用户看到的效果 |
| --- | --- | --- | --- |
| 甘特图 | `0 0 980 128` | **`0 0 19292 128`** | 宽高比 151:1，压成一条细线 → **「无法预览甘特图」** |
| 时序图 | `-50 -10 440 234` | **`-50 -10 440 2012`** | 内容只占高度约 12%，缩在面板顶部 → **「显示面板有问题」** |

**修法**：不再用整图 `getBBox()`，改成按**真正值得装进 viewBox 的内容**量：

1. 所有非空 `<text>` 一律计入（文字被裁是最不可接受的）；
2. 图形只在**每个方向**的超出量不超过「该方向 viewBox 尺寸（下限 48）」时才计入 ——
   辅助线超出 1800~28000、真实内容不到 ~100，两类差一个数量级，判据不敏感；
3. 换算用"相对 SVG 自身 `getBoundingClientRect()` 的差值法"，**不用** `getCTM()`
   （离屏页里它会把页面位置算进去，实测偏 30 万）；
4. **只放不缩**：本来装得下的图尺寸不变。

### 2.【真 bug / 用户可见】展示页 CSS 无条件横向拉伸

`_wrap`（内联画布）与 `_viewerHtml`（全屏查看器）都是
`svg{width:100%!important}` —— 会把自然宽仅 ~131 的类图拉到手机宽度，方框与文字横向变形
（Web 端实测并修过同一个坑）。改为：

- 内联画布：`width:auto!important; max-width:none; height:auto!important` + 容器 `overflow:auto`
  —— 按固有尺寸显示，宽图（甘特图 980）横滑查看，窄图 `margin:0 auto` 居中；
- 全屏查看器：`width:auto!important; max-width:100%; height:auto!important`
  —— 允许等比缩小到屏幕宽，但**不放大**。

### 3.【真 bug / 静默失败】远端子目录读取失败被显示成"空目录"

`_loadSubdirs` 的 catch 只做 `_subdirs = []`，界面因此落到
「此目录下没有子文件夹」空态 —— **网络失败看起来像"远端没内容"**，且没有重试入口。
→ 新增 `_subdirsError` 字段，渲染改为三态（加载中 / 读取失败可重试 / 确实是空），
与本地目录选择器保持一致。

### 4. 缓存版本必须 +1

`renderConfigVersion` 由 `'3'` → `'4'`：v3 缓存里存的正是被 `getBBox()` 写坏的 SVG
（viewBox 19292×128 等），不失效的话老用户会继续看到压扁的图。

### 经验（已写入技能）

- **"整图 `getBBox()`"不是内容尺寸**：引擎会画超长辅助线（生命线、今日线），
  任何"按 bbox 撑开/收缩"的逻辑都必须过滤它们。三端同款陷阱（桌面端同源实现也有）。
- **判据要量在"真正交付给用户的那份产物"上**：APP 显示的是**回传串**，
  不是渲染页 DOM —— 只看 DOM 会得出"一切正常"的错误结论（本脚本第一版就是这样误判的）。
- **JS 里 `replace(str, str)` 会展开 `$'` / `` $` `` / `$&`**：给 3.4MB 的压缩 bundle
  做内联时，脚手架必须用函数形式的替换（Dart 的 `replaceAll` 是字面量的，没这个问题）。

## 八、反馈修复第三轮（用户报「甘特图还是显示不出来」）

### 根因：mermaid 按 WebView 的**布局视口**排版，而 Android 默认是 980px

上一轮修掉了 viewBox 被辅助线污染的问题，但甘特图仍然显示不出来。继续用同一份资产
做**视口条件对照**（`设计预览/probe_app_gantt_viewport.mjs`）后定位到：

Android WebView 在页面**没有 viewport meta** 时使用 **980px 的布局视口**，而 mermaid
的 `useMaxWidth: true` 按"能看到的宽度"排版：

| 渲染页的宽度条件 | 甘特图回传串 | 在 360 宽屏幕上的结果 |
| --- | --- | --- |
| 布局视口 980（原生默认，未钉宽度） | `viewBox="0 0 980 128"` | 980px 宽塞进 360px 屏：**要么压到 0.37x（11px 字号变 ~4px，不可读），要么被裁** |
| 布局视口 980 + **钉住 html/body = 360** | `viewBox="0 0 360 128"` | **360×128，14px 字号，整图完整可见** ✅ |

**为什么只有甘特图中招**：其它图的尺寸由自身内容决定（类图 ~130、ER ~144、流程图 ~355），
无论视口多宽都落在手机屏内；只有甘特图会**跟着容器变宽**（它把日期轴铺满可用宽度），
于是 980 的默认视口把它撑成了一屏放不下的宽图。

**顺带发现的第二层问题**：上一轮我把展示页 CSS 改成了 `max-width:none` + `margin:0 auto`，
想让宽图靠横滑查看 —— 实测这个组合下超宽图会**同时向左右两侧溢出**，而文档
`scrollWidth` 仍等于屏宽，**横滑也够不到**（等于把图藏起来）。已改为 `max-width:100%`
（必要时等比缩小），保证整图一定落在屏宽内。

### 改动

| 文件 | 改动 |
| --- | --- |
| `assets/mermaid/renderer.html` | 新增占位符（宽度）+ `mmApplyTargetWidth()`：在 `initialize()/render()` **之前**把 `html`/`body` 钉成 Dart 传入的展示宽度；另加 viewport meta。注释里写明"只钉 `#stage` 无效（实测 mermaid 看的是文档宽度）" |
| `lib/services/mermaid/mermaid_render_service.dart` | `buildHtml({code, theme, **width**})` + `_jsNumber`；`cacheKey(code, themeName, **width**)`（宽度影响排版 ⇒ 必须进缓存键，否则横竖屏互相命中）；`renderConfigVersion` `'4'` → **`'5'`** |
| `lib/widgets/mermaid_block.dart` | 新增 `_targetRenderWidth()`（优先用块自身实测宽度，拿不到退回"屏幕宽 - 内边距"，clamp 240~1200）并传给渲染页；展示页 CSS 改为 `width:auto + max-width:100% + height:auto` 并补 viewport meta |

### 验证

| 检查 | 结果 |
| --- | --- |
| `设计预览/probe_app_renderer.mjs`（真 bundle，判据量在回传串 + 同款展示页） | **2 种视口 × 7 类图 = 14/14 全绿**；新增两条判据：整图必须落在屏宽内、文字中位高度 ≥ 8px |
| 甘特图实测 | 360 视口：`viewBox="0 0 360 128"`、展示 360×128px、**14px 字号**、0 段被裁 ✅；800 视口：`0 0 800 128` ✅ |

## 九、「局域网播大视频卡死、移动网络反而正常」——背压缺失

- **用户现象**：手机移动网络（IPv6）播 1GB 视频正常；换内网地址（局域网，更快）播同一个
  视频就卡住、卡死。反直觉之处在于"更快的链路反而更差"。
- **根因**：`lib/utils/stream_proxy.dart` 的转发循环**没有背压**。

```dart
await for (final chunk in stream) {
  resp.add(chunk);      // ← 非阻塞：只往 HttpResponse 的内存缓冲里塞
}
await resp.close();
```

`HttpResponse.add()` 不阻塞，而 `HttpResponse` 的缓冲**无界**：

1. 播放器只按播放速率取数据，取不走的部分全堆在内存 —— **上游越快堆得越猛**。
   1GB 的视频足以吃满内存、GC 疯狂抖动 → 界面卡死；
2. 这条循环还跑在**主 isolate** 上（每 64KB 一帧的纯 Dart ChaCha20-Poly1305 解密），
   上游不停就永远不让出事件循环 → 界面失去响应。
3. 慢链路自带节流（TCP 窗口就是天然的限速器），所以移动网络反而正常 ——
   **正是因为快，才把背压缺失暴露出来**。

### 改动

| 位置 | 改动 |
| --- | --- |
| `_handleGet` 转发循环 | 每块之后 `await resp.flush()`：flush 会等到数据真正被 socket 接收，背压因此一路传导回上游（**播放器不取，就不继续下载、不继续解密**），内存占用与上游速率彻底解耦 |
| `_fetchStreamRequest` 的 `receiveTimeout` | `30 秒` → **5 分钟**：背压会在播放器缓冲满/用户暂停时**主动暂停读上游**，30 秒的"帧间无数据"超时会误判成连接故障。保留 5 分钟上限只为兜住"服务端彻底挂死" |
| `_handleGet` 的错误分支 | 客户端断开/异常时**也关闭响应**（旧实现直接 return，响应与连接一直挂着） |

### 验证

- `test/stream_proxy_backpressure_test.dart`（新增 4 条）：转发循环内必须同时有 `resp.add`
  与 `await resp.flush()`、不得再出现 30 秒级 `receiveTimeout`、`connectTimeout` 仍在、
  客户端断开分支必须 close 响应。**断言打在去注释后的代码上**。
- ⚠ **真实播放行为需要真机 + 大文件验证**（接口层已锁定，但"局域网播 1GB 是否还卡"
  只能在设备上确认）。建议复现方式：内网地址 → 播放 1GB 视频 → 拖动进度 → 长时间暂停
  →再恢复，观察是否还卡死、以及内存占用是否随播放时长线性增长（修复前会）。
