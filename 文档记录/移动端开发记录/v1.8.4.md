# JFLove v1.8.4 移动端开发记录

> 阶段：Phase 4b（快速修复通道，`AGENTS.md §7.5.3`）｜ 版本 **1.8.4** ｜ 角色：cross-platform-mobile
> 依据：v1.8.3 用户反馈（相册同步时 1GB+ 文件长期停在「校验中」且不上传）+ 历史候选台账
> 范围：仅 `jflove-app`；无服务端改动 / 无接口 / 无服务端 DDL（移动端本地 sqflite v4 → v5）

## 1. 问题与根因

**用户现象**：相册自动同步时，1GB+ 的视频经常长时间停在「校验中」，不上传；取消后其它文件也一起卡住。

**根因（v1.8.3 代码实据）**：

| # | 位置 | 事实 |
|---|---|---|
| R1 | `transfer_service.dart`（v1.8.3）`_doUpload` | `hashing` 阶段只做「读整文件 + SHA256」，**期间不更新任何进度** → `percent` 恒为 0 |
| R2 | `utils/file_hash.dart`（v1.8.3） | 纯 Dart `pointycastle` SHA256，实测 **37.5 MB/s**（1GB ≈ 27s，手机更慢）；`Isolate.run` **无法中断** |
| R3 | `transfer_service.dart` `maxConcurrent = 3` | 最多 3 个大视频**同时**哈希，手机 CPU 互抢 |
| R4 | `transfer_page.dart` | 徽标是静态「校验中」，进度条取 `percent`（恒 0）→ 观感就是卡死 |
| R5 | `transfer_service.dart` `cancel()` | 只置取消标志：哈希 isolate 继续跑满全程，`_concurrentRunning` 槽位不释放 → 后续任务一起排队 |
| R6 | `album_backup_service.dart` 失败重试 | 每轮自动重试 3 次，每次**重头再哈希**（无缓存） |
| R7 | 无看门狗 | 读取被存储/云端占位卡住时永远停在「校验中」 |

**哈希为什么必须保留**（用户质询后的结论，见 §6）：`file_hash` 是服务端 `complete_upload`
合并分片时比对的**传输完整性**依据（`jflove-server/src/services/file_service.py:527-536`），
并写入变更日志 `content_hash`；远端去重并不依赖它（那是本地远端索引的「同名 + 同大小」）。
服务端本来也要对整份数据算一遍，所以成本是协议固有的 —— 该优化的是**客户端算得慢、看不见、取消不掉、重试重算**。

## 3. 关键实现

### 3.1 校验段（F45）

- `IsolateHashingJob.start(path, onProgress:, stallTimeout:)`：
  - worker 每 16MB 回报一次 `{t:'p', d, n}`；结束回报 `{t:'d', h}`；异常回报 `{t:'e'}`；
  - 主 isolate 侧 `ReceivePort` 监听 → 回调进度；`Timer(stallTimeout)` 每收到一次进度重置，
    超时按 `HashingStalled` 失败（文案：「文件校验超时（90 秒无进展）：文件可能仅在云端，或存储暂时不可读」）；
  - `cancel()` 立即 `Isolate.kill(immediate)` 并以 `HashingCancelled` 结束，槽位当场释放。
- 校验并发 **1**：`TransferService.maxConcurrentHashes = 1`，避免多个大视频同时抢 CPU；
  校验完的任务回到「等待中」进 `_readyQueue`，下一个文件立刻开始校验（与上传重叠）。

### 3.2 哈希缓存

- key = `绝对路径 + size + mtimeMillis`，完全一致才复用；命中时任务直接显示「校验中 100%」并进入上传段；
- 落盘 `<应用支持目录>/transfer-hash-cache.json`，最多 500 条按写入时间淘汰；平台不可用时自动降级（不影响上传）；
- 依据：桌面端 `jflove-desktop/src/services/file_service.py::_cached_file_hash` 已是同款做法；
  相册备份「每轮自动重试 3 次」以前每次都重头哈希 1GB+，现在只有第一次付成本。

### 3.3 M-1 / M-2 / C1（历史遗留）

- **M-1**：`_ensureRemoteIndex` 因「有 pending 上传」跳过重建时置 `_indexRebuildDeferred`，
  随 `AlbumBackupProgress` 暴露，相册页明确写出原因（此前是静默沿用旧索引）。
- **M-2**：`AlbumBackupService` 提交前判 `_transfer.queueSaturated`（未开始传输的任务 ≥ 10），
  达上限则本轮只扫描不提交，剩余资源下一轮继续 —— 传输页不会无限变长，也不写失败记录。
- **C1**：`album_backup_fail` 增 `disk_id` / `remote_root`（本地库 v5），`markFailed/ failedEntries/
  failedCount / clearAllFailures` 全部按目标；换目标不再需要「清空失败记录」——回到同一目标仍可继续重试。
  升级时 `backfillFailureTarget` 把旧记录认领到当前目标，失败数不归零。

## 5. 已知限制

1. 校验期间仍会读整份文件：1GB 在桌面 x86 上约 16s（`crypto`），手机大核/小核调度会更慢；
   现在**有百分比**且可取消、重试不重算，但「1GB 只花 1 秒」是不可能的（SHA256 协议要求）。
2. 应用在后台被 Android 冻结/杀死时同步会暂停；恢复前台后继续（本轮未引入前台服务）。
3. 断网重传仍从第 0 片开始（服务端已保留分片，可做续传，本轮未做）。
4. 相册「仅 Wi-Fi」判定依赖 `connectivity_plus`，模拟器/部分机型可能把蜂窝识别为 Wi-Fi（既有行为）。
