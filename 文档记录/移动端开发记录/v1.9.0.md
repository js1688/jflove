# JFLove v1.9.0 移动端开发记录（Phase 4b）

> 版本：1.9.0｜角色：cross-platform-mobile｜日期：2026-11-09
> 需求：`文档记录/需求文档/v1.9.0.md`；设计：`文档记录/设计文档/v1.9.0.md`

## 1. 功能与改动点

1. **上传断点续传**
   - `TransferService._doUpload`：init 带 `client_type: "app"`；按服务端 `received_chunks` 跳过已传分片；网络/合并失败**不 DELETE** 服务端会话（仅用户取消时清理）。
   - 分片大小改为 **512KB**（`AppConfig.uploadChunkSize`）；单片失败指数退避重试最多 5 次（300ms 起）。
   - 新增 `TransferResumeStore`：本地记录 `upload_id / sent_chunks / expires_at`（应用支持目录 `transfer_resume.json`），服务端状态为准、本地仅兜底；每 16 片落盘一次，成功后清除。

2. **合并异步化**
   - `complete` 传 `async_mode: true`；每 2.5s 轮询 `upload/progress`，处理 `queued/merging/done/failed/unknown`；
   - 合并进度映射到任务百分比；`failed` 显示服务端中文原因；
   - `unknown` 时用远端列表核验同名同大小（避免「合并成功但响应丢失」重传）；
   - 兼容过渡期服务端/测试桩：complete 无 `state` 字段时按旧同步模式视为完成。

3. **下载断点续传**
   - 目标文件旁写 `<name>.jflove-part` + `<name>.jflove-part.json`（版本/大小/offset）；
   - 请求带 `range_start`；读取 `X-Stream-Offset` / `X-Stream-Total` / `X-File-Version`；
   - 版本不一致或 416 → 删除 part 从头一次；完成后校验大小并 `rename` 目标；失败保留 part/meta；取消删除。
   - `HttpService.encryptedDownloadStreamWithHeaders`：返回解密流 + 响应头；旧 `encryptedDownloadStream` 保持兼容。

4. **系统设置（管理员）**
   - `AdminSystemPage` 新增「存储与临时文件」卡片：自动清理开关、TTL(1~168h)、清理间隔(5~1440min)、客户端类型多选、孤儿保留期、每用户会话上限、合并并发(0~4)、分片并发(1~8)、弱服务端模式预设、立即清理；
   - `ConfigService.runCleanup()` 调 `POST /api/v1/config/cleanup`；
   - 文案明确「TTL 同时决定续传有效期与清理保护期」。

## 4. 与上一版差异 / 取舍

- 上传分片 1MB → 512KB；上传并发 3 → 2（弱服务端优先）。
- 失败重试语义：v1.8.4 失败即清服务端分片；v1.9.0 失败保留，仅取消清理。
- 服务端是「已收分片」唯一真相；本地续传记录仅兜底（跨重装/本地记录损坏时由 init 返回的服务端状态恢复）。
- `TransferResumeStore` 在平台通道不可用（单元测试/特殊环境）时写盘失败静默跳过，不阻断上传。

## 5. 已知限制

- 服务端若仍为 v1.8.x（无 `async_mode`/`client_type` 契约），App v1.9.0 不能完成上传——发布要求三端与服务端同版本。
- 下载 part 的 7 天清理尚未做「启动扫描」；目前依赖再次下载同一目标时判定。
- Web/桌面端命名口径（桌面 `<save>.part`、App `.jflove-part`）不同，均为本地隐藏文件，不影响服务端协议。
