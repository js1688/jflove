## 1. S2：出站出口（2026-10-20）

### 1.1 为什么先做这一片

本版是服务端**第一次主动出网**（需求 §4 / 设计 §1.4）。若先写分析器/下载器，
网络请求会散落在各 service 里，SSRF 策略、超时、大小上限、日志脱敏都无法统一收口。
因此顺序固定为：**出站出口 → 分析器 → 下载器 → 任务 → 接口**。

### 1.2 新增文件

| 文件 | 职责 |
|---|---|
| `src/utils/outbound_http.py` | **全仓唯一允许 `import httpx` 的模块**：UA/Referer、超时、逐跳重定向复检、大小上限、流式落盘、Range 续传、取消、URL 脱敏日志 |
| `src/utils/egress_proxy.py` | 仅绑定 `127.0.0.1` 的 HTTP/CONNECT 策略代理：随机端口 + 随机 Basic 令牌，每个请求过 `ssrf_guard`，供 yt-dlp / 无头浏览器使用 |
| `tests/test_offline_outbound_http_v1_8_0.py` | 21 条：策略拒绝零连接、重定向上限、大小上限、错误分类、续传、取消、日志脱敏、httpx 收敛不变量 |
| `tests/test_offline_egress_proxy_v1_8_0.py` | 13 条：只绑 loopback、407/403 且零连接、CONNECT/HTTP 转发、502、关闭不挂起 |

### 1.3 对外 API（供 S3/S4 使用）

```python
async with OutboundClient() as client:
    page = await client.get_bytes(url, max_bytes=OFFLINE_HTML_MAX_BYTES)
    await client.stream_to_file(
        segment_url, tmp_path,
        max_bytes=OFFLINE_SEGMENT_MAX_BYTES,
        resume=True, progress=on_progress, cancel_event=cancel_event,
    )

async with EgressProxy() as proxy:
    ydl_opts["proxy"] = proxy.proxy_url   # yt-dlp / Playwright --proxy-server
```

- 稳定错误码：`ssrf_blocked / invalid_url / net_timeout / network_error / too_many_redirects`
  `/ too_large / range_mismatch / canceled / http_status`，中文文案映射在 S3/S4 统一做（需求 F29）。
- `OutboundStatusError` 带 `status_code / headers / body(≤8KB)`，用于区分防盗链、签名过期、需登录。

### 1.4 关键实现决策

| 决策 | 做法 | 理由 |
|---|---|---|
| 重定向 | `follow_redirects=False` 手动跟随，**每一跳**先 `validate_url()` 再发 | 设计 §9.1 第 5 条；只校验首次会被 302 绕过 |
| 环境代理 | `trust_env=False` | 不读 `HTTP_PROXY` / `NO_PROXY` / netrc，出站路径只由本模块决定 |
| 编码 | 默认 `Accept-Encoding: identity` | 保证 Range / Content-Length / 大小预估语义不被 gzip 破坏 |
| 大小上限 | Content-Length 预检 + 流式累计双检 | 无 Content-Length 的响应也能在超限时立即中断 |
| 断点续传 | `Range` + 206 起点校验；200 截断重下；416 且总长相等视为完成 | AC-216；不把整文件追加成两倍 |
| 错误页 | `stream_to_file` 在写文件前抛 `OutboundStatusError` | 防止"下载成功但产物是 HTML 错误页" |
| httpx 日志 | 模块导入时把 `httpx` / `httpcore` 压到 WARNING | 实测 httpx 在 INFO 会打印**完整 URL（含 query 签名）**，违反设计 §9.2 |
| 代理认证 | `Proxy-Authorization: Basic jflove:<token_hex(16)>`，`hmac.compare_digest` | 设计 §9.1 第 8 条；令牌随进程随机生成，不落盘 |
| 代理上游 | 连接 `validate_url()` 返回的**已校验 IP**，而非再次解析域名 | 顺带收窄设计 §9.1 记录的 DNS rebinding 残余风险 |
| 代理关闭 | 先取消处理协程再 `wait_closed()` | Python 3.12+ 的 `wait_closed()` 会等活跃连接，长隧道会卡住停机 |

| 主题 | 做法 |
|---|---|
| L1（yt-dlp） | `extract_info(download=False)`；`skip_download/noplaylist/socket_timeout=20/cachedir=False`；**必须**传 `proxy=<策略代理 URL>`；在线程里执行，失败只降级不炸整次分析 |

### 4.1 改动文件

| 文件 | 改动 |
|---|---|
| `src/repositories/offline_download_repository.py` | 新增 `_ITEM_SOURCE_UPDATABLE` 白名单、`refresh_item_source()`、`reset_failed_items()` |
| `src/services/offline_download_service.py` | 新增 `_match_reanalysis_item()` / `_auto_reanalyze()` / `_fetch_selected_items()` / `_sync_state_from_items()`；下载 worker 增加「过期 → 重分析一次 → 断点续传」循环；修正多任务项进度重复计数 |
| `tests/test_offline_reanalyze_v1_8_0.py` | 新增 8 条回归（自动重分析成功/仍失败/队列满/其他错误不触发/断点不重下/匹配优先 variant_id/重分析失败/进度不重复计数） |

### 4.2 修改前后逻辑

**修改前**：`self_fetch_item()` 遇到 `FetchError("url_expired")` 直接把 item 置 `failed`，
下载 worker 把任务置 `failed` + `url_expired`，用户只能自己重新贴地址。

**修改后**（`_run_download`）：

```text
下载被勾选项（已成功项跳过）
  └─ FetchError(url_expired) 且本轮尚未重分析
       ├─ 分析队列 ≥ OFFLINE_QUEUE_MAX(20) → 放弃，按 url_expired 失败
       ├─ 调 MediaAnalyzerService.analyze(原页面) 一次
       │    ├─ 失败/异常 → 放弃，仍按 url_expired 失败
       │    └─ 成功 → 按 variant_id → display_name → ext/宽高 匹配旧项
       │             刷新 source_url/aux_url/宽高/时长/体积（不碰 status/勾选/产物名）
       │             只重置「确实被刷新过」的 url_expired 失败项
       ├─ 同步已成功项进度，再跑一轮（已成功项不重复下载）
       └─ 仍过期 → 失败 + url_expired（只重试一次，不循环）
```

### 4.3 关键设计取舍

1. **重分析用原页面 URL，不用媒体直链**：媒体直链签名过期后不可分析；原页面重新解析才能拿到新签名。
2. **内联执行而非入分析队列**：下载 worker 需要拿到新清单才能继续；用 `count_pending()` 做与设计一致的
   队列额度判断，队列满即不重分析，避免雪崩。
3. **匹配不做「按顺序硬配」**：站点改版时错配会把 A 的地址写到 B 上；宁可最终失败也不下载错内容。
4. **保留断点与勾选**：只刷新来源字段，已成功项/产物名/用户勾选不动；重试轮跳过已成功项。
5. **失败语义不变**：重分析自身失败不把分析错误透给用户，最终仍是 `url_expired`（AC-225 原文要求）。

### 4.4 顺带修复：多任务项进度重复计数

E2E 发现任务 `bytes_done = 2 × 文件大小`（如 2,848,208 B 的文件显示 5,696,416 B）。
根因：`self_fetch_item()` 的进度回调已把本次下载字节写入 `state["done"]`，结束时又
`state["done"] += outcome.bytes_written`，同一批字节计两次；多任务项时还会让进度卡住。
修复：为每项传入 `base_done`，回调写 `base_done + done`，结束后按 `base_done + 产物字节`
**赋值**而非累加；图片批次同理按批次基准重算。新增回归用例断言 `bytes_done == bytes_total == 100`。
