# v1.4.2 后端开发记录：手动离线媒体修复 + 播放路径纯净化

## 一、变更概述

v1.4.2 把媒体修复从「播放时实时计算」迁移到「播放前离线完成」，播放路径零 ffmpeg：

| 编号 | 变更 | 说明 |
|------|------|------|
| ARC-1 | **移除 time 实时修复流** | `stream_repaired_frames` / `ensure_playable` 整体删除；`/stream` 只输出健康文件字节流 |
| ARC-2 | **播放门禁** | `/stream` 播放前探测，真损坏文件 415 + `[MEDIA_NEEDS_REPAIR]` 错误码前缀；MKV/AVI/moov 尾部等原生可播格式放行 |
| ARC-3 | **离线修复任务** | 新增任务表 + asyncio 队列 worker；ffmpeg 无损重封装产物落盘 `.jflove-repair/` |
| ARC-4 | **产物管理** | 自动验证（probe 有流+无致命错+有时长）→ success；覆盖 = `os.replace` 原子替换（不留备份）；删除产物/记录 |
| ARC-5 | **健康判定修正** | `_moov_at_front` 不再要求 mvex：faststart MP4（moov 前置）判定为健康（v1.4.1 把它误判为需修复，是播放卡顿重灾区） |
| ARC-6 | **隐藏目录防护** | `list_files` 过滤 `.jflove-repair`；`_safe_join` 拒绝任何含该路径段的访问（下载/删除/重命名全拦截） |

## 二、新增 API（6 个，全部加密 body）

| 接口 | 方法 | 鉴权 | 说明 |
|------|------|------|------|
| `/api/v1/files/repair/create` | POST | JWT + 磁盘写+删 | 创建修复任务；健康拒绝（400 无需修复）；同文件未完成任务拒绝 |
| `/api/v1/files/repair/tasks` | GET | JWT | 任务列表（分页，**全平台共享**——所有登录用户可见，避免重复修复） |
| `/api/v1/files/repair/cancel` | POST | JWT + 磁盘写+删 | 取消（pending 直接取消；running/verifying 置信号，worker 终止 ffmpeg 清理半成品） |
| `/api/v1/files/repair/override` | POST | JWT + 磁盘写+删 | 覆盖原文件（原子替换、直接删除原文件不留备份；客户端须先二次确认） |
| `/api/v1/files/repair/delete-artifact` | POST | JWT + 磁盘写+删 | 删除未覆盖产物；空目录顺带清理 |
| `/api/v1/files/repair/delete-record` | POST | JWT | 软删除终态任务记录 |

`/stream` 扩展：请求体新增可选 `repair_task_id`（验证播放修复产物，复用同一 v2 加密帧管线，支持字节 range）；meta 帧 `stream_mode` 恒为 `"byte"`（字段保留，三端统一判断）。

任务状态机：`pending → running → verifying → success/failed/canceled`；`success --覆盖--> overridden`。服务重启时 startup 把未终态任务标记 failed 并按任务表目录范围清理 `*.repairing.mp4` 半成品。

## 五、关键设计取舍

1. **播放门禁只拦"真损坏"，不拦"格式不理想"**：`is_broken_media`（门禁）与 `is_mse_friendly`（修复必要性）分离。MKV/AVI 等在桌面/移动端原生可播，播放放行原文件字节流——三端原生播放器能力交还给端侧，服务端不再代劳转码。修复入口判定仍用 `is_mse_friendly`（MKV 可无损转 MP4，值得修）。
2. **`_moov_at_front` 放宽**：v1.4.1 要求 mvex（fMP4）导致 faststart MP4 被判"需修复"→ 每次播放都实时转码（卡顿根因之一）且修复产物（faststart）覆盖后会再次被判需修复形成死循环。v1.4.2：moov 前置即健康。
3. **产物写临时名再 rename**：`{stem}.repairing.mp4` → 成功 rename 正式名；取消/失败/超时删临时文件；失败重试创建前先按任务记录精确清理旧产物——任何路径不留垃圾。
4. **覆盖用 `os.replace`**：单原子调用完成"删除原文件+顶替"，无中间态（Windows/Linux 均原子）；不留备份（用户决策）。
5. **worker 进度估算**：临时产物大小 / `source_size` 百分比（节流 1s），上限 99；验证通过写 100。无损重封装产物大小 ≈ 源大小，估算误差可接受。
6. **重启恢复不续传**：startup 把未终态任务标记 failed（错误信息"服务重启导致任务中断"）；无损重封装很快，重跑成本低（用户决策：不支持断点续修）。

## 六、安全落实（§9 宪法）

- 6 个新接口全部 `decrypt_request_body` + `encrypt_response`，不在明文白名单；无路径参数路由（task_id 在加密 body 内）
- 操作接口统一校验磁盘写+删权限（任务全平台共享，不做归属隔离；只读账号可看列表不可操作）
- 产物路径由服务端任务记录推导（`_safe_join(磁盘根, rel_path)` + 隐藏目录），客户端不可传路径；隐藏目录路径段在 `_safe_join` 层统一拒绝
- `/stream` 产物流复用 `StreamingResponse + encrypt_stream_chunk`（v2），无 FileResponse
- 日志只记 task_id / disk_id / 状态，不记文件名与路径明文
- ffmpeg 参数列表（无 shell 拼接），stderr 丢弃
