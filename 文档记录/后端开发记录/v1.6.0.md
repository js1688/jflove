## 3. BL-8：`complete_upload` 覆盖写原子化（重点 · 数据安全）

### 3.1 改前的危险链（`src/services/file_service.py`，HEAD 版本行号）

| 步 | 代码位置 | 危险 |
|----|---------|------|
| ① | `:270` `async with aiofiles.open(dest_file, "wb") as out:` | **目标文件原位置先被截断**：只要进入这一行，原文件就已经没了 |
| ② | `:271-276` 循环读分片并写入 | 任一 `aiofiles.open(chunk_path,"rb")` 失败（分片丢失 / IO 异常 / 连接中断 / 进程被杀）⇒ 目标文件停在**半截内容** |
| ③ | `:279-281` `if sha256.hexdigest() != session["file_hash"]: os.remove(dest_file)` | **校验失败 = 删除目标文件** ⇒ 原文件彻底丢失 |
| ④ | `:285-290` `os.utime(dest_file, ...)` | mtime 还原本身正确，但作用在**已被 ①②③ 破坏的文件**上 ⇒ "时间对了，内容没了/残了" |

> 影响面（需求 §4 BL-8）：该接口被 **Web / 桌面 / 移动三端共用**（文件管理与目录同步都会走到），因此这是跨端的数据丢失风险，而非边缘场景。

### 3.2 改后的原子写链

| 步 | 代码位置（改后） | 行为 |
|----|----------------|------|
| ① 前置检查 | `src/services/file_service.py:320-323` | 缺分片在**任何写操作之前**就抛 `ValueError`（原文件未被触碰） |
| ② 临时文件落点 | `:333-335` `tmp_file = os.path.join(dest_dir, f".{filename}.jflove-upload-{upload_id}.part")` | 临时文件**与目标文件同目录**（同文件系统 ⇒ `os.replace` 才原子） |
| ③ 合并 + 算 sha256 | `:337-345` `aiofiles.open(tmp_file, "wb")` | 只写临时文件，**全程不触碰 `dest_file`** |
| ④ 校验 | `:347-350` `raise ValueError("文件校验失败，hash 不匹配")` | 失败**只**由 `finally` 清临时文件；`os.remove(dest_file)` 从代码中**消失** |
| ⑤ mtime 还原 | `:352-362` `os.utime(tmp_file, ...)` | 作用在**临时文件**上（日志改为只记异常类型，不回显路径） |
| ⑥ 原子替换 | `:364-365` `await asyncio.to_thread(_replace_with_retry, tmp_file, dest_file)` | 一次性 `os.replace` ⇒ 目标文件"内容 + mtime"同时可见，无中间态；重试在**线程池**内 sleep，不阻塞事件循环 |
| ⑦ 兜底清理 | `:366-369` `finally: _remove_quietly(tmp_file)` | 失败 / 异常路径只删临时文件，不残留半截 `.part` |
| ⑧ 会话清理 | `:371-374` `shutil.rmtree(tmp_dir)` + `del _upload_sessions[...]` + `return dest_file` | 与改前一致（成功路径） |

新增的两个模块级私有工具（同文件）：

| 位置 | 名称 | 职责 |
|------|------|------|
| `:42-43` | `_REPLACE_MAX_ATTEMPTS = 5` / `_REPLACE_RETRY_INTERVAL_SEC = 0.1` | 重试参数显式常量化 |
| `:46-58` | `_remove_quietly(path)` | 静默删除（`OSError` 全忽略），仅用于清理临时产物；绝不让清理失败掩盖真正的异常 |
| `:61-87` | `_replace_with_retry(src, dst)` | `os.replace` + 有限次短重试，全败才抛最后一次异常（`raise last_error` 在 `:87`） |

### 3.3 前后对比（危险链 → 原子写链）

| 失败场景 | 改前（`file_service.py:270` / `:280`） | 改后（`:333-369`） |
|---------|-----------------------------------|------------------|
| 合并中途分片读取失败 | 原文件已被截断为**已写入的前几个分片**（实测留下 `b"NEW-"` / `b"ANOT"`） | 原文件**逐字节不变**（临时文件被清掉） |
| 缺分片 | 前置检查拦下（`received` 集合口径内），未走到写；但"分片文件已丢"时同样走①的路 | 同前（前置检查不变），且写入阶段失败也不动原文件 |
| sha256 不匹配 | **原文件被 `os.remove` 删除** | 原文件**仍存在且内容不变**；只清临时文件 + 抛同样的 `ValueError` |
| 成功覆盖 | 内容正确，但写盘期间存在"半截文件"窗口 | 内容 + mtime 一次性原子生效；无中间态；成功后无 `.part` 残留 |

### 3.5 设计取舍（为什么这样做）

| 决策 | 理由 / 取舍 |
|------|-----------|
| **临时文件必须放在目标目录内**（`dest_dir`） | `os.replace` **只在同一文件系统内原子**。若用上传临时目录 `UPLOAD_TEMP_DIR`（`src/config/settings.py:9` = `<server>/build/upload_tmp`，生产 Docker 中可能位于另一挂载点/盘符），跨设备时 `os.replace` 抛 `OSError(EXDEV)`，或退化成"复制 + 删除"的**非原子**实现 ⇒ 原子性直接失效。放目标目录是"最小且唯一正确"的落点 |
| **绝不"先删后写"** | 先删/先截断都会制造一个"原文件不存在"的时间窗口，窗口内任何失败（IO 错误、连接中断、进程被杀）都是**不可恢复的数据丢失**；`os.replace` 没有这个窗口——要么旧文件、要么完整新文件 |
| **hash 失败只删临时文件** | 校验失败说明"新内容不可用"，此时**保留旧内容**才是唯一安全动作。旧实现删原文件是"新数据没用、旧数据也没了"的双输 |
| **mtime 先作用在临时文件** | 让目标文件的"最终状态一次成型"：内容与 mtime 同时可见，避免"内容已是新的、时间是旧的"的中间态（也是同步逻辑最容易误判的窗口） |
| **Windows 需要重试** | Windows 上 `os.replace` 会因目标文件被其它进程**短暂**持有而失败：杀软实时扫描、资源管理器缩略图/预览句柄、云盘同步进程等，表现为 `PermissionError`（WinError 5/32）。这类占用是瞬时的，**有限次短重试**即可成功；不重试会让"覆盖同名文件"在**没有真实错误**的情况下失败。参数：**最多 5 次（含首次）、间隔 0.1s、最长等待 0.4s**，对一次上传请求可忽略；仍失败则抛最后一次异常（**原文件此时仍是完好的旧内容**，因为替换从未发生） |
| **重试放进 `asyncio.to_thread`** | `_replace_with_retry` 内含 `time.sleep`，直接在事件循环里调用会阻塞整个服务；线程池执行是既有项目惯例（`asyncio.to_thread` 亦用于其它耗时操作） |
| **不引入回滚备份** | 需求 §4 明确"无远端保存 ⇒ 编辑器侧备份作废"；此处目标只是"原文件不被破坏"，`os.replace` 已充分。多留一份备份会引入"备份何时清理"的新问题（过度设计，`SKILL.md` 明令避免） |
| **不改 `init_upload` / `upload_chunk` / `cancel_upload` / 路由 / 加密信封** | BL-8 范围纪律：失败路径的会话与分片目录清理仍由调用方 `cancel_upload` 负责（既有行为） |

## 10. BL-10：上传文件名路径穿越（**严重 · 安全**；用户 2026-10-14 裁决「修」）

> 归口：`BACKLOG BL-10`（来源 = BL-8 实施期额外发现）。与 BL-8 **同一函数、不同缺陷**：
> BL-8 修的是「覆盖失败会毁掉原文件」，BL-10 修的是「目标路径本身可以被穿越」——
> BL-8 的原子写改造**沿用了**同一条 `os.path.join(dest_dir, filename)`，并未消除穿越。

### 10.1 攻击面（代码为准，HEAD 行号）

| 落点 | 事实 |
| --- | --- |
| `src/controllers/file_controller.py:152-159` | `filename` 只做 `strip()` + 非空校验（空 → 400），**未过滤** `/`、`\`、`..`、盘符 |
| `src/services/file_service.py::init_upload` | 只对 `rel_path` 调 `_safe_join`；`filename` **原样**存入内存上传会话 |
| `src/services/file_service.py::complete_upload` | `os.path.join(dest_dir, session["filename"])` ⇒ `filename = "../../evil.txt"` 即可让目标路径**逃出虚拟磁盘目录** |

- **触发前置**：已认证 + 对该磁盘有写权限（`init_upload` 内有 `check_disk_permission(..., "write")`）⇒ 属**认证后路径穿越**；写入范围仍受进程权限限制。
- **不在面内的相邻点**（本次只登记，不顺手改）：`get_stream_range`（`file_service.py:652`）也把 `filename` 拼进路径，但**拼接结果整体过了 `_safe_join`**，故不可穿越。

### 10.2 改法（两层防护）

| 层 | 落点 | 内容 |
| --- | --- | --- |
| **第一层（口径）** | 新增 `file_service._validate_filename()`，由 `init_upload` 调用 | 拒绝：空 / `.` / `..` / 含 `/`、`\`、NUL / Windows 盘符前缀（`C:` 在 ntpath 下是**驱动器相对**路径）/ `os.path.basename(name) != name` / 含当前平台 `sep`·`altsep`；合法名 `strip()` 后原样返回 |
| **第二层（兜底）** | `complete_upload` | `dest_file = _safe_join(dest_dir, session["filename"])`；越界时把 `PermissionError` 统一转 `ValueError("filename 非法：…")` —— 保持 complete 接口「非法输入 ⇒ 400」的既有契约（控制器只捕 `ValueError`） |
| 附带加固 | `complete_upload` 的临时文件名 | `f".{os.path.basename(dest_file)}…"`（不再直接用会话里的 `filename`），临时文件与校验后的目标文件同名同目录 |

- **校验位置**：放在**权限判定之后**、`_safe_join(base, rel_path)` 之前 —— 与既有惯例一致，且无写权限者仍先得 `403`（不因参数合法性改变越权可见性）。
- **零接口新增**：仍只有既有 `POST /api/v1/files/upload/init`；请求 / 响应字段与状态码语义不变（同一恶意输入此前会**静默成功**，现在返回 400）。
