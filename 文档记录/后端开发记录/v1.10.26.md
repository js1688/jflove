## 2. P1：refresh 恒 500（软删除 + 列级 UNIQUE 冲突）

### 2.1 现象与复现

```text
POST /api/v1/auth/refresh  →  500 {"detail":"服务器内部错误"}
服务端日志：sqlite3.IntegrityError: UNIQUE constraint failed: sessions.session_id
```

**影响面比报告里写的更大** —— 实测不止 refresh：

| 触发路径 | v1.10.25 行为 |
| --- | --- |
| 同一会话第二次登录 | **500** `UNIQUE constraint failed: sessions.session_id` |
| `auth/refresh` 续期 | **恒 500**（token 续期彻底不可用） |

### 2.2 根因

`sessions.session_id` 是**列级 `UNIQUE`**，而 `sessions` 是软删除表（有 `deleted_at`）。
`auth_service.login()` 与 `refresh_token()` 的流程都是：

```python
await session_repository.revoke(db, session_id)   # 只置 deleted_at，行仍在
await session_repository.create(db, user_id, session_id, ...)  # 同一 session_id 再插
```

⇒ 必然撞唯一约束。这正是 `AGENTS.md §5.2` 与 backend 技能「软删除 + 唯一约束会互相打架」
描述的反面案例，与 v1.5.0 `users.username` 事故**同一模式**。

### 2.3 修改前后对比

| | 修改前 | 修改后 |
| --- | --- | --- |
| 列定义 | `session_id TEXT NOT NULL **UNIQUE**` | `session_id TEXT NOT NULL` |
| 唯一性保证 | 列级约束（不区分软删除） | 部分唯一索引 `sessions_session_active_uidx ... WHERE deleted_at IS NULL` |
| 同一会话二次登录 | 500 | 200 |
| refresh 续期 | 恒 500 | 200，可反复续期 |
| 活跃会话数 | — | 恒为 1（部分唯一索引仍然生效，不产生幽灵会话） |
| 历史吊销行 | 无法共存 | 保留（软删除语义不变） |

### 2.4 DDL / 迁移

- **新建库**：`_CREATE_SESSIONS` 已去掉 `UNIQUE`；`_INDEXES` 增加
  `_CREATE_SESSIONS_ACTIVE_UIDX`。
- **既有库**：新增运行时迁移 `_migrate_sessions_drop_session_id_unique()`
  → `_rebuild_sessions_table()`，与 v1.5.0 的 `_rebuild_users_table` 同一套做法：
  建新表 → 拷贝（**主键 id 原样保留**）→ 替换。**不用** `PRAGMA writable_schema`
  （会留悬空自动索引，见该函数注释）。
- **幂等**：先剥 SQL 注释再用精确正则判断 `session_id TEXT NOT NULL UNIQUE`，
  已迁移则直接返回（实测连跑 3 次不再重建）。
- **交付脚本**：`jflove-db/migrate-1.10.26.sql` + `jflove-db/rollback-1.10.26.sql`。

## 3. R1：磁盘四项容量/类型（服务端侧）

### 3.1 需求

文件管理（磁盘列表）与磁盘设置（管理 → 磁盘管理）都要展示
**最大空间 / 已用空间 / 可用空间 / 磁盘类型**，三端都要。路径不可读时兜底 `—` 不崩。

### 3.2 实现

新增 `src/utils/disk_info.py`：

| 函数 | 作用 |
| --- | --- |
| `get_usage(path)` | 返回 `total_size` / `used_size` / `free_size` / `disk_type`；**任何失败都不抛异常**，对应字段 None |
| `get_disk_type(path)` | 分平台：Linux `/proc/mounts`（**最长前缀匹配**挂载点）、Windows `GetVolumeInformationW`（ctypes）、macOS `stat -f %T` |
| `get_usage_for_disks(paths)` | 批量去重取用（同一路径只算一次） |

容量来自 `shutil.disk_usage`，**实时探测、不落库**（落库会立刻过期，且和 `df -h` 对不上）。

接入两个接口：

| 接口 | 改动 |
| --- | --- |
| `GET /api/v1/files/disks`（`file_service.list_accessible_disks`） | 每个磁盘补 4 个字段；admin 与普通用户两条分支都补 |
| `GET /api/v1/virtual-disks`（`virtual_disk_service.list_disks`） | 同上 |

### 3.3 实测数值（与 `df -h` 对照）

```text
$ df -h /tmp /home /
tmpfs            16G  2.5G   13G   16% /tmp
/dev/nvme0n1p7  952G  243G  709G   26% /home

接口返回（字节）：
/tmp/jfqa-sandbox/disk1 → total=16514908160 used=2637852672 free=13877055488 type=tmpfs   （16G/2.5G/13G ✓）
/home/tanjun            → total=1021788028928 used=259878273024 free=761118752768 type=btrfs（952G/243G/709G ✓）
```

不可读路径：`/nonexistent-path-xyz` → 三个容量字段均为 `null`，**接口不报错**（`disk_type` 仍能从
挂载点推断出 `btrfs`，因为路径不存在不影响读挂载表）。

## 5. 接口变更（对客户端的影响）

两个接口**只新增字段，不改/不删原有字段**，向后兼容：

```diff
 GET /api/v1/files/disks
 [
   { "id": 1, "name": "test", "can_write": true, "can_delete": true,
+    "total_size": 1021788028928, "used_size": 259878273024,
+    "free_size": 761118752768, "disk_type": "btrfs" }
 ]

 GET /api/v1/virtual-disks
 [
   { "id": 1, "name": "test", "real_path": "...", "created_by": 1, "created_at": "...",
+    "total_size": ..., "used_size": ..., "free_size": ..., "disk_type": "btrfs" }
 ]
```

旧客户端忽略新字段即可，无需同步升级；新客户端对 `null` 渲染 `—`。
