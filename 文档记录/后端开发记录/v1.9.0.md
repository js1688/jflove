# JFLove v1.9.0 后端开发记录（Phase 3）

> 版本：1.9.0｜角色：backend｜日期：2026-11-09
> 需求：`文档记录/需求文档/v1.9.0.md`；设计：`文档记录/设计文档/v1.9.0.md`
> 数据库：**无 DDL**（不新建表、不加列；仅 `config` 键值表新增键）

## 1. 功能与改动点

1. **上传会话持久化与恢复**
   - `file_service.init_upload_ex` 在 `build/tmp/upload/<upload_id>/session.json` 写会话元数据；
   - `restore_upload_sessions(db)` 启动时恢复未过期会话；已收分片以磁盘 `<index>.chunk` 实际存在性重建（不信任内存/JSON 计数）；
   - 崩溃/重启后 `session.json` 的 `updated_at` 作为最后活动时间（每 8 片或每 30s 回写）。

2. **内容指纹幂等 init**
   - 指纹含 `owner_user_id|disk_id|rel_path|filename|file_size|file_hash|total_chunks`；
   - 相同内容在保障期内重复 init 复用同一 `upload_id`/目录，响应返回 `received_chunks/resumed/expires_at`；
   - 指纹补 `total_chunks`：避免 1MB（v1.8.x）与 512KB（v1.9.0）客户端跨版本复用会话导致分片索引越界；
   - 每用户未完成会话上限（默认 8）防止临时分片堆积。

3. **状态查询**
   - 新增 `POST /api/v1/files/upload/status`：返回是否存在、状态、已收/缺失分片、过期时间、客户端类型；
   - 归属校验失败/不存在统一返回 `exists=false`，避免枚举他人会话。

4. **合并异步化**
   - `POST /upload/complete` 支持 `async_mode=true`：立即返回 `queued/merging` + `poll_interval_s`；
   - 合并任务在后台协程中执行，合并体放 `asyncio.to_thread`（同步顺序读写 + 写时 SHA256），事件循环不再被哈希/同步 IO 阻塞；
   - 全局合并信号量（`upload_merge_concurrency`，默认 1；0 = 暂停排队）；同一 upload_id 串行；
   - 失败分类：`missing_chunks` / `hash_mismatch` / `io_error`；缺片通过 progress 返回缺失索引；
   - 进度记录带 `owner_user_id`，会话删除后仍可查询 `done/failed`（保留 24h，与续传 TTL 同源）。

5. **分片上传资源限制**
   - 全局分片信号量（`upload_chunk_concurrency`，默认 2），等待超时 429；
   - 单分片硬上限 1MB；负索引/越界 400；
   - `init` 响应返回 `max_chunk_size` / `recommended_concurrency`。

6. **下载 Range**
   - `GET /files/download` 支持 `range_start`（加密 body）；越界 416；
   - 响应头 `X-Stream-Offset` / `X-Stream-Total` / `X-File-Version`（size:mtime），不含文件名/路径/用户标识；
   - 帧格式保持 v1 纯数据帧（`_build_encrypted_range_stream`，不含 v2 meta 帧）；
   - 服务端不保存下载临时文件。

7. **隐藏项与访问隔离**
   - `list_files` 过滤所有名称以 `.` 开头的条目；
   - `scan_tree`/`_collect_tree` 默认跳过隐藏项（对账不把临时目录当业务文件）；
   - `_safe_join` 路径段拒绝 `.jflove-repair` / `.jflove-download` / `.jflove-tmp`；
   - 用户自己的 `.` 文件仍可按精确路径访问（列表不展示）。

8. **统一临时根与迁移**
   - 进程级：`build/tmp/upload`（旧 `build/upload_tmp` 迁移）；
   - 磁盘级：`<磁盘根>/.jflove-tmp/` 下 `offline/`、`repair/`；
   - `temp_root_service.migrate_legacy_temp_dirs(db)` 启动迁移旧 `.jflove-download/<task_id>` 与 `.jflove-repair` 产物（按修复任务记录映射到 `repair/<task_id>`）；
   - 离线下载临时目录改到统一根；修复产物新任务写统一根，旧路径读取回退；
   - 合并临时文件仍留在目标目录（原子替换例外），命名 `.<name>.jflove-upload-<uuid>.part`。

9. **可配置清理**
   - 新增 `upload_cleanup_service`：读取/校验 8 个 config 键，触发安全清理；
   - 清理阈值 = `upload_resume_ttl_hours`（唯一 TTL 来源），启动首轮也遵守（删除旧「启动 1 小时就清」）；
   - 按客户端类型白名单过滤；`updated_at` 判定；孤儿目录按目录 mtime；
   - 只删：UUID 会话目录内 `*.chunk`/`session.json`、`.jflove-upload-<uuid>.part`、统一根/旧根的数字任务子目录；非预期文件名整个目录跳过并告警；
   - 新增 `POST /api/v1/config/cleanup`（admin）立即清理并返回统计。

10. **配置接口**
    - `GET /config` 注入上传清理默认值；
    - `PUT /config` 校验上传清理键并立即刷新合并/分片信号量；
    - 新增配置键：`upload_resume_ttl_hours=24`、`upload_cleanup_enabled=1`、`upload_cleanup_interval_minutes=60`、`upload_cleanup_client_types=""`、`upload_orphan_ttl_hours=24`、`upload_max_sessions_per_user=8`、`upload_merge_concurrency=1`、`upload_chunk_concurrency=2`。

## 3. 修改前后逻辑对比

| 场景 | v1.8.4 | v1.9.0 |
|---|---|---|
| 3GB 合并 | 同步请求内合并，App 120s 超时判失败 | 立即受理 + 后台线程合并 + progress 轮询 |
| 上传重试 | 客户端新 init → 新会话 → 从头传 | 指纹复用 + `received_chunks` 跳过已传片 |
| 服务端重启 | 会话丢失，旧 upload_id 失效 | `session.json` 恢复未过期会话 |
| 合并并发 | 不同 upload_id 可同时合并 | 全局并发默认 1，其余排队 |
| 合并阻塞 | SHA256 在事件循环线程 | 合并体在线程，事件循环可响应 |
| 下载 | 无 Range | 支持起始偏移续传 |
| 临时目录 | `.jflove-download` 每目标目录一个、上传在旧目录 | 统一根 + 迁移 |
| 隐藏项 | 只过滤 `.jflove-repair` | 所有 `.` 开头过滤 |
| 清理 | 24h 硬编码 / 启动首轮 1h / 不可配 | config 单一 TTL / 启动同 TTL / 客户端类型白名单 |

## 4. 关键取舍

- **过渡兼容**：`complete` 未传 `async_mode` 时仍执行同步合并，仅为 v1.8.x 回归用例/旧调用保留；新客户端（App/桌面/Web）全部传 `async_mode=true`。旧客户端在 init 阶段（缺 `client_type`）已被 409 拒绝。建议 v1.10 移除该分支。
- **`already_exists`**：设计文档字段保留但恒为 false；服务端不自动用「同大小」判定已完成（同大小≠同内容），由客户端用远端索引/列表核验。
- **修复产物统一根**：新任务写 `.jflove-tmp/repair/<task_id>/`；旧 `.jflove-repair` 读取回退，迁移失败不阻塞启动。
- **离线下载临时目录**：统一到磁盘根 `.jflove-tmp/offline/`，最终仍 `os.replace` 到目标目录（同盘原子）。
- **进度记录 TTL**：与续传 TTL 同源（默认 24h），避免完成后立即 403/unknown。
