## 后端开发（jflove-server）

### 完成内容

#### 项目初始化

- 创建完整目录结构（config / models / repositories / services / controllers / utils）
- 配置 Python 虚拟环境（`venv/`）
- 完成 `requirements.txt`，解决 Python 3.14 下 pydantic-core 无预编译包问题（使用 `--pre` 安装 2.46.3 版）

#### 数据库层（models）

- 建表：`users`、`virtual_disks`、`user_permissions`、`notes_permissions`、`sessions`、`config`
- 所有表包含 `id / created_at / updated_at / deleted_at` 固定字段，支持软删除
- 异步连接（aiosqlite），通过 FastAPI `Depends(get_db)` 注入
- 服务启动时自动执行建表，幂等安全

#### 数据访问层（repositories）

- `user_repository`：用户 CRUD、管理员计数、软删除
- `session_repository`：会话创建、吊销（按 session_id / 按 user_id 批量）
- `virtual_disk_repository`：虚拟磁盘 CRUD、软删除
- `permission_repository`：磁盘权限 upsert/删除，笔记权限 upsert
- `config_repository`：配置 key-value get/set/list

#### 业务逻辑层（services）

- `auth_service`：
  - X25519 密钥交换，HKDF-SHA256 派生 32 字节会话密钥
  - 会话密钥**仅存内存**（`dict: session_id → session_key`），不落库
  - 支持密钥刷新（旧 session_id 失效，派生新密钥）
  - bcrypt 密码验证，ES256 JWT 签发与验证
- `user_service`：用户创建（bcrypt 哈希）、密码修改、启用/禁用、删除（保护管理员不可删）
- `virtual_disk_service`：虚拟磁盘增删改，校验服务端真实路径存在
- `permission_service`：磁盘权限与笔记权限的读写，权限校验方法
- `file_service`：
  - 防目录遍历路径校验（`_safe_join`）
  - 分片上传（init → chunk → complete），SHA256 完整性校验
  - 断点续传支持（分片独立存储，complete 时合并）
  - 取消上传自动清理临时分片
- `note_service`：
  - 笔记目录由用户表的 `notes_disk_id` + `notes_path` 两字段联合决定（磁盘根路径 + 用户指定子目录）
  - `_get_notes_base(db, user_id)` 做防目录遍历校验（`os.path.realpath` + `startswith`）及目录存在性校验
  - .md 文件 CRUD
- `config_service`：系统配置读写

### 2026-05-04 上传保留 mtime（性能优化）

#### 背景

桌面端反馈：目录同步过程"卡"，每次同步都看到所有文件被重传。根因是上传完成后服务端 `complete_upload` 用 `aiofiles.open(..., 'wb')` 写盘，文件 mtime 默认为"当前时间"，导致同步算法看到本地 mtime（旧）vs 服务端 mtime（新）总是判定要重新下载。下载完成后客户端文件 mtime 又变成下载时刻 → 又超过远端 → 下次又重新上传。形成"永动机式重传"。

#### 之前的逻辑

- `init_upload` 只接受 `filename / file_size / total_chunks / file_hash`
- `complete_upload` 合并分片并校验 SHA256 后直接结束，没有任何对 mtime 的处理
- 服务端 mtime 来自文件系统操作时刻

#### 本次修改

##### `services/file_service.py`

- `init_upload` 新增可选参数 `mtime: float | None = None`（源文件 Unix 时间戳，浮点秒）
- 该字段写入内存上传会话 `_upload_sessions[upload_id]["mtime"]`
- `complete_upload` 合并校验完成后，若 session 中带有 `mtime`，调用 `os.utime(dest_file, (mtime, mtime))` 将文件 atime/mtime 都还原到源时间戳
- `os.utime` 失败时仅 warning 日志，不影响上传成功结果（best-effort）

##### `controllers/file_controller.py`

- `POST /api/v1/files/upload/init` 新增可选请求字段 `mtime`（OpenAPI description 中文化说明）
- 控制器从 body 读取 `mtime`：空值 / `None` / `0` 都视为未提供，否则转 float 传入 service
- 完全向后兼容：旧客户端不传 `mtime` → 行为与之前一致

#### 关键代码片段

```python
# complete_upload 末段
src_mtime = session.get("mtime")
if src_mtime:
    try:
        os.utime(dest_file, (src_mtime, src_mtime))
    except OSError as e:
        logger.warning("无法还原文件 mtime（不影响上传结果）: %s -> %s", dest_file, e)
```

#### 自测验证

- `python -m py_compile src/services/file_service.py src/controllers/file_controller.py` 通过
- 旧客户端兼容：不传 `mtime` 字段时，控制器把 `mtime_raw` 解析为 `None`，service 跳过 utime 调用
- 配合桌面端 v1.0.6 的同步快路径（size 一致 + mtime 容差内 → 跳过），首次同步后所有未变更文件都不会再产生上传/下载任务

### 2026-05-04 移除笔记权限模块（业务简化）

#### 背景

每个用户的笔记目录由 `users.notes_disk_id` / `users.notes_path` 独立配置（详见 [v1.0.1 节](文档记录/桌面端开发记录/v1.0.md)），用户之间笔记目录互不可见。在这一前提下，原本通过 `notes_permissions` 表区分用户是否能"使用笔记功能"已无业务必要——管理员只要还想给某用户用笔记，那直接给他配磁盘即可（笔记目录就是磁盘内一个子目录）；如果不想给，禁用账号即可。

- `permission_service.check_notes_permission()`：所有 note_service 操作（list/read/write/delete/rename）开头都校验
- `POST /api/v1/permissions/users/{user_id}/notes`：管理员用此接口设置笔记权限
