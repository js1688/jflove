## 2. 数据库

### 2.1 DDL

```sql
CREATE TABLE IF NOT EXISTS file_changes (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    disk_id      INTEGER NOT NULL,
    rel_path     TEXT    NOT NULL,
    op           TEXT    NOT NULL,              -- upsert / delete
    is_dir       INTEGER NOT NULL DEFAULT 0,
    size         INTEGER NOT NULL DEFAULT 0,
    mtime        REAL    NOT NULL DEFAULT 0,
    content_hash TEXT    NOT NULL DEFAULT '',
    created_at   TEXT    NOT NULL,
    updated_at   TEXT    NOT NULL,
    deleted_at   TEXT
);
CREATE INDEX IF NOT EXISTS file_changes_disk_id_idx ON file_changes(disk_id);
CREATE INDEX IF NOT EXISTS file_changes_rel_path_idx ON file_changes(rel_path);
```

**为什么没有唯一索引**：同一路径允许多条历史记录（append-only 日志）。若加唯一索引，
就会与 `AGENTS.md §5.2` 的软删除约定冲突（见 `backend/SKILL.md`「数据库变更硬约束」第 1 条）。

## 3. 接口

### 3.1 `POST /api/v1/files/journal`

拉取增量变更。

- 明文白名单：否；加密：`decrypt_request_body` + `encrypt_response`
- 鉴权：JWT（body `token`）+ `check_disk_permission(read)`；admin 免检
- 路径参数：无（`disk_id` / `prefix` 均在加密 body）

请求：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `token` | string | 是 | JWT |
| `disk_id` | int | 是 | 虚拟磁盘 ID |
| `prefix` | string | 否 | 子目录前缀（空 = 根） |
| `since_rev` | int | 否 | 上次最大 rev（默认 0） |
| `limit` | int | 否 | 默认 500，最大 2000 |

响应：

| 字段 | 类型 | 说明 |
|---|---|---|
| `changes` | array | `rev` / `path` / `op` / `is_dir` / `size` / `mtime` / `hash` |
| `latest_rev` | int | 本次最大 rev |
| `has_more` | bool | 是否还有更多 |
| `reset_required` | bool | 为真时客户端应改走全量对账 |

### 3.2 `POST /api/v1/files/scan`

全量对账（只 stat，不读内容），分页。

- 请求：`disk_id` / `prefix` / `cursor` / `limit`（默认 2000，最大 5000）
- 响应：`entries[]`（`path` / `is_dir` / `size` / `mtime`）/ `next_cursor` / `has_more` / `latest_rev`
- 鉴权与加密同 3.1

### 3.3 兼容性

- `POST /api/v1/sync/snapshot` **保留**（过渡期），本版未改动其行为。
- `complete_upload(upload_id, db=None)` 的 `db` 为可选参数：不传时与旧版行为完全一致。

## 4. 关键取舍

| 取舍 | 结论 | 理由 |
|---|---|---|
| `rev` 语义 | 用 `file_changes.id`（全局单调） | 客户端只记一个整数；AUTOINCREMENT 删除不回收号 |
| 前缀匹配 | `substr(rel_path, 1, n) = prefix + '/'` | 大小写敏感、边界精确，`photos` 不会误匹配 `photos2` |
| 范围隔离 | SQL 过滤 + Python 二次断言 | 防御深度（AC-112） |
| journal 写失败 | 只记 warning，不影响主操作 | 文件已落盘，日志失败不能回滚用户操作 |
| 清理策略 | 保留最近 10 万条（由调用方传参） | 防表无限增长；老游标失效时用 `reset_required` 兜底 |
| 分片清理 | 24h + 不在内存会话 | 服务重启后内存会话丢失，残留目录需回收 |
| 目录删除 | 删除前先 `_collect_tree` | 删除后无法再遍历，必须提前收集 |

## 上传残留清理补强（2026-10-19，客户端反馈「上传卡住一晚、临时目录一直占用」）

### 现象与根因

客户端上传大文件时卡在「100%」，同时服务端 `UPLOAD_TEMP_DIR` 的分片目录**长期不释放**。

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | `cleanup_stale_uploads` **跳过**仍存在于 `_upload_sessions` 的目录 | 客户端崩溃 / 强杀后会话留在内存，其临时目录**永不清理**（只有重启服务端才清） |
| 2 | `_upload_sessions` **没有空闲过期**机制 | 会话字典只增不减 ⇒ 内存与磁盘双向泄漏 |
| 3 | 合并期间被强杀会留下 `.<文件名>.jflove-upload-<id>.part` | 目标目录里残留隐藏文件，长期占用空间 |
| 4 | 同一 `upload_id` 的并发 `complete` 无互斥 | 客户端超时重发时可能并发重写同一批分片 |

### 改动（全部在 `jflove-server`）

| 位置 | 变化 |
| --- | --- |
| `src/services/file_service.py` | 新增 `UPLOAD_SESSION_TTL_SECONDS = 24h`；会话记录 `updated_at`（init / 每片刷新）；新增 `expire_stale_sessions()`；`cleanup_stale_uploads()` 先回收空闲会话再清孤儿目录；新增 `cleanup_orphan_partials()` 清理遗留 `.part`；`complete_upload` 按 `upload_id` 加 `asyncio.Lock` 串行化 |
| `src/main.py` | 每小时清理循环同时执行 `cleanup_orphan_partials(db)`；**首轮**（进程刚启动，内存会话必然为空）用 1 小时阈值，尽快回收上次崩溃遗留的目录 |

### 兼容性

- 接口、表结构、加密协议**均未改动**；纯清理逻辑 + 并发保护。
- 客户端无需任何改动即可受益。

### 验证

| --- | --- |
| 构建废弃会话（空闲 25h）+ 写分片 ⇒ 调 `cleanup_stale_uploads` | ✅ 返回 1；内存会话数 1→0；临时目录被删除；`UPLOAD_TEMP_DIR` 变空 |

### 部署说明（重要）

**需要重启服务端**才会生效：清理逻辑在进程内运行，且重启时内存会话被清空 ——
这正是「立即释放历史残留」的时机（重启后首轮按 1 小时阈值清理）。
不重启的话，旧进程里的会话表仍然持有那些 upload_id，目录继续不会被清理。

### 合并耗时实测与判读（2026-10-19）

> 澄清：此前复现脚本里的「60 秒」是**人为 `await asyncio.sleep(60)`**，用于验证客户端超时行为，
> **不是**真实合并耗时。真实数据如下。

**本机（22 核 / NVMe / btrfs）直接调用 `complete_upload`：**

| 文件 | 分片数 | 合并+校验耗时 | 归一化 |
| --- | --- | --- | --- |
| 4 GB | 4096 | 7.3 s | 1.8 s/GB |
| 12 GB | 12288 | 21.1 s | 1.8 s/GB |
| 12 GB（加日志后复测） | 12288 | 22.7 s | 1.9 s/GB |

基线对照（同机）：纯 SHA256 4GB = 2.7 s（≈1.5 GB/s），纯顺序写 4GB = 1.8 s（≈2.2 GB/s）。
⇒ 合并耗时 ≈ **读 N + 写 N + 算哈希 N**，是 disk + CPU 的线性叠加，**与文件大小成正比**。

**弱配置机器的估算方法**（合并是单进程串行的）：

```
合并秒数 ≈ 2 × 文件GB / 磁盘顺序写(GB/s) + 文件GB / SHA256(GB/s) + 片数开销
```

可在服务端机器上直接量：

```bash
# 磁盘顺序写
dd if=/dev/zero of=/tmp/wtest bs=1M count=2048 conv=fsync status=none && rm -f /tmp/wtest
# SHA256
dd if=/dev/zero of=/tmp/htest bs=1M count=2048 status=none && time sha256sum /tmp/htest; rm -f /tmp/htest
```

**已为此新增可观测性**：`complete_upload` 完成时打印

```
合并完成: <文件名> 共 12.0 GB，耗时 21.3 秒（1.8 秒/GB，12288 片）
```

运维可直接从日志判断「是慢还是在跑」。客户端侧也会在「服务端处理中」显示**已耗时**
（`finalizing · 已 1 分 30 秒`），且该阶段**不再**被判定为「无进展」。

## 合并进度回传（`POST /api/v1/files/upload/progress`，2026-10-19）

### 背景

合并耗时随文件线性增长（实测 1.8–2.4 秒/GB），弱配置服务器上 12GB 要几十秒到几分钟。
只靠日志根本看不出"是在合并还是挂了"，用户明确要求**把进度/状态回传给客户端**。

### 实现

| 位置 | 改动 |
| --- | --- |
| `src/services/file_service.py` | 模块级 `_merge_progress: dict[str, dict]`：`state`（`queued`/`merging`/`done`/`failed`）、`processed`、`total`、`file_size`、`started_at`、`elapsed_seconds`、`error`；`merge_progress(upload_id)` 查询并补算 `percent`；`prune_merge_progress(max_age=3600)` 清理 |
| 合并循环 | 每 16 片更新一次 `processed` 并 `await asyncio.sleep(0)`——**必须让出事件循环**，否则合并期间进度接口无法响应（合并是同步磁盘 I/O，占满事件循环会让整个服务卡住） |
| `src/controllers/file_controller.py` | `POST /api/v1/files/upload/progress`：`decrypt_request_body` → `_get_user`（token 从加密 body 取）→ `is_upload_owned_by` 校验归属（他人 upload_id ⇒ 403）→ `encrypt_response` |
| `src/main.py` | 每小时清理循环追加 `prune_merge_progress()` 与 `cleanup_orphan_partials(db)` |

### 安全核对（AGENTS.md §9）

- 请求 / 响应全程加密信封；**未扩大明文白名单**。
- `upload_id` 是路径外的 body 参数，且做了**归属校验**（`is_upload_owned_by`），换 ID 拿不到他人进度。
- 返回体只含状态与计数，**不含文件名 / 路径 / 用户标识**。
- 未引入新算法、新密钥、长期密钥。
