## 二、核心问题与修法（U-1 ~ U-6）

### 2.1 问题

用户反馈：**账号删除后，用同一个用户名重新创建会报错。**

根因是两条口径打架：

| 口径 | 出处 | 后果 |
|------|------|------|
| 用户删除是**软删除**（保留历史行，写 `deleted_at`） | `AGENTS.md §5.2` 必备字段约定 | 历史行一直在表里 |
| `username` 是**列级 `UNIQUE`** | v1.4.2 及之前的建表语句 | 列级 UNIQUE **不区分是否已删除** ⇒ 用户名被历史行永久占用 |

于是管理员删了账号却无法用同名重建，前端看到的是数据库原始错误 `UNIQUE constraint failed`。

### 2.2 修法：把"唯一"从列约束搬到**部分唯一索引**

```sql
-- 建表：username 不再带 UNIQUE
username      TEXT    NOT NULL,

-- 索引一：普通索引，负责按用户名查询
CREATE INDEX IF NOT EXISTS users_username_idx
    ON users(username);

-- 索引二：部分唯一索引，只对「活跃行」保证唯一
CREATE UNIQUE INDEX IF NOT EXISTS users_username_active_uidx
    ON users(username) WHERE deleted_at IS NULL;
```

**语义保证（修复后）**：

- **活跃账号仍然不允许重名** ⇒ 登录与查重不会出现歧义；
- **被软删除的历史行不再占用用户名** ⇒ 删掉账号后可以用同名重建；
- 主键 `id` 原样保留 —— 其它表（`user_permissions` / `sessions` / `media_repair_tasks` 等）按 `user_id` 整数引用它。

### 2.3 为什么不用 `PRAGMA writable_schema` 直接改写 `sqlite_master`

实测过：那样会留下**悬空的自动索引**，之后任何访问都报
`malformed database schema ... orphan index`，**且当时不抛异常**（危险点就在这里）。
因此改为标准的「重建表 + 拷贝数据 + 改名 + 重建索引」路径。

### 2.4 迁移的幂等性

`_migrate_users_drop_username_unique` 先检测旧结构是否还在：

- 判据用**精确正则** `username\s+TEXT\s+NOT\s+NULL\s+UNIQUE`，而不是搜 `"UNIQUE"` 子串 ——
  因为新结构的注释里就写着"去掉了原来的 UNIQUE"，**搜子串会把新库误判成旧库**、导致反复重建表；
- 已是新结构则直接返回，重复执行无副作用。

## 三、接口行为与文案变化（U-7）

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 创建与**活跃**账号重名 | 400（文案含糊） | 400 + **人话**：「用户名「xxx」已存在，请换一个」（前端原样弹给用户） |
| 创建与**已软删除**账号重名 | 400 数据库原始错误 | **允许创建**（历史行不再占用用户名） |
| 已删除账号登录 | 依赖查询口径 | **明确拒绝**（U-5 防御性判断，`deleted_at` 非空即拒） |
| 删除后重建的账号登录 | —— | 正常登录 |

接口文档字符串同步更新，写明 `username` 的唯一性是**"活跃账号内唯一，且含已软删除的历史行"**这一口径，
避免后来人误改成"含历史行"的判定（那会让登录产生歧义 —— 见 `user_repository.py` 的显式警告）。

## 四、构建校验：生产库"空库"口径修正（B-1）

`build.py::assert_prod_db_empty()` 原先是「prod 库所有表必须 0 行」。
但 `init_db()` 首次运行会**幂等写入两个默认配置键**（`media_repair_enabled=0`、
`media_repair_allow_transcode=0`）—— 只要服务端启动过一次，生产库就不再是"全 0 行"，
**打包会被误拦**。

修法：放行**初始化数据**，但把白名单**精确到「键名 + 默认值」且只对 `config` 表生效**：

```python
_INITIAL_CONFIG_ROWS: dict[str, str] = {
    "media_repair_enabled": "0",
    "media_repair_allow_transcode": "0",
}
```

- 键在白名单**但值被改过**（例如管理员把总开关打开） ⇒ **仍算业务数据，中止构建**；
- 除 `config` 外任何表非空 ⇒ 中止构建；
- 数据泄漏防线**不降低**（这一点是该改动的关键约束，不是"顺手放宽"）。

## 八、已知边界

- **删除用户不会释放磁盘上的文件**：本改动只解决"用户名可复用"，不涉及数据清理。
- **同名重建得到的是全新账号**：`id` 是新的，原账号的权限、会话、笔记目录配置**不会继承**
  （历史行仍以旧 `id` 留在 `users` 表里，供审计追溯）。
- 迁移会**重建 `users` 表**：数据行数、内容指纹与主键 `id` 都必须原样保留，
  这一点由 `test_users_schema_migration_v1_5_0.py::test_迁移不丢数据` 与
  `test_expected_schema_v1_5_0.py` 守住。
