## 七、发现问题（未修复，交 Phase 5 / 后续修复）

> 按任务要求：发现生产代码问题**不修改**，仅给出证据与建议。

### 问题 1（中等）：移动端渲染模板在 HTML 注释里原样写了 4 个占位符

- **证据**：`jflove-app/assets/mermaid/renderer.html` 注释第 30 行与第 39 行原样列出 `__JF_BUNDLE__ / __JF_CODE__ / __JF_THEME__ / __JF_ID__`，而 `MermaidRenderService.buildHtml()`（`lib/services/mermaid/mermaid_render_service.dart:59-63`）用的是 **`replaceAll`**。
- **自动化证据**：`test/mermaid_security_test.dart::已知问题：注释里原样写了占位符（bundle 会被内联两次 + \`-->\` 会提前闭合注释）`（通过 → 说明缺陷当前存在）。
- **影响**：
  1. `__JF_BUNDLE__` 被内联**两次**（脚本 1 份 + 注释 1 份）：送进 `loadHtmlString` 的 HTML 由约 3.4MB 变成约 6.8MB，每次图块渲染都要多拼一份字符串；
  2. 图表源码若含 `-->`，注入到注释里会**提前闭合 HTML 注释**，注释剩余文字会作为可见文本出现在图块上方（该用例已断言注释在源码位置之前被闭合，且可见文本切片含 `are bare placeholders`）。
- **建议**：模板注释里改用文字描述（桌面端 `resources/mermaid/renderer.html` 已明确「NEVER write a placeholder literally in a comment」，并有对应单测），或在 `buildHtml` 里先剥离 HTML 注释再替换。

### 问题 2（中等，防御纵深）：Web `sanitizeSvg` 有两处清洗缺口

- **证据**：`jflove-web/src/utils/mermaid/sanitize.ts` 正则只覆盖「完整 `<script …>` 标签」与 `href` / `xlink:href` 两类引用。
- **自动化证据**：`tests/utils/mermaid-security.test.ts::已知缺口：未闭合 script 与 src 形态的外部引用不会被移除`（通过 → 缺陷存在）：
  - `'<svg><script src="http://evil.example/x.js"'` 清洗后仍含 `<script`；
  - `'<svg><img src="http://evil.example/x.png"/></svg>'` 清洗后仍含 `http://evil.example`。
- **影响评估**：当前插入点是 `canvas.innerHTML = sanitizeSvg(svg)`，HTML 解析器会丢弃末尾残缺标签，且 mermaid 在 `securityLevel: 'strict'` 下不产出 `<img>`，故**当前不构成可利用路径**；但设计文档 §4.8 明确要求「插入前过滤 `script`/`on*`/`foreignObject`/外部引用」，实现未覆盖 `src` 形态，属防御纵深不足。
- **建议**：改为 DOMParser + 白名单重建，或在正则中补 `src` 形态与未闭合标签。

### 问题 3（中等，功能缺失）：移动端笔记编辑器没有「插入图表」入口（AC-15）

- **证据**：`jflove-app/lib/pages/notes/note_edit_page.dart` 工具栏共 9 个按钮（粗体/斜体/标题/无序/有序/链接/图片/代码块/引用，见 `_insertMarkdown(...)` 调用点 L336-376），**无 mermaid 模板插入**；全 `lib/` 内 `图表` 命中仅出现在渲染与错误文案中（无插入模板）。
- **对照**：Web `src/pages/NoteEditPage.tsx:36-42,346` 有「插入图表」+ 模板；桌面 `src/ui/pages/note_page.py:38,197,379,386` 有「插入图表」+ 模板。→ 三端中仅移动端缺失，AC-15 不满足。
- **建议**：在移动端编辑器工具栏补一个图表按钮 + 类型选择（对齐桌面端 `QInputDialog` 的交互），并补「插入后自动定位到模板」的用例。

### 问题 4（轻微，一致性）：移动端缓存键用的不是 `sha256`

- **证据**：设计文档 §4.1 约定缓存键为 `sha256(code + "\n" + theme + "\n" + MERMAID_VERSION)[:16]`；桌面端（`cache_key`，sha256）与 Web 端（`shortHash`，WebCrypto）均遵守，移动端 `MermaidRenderService.cacheKey`（`mermaid_render_service.dart:143`）实际用 64 位 FNV 变体哈希（文件注释已自陈「轻量稳定哈希（非加密用途，只做缓存键）」）。
- **影响**：仅影响缓存键形态（非安全用途、三端不共享缓存），**不影响渲染一致性**；但与「三端统一约定」不符，且 64 位哈希的碰撞概率高于 128 位截断。
- **建议**：统一为 sha256 前 16 位（Dart 侧可用 `crypto` 包或 `pointycastle` 已有依赖），或在设计文档中把该偏差记录为「移动端允许的实现差异」。

### 问题 5（轻微）：移动端回传 SVG 未做字符串级白名单过滤

- **证据**：设计文档 §4.4.4 要求「回传的 SVG 字符串在显示前过滤：移除 `<script>`、`on*` 属性、`<foreignObject>`、外部 `href`/`xlink:href`」；实测 `lib/` 内无任何 SVG 过滤实现（`grep foreignObject|sanitize|xlink` → 0 命中），`_StaticSvgView._wrap` 只做尺寸硬化后 `loadHtmlString`。
- **缓解**：`_StaticSvgView` 与 `MermaidViewerPage` 均为 `JavaScriptMode.disabled`（已由 `mermaid_webview_security_test.dart` 锁死），脚本不执行；但 `NavigationDelegate.onNavigationRequest` **只拦导航、不拦子资源加载**，若 SVG 内残留 `<img src="http://…">`，WebView 仍可能发起网络请求，与「渲染全程零网络依赖」存在缺口。
- **建议**：在移动端补一个 SVG 白名单过滤（可参考 Web `sanitize.ts` 但改用 DOM/正则双重处理），或改用「把渲染结果光栅化为图片后显示」的方案。

### 六、发现的问题与处理（**未改应用代码**）

#### 问题 1（**严重，阻塞发布**）：点击侧栏条目**不切页**（本轮 UI 重构引入）

- **位置**：`jflove-desktop/src/ui/main_window.py:213`
  ```python
  self.navigationInterface.addWidget(
      route_key,
      NavItem(icon, text),
      onClick=lambda p=page: self.switchTo(p),   # ← p 被 clicked(bool) 覆盖
      position=position,
  )
  ```
- **根因链（全部有行号）**：
  1. `NavigationWidget.clicked = Signal(bool)`（`qfluentwidgets/components/navigation/navigation_widget.py:25`）；
  2. 真实点击走 `mouseReleaseEvent → self.clicked.emit(True)`（同文件 **68 行**）；
  3. `NavigationPanel._registerWidget()` 是 `widget.clicked.connect(onClick)`（`navigation_panel.py:403`）
     —— PySide6 按可调用对象的**元数**投递参数，`lambda p=page:` 的**第一个位置参数**会被投成 `True`；
  4. 于是实际执行 `switchTo(True)` → `StackedWidget.setCurrentWidget(True, popOut=True)`
     （`qfluentwidgets/window/stacked_widget.py:43-51`）→ `PopUpAniStackedWidget.indexOf(True)`
     → **`TypeError: 'QStackedWidget.indexOf' called with wrong argument types: indexOf(bool)`**。
- **复现（真实鼠标点击，非直接调函数）**：
  ```python
  QTest.mouseClick(panel.items["notePage"].widget, Qt.MouseButton.LeftButton)
  ```
  实测输出：`before click -> current: 0 filePage` /
  `TypeError: QStackedWidget.indexOf(bool)` /
  `after click -> current: 0 filePage | notePage.isSelected: False | filePage.isSelected: False`
  —— **页面不切换，且侧栏最后一条都不高亮**（点击等于没有发生）。
- **自动化证据**：`tests/test_v150_main_window_shell.py::test_点击自绘条目必须切到同名页面`、
  `::test_条目_onClick_收到的第一个参数必须是页面`（两条 `xfail(strict=True)`，即缺陷当前存在）。
- **性质**：**本轮回归**。改造前走 `FluentWindow.addSubInterface()`，它的 onClick 是
  `lambda: self.switchTo(interface)`（**零参数**，多余参数被丢弃）。全仓 `src/` 共 **66 处**
  `connect(lambda …)`，其中把**信号参数**放在第一个位置参数的只有 **2 处**：
  本处（错）与 `src/utils/sync_engine.py:262` 的 `timer.timeout.connect(lambda c=cid: …)`
  —— 后者安全，因为 `QTimer.timeout` **不带参数**。其余 64 处要么是零参数
  `lambda: …`，要么是 `lambda _=False, x=…`（把 bool 收进 `_`）—— 也就是**唯一一处笔误**。
- **建议修法**：`onClick=lambda _checked=False, p=page: self.switchTo(p)`（或零参数
  `lambda: self.switchTo(page)`）。改完两条 xfail 会转为 XPASS ⇒ 按 `strict` 语义**变红提醒转正**。
- **为什么之前没被发现**：截图/探针走的是 `switchTo()` / `setCurrentWidget()` **程序化**切页，
  从没模拟过真实点击；UI 验收也是看截图。这正是"存在性断言最弱"的实例。

#### 问题 2（**中等，既有实现，非本轮引入**）：200 + 不可解密信封被当明文返回 ⇒ "成功但空"的静默失败

- **位置**：`jflove-desktop/src/utils/http_client.py:152-160`（`_decrypt_envelope_or_none` 返回 None）
  → `:193-198`（`_parse_response` 走"明文响应"分支 `return body`）。
- **我独立核实的路径**（不是引用审查报告）：读 `_parse_response()` 后确认 200 分支只有
  "解开了 → 返回明文 dict"与"没解开 → `return body`"两条出口，而 `body` 此时正是
  `{"nonce": ..., "ciphertext": ...}` 外壳；再逐个查消费方：
  `src/services/file_service.py:60 resp.get("files", [])`、
  `src/services/note_service.py:21 resp.get("notes", [])`、
  `src/services/disk_service.py:21 resp.get("disks", [])`、
  `src/services/user_service.py:21 resp.get("users", [])`
  ⇒ **页面拿到空列表，既不报错也不重试**（`_decrypt_envelope_or_none` 只在日志里记一条 error）。
- **可达性（不是纯理论）**：ECDH 会话失配 / 静默续约竞态会让**每一次** 200 响应都解不开
  （`_try_resync_ecdh` 正是为这类问题存在的）；被动 MITM 改包也会撞到同一条路径。
- **自动化证据**：`tests/test_security_client_authorization.py:391-398` 的
  `@pytest.mark.xfail(strict=True, reason="已知缺陷（待修，**既有实现**不是本轮引入**）：…")`
  → 函数 `::test_200_响应解密失败必须报错而不是把信封外壳当数据`（**:399**）。
  它断言的具体行为是：**200 + body 是认证失败的信封时必须抛 `ApiError`，不得返回信封外壳**。
- **建议**：`_parse_response` 里把"body 是信封形状但解不开"单列一条路径（抛
  `ApiError(502, "响应解密失败，请重试或重新登录")`），与"确实是明文响应"区分开。
- **xfail(strict=True) 的语义**（给后来人的提醒）：现在这条用例**预期失败**，所以它红了
  也不算失败（报 xfailed）；一旦实现被修好、断言通过，就会变成 **XPASS** —— 在 `strict=True`
  下 XPASS **记为失败**，从而强制后来人去删掉 `xfail` 标记**把它转正**，而不是"悄悄通过"。
  这也是为什么它没有写成"断言当前的错误行为"（那样修好后测试反而继续绿，等于把 bug 固化）。

#### 问题 3（轻微，验证环境纪律）：`theme.json` 会被并发运行的东西互相覆盖

- 实测：我跑完整套 pytest 后读到 `%APPDATA%\JFLove\theme.json` 是 `{"mode": "light"}`
  （mtime 22:47:19），而**隔离实验证明我的 4 个新文件一个字节都不写它**；
  单跑 `test_ui_widgets_theme.py` 会把它写回 `{"mode": "system"}`（实测 22:49:29）。
- 结论：那个 `light` 来自**同时段运行的探针/截图脚本**（它们为出图会切 light/dark）。
  ⇒ 重申计划 §9.1 的纪律：**探针与 pytest 不要并发跑**；并发跑出来的"绿"与"状态"都不可信。
