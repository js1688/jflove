### 2.1 服务端策略

#### `test_file_manage_v1_1_3.py`（26 用例）

走完整加密链路（`do_key_exchange` → 加密 body 发起 API → 解密响应断言），覆盖：

  - 文件重命名成功（文件系统验证）
  - 目录重命名成功
  - 同名静默跳过（200）
  - 409 冲突（响应含加密信封）

- **`POST /files/move`**：
  - 文件移动到目录 / 移动到根目录（`dst=""`）
  - 目录移动（含内部文件递归验证）
  - 同目录静默跳过（200）
  - 409 同名冲突 / 400 src 不存在 / 400 dst 不存在
  - 400 移动目录到自身 / 400 移动目录到子目录（循环嵌套，安全宪法专项）
  - 明文请求体拒绝 / 无写权限 → 403

### §9 安全宪法合规性回答

**本次 v1.1.3 变更未破坏 §9 安全宪法的任何一条。**

具体确认：
1. **加密通道**：`POST /files/rename` 和 `POST /files/move` 两个新接口均走 `decrypt_request_body` + `encrypt_response`，请求/响应/错误三者全程加密 ✅
2. **明文白名单**：白名单仍仅含 3 项（`/health` / `/auth/key-exchange` / `/auth/admin-exists`），rename/move 均不在白名单，已用反向测试验证 ✅
3. **JWT 鉴权**：新接口仍仅从加密 body 的 `token` 字段读取 JWT，`Authorization` header 读取零命中 ✅
4. **权限校验**：rename/move 均实现了磁盘 write 权限校验（service 层），服务端是权威防线，客户端灰化只是附加 UX 保护 ✅
5. **日志合规**：rename/move 日志仅记录 `disk_id`，无明文路径/文件名泄露 ✅
6. **加密原语**：未引入新算法，复用 ChaCha20-Poly1305 / X25519 / HKDF-SHA256 ✅
7. **桌面端**：`services/` `ui/` `components/` 零处直接 `import requests` ✅
8. **安全五大类**：全部通过（16 新增安全专项 + 29 原有安全回归）✅
