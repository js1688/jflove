## 一、总体结论

**不通过。** Web 端 v1.3.0 存在 1 个致命问题（GET 加密请求在浏览器无法发送）、3 个严重问题（笔记接口全错、免登录恢复失效、登出 404），以及若干中/轻微问题。**核心业务（文件管理、笔记管理、管理面板）因致命问题无法使用**。

> 关键提示：代码审查报告 v1.3.0 中「严重 #2 — GET 请求不发送加密 body」的修复方向（`body: envelope` 所有方法都发 body）在**真实浏览器中不可行**——浏览器 fetch 规范禁止 GET/HEAD 携带 body。这是本次验证发现的根因性问题。

## 二、缺陷列表

### 🔴 致命

#### Bug #1 — GET 加密请求在浏览器中无法发送（阻塞文件/笔记/管理面板）

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/utils/http-client.ts` `encryptedRequest()` |
| 现象 | 所有 GET 加密接口请求直接抛 `TypeError: Request with GET/HEAD method cannot have body`，无任何网络请求发出 |
| 根因 | `http-client` 对所有方法（含 GET）都设置 `body: envelope`；浏览器 fetch 规范禁止 GET/HEAD 携带 body |
| 受影响接口 | `GET /api/v1/files/disks`（磁盘列表）、`GET /api/v1/notes/list`（笔记列表）、`GET /api/v1/disks/list`、`GET /api/v1/users/list`、`GET /api/v1/permissions/list`、`GET /api/v1/config` |
| 已验证现象 | ① admin/tanj 文件管理页磁盘列表永远「暂无可用磁盘」；② 设置页「浏览选择」点击无反应（`listAllDisks()` 静默 catch）；③ 用户管理页「暂无普通用户」（实际存在 `tanj`） |
| 修复建议 | 后端将这些只读路由改为支持 POST（如 `@router.api_route("/disks", methods=["GET","POST"])` 或新增 POST 路由），Web 端统一改用 `POST` 发送加密 body（对标桌面/移动端的加密 body 传输，浏览器只能 POST）；同时 `http-client` 移除 GET 携带 body 逻辑 |

> 次要关联：`file-service.listDisks()` 期望返回数组，但后端 `GET /files/disks` 返回 `{disks:[...]}` 包裹对象（修复 #1 后仍会暴露此格式问题，需一并修正为取 `resp.disks`）。

### 🟠 严重

#### Bug #2 — 笔记接口路径/字段与后端完全不一致（笔记功能全挂）

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/services/note-service.ts` |
| 现象 | 新建笔记 404（后端无 `POST /notes/create`）；保存/读取/删除/重命名均会失败 |
| 根因 | Web 端接口定义与后端 `note_controller.py` 实际路由不一致 |
| 对照 | 桌面端 `note_service.py` / 移动端 `note_service.dart` 均使用正确接口 |

| Web 端当前 | 后端实际 | 结果 |
|-----------|---------|------|
| `POST /api/v1/notes/get` | `GET /api/v1/notes/read`（body: filename） | ❌ 404 |
| `POST /api/v1/notes/save` | `POST /api/v1/notes/write`（body: filename, content） | ❌ 404 |
| `POST /api/v1/notes/create` | 后端无此接口，创建应走 `POST /notes/write`（空 content） | ❌ 404 |
| `POST /api/v1/notes/rename`（字段 old_filename/new_filename） | `POST /api/v1/notes/rename`（字段 old_name/new_name） | ❌ 字段错 |
| `POST /api/v1/notes/delete` | `DELETE /api/v1/notes/`（body: filename） | ❌ 404 |

| 修复建议 | 按后端实际路由重写 note-service：get→`GET /notes/read`、save/create→`POST /notes/write`、rename→`POST /notes/rename`（old_name/new_name）、delete→`DELETE /notes/` |

#### Bug #3 — 免登录恢复完全失效（AC-4 未实现）

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/stores/auth-store.ts`（`initFromStorage()` 定义但从未被调用）；`main.tsx` / `App.tsx` 未初始化 |
| 现象 | 登录成功后整页刷新/直接导航受保护路由（如 `/files/2`）被踢回 `/login` |
| 根因 | 没有任何地方在应用启动时调用 `useAuthStore.getState().initFromStorage()`，`isLoggedIn` 永远为 false |
| 修复建议 | 在 `main.tsx` 或 `App.tsx` 挂载时调用一次 `initFromStorage()`（从 localStorage 恢复 token/用户并校验过期） |

#### Bug #4 — 登出调用后端不存在的接口（404）

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/services/auth-service.ts` `logout()` → `POST /api/v1/auth/logout` |
| 现象 | 登出流程完成（回登录页），但 console 报 `404 Not Found` |
| 根因 | 后端 `auth_controller.py` 无 logout 接口（仅 key-exchange/init-admin/admin-exists/login/refresh-token）；桌面端/移动端 logout 均**仅本地清除会话**，不调后端 |
| 修复建议 | Web 端 `logout()` 仅清除本地会话（session.ts clearSession + auth-store 置空），删除对后端接口的调用 |

#### Bug #5 — 登录失败错误处理不当（提示含糊 + 误清会话）

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/utils/http-client.ts` `handle401AndRetry()` |
| 现象 | ① 密码错误仅提示 `[401]`，无具体错误描述；② 密码错误后 session_key 被 `clearSession()` 清除，用户必须重新点「连接」才能再次登录 |
| 根因 | ① `extractErrorDetail()` 不解密 401 错误信封（`{nonce,ciphertext}`），拿不到 detail；② 登录接口的 401（密码错误）被当作「JWT 过期」误执行 `clearSession()` |
| 修复建议 | ① 401 时先 `tryDecryptError()` 解密错误响应取 detail；② 仅 ECDH 会话类 401（命中 `ECDH_401_PATTERNS`）才 `resyncSession()`，JWT 类 401 才 `clearSession()`；登录失败不应清除会话密钥 |

#### Bug #6 — 预览页 URL 携带业务数据 + Markdown XSS 风险

| 项 | 内容 |
|----|------|
| 文件 | `jflove-web/src/pages/DiskBrowserPage.tsx:102-103`（导航带 query）；`FilePreviewPage.tsx`（`useSearchParams` + `dangerouslySetInnerHTML` + 正则 Markdown） |
| 现象 | ① 预览页 URL 为 `/files/2/preview?path=...&name=...`，**文件路径/文件名明文暴露在 URL**（违反 §9.1.4「禁止 URL 携带业务数据」与需求 §3.3）；② `renderMarkdown()` 未真正接入 `marked` 库（注释自称"动态导入"但未实现），正则替换后经 `dangerouslySetInnerHTML` 渲染，笔记/文件名含 HTML 标签时存在 XSS 注入风险 |
| 修复建议 | ① 业务数据走内部状态/加密信封传递，不放 query string；② 接入 `marked` + DOMPurify 清洗后再渲染 |
