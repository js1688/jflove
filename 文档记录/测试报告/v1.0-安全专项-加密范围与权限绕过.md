## 一、执行摘要

本次为针对「公司网络存在企业级 MITM 代理（员工电脑预装公司根 CA，HTTPS 可被透明终结再重签发）」威胁模型的端到端安全回归测试。

### 4.1 业务响应（POST `/api/v1/auth/login` 实抓）

抓取脚本透传 `TestClient` 的 raw response bytes，模拟「公司代理解密 HTTPS 后看到的明文 HTTP body」。结果如下：


**MITM 能看到的字段只有 `nonce` 和 `ciphertext`**：

- `nonce`：12 字节随机数，每次请求都不同，无法用作指纹
- `ciphertext`：base64(密文 + Poly1305 16B tag)，需要 ChaCha20-Poly1305 + 客户端持有的 session_key 才能解密
- 看不到：JWT token、用户名 `evidence`、role、user_id

### 4.2 文件流响应（GET `/api/v1/files/download` 实抓）

服务端用 `StreamingResponse` 输出帧加密文件流，每帧结构：

```
[4 字节 BE 长度 N] [12 字节 nonce] [N 字节密文，含末尾 16 字节 Poly1305 tag]
```

测试用例 `test_下载响应是帧加密流且无文件名泄漏` 中：

- 上传 150KB 文件，包含明文标记字符串 `TOP_SECRET_NOTE_数据_2026`（utf-8）
- MITM 即便完整捕获响应字节流，**对该字符串、对原始字节中的随机部分、对所有加密部分做明文搜索均找不到**
- 客户端用 `parse_stream_frame` 解密后，**字节级与原文一致**

### 4.3 响应头零泄漏

抓取响应头实测：

- 业务响应：仅 `content-type: application/json`、`x-encrypted-stream: v1`、`content-length`，无任何用户标识
- 文件下载响应：`content-type: application/octet-stream`，**无 `Content-Disposition: filename=`**，header 中找不到原始文件名

## 七、测试结论

> **是否达到「公司 MITM 即便解密 HTTPS 也看不到任何明文」的目标？—— 是。**

1. **接口加密范围**：除了三条明文白名单（`/health`、`/api/v1/auth/key-exchange`、`/api/v1/auth/admin-exists`，均为系统首启所必需），**所有 GET / POST / PUT / DELETE 业务请求与响应、所有错误响应（包括 404 / 405 / 422 / 400）都使用 ChaCha20-Poly1305 加密信封**。
2. **URL 零泄漏**：业务参数全部走加密 body；URL path 仅含已公开的非敏感数字 ID。
3. **文件流强加密**：上传分片在加密信封内，下载/预览采用帧式 AEAD 流加密。**篡改任意 1 字节即被 InvalidTag 拒绝**，不接受错密钥解密。
4. **响应头零敏感**：文件下载响应头**不带 filename**，业务响应头不含用户名等可关联字段。
5. **权限边界严格**：路径参数与 token user_id 绑定校验，**用户 B 用自己的 token 操作用户 A 的 upload_id / sync_config 全部 403**。admin-only 接口被普通用户调用 403；admin 自禁用 400。
6. **JWT 通道纯加密**：仅 `Authorization: Bearer xxx` header 不通过认证，强制走加密 body 的 token 字段。
7. **笔记权限已彻底移除（v1.0.11 验收）**：旧接口 404 / 405，普通用户可直接列自己的笔记，且**用户间笔记目录天然隔离**（每个用户配置独立子目录）。

测试通过，可移交到代码审查 / 发布流程。建议将 `tests/test_security_e2e.py` 列入 CI 必跑用例集。
