### R1 磁盘信息展示需补齐「最大空间 / 已用空间 / 可用空间 / 磁盘类型」

| 项 | 内容 |
| --- | --- |
| 严重级别 | 需求（功能缺失） |
| 影响端 | 桌面端、Web 端、移动端（**三端都要**） |
| 影响位置 | ① **文件管理**（磁盘列表 / 磁盘卡片）② **磁盘设置**（管理 → 磁盘管理） |
| 现状（已核实） | `GET /api/v1/files/disks` 与 `GET /api/v1/virtual-disks` 只返回 `id / name / path(real_path) / created_by / created_at`；三端页面只展示「名称 + 路径」 |
| 证据 | `jflove-server/src/services/virtual_disk_service.py::list_disks()` 返回体仅 5 个字段（本地文件 L119-L135）；`jflove-app/lib/models/virtual_disk.dart` 已定义 `totalSize`/`usedSize` 但后端不下发（解析恒为 0）；桌面/Web `AdminDisksPage.tsx` 无任何容量字段 |
| 要求 | 四处位置展示：**最大空间（total）**、**已用空间（used）**、**可用空间（free）**、**磁盘类型（文件系统类型，如 ext4/xfs/ntfs/fuse）** |
| 修复方向（供确认） | 服务端 `list_disks` / `virtual_disk_service` 增加 `shutil.disk_usage(real_path)` 取 total/used/free，`disk_type` 取自挂载信息（Linux `os.statvfs` + `/proc/mounts`，Windows `GetVolumeInformation`）；三端字段渲染 + 单位换算（人类可读）+ 容量进度条；不可读路径兜底为 `—` 不报错 |
| 验收判据 | 三端文件管理页与磁盘管理页均出现四项；数值与服务端 `df -h` 对得上；路径不可读时不崩溃 |

### P1 `POST /api/v1/auth/refresh` 恒返回 500（三端共用，token 无法续期）【严重】

| 项 | 内容 |
| --- | --- |
| 严重级别 | **严重**（核心鉴权链路不可用） |
| 端 | server（桌面 / Web / 移动三端共用同一接口） |
| 功能点 | JWT 令牌续期 |
| 现象 | 任何已登录会话调用 refresh 都返回 `500 {"detail":"服务器内部错误"}`，服务端日志 `sqlite3.IntegrityError: UNIQUE constraint failed: sessions.session_id` |
| 根因 | `jflove-server/src/services/auth_service.py:196-200`：`refresh_token()` 先调 `session_repository.revoke()`（**软删除**，只置 `deleted_at`，不删行），随后 `session_repository.create()` 用**同一个 session_id** 再插一条 → 撞 `sessions.session_id` 唯一索引 |
| 复现步骤 | ① `bash scripts/verify/server.sh start`<br>② 完成 key-exchange<br>③ `POST /api/v1/auth/refresh`（加密 body 带有效 token）<br>④ 稳定复现 500，连打 3 次都是 500 |
| 证据 | `/tmp/jfqa/evidence/route-matrix.json`（`refresh` 行 status=500）<br>`/tmp/jfqa/evidence/A-6_refresh.json`<br>`/tmp/jflove-server-verify.log` L137–L192（完整 traceback） |
| 建议修法 | `revoke()` 改为「物理删除该 session_id 的旧行」或 `create()` 改用 `INSERT ... ON CONFLICT(session_id) DO UPDATE`；同时补一条 refresh 的回归用例（当前 `tests/` 中 **0 条** refresh 测试，所以 468 条全绿也没拦住） |
| 状态 | ✅ **已修复（v1.10.26）**：去掉列级 UNIQUE，改部分唯一索引；新增 7 条回归 + 反向验证（修复前 7 failed） |

### P3 Web 端把健康的普通 MP4 判为「该文件已损坏」并引导修复【中】

| 项 | 内容 |
| --- | --- |
| 严重级别 | **中**（正常文件被误判 + 文案错误 + 三端结论矛盾） |
| 端 | Web |
| 现象 | 完全健康的 H.264/AAC `good.mp4`（ffmpeg 探测 `has_stream=True / fatal=False / duration=2.0`）在 Web 预览时返回 415，界面显示「该文件已损坏，无法在线播放」+「立即修复」 |
| 根因 | ① `jflove-server/src/utils/media_probe.py:311-331` `is_web_streamable()` 只放行分片 fMP4（moov 含 mvex），普通 MP4/faststart MP4 一律 False；<br>② Web 收到 415 后**统一按「已损坏」措辞**：`jflove-web/src/pages/FilePreviewPage.tsx:183` `setError('该文件已损坏，无法在线播放')`，未区分「不可边下边播」与「真损坏」 |
| 影响 | 用户上传的绝大多数正常 MP4 在 Web 端都提示「已损坏」并被引导去修复；而桌面/移动端用原生播放器能直接播同一个文件（`is_broken_media` 放行）→ 同一文件三端结论相反 |
| 复现步骤 | ① 上传 `ffmpeg -f lavfi -i testsrc ... good.mp4`（H.264+AAC）<br>② Web → 文件管理 → 点 `good.mp4`<br>③ 显示「加载失败 / 该文件已损坏，无法在线播放」 |
| 证据 | `/tmp/jfqa/web/B-pv5-视频mp4.png`；同文件移动端可播 `/tmp/jfqa/android/23-video.png`（00:02 / 100%） |
| 建议修法 | 文案拆分两种情况：「该格式不支持网页边下边播，建议修复为 MP4（fMP4）」vs「文件已损坏」；或对 415 detail 里的 `[MEDIA_NEEDS_REPAIR]` 按 `mse_only` 语义给不同文案 |
| 状态 | ✅ **已修复（v1.10.26）**：服务端两接口各补 4 字段；Web/桌面/移动三端渲染并实测与 `df -h` 一致 |
