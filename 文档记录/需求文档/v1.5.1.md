# JFLove v1.5.1 需求文档

> 本版本为 **v1.5.0 发布后的用户实测反馈修复版本**，需求来源为 GitHub 仓库 `js1688/jflove` 的 4 条 open issue。
> 基线：`文档记录/需求文档/v1.5.0.md`。上游决策记录：`plans/v1.5.1-github-issues-fix.md`。

## 0. 背景与来源

用户在 v1.5.0（桌面端已迁移为 Web UI，与 Web 端同源快照）实际使用后，通过 GitHub issue 提交了 4 条问题（截至 2026-10-10 全部为 open、无标签、无评论）：

| Issue | 标题 | 用户标注的端 | 客户端版本 |
|-------|------|-------------|-----------|
| [#1](https://github.com/js1688/jflove/issues/1) | web 端 logo 不一致 | web | 1.5.0 |
| [#2](https://github.com/js1688/jflove/issues/2) | web 端 系统设置中功能不全 | web | 1.5.0 |
| [#3](https://github.com/js1688/jflove/issues/3) | 视频播放器框不联动问题 | 桌面端 | 1.5.0 |
| [#4](https://github.com/js1688/jflove/issues/4) | 笔记本显示体验问题 | web + 桌面端 | 1.5.0 |

## 1. 项目概述

### 1.1 目标

1. 消除 **Web 端与桌面端在同一功能上的可见差异**（品牌标识、系统设置项）；
2. 让**笔记编辑页的默认交互符合"阅读为主"的真实使用场景**（大纲在侧边、打开即预览）；
3. 修复**桌面端原生媒体浮层的生命周期与几何同步缺陷**（关窗残留、拖动掉画面）。

### 1.2 核心原则

- **只修这 4 条**：不夹带任何其他重构、性能优化或新功能。
- **两端一致优先**：桌面端 `ui/` 与 Web 端 `jflove-web/` 是**同源快照、各自独立演进**的两份工程，凡涉及共同页面的改动必须两端同步，且以**逐字节一致**为交付判据。
- **不新增接口、不变更加密策略、不扩大明文白名单**（`AGENTS.md §9`）。
- **删除"看起来能配、实际不生效"的界面**：宁可少一个开关，也不保留会误导用户的死开关。

## 2. 功能需求

### 2.1 品牌标识两端一致（#1）

**用户原话**：桌面端左上角是"一只可爱的猫猫"，Web 端左上角是"一个盾牌"，应把 Web 端改成与桌面端一致的猫猫。

**用户故事**：作为同一产品的使用者，我在 Web 端与桌面端看到的品牌标识应当是同一个形象，否则会怀疑自己打开的是不是同一个产品。

**功能规则**：

1. Web 端**左上角品牌区**（侧边栏顶部）显示与桌面端相同的猫猫 logo 图片；
2. Web 端**登录页**的品牌标识同样使用该猫猫 logo（用户反馈的是"左上角"，但登录页是同一品牌位的另一处，一并统一，避免只改一处又留下第二种形象）；
3. 桌面端品牌标识**保持不变**（它已是用户认可的基准）；
4. 浏览器标签页图标（favicon）**不在本次范围**（它当前既不是盾牌也不是猫，与用户描述的"左上角"无关）。

### 2.2 系统设置两端一致（#2）

**用户原话**：系统设置里应该有「允许重编码降级」开关，这个开关在桌面端存在、Web 端不存在，应该在 Web 端加上。

**需求澄清（关键，已与用户确认）**：

- 服务端自 **v1.4.2 hotfix** 起**已不再读取** `media_repair_allow_transcode` 这个配置键（任何代码都不读），也就是说**桌面端这个开关拨了没有任何效果**，是一个"僵尸 UI"。
- 因此"在 Web 端补上开关"会把两端一起对齐到一个**失效**的交互上。
- **最终裁定：删掉桌面端的「允许重编码降级」开关**，使两端系统设置项完全一致，且界面上不再出现任何不生效的配置项。

**功能规则**：

1. 桌面端系统设置页**移除**「允许重编码降级」开关；
2. Web 端系统设置页**保持现状**（不新增该开关）；
3. 两端系统设置页的**可见配置项集合完全一致**：仅「修复并发数」；
4. 服务端配置键 `media_repair_allow_transcode` **保留在库中不删**（服务端既有约定，本次不动后端）。

### 2.3 笔记大纲移至侧边（#4-a）

**用户原话**：笔记本的大纲目录在底部，"这个感觉很怪"，应该改为侧边，"符合正常体验"。

**功能规则**：

1. 笔记编辑页的大纲由**底部折叠区**改为**右侧竖栏**；
2. 大纲栏在 **预览模式**与**分屏模式**下均可见（分屏时用户同样需要快速跳转）；
3. 大纲栏**可折叠/展开**（给编辑留出完整宽度）；
4. 点击大纲条目仍跳转到预览区对应标题（沿用既有行为）；
5. 仅当笔记含标题（≤3 级，与 v1.4.2 口径一致）时展示大纲栏。

### 2.4 打开笔记默认为预览模式（#4-b）

**用户原话**：笔记本打开应该默认为预览模式，而不是分屏展示，"因为对于已存在的笔记本内容，默认预览体验感会好一些，毕竟编写的概率比较小"。

**功能规则**：

1. 打开**已有内容**的笔记 → 默认 **预览模式**；
2. **新建**的（空）笔记 → 默认 **编辑模式**（新建的目的就是写）；
3. 用户**手动切换**过模式后，本次编辑期间不再被自动改动；**该"手动优先"的作用域是当前这篇笔记**——切换到另一篇笔记时，按该篇内容重新判定（有内容→预览、空→编辑）。
4. 自动保存、离开确认、图表"跳到源码"等既有交互**行为不变**。

### 2.5 桌面端媒体浮层与主窗同步（#3）

**用户原话**：桌面端播放视频时，① 直接关闭窗体，视频播放器"还会停留在原地"；② 拖拽时视频播放框不会随主框移动，拖拽后播放内容消失但音频继续播放。用户怀疑是嵌套问题，并**不确定 Web 端是否也有此问题**。

**功能规则**：

1. 主窗口**关闭（= 最小化到系统托盘，既有语义）**后，原生媒体浮层**必须一并隐藏**，屏幕上不得残留画面；应用继续在后台运行（音频是否继续播放：**保持现状继续播放**，因为托盘语义就是"后台运行"；若用户实测认为应暂停，另立需求）；
2. **拖动 / 缩放主窗口**时，浮层画面**跟随主窗**，不得停留在旧屏幕位置；画面与音频始终同步；
3. 全屏播放状态下，拖动/缩放主窗**不得**把浮层从全屏态拉回；
4. Web 端（浏览器）**不在本次范围**：该问题是桌面端原生浮层（OS 解码器 + 独立顶层窗口）的实现缺陷，浏览器端没有这层结构。

## 3. 非功能需求（体验层面）

| 维度 | 要求 |
|------|------|
| 视觉一致性 | 同一品牌位在两端呈现同一形象；两端系统设置页配置项集合一致 |
| 交互一致性 | 大纲栏的折叠/展开、条目跳转在两端表现一致 |
| 稳定性 | #3 的修复不得引入浮层抖动、闪烁或画面残留；`_force_repaint` 语义保持（原生窗口隐藏后 Chromium 必须重绘，见 `LESSONS.md` L40） |
| 性能 | 拖动主窗时不得出现明显的画面滞后或卡顿；不得为同步几何引入定时轮询 |
| 兼容性 | 桌面端 Windows / Linux 行为一致；Web 端 PC 与移动浏览器布局均正常 |
| 安全（不变） | 不新增接口、不新增路径参数、不变更加密信封与明文白名单、不引入新密钥/静态盐（`AGENTS.md §9`） |
| 可追溯 | 4 条 issue 在本版本内闭环，交付物中注明对应 issue 编号 |

## 4. 关键决策与最终裁决

> 决策日期 2026-10-10，均已获用户确认（见 `plans/v1.5.1-github-issues-fix.md` §4）。

| 决策点 | 最终结论 | 被否决的方案（及原因） |
|--------|---------|----------------------|
| **D1 版本与流程** | 新建 **v1.5.1**，走完整迭代 Phase 1→8 | 沿用 v1.5.0 + 快速修复通道：被否决，因为 #4 会**改变默认交互行为**，没有需求/设计记录会导致后续无法追溯 |
| **D2 #2 方向** | **删除桌面端的僵尸开关**（服务端契约事实：该键已无人读取） | ① "Web 端照抄加上开关"：把两端一起对齐到失效交互，且继续误导用户；② "恢复服务端重编码降级能力"：属新功能（ffmpeg 降级链路 + 设计文档），超出本次修复范围 |
| **D3 大纲形态** | **右侧可折叠竖栏**，预览与分屏下均显示 | ① 左侧竖栏：与左侧导航栏视觉混淆；② 仅预览模式显示：分屏下失去快速跳转便利 |
| **D4 默认模式与范围** | **已有内容→预览、空笔记→编辑**；移动端**不动** | ① 新建也走分屏：小屏体验差；② 移动端同步改：超出 issue 描述范围（issue 仅写 web/桌面端） |
| **D5 全屏 vs 渲染层信号**（R5-T3 / AC-14b） | **全屏优先**：浮层处于全屏时，渲染层上报的 `visible=false`（内容滚出视口）**不得**把全屏拉回；非全屏时仍尊重 `visible=false` | 备选"渲染层优先"被否决：全屏是用户**显式点击**的意图，而 `visible=false` 是布局派生信号，用它打断全屏会出现"全屏播放中主窗一变就掉出全屏"的观感。**用户 2026-10-10 确认；实现零改动（当前代码即此口径）** |

> 关于 #2 的另一条事实（供追溯）：`media_repair_enabled`（实时修复总开关）与 `media_repair_allow_transcode`（重编码子开关）**同批废弃**，但**只有重编码子开关的 UI 残留**在桌面端，这也是"两端不一致"的直接原因。

## 7. 本次不做（范围外）

- 浏览器标签页 favicon 换图（与用户描述的"左上角"无关，避免夹带）。
- 服务端重编码降级能力的恢复（属新功能，需独立需求 + 设计）。
- 移动端（`jflove-app`）的大纲形态与默认模式调整（issue 未涉及）。
- 清理数据库中已废弃的配置键（`AGENTS.md §5` 相关流程，且服务端明确"保留在库中不删"）。
- Web 端（浏览器）媒体播放的任何改动（#3 只发生在桌面端原生浮层）。
