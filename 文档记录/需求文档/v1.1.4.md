# JFLove v1.1.4 需求文档

## 0. 与 v1.1.3 的差异说明

| 项 | v1.1.3 行为 | v1.1.4 期望行为 |
|---|---|---|
| 服务端地址持久化 | 关闭程序或 token 到期弹出登录窗时，已连接过的服务端地址历史**丢失**，下拉框为空 | 所有连接成功的地址永久保留在本地缓存中，重启/过期后仍在下拉框可选；还可删除历史记录 |
| token 有效期 | 下拉可选：30分钟 / 1小时 / 2小时 / 4小时 / 8小时 | 替换为按天选择：**1天 / 7天 / 30天**；服务端同步扩展 JWT 最大有效期至 30 天 |
| rename/move 错误码 | 重命名或移动不存在的路径时返回 400（参数错误） | 返回 404（资源不存在），符合 REST 语义 |
| token 过期弹窗 → 双窗口 | **必现 Bug**：会话到期弹框「登录已过期」→点击确认→出现新登录窗→登录成功→新旧两个主窗口并存，旧窗口仍残留 | 仅保留一个新主窗口；旧主窗口在登出流程中彻底关闭并清理 |

**保持不动的事项**：
- v1.1.3 全部功能行为不变；
- 端到端加密协议不变；
- 数据库表结构不变；
- 除 JWT 最大有效期外，其他服务端配置常量不变。

---

## 1. 项目概述

v1.1.4 是补丁版本（小迭代），聚焦三类问题：
- **缺陷修复**：v1.1.3 遗留的 404 错误码问题 + 必现的双主窗口 Bug；
- **本地缓存修复**：服务端地址历史在重启/过期后丢失，需确保持久化始终有效；
- **体验优化**：token 有效期从"按小时"改为"按天"选择，减少频繁登录。

涉及模块：
- **jflove-desktop**：登录页地址历史修复、TTL 下拉替换、双窗口 Bug 修复；
- **jflove-server**：`rename`/`move` 404 修复、JWT 最大有效期扩展至 30 天。

---

## 2. 目标用户

与已有版本一致。核心受益场景：
- 需要**长期登录不重复输入密码**的用户（7 天/30 天选项）；
- 使用多台服务端的用户（地址历史不丢，方便切换）；
- 日常使用中遇到 token 过期弹窗后出现两个窗口的用户（Bug 修复）。

---

## 3. 功能需求

### 3.1 服务端地址历史持久化修复

#### 3.1.1 用户故事

> 作为用户，我成功连接过的服务端地址应该一直保留在下拉框的历史记录中，不管我关闭程序还是 token 过期后重新打开，都能直接选择之前用过的地址，而不是每次都要重新手打。

#### 3.1.2 现状与期望

| 场景 | 当前行为（Bug） | 期望行为 |
|---|---|---|
| 关闭程序后重新打开 | 历史下拉为空 | 之前成功连接过的地址正常显示 |
| 会话到期后弹出登录窗 | 历史下拉为空 | 同上，历史记录保留 |
| 正常退出登录（设置页「退出登录」） | 历史未丢失 | 保持现状 |

#### 3.1.3 规则约束

- 连接成功后**立即**写入本地缓存（磁盘文件），不依赖程序正常退出流程；
- 最多保留 10 条历史记录，最近使用的置顶；
- 历史文件损坏或不存在时，兜底显示 `http://localhost:8989`；
- 用户可从下拉框手动删除某条历史记录。

---

### 3.2 Token 有效期改为按天选择

#### 3.2.1 用户故事

> 作为用户，我希望登录时可以选择 1 天、7 天、甚至 30 天的有效期，而不是每次用几小时就要重新登录。

#### 3.2.2 交互变化

**登录页「登录有效期」下拉选项替换为**：

| 选项 | 对应秒数 |
|---|---|
| 1 天 | 86,400 |
| 7 天 | 604,800 |
| 30 天 | 2,592,000 |

- 默认选中「1 天」（首次使用）；
- 用户选择后持久化偏好，下次登录时自动选中上次选择；
- 服务端 JWT 签发上限从 8 小时放宽到 30 天。

#### 3.2.3 规则约束

- 实际生效时长 = min(用户选择天数, 服务端 JWT 签发值)；两者取最小值；
- 有效期只影响 JWT，不影响 ECDH 会话密钥（会话密钥仍为临时生成，用完即丢，保持前向保密）；
- 服务端管理员不可单独限制某个用户的 TTL 上限（不增加服务端配置接口，保持简单）。

---

### 3.3 rename/move 路径不存在时返回 404

#### 3.3.1 用户故事

> 作为开发者，当重命名或移动一个不存在的文件/目录时，服务端应返回 404（资源不存在）而非 400（参数错误），符合 REST 规范，也方便客户端精确判断错误类型。

#### 3.3.2 期望行为

| 场景 | v1.1.3 | v1.1.4 |
|---|---|---|
| 重命名不存在的文件/目录 | 返回 400 | 返回 404，detail 说明目标资源不存在 |
| 移动不存在的源文件/目录 | 返回 400 | 返回 404 |
| 目标名称已存在（重命名冲突） | 返回 400 | 保持 400（不是 404） |
| 目标位置已有同名项（移动冲突） | 返回 400 | 保持 400 |

- 仅改错误码，不改变加密信封格式；
- 不新增接口，不改变鉴权逻辑。

---

### 3.4 双主窗口 Bug 修复

#### 3.4.1 用户故事

> 作为用户，当我的登录凭证到期后，系统弹出对话框提示「登录已过期」—我点击确认—出现新的登录窗口—登录成功后，不应该同时存在新旧两个业务主窗口。旧窗口必须被自动清理。

#### 3.4.2 当前 Bug 现象（必现）

1. 定时器（60 秒）检测到 token 过期；
2. 弹出 `MessageBox`「登录已过期，请重新登录」；
3. 用户点击确认；
4. 原业务主窗口**未关闭**，同时出现新的登录窗口；
5. 登录成功后，新主窗口创建，**旧主窗口依然可见**——用户看到两个业务窗口。

#### 3.4.3 期望行为

1. 弹出对话框「登录已过期」；
2. 用户点击确认后：旧主窗口**立即关闭并销毁**（从屏幕消失，页面/定时器等资源全部释放）；
3. 然后弹出登录窗口；
4. 登录成功后，仅创建一个新主窗口——任何时候最多只有一个业务主窗口。

## 4. 非功能需求

| 维度 | 要求 |
|---|---|
| 安全性 | 服务端地址历史缓存在客户端本地磁盘，不通过网络传输；TTL 仅影响 JWT，ECDH 会话密钥仍保持临时性（前向保密）；404 修复不影响加密信封 |
| 性能 | 地址历史为静态 JSON 文件读写，无性能影响；TTL 选项变更为纯配置改动 |
| 兼容性 | 旧客户端请求小于 1 天的 TTL 时，服务端正常签发（未修改下限，仅上移上限）；新客户端请求 30 天 TTL 时，旧服务端会 clamp 到 8 小时——升级服务端后完整生效 |
| 体验 | 地址历史「失忆」问题彻底修复后，用户不再需要每次重新输入；1/7/30 天选项减少日常登录频率 |
| 错误处理 | 404 返回时，客户端 InfoBar 显示「目标资源不存在」而非通用错误，帮助用户理解问题 |

## 5. 验收标准

| # | 验收点 | 期望 |
|---|---|---|
| AC-1 | 连接服务端 A → 关闭程序 → 重新打开 → 服务端地址下拉框中 A 存在 | 是 |
| AC-2 | 连接 A → 等待 token 过期弹窗 → 点击确认 → 登录页下拉框中 A 存在 | 是 |
| AC-3 | 连接 A → 连接 B → 连接 C → 下拉框中 B、C、A 排序（最近使用优先） | 是 |
| AC-4 | 历史记录满 10 条后新增 → 最早的记录被淘汰 | 是 |
| AC-5 | 下拉框中可删除某条历史记录 | 是 |
| AC-6 | 登录有效期下拉包含「1天 / 7天 / 30天」三个选项 | 是 |
| AC-7 | 选择「7天」登录成功后，下次打开登录页默认选中「7天」 | 是 |
| AC-8 | 服务端接受 30 天 TTL 请求并正常签发 JWT | 是 |
| AC-9 | 用旧版桌面端（请求 8 小时）连接新版服务端，仍正常工作 | 是 |
| AC-10 | 重命名一个不存在的文件 → 返回 404，客户端显示「目标资源不存在」 | 是 |
| AC-11 | 移动一个不存在的文件 → 返回 404 | 是 |
| AC-12 | 重命名/移动时名称冲突 → 仍返回 400 | 是 |
| AC-13 | token 过期弹窗 → 点击确认 → 旧主窗口消失 | 是 |
| AC-14 | token 过期弹窗 → 点击确认 → 登录成功后只有一个主窗口 | 是 |
| AC-15 | v1.1.3 已有功能（上传、下载、预览、删除、重命名、移动、新建目录）回归不受影响 | 是 |

- C-6（批量操作）——低优先级，留后续版本；
- 服务端 TTL 管理接口（管理员限制用户 TTL 上限）——不引入；
- 地址历史加密存储——不引入（仅存 URL，无敏感信息）。
