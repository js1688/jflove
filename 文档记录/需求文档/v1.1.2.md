# JFLove 1.1.2 需求文档

## 0. 与 v1.1.1 的差异说明

本版本聚焦两个体验问题：

1. v1.1.1 上线"登录有效期"下拉后用户实测发现：选择 4 小时 / 8 小时**实际上不会真的延长会话**，会话仍然在 1 小时（服务端默认 JWT 有效期）就被踢出。原因是 JWT 是服务端签发的，客户端 UI 选项只能在本地做"更早过期"的限制，无法延长。
2. v1.1.1 在登录页加入"登录有效期"下拉后，整页布局变得拥挤，控件过多、视觉层次混乱。

| 项 | v1.1.1 行为 | v1.1.2 期望行为 |
|---|---|---|
| "登录有效期"下拉 | UI 提供 30 分钟/1 小时/2 小时/4 小时/8 小时 5 档；但**只能让会话提前到期，不能延长**。选 4h/8h 实际仍按 1h 失效 | 服务端在签发 JWT 时支持按客户端请求的 TTL 来定 `exp`，**真正按用户选择延长有效期**。允许的最大值由服务端硬上限保护（详见 §4.1.3） |
| 登录页布局 | 8 行控件垂直堆叠：标题 / 说明 / 用户名 / 密码 / "登录有效期"标签（独占一行）/ 下拉（独占一行）/ 登录按钮（独占一行）/ 返回按钮（独占一行），间距均为 14px → 拥挤 | 整理为 6 行：标题 / 说明 / 用户名 / 密码 / 「登录有效期 + 下拉」横向同行 / 「返回 + 登录」按钮横向同行 |
| 服务端 JWT_EXPIRE 配置 | 写死 1 小时（`JWT_EXPIRE_HOURS = 1`） | 保留 1 小时为默认值；新增硬上限常量 `JWT_EXPIRE_MAX_HOURS = 8`，禁止任何客户端请求超过该值；登录接口接受可选的 TTL 入参 |

**保持不动的事项**：

- v1.1.0 / v1.1.1 已有的全部功能行为不变；
- 端到端加密协议、加密信封格式、流式帧格式不变；
- ECDH 静默续约逻辑（v1.1.1 引入）不变；
- "JWT 真到期 = 退出登录"原则不变（不引入 JWT 自动续期）；
- 数据库表结构不变。

## 1. 项目概述

v1.1.2 是 v1.1.1 的小补丁版本，把 v1.1.1 引入但未完全闭环的"登录有效期"功能补完整：让用户在 UI 上选择的有效期**真正生效**；同时修复 v1.1.1 引入的登录页 UI 拥挤问题。

涉及模块：

- **jflove-server**：登录接口扩展、JWT 签发支持自定义 TTL、新增硬上限校验；
- **jflove-desktop**：登录请求带上用户选择的 TTL；登录页布局重排。

## 2. 目标用户

与 v1.1.1 一致，无新增用户群。重点改善以下场景：

- **长时间挂机的用户**：希望 4 小时 / 8 小时下拉选项真的能让自己长时间不被踢；
- **新用户的首次登录体验**：希望登录页看起来清爽不挤，按钮主次清晰。

## 3. 核心价值变化

- **"所见即所得"的会话有效期**：用户在 UI 上选 8 小时，本地会话就真的有 8 小时；不再让用户疑惑"我选了 4 小时为什么 1 小时就被踢"；
- **登录页清爽**：控件分组合理，按钮主次清晰，不会因为 v1.1.1 加了一个下拉就把整页搞拥挤。

## 4. 功能需求

### 4.1 登录有效期真延长

#### 4.1.1 用户故事

> 作为一名重度使用者，我已经习惯在登录页选 8 小时来覆盖一个工作日。
> 我希望选 8 小时之后真的过 8 小时才被踢，而不是 1 小时就弹"会话已过期"。

#### 4.1.2 交互期望

- 登录页"登录有效期"下拉的 5 档（30 分钟、1 小时、2 小时、4 小时、8 小时）**全部真实生效**；
- 用户登录成功后，服务端签发的 JWT 的有效期等于用户选择的值（除非超出服务端硬上限——详见 4.1.3）；
- 客户端的 `effective_expire_at` 计算口径不变（仍取 min(JWT exp, 本地上限) ），但因为服务端 JWT 已经按用户选择签发了，所以两者基本相等。

#### 4.1.3 安全约束

- 服务端必须有"硬上限"保护：客户端请求的 TTL 不得超过 8 小时（`JWT_EXPIRE_MAX_HOURS = 8`）。任何超过该值的请求由服务端 clamp 到上限，不向客户端报错（保持容错）；
- 服务端必须有"硬下限"保护：客户端请求的 TTL 不得低于 60 秒（避免恶意客户端请求 0 秒导致登录无意义）；
- 客户端不传 TTL 字段时，服务端使用默认值 1 小时（`JWT_EXPIRE_HOURS = 1`），保持向后兼容；
- 不引入"超过 8 小时"的档位——这是与"安全 > 便利"取舍一致的产品决策。如果用户的工作场景必须超过 8 小时，可以在服务端 settings.py 里调高常量（属于运维决策，不是用户决策）；
- JWT 自动续期仍然不引入。

### 4.2 登录页布局优化

#### 4.2.1 用户故事

> 作为新用户，登录页应该清爽、专业、不像草稿；现在 8 个控件全垂直堆着，太挤了。

#### 4.2.2 布局期望

```
[标题:    登录 JFLove]
[说明:    所有通信均经过加密……]
[输入:    用户名]
[输入:    密码]
[行 5:    登录有效期 [▼ 1 小时]   ]   ← 横向：左标签 + 右下拉
[行 6:    [返回]            [ 登录 ] ]   ← 横向：左次按钮 + 右主按钮（占大头）
```

要求：

- "登录有效期"标签和下拉同行，标签左对齐，下拉右侧填满剩余宽度；
- 登录按钮（PrimaryPushButton）与返回按钮（PushButton）同行，登录在右侧主位、占据较大宽度；返回在左侧次位、宽度紧凑；
- 整体行间距适当（建议 14~16 px），不过密也不过疏；
- 视觉上：登录按钮明显比返回按钮显眼（颜色 + 宽度）；
- 回车键触发登录的行为保持。

#### 4.2.3 边界

- 仅修改"用户登录页"（已有管理员的登录场景）的布局；
- 管理员初始化页（首次创建管理员）暂不调整（控件本来就不多）；
- 服务端地址输入页不调整。

### 4.3 服务端硬上限的展示（可选，非阻塞）

服务端 8 小时上限是产品保留的"安全开关"，**不在 UI 上向用户暴露**——用户在 UI 上看到的最大值就是 8 小时，与服务端硬上限默认一致。如果某一天后续版本需要让运维团队改大这个值，再考虑在 UI 上同步显示。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 兼容性 | v1.1.2 桌面端连 v1.1.1 服务端：v1.1.1 服务端不识别 TTL 字段，依旧签发 1 小时 JWT，4h/8h 选项失效但不报错；v1.1.1 桌面端连 v1.1.2 服务端：服务端识别不到 TTL 字段时使用默认值 1 小时。两端均无破坏性升级 |
| 安全 | 必须有 8 小时硬上限；不引入"长期 token / 自动续期"；不变更加密协议 |
| 性能 | 无新增网络往返，无新增数据库读写，仅修改 JWT 的 exp 字段计算 |
| 体验 | 登录页拥挤问题修复，整页一眼看完毕 |

## 6. 验收标准

| # | 验收点 | 期望 |
|---|---|---|
| AC-1 | 登录页"登录有效期"标签与下拉同行 | 是 |
| AC-2 | 登录页"返回"和"登录"按钮同行，登录在右侧主位 | 是 |
| AC-3 | 用户在 UI 选 4 小时登录后，4 小时内不会因为 JWT 过期被踢 | 是（误差 ≤ 30s） |
| AC-4 | 用户在 UI 选 8 小时登录后，8 小时内不会因为 JWT 过期被踢 | 是 |
| AC-5 | 用户在 UI 选 30 分钟登录后，30 分钟内不会被踢，30 分钟整后被踢 | 是 |
| AC-6 | 客户端不带 TTL 字段调用 login（v1.1.1 桌面端连 v1.1.2 服务端场景）| 服务端按默认 1 小时签发，无报错 |
| AC-7 | 客户端发送超过 8 小时的 TTL（伪造请求） | 服务端 clamp 到 8 小时，不报错；签出来的 JWT exp 不超过 8 小时 |
| AC-8 | 客户端发送 0 或负数 TTL（伪造请求）| 服务端 clamp 到下限 60s 或返回 400；不签出无效 token |
| AC-9 | "登录有效期"下拉记忆上次选择（v1.1.1 已通过的功能） | 仍然通过 |

## 7. 不在本期范围

- 仍然不做 JWT 自动续期；
- 不引入超过 8 小时的档位；
- 不在 UI 上展示服务端硬上限（运维信息）；
- 不调整管理员初始化页与服务端地址页的布局；
- 不变更数据库；
- 不变更加密协议。
