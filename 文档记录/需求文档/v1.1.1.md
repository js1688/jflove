# JFLove 1.1.1 需求文档

## 0. 与 v1.1.0 的差异说明

本版本仅修复"会话频繁过期"的体验问题，所有 v1.1.0 的现有功能保持不变。变更项：

| 项 | v1.1.0 行为 | v1.1.1 期望行为 |
|---|---|---|
| 登录有效期 | 默认 1 小时，写死，不可配置 | 默认仍为 1 小时；登录页提供"登录有效期"下拉项可改（30 分钟 / 1 小时 / 2 小时 / 4 小时 / 8 小时） |
| 登录到期后的表现 | 客户端定时器检测到过期 → 弹"登录已过期" → 退出登录 | 行为保持：到期即退出；但保证**只弹一次**对话框、**只回到一个登录窗口**，绝不出现两个"已过期"提示或两个登录窗口 |
| 服务端重启 / ECDH 会话失效 | 任意请求得到 401 → 客户端把它当作"登录过期"弹窗 → 强制退出 | **客户端在后台静默重新建立加密通道，并自动重发当次请求**，整个过程对用户不可见；视频播放、文件预览、文件传输都不应被中断或弹窗 |
| 视频在线预览长时间播放 | 跨过 1 小时即被弹窗踢出 | 行为保持：JWT 真过期时仍会到期退出；但不会再因为"加密会话掉了"被无端踢出 |
| 后台请求出现 401 | 一律提示"令牌无效或已过期" | 区分两类：JWT 类 = 退出登录；ECDH 类 = 后台续约后透明重试，不打扰用户 |

**保持不动的事项（与上一版一致）**：

- v1.1.0 的全部功能与既有交互不变；
- 端到端加密协议、加密信封格式、流式帧格式不变；
- 不引入"长期身份密钥 / 公钥固定 / 持久化 session_key"等机制（继续遵守 AGENTS.md §9.2）；
- 不做"JWT 自动续期"——到期=退出，符合用户对"安全 > 便利"的取舍偏好。

## 1. 项目概述

JFLove 1.1.1 是 1.1.0 之后的小补丁版本，焦点是修复用户在使用 1.1.0 时反馈的一个体验问题：

> "在线预览视频时经常弹出'会话已过期'，必须重新登录，明明刚登录没多久。"

经定位，问题源自客户端把两类不同的 401 错误（JWT 失效 / ECDH 加密会话失效）混在一起处理；两者中只有前者真正应该让用户重新登录，后者完全可以由客户端在后台静默恢复。

## 2. 目标用户

与 v1.1.0 一致，无新增用户群。重点改善以下两类高频用户的体验：

- **媒体爱好者**：长时间观看远程视频时不希望被无端打断；
- **重度使用者**：长时间挂机、白天不关闭客户端的用户。

## 3. 核心价值变化

- **会话稳定**：开机一整天的客户端在 JWT 过期前应当持续可用，绝不因为服务端重启等"加密会话级"事件被打扰；
- **可控的安全过期**：用户可以根据自己的工作场景在登录界面选择登录有效期，默认仍为 1 小时（保守值，遵循"安全优先"的产品定位）；
- **过期体验干净**：到期那一刻只看到一次提示、一个登录窗口，不会出现两个对话框堆叠、两个登录界面同时打开等让人困惑的现象。

## 4. 功能需求

### 4.1 登录有效期可配置

#### 4.1.1 用户故事

> 作为一名管理员，我希望在登录界面就能选择本次登录的有效期。
> 默认 1 小时是合理的；但如果我在维护一段较长的运维任务（比如批量同步 / 检索大日志），我希望能选 4 小时或 8 小时，避免中途被踢。
> 我也接受最长 8 小时；超过这个值我宁愿重新登录。

#### 4.1.2 交互

- 登录界面在用户名 / 密码下方新增一个下拉选项："登录有效期"；
- 可选值：30 分钟、1 小时（默认）、2 小时、4 小时、8 小时；
- 用户的上次选择持久化保存到本地配置（与"服务器地址"等已有持久化字段并列），下次启动客户端时默认勾选用户上次选择的值；
- 选项不影响"免登录恢复"逻辑：仍然以服务端签发 token 的真实 `exp` 为准。

#### 4.1.3 边界

- 选项仅作用于**本地客户端的会话计时器**：到期即视为本地登出，不依赖服务端。
- 服务端签发 token 的有效期仍由服务端控制（默认 1 小时，与本期前后端兼容）；如果用户在 UI 上选择了 8 小时，但服务端 token 1 小时到期了，客户端仍然以"两者中较短者"为准——即按服务端 token 真实有效期 1 小时为最终有效期。
- 因此选项的实际意义是"我希望本地最长保留的会话时长不超过 X"——这是一个"更严格"的开关而不是"延长"开关，符合安全宪法精神。

### 4.2 登录到期的表现修复

#### 4.2.1 用户故事

> 作为用户，登录到期我接受被踢回登录页。
> 但我不接受看到两个"会话已过期"对话框、或者两个登录窗口同时存在。

#### 4.2.2 交互期望

- 客户端检测到 token 到期 → **只弹一次**"登录已过期"对话框；
- 用户点击对话框确认后，关闭主窗口、打开**唯一一个**登录窗口；
- 在弹窗未关闭、登录窗未销毁前，所有后台请求若再次得到 401，都不再触发新的弹窗、不重复打开新的登录窗口；
- 用户从托盘恢复窗口时，看到的也是一致的状态（要么主界面，要么登录界面，没有"两层叠加"现象）。

### 4.3 加密会话失效的静默恢复

#### 4.3.1 用户故事

> 作为用户，我并不在意"加密通道"这个概念。
> 我只希望我的客户端能正常工作。
> 服务端如果重启了 / 加密会话被清掉了，我希望客户端能自己悄悄恢复，而不是丢一句"会话已过期"让我重新登录。

#### 4.3.2 交互期望

- 后台所有请求，包括视频播放过程中的 Range 请求、文件下载、文件上传分片，遇到"加密会话失效"类 401 时，应当：
  1. 在后台重新执行密钥交换；
  2. 自动用新会话重发当前请求；
  3. 整个过程不弹窗、不闪烁界面、不打断用户操作。
- 用户唯一可能感知的是"短暂的卡顿"（重新交换密钥需要一次额外的网络往返），但绝不出现"被踢出登录"。
- 如果重试后仍然失败（例如服务端真的不可达），则按已有的"网络错误"路径处理（在当前操作所在的 UI 区域显示错误，而不是弹"登录已过期"）。

#### 4.3.3 安全约束（与产品体验配套）

- 静默续约的密钥交换仍然走 v1.0 已有的 `key-exchange` 接口（X25519 + HKDF），保留前向保密；
- 不允许引入"长期 session_key 缓存到磁盘"等违反 §9.2 的捷径；
- 静默续约必须有限次（不论是单次请求还是同一进程内）兜底，避免因服务端持续异常而无限重试。

### 4.4 视频在线预览的"持久播放"体验

延伸自 4.3：v1.1.0 的 `StreamProxy` 在 FFmpeg 持续 Range 请求过程中，只要服务端某次 401 发生在加密会话级，客户端就应该自动续约后让 FFmpeg 的下一次 Range 自然成功，用户应感知不到中断。

JWT 真到期时，行为按 4.2 处理：弹一次提示 + 唯一登录窗口。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | ECDH 静默续约带来的额外开销不超过一次额外的密钥交换 RTT；视频播放允许在续约期间出现 ≤2 秒卡顿，不允许出现"播放器报错弹窗" |
| 可观测 | 静默续约要有日志（不暴露 session_key），便于排障 |
| 兼容 | 服务端不需要升级也能享受本版改动；老版本服务端（v1.1.0）已具备 `key-exchange` 与 `refresh` 接口 |
| 安全 | 必须与 AGENTS.md §9 安全宪法 100% 兼容；不得新增长期密钥、不得放宽明文白名单 |
| 体验 | 用户在 8 小时持续使用客户端的全过程中，不应该看到"会话已过期"被弹超过一次（即仅在 JWT 真过期时） |

## 6. 交互流程描述

### 6.1 登录流程（含新增有效期选项）

```
打开客户端
   │
   ▼
┌────────────────────────────────────────┐
│ 登录窗口                                │
│  服务器地址：[..............]           │
│  用户名：    [..............]           │
│  密码：      [..............]           │
│  登录有效期：[1 小时 ▼]                 │  ← 新增
│  [ 登录 ] [ 退出 ]                     │
└────────────────────────────────────────┘
   │
   ▼ 登录成功
本地会话计时器：取 min(用户选择, 服务端 exp)
```

### 6.2 加密会话失效的自愈流程

```
任意请求
   │
   ▼
[发送加密请求] ────► 服务端响应
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
          200 OK     ECDH 401    JWT 401
            │          │          │
        正常返回      静默续约   弹一次过期提示
                        │       打开唯一登录窗
                        ▼
                  自动重发请求
                        │
                        ▼
                     正常返回
```

## 7. 验收标准

| # | 验收点 | 期望 |
|---|---|---|
| AC-1 | 登录界面"登录有效期"下拉默认值 | 1 小时 |
| AC-2 | 修改下拉值后重启客户端 | 默认值=用户上次选择的值 |
| AC-3 | 登录后让 JWT 自然到期 | 仅出现 1 次"登录已过期"对话框，关闭后看到唯一一个登录窗 |
| AC-4 | 在后台请求频繁的页面（同步页 / 文件页 / 预览中）让 token 到期 | 仍然只有 1 次提示 + 1 个登录窗 |
| AC-5 | 在视频预览过程中重启服务端 | 视频允许短暂卡顿，但应当继续播放（FFmpeg 下次 Range 触发后自动恢复），不弹"会话已过期" |
| AC-6 | 在文件页操作过程中重启服务端 | 当前操作显示"网络错误"或自动恢复，不弹"登录已过期" |
| AC-7 | 服务端持续不可达（例如关掉服务端） | 客户端不应进入"无限续约"循环，应在合理重试后给出网络错误提示 |
| AC-8 | 关闭对话框 → 退出登录 → 再次启动 | 看到登录界面，且"登录有效期"下拉记忆上次选择 |

## 8. 不在本期范围

- 不做"在主窗口右上角显示剩余时间"等可视化（保留为后续优化候选）；
- 不做"在到期前 N 分钟自动弹出'是否续期'询问框"——本期的取舍是：到期=退出，简单直接；
- 不做"通过 Refresh Token 自动续期 JWT"——已与用户明确协商，不引入此机制；
- 不做服务端任何改动（refresh 接口已存在但本期客户端**不主动调用**它）。
