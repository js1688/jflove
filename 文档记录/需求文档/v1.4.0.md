# JFLove v1.4.0 需求文档

## 0. 背景说明

v1.3.0 是 jflove-web 浏览器端模块的首个版本，已实现对标桌面端的文件/笔记/传输/安全/管理等功能，其中视频/音频预览的边下边播依赖 **Service Worker（SW）流式代理** 作为主路径。经过 v1.3.x 的实际使用，发现两个体验问题：

1. **HTTP 环境下无法边下边播**：SW 仅在安全上下文（HTTPS / localhost）可用，因此当用户通过**内网 IP 或 HTTP 公网地址**访问时，SW 不可用，边下边播退化为"等待完整下载"或 MSE 回退，体验差。用户的诉求是**无论内网还是公网、无论 HTTP 还是 HTTPS，都要能正常边下边播**。
2. **损坏/非流式媒体文件浏览器无法播放**：已有的大量视频/音频资源（普通 MP4 moov 在尾部、MKV、AVI、MOV、FLV 等，或容器内存在损坏片段）在桌面播放器（PotPlayer/VLC 等）中可以正常播放，但**浏览器原生解码器无法播放**。用户希望这类资源也能在线播放。

经多轮方案讨论，确认 v1.4.0 的核心思路为：**"端上解密代理 + 原生播放器" 的架构不变，通过服务端对损坏/非流式媒体做"无损修复（实时计算、不落盘缓存）"，并把 Web 端边下边播统一到 MSE（Media Source Extensions）主路径**，从而：

- 任意 HTTP/HTTPS（内网/公网）环境下都能边下边播；
- 损坏/非流式文件经修复后浏览器也能播放；
- 修复仅用于在线播放，**永不覆盖/破坏原始文件**；
- 加密协议（X25519 + ChaCha20-Poly1305）完全不变。

**模块范围**：本次涉及 **jflove-server（后端）**、**jflove-web（Web 端）**、**jflove-desktop（桌面端）** 与 **jflove-app（移动端）**。
**各端范围**：桌面端/移动端**不改播放管线**（本地解密代理 + 原生播放器已满足边下边播），本次仅为三端统一新增"媒体修复"开关的配置界面；开关为**服务端配置**（存服务端 `config` 表），三端共享同一开关，任一客户端修改后所有端立即生效。

## 1. 项目概述

### 1.1 目标

为用户提供**任意网络环境（HTTP/HTTPS、内网/公网）下均可正常边下边播**的视频/音频在线预览能力，并让**已有损坏/非流式媒体文件也能在浏览器中播放**，同时保证原始数据安全、加密协议不变。

### 1.2 核心原则

- **加密协议不变**：全链路仍为 X25519 ECDH + ChaCha20-Poly1305，媒体流仍为加密帧，URL 不暴露任何业务数据。
- **原始文件永不改写**：媒体修复结果仅用于在线播放，实时计算、不落盘持久化缓存；任何情况下原始文件字节不被修改。
- **正常文件零处理**：健康的媒体文件不经过任何修复处理，直接原文件流式播放，零额外开销。
- **修复按需开关**：媒体修复能力默认关闭，由管理员在任一客户端（Web/桌面/移动）开启/关闭服务端配置，立即生效、无需重启任何端。
- **弱 CPU 友好**：修复开关默认关闭时，对低性能设备（如 N2850）无任何额外 CPU/IO/磁盘压力。
- **体验兜底明确**：确实无法修复的损坏文件，给出清晰提示（建议下载查看），不出现白屏或无限加载。

## 2. 功能需求

### 2.1 视频/音频边下边播（Web 端，任意 HTTP/HTTPS 环境）

| 功能 | 说明 |
|------|------|
| 边下边播 | 视频（mp4/webm/ogg/mkv/avi/mov/flv 等）、音频（mp3/wav/flac/aac/ogg/m4a 等）在线预览时**边下边播**，无需等待完整下载 |
| 环境无关 | 在 HTTPS 与 HTTP（内网 IP / 局域网 / 公网 HTTP）环境下均可边下边播，不依赖 Service Worker |
| 拖动 seek | 播放进度条可拖动跳转，跳到未加载区域时按需拉取对应数据 |
| 首帧快速 | 点击预览后尽快出画面（目标首帧 < 3s） |
| 全屏/音量/倍速 | 保留原生播放器的全屏、音量、播放速度等控制能力 |
| 不写磁盘 | 预览过程不落本地磁盘，不产生临时文件 |

**用例（User Story）**：用户在浏览器（无论通过 HTTPS 公网域名，还是 HTTP 内网 IP）打开一个视频文件，播放器立即开始边下边播，可随时拖动进度条，全程无需等待文件下载完成。

**AC-1**: 在 **HTTPS** 环境下，视频/音频可边下边播，首帧 < 3s，可拖动 seek。

**AC-2**: 在 **HTTP** 环境下（内网 IP / 公网 HTTP），视频/音频同样可边下边播，可拖动 seek，不依赖 Service Worker。

### 2.2 损坏/非流式媒体文件在线播放（服务端媒体修复）

| 功能 | 说明 |
|------|------|
| 健康判定 | 预览媒体文件前，先判定该文件是否为"浏览器可直播的标准流式文件"；**健康文件直接原文件播放，不做任何处理** |
| 无损修复 | 对非流式/需修复的文件做无损重封装（如普通 MP4 将 moov 移到前部、MKV/AVI/MOV/FLV 转封装为浏览器可播放格式），**不改动音视频数据本身** |
| 容错播放 | 对容器内有损坏片段的文件，修复时跳过损坏片段，使整体仍可播放 |
| 实时修复不落盘 | 修复结果仅用于本次在线播放，**不保存持久化缓存**、不占用服务器磁盘；**原始文件永不覆盖** |
| 修复失败兜底 | 确实无法修复的损坏文件，预览时给出明确提示（如"该文件无法在线预览，请下载后查看"） |
| 修复资源控制 | 修复过程不落盘持久化缓存；如使用临时文件则及时清理，避免占用服务器磁盘 |

**用例（User Story）**：用户在网盘中打开一个之前用 PotPlayer 能播、但浏览器一直播不了的视频（如 AVI 或 moov 在尾部的 MP4），在修复开启后，浏览器现在可以正常边下边播；而原始文件保持原样，未被动过。

**AC-3**: 修复开关开启时，**损坏/非流式文件**（普通 MP4 moov 在尾部、MKV、AVI、MOV、FLV 等）在 Web 端可正常播放。

**AC-4**: 修复开关关闭时，**健康文件**直接原文件播放，服务端零额外开销（不进行任何探测/修复）。

**AC-5**: 修复过程**不覆盖原始文件**：预览前后原始文件字节完全一致；修复结果不落盘持久化缓存，不占用服务器磁盘。

**AC-6**: 无法修复的损坏文件，预览时给出清晰提示，不白屏、不无限加载。

### 2.3 管理员"媒体修复"开关（C 端配置，立即生效）

| 功能 | 说明 |
|------|------|
| 开关位置 | Web 端管理面板 / 桌面端设置页 / 移动端设置页（仅管理员可见）新增"媒体修复"开关 |
| 默认状态 | 默认**关闭**（低性能设备无额外负担） |
| 立即生效 | 管理员切换开关后，下一次预览立即按新状态生效，**无需重启任何端** |
| 权限控制 | 仅管理员可查看/操作该开关，普通用户不可见 |
| 服务端配置 | 开关为**服务端配置**（非 C 端本地配置），三端共享；任一客户端修改后所有端立即生效，服务端重启后保持上次设置 |
| 并发数配置 | 管理员可配置修复并发数上限（1~8），默认按服务器 CPU 核数自动推导，立即生效 |

**用例（User Story）**：管理员在某台弱 CPU 服务器（N2850）上默认保持修复关闭；当更换为更强 CPU 的服务器后，管理员在 Web 端 / 桌面端 / 移动端任一管理界面一键开启"媒体修复"（服务端配置，三端共享），之后所有损坏/非流式文件即可在线播放，全程无需重启任何端。

**AC-7**: 管理员在 Web 端开启/关闭"媒体修复"开关后，下一次预览立即生效，**无需重启任何端**。

**AC-8**: 开关默认关闭；关闭状态下，预览健康文件时服务端不产生任何探测/修复开销。

**AC-9**: 普通用户看不到也无法操作该开关；非管理员调用相关配置接口返回 403。

## 3. 非功能需求

### 3.1 性能

| 指标 | 目标 |
|------|------|
| 视频流式首帧（修复开启、健康文件） | < 3s |
| 健康文件预览额外开销（修复关闭时） | 零（不探测、不修复） |
| 无损修复耗时 | 秒级（-c copy 重封装，不重编码），每次预览实时触发 |
| 重复预览 | 每次预览均实时修复（秒级），不落盘缓存；因不占用服务器磁盘，可接受 |
| 弱 CPU（N2850） | 修复关闭时无感知；开启时无损修复（IO 主导）可承受 |

### 3.2 兼容性

| 浏览器 | 最低版本 |
|--------|---------|
| Chrome | 90+ |
| Firefox | 90+ |
| Safari | 15+ |
| Edge | 90+ |

> 依赖 Media Source Extensions（MSE），以上版本均支持。

### 3.3 安全性

- 严格遵循 `AGENTS.md §9` 安全宪法，**不新增任何明文白名单**。
- 媒体流仍为端到端加密帧（ChaCha20-Poly1305），URL 不暴露文件名/路径/用户标识等业务数据。
- 修复服务只读原始文件，修复输出不落盘持久化缓存（临时产物及时清理），**永不写回原始文件**。
- 修复缓存目录禁止越过虚拟磁盘边界；对磁盘路径做安全校验。
- 开关配置接口走加密 body + JWT 鉴权 + 管理员角色校验。

## 4. 与上一版本差异

上一版本为 v1.3.0（Web 端首个版本）+ v1.3.1（快速修复），本版本为新增功能版本。

| 能力 | v1.3.x（现状） | v1.4.0（目标） |
|------|--------------|---------------|
| Web 端边下边播主路径 | Service Worker（仅 HTTPS/localhost 可用） | **MSE 统一主路径**，HTTP/HTTPS、内网/公网均可用 |
| HTTP 环境下边下边播 | 不可用（SW 失效） | ✅ 可用 |
| 损坏/非流式文件（MKV/AVI/普通 MP4 等）在线播放 | ❌ 浏览器无法播放 | ✅ 修复后在线播放 |
| 原始文件保护 | — | 修复仅用于在线播放，不落盘缓存，原始文件永不改写 |
| 健康文件处理 | 原文件直连 | 原文件直连，零额外开销（不变） |
| 媒体修复能力 | 无 | 新增服务端无损修复（开关控制，实时修复不落盘） |
| 管理员"媒体修复"开关 | 无 | Web/桌面/移动三端管理界面可配置（服务端配置），立即生效 |
| 桌面端/移动端 | 本地解密代理 + 原生播放器 | 增加"媒体修复"开关配置界面（播放管线不变） |
| 加密协议 | X25519 + ChaCha20-Poly1305 | 完全不变 |

## 6. 已确认的设计决策

1. **三端同时修改**：Web / 桌面 / 移动端均提供"媒体修复"开关配置界面；开关为**服务端配置**（存服务端 `config` 表），非 C 端本地配置，三端共享。
2. **不做缓存**：修复每次实时计算、不落盘持久化缓存（服务器内存/磁盘有限），原始文件永不覆盖。
3. **全局开关**：开关为全局粒度，后续不按磁盘/文件类型细分。
4. **并发数可配置**：修复并发数上限默认按服务器 CPU 核数自动推导，管理员可在 C 端覆盖（1~8），立即生效、无需重启。
