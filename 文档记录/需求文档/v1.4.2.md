# JFLove v1.4.2 需求文档

> 状态：**草稿**（待用户确认后定稿）
> 版本类型：架构调整 + BUG 修复（播放路径变更，涉及四端）

## 0. 背景说明

v1.4.0 引入「在线播放实时修复」：损坏/非流式媒体在播放时由服务端 ffmpeg 实时重封装（`-c copy` + 音频转 AAC），流式输出给播放器。v1.4.1 修复了一批该方案的 seek BUG。实际使用后暴露出**架构级问题**：

1. **播放卡顿**：播放路径上叠加实时转码，转码速度跟不上播放速度即卡顿；且系统本身全链路加密（X25519 + ChaCha20-Poly1305），加密帧 + 实时转码双重开销；
2. **修复成果不可复用**：看完即弃，下次播放同一文件重复修复，长期占用服务端并发槽（上限 8）；
3. **复杂度外溢**：为让三端播放器消费「实时修复流」，桌面/移动端引入「重拉流 + 偏移补偿」逻辑，Web 端引入 timestampOffset/代际计数等补丁，v1.4.1 仍残留健康文件（byte 模式）seek 回归 BUG（拖进度条后从头播放、时间显示错位）。

用户决策（2026-08-28 确认）：**去掉边播边修复，改为「手动按需修复 + 产物复用 + 播放纯净化」**：

- 在文件管理中右键提供「修复损坏视频/音频」功能，按需修复想播放的文件，不做全盘扫描；
- 无损（健康）文件拒绝修复；
- 修复异步执行，有专门的修复进度管理页面；
- 修复完毕后可验证播放，验证满意后可选择用修复产物覆盖损坏的原文件；
- 在线播放时任何端遇到损坏文件一律拒绝播放，弹窗提示并引导用户先修复；
- 修复 + 覆盖后，下次播放即为健康文件，在线播放端只需处理无损资源。

**模块范围**：jflove-server（后端）、jflove-web（Web 端）、jflove-desktop（桌面端）、jflove-app（移动端）。

## 1. 项目概述

### 1.1 目标

把媒体修复从「播放时实时计算」迁移到「播放前离线完成」，实现：

- **播放路径纯净化**：在线播放只处理健康文件（原文件字节直读 + 加密帧输出），无 ffmpeg、无转码、无 seek 补偿逻辑；
- **修复按需触发**：用户对单个文件发起修复，服务端异步执行，不扫全盘；
- **产物可验证、可复用**：修复产物落盘保存，验证播放满意后可一键覆盖原文件；之后该文件永久恢复正常播放；
- **三端体验一致**：损坏文件的播放拒绝、修复入口、修复中心三端行为统一。

### 1.2 核心原则

- **加密协议不变**：全链路 X25519 ECDH + ChaCha20-Poly1305，媒体流仍为加密帧，URL 不暴露任何业务数据（§9 安全宪法）。
- **原始文件默认不动**：修复产物存放在原文件同目录的隐藏文件夹 `.jflove-repair/` 中，与原文件并存；**只有用户验证后主动二次确认覆盖时**，修复产物才顶替原位置——**直接覆盖，不留备份文件**（原损坏文件被删除，磁盘不额外占用空间）。
- **健康文件零打扰**：健康媒体文件修复请求直接拒绝（提示「该文件无需修复」）；在线播放不受任何影响。
- **不做全盘扫描**：修复只针对用户主动选择的文件发起。
- **修复可取消**：异步任务排队/执行中均可取消，产物不完整时清理，不残留垃圾文件。
- **修复权限门槛**：发起修复（含覆盖）要求用户对目标磁盘**同时具备写权限和删除权限**（修复涉及写入产物与删除/替换原文件两种操作）；权限不足时入口不可用/请求被拒。

## 2. 功能需求

### 2.1 播放路径纯净化（移除实时修复）

| 功能 | 说明 |
|------|------|
| 损坏文件拒绝播放 | 任何端在线播放损坏/非流式媒体文件时，服务端返回明确错误（如 `MEDIA_NEEDS_REPAIR`），不再实时修复 |
| 引导修复 | 三端播放失败弹窗提示「该文件已损坏，无法在线播放」，并提供「立即修复」按钮直达修复流程 |
| 健康文件直连 | 健康文件仍为原文件字节 range + 加密帧流式，行为与 v1.4.0 一致，零额外开销 |
| 移除实时修复代码 | 服务端移除 time 修复流分支；三端播放器移除 time 模式消费逻辑（桌面/移动的偏移补偿、重拉流；Web 的 timestampOffset、代际计数、-ss 重拉） |
| seek 回归修复 | 桌面端/移动端健康文件拖进度条恢复播放器原生 seek（字节 Range 直通），修复 v1.4.1 引入的「拖拽后从头播放/时间错位」回归 |
| Web 端 seek 增强 | Web 端 MSE byte 模式下，seek 目标超出已缓冲范围时按字节偏移重拉对应区段，不再干等顺序下载 |

**用例**：用户在 Web 端打开一个损坏视频 → 弹窗「该视频已损坏，无法在线播放」+「立即修复」→ 点击后进入修复流程（见 2.2）。用户在桌面端打开健康 MP4 → 拖进度条到任意位置 → 从目标点继续播放（v1.4.1 回归已修复）。

**AC-1**：任何端播放**损坏**媒体文件时被拒绝，返回统一错误码，弹窗含「立即修复」入口，不出现转码等待、白屏或无限加载。
**AC-2**：任何端播放**健康**媒体文件时行为正常：边下边播、可拖动 seek、首帧 < 3s；桌面端/移动端拖拽后从目标点继续播放，进度与画面一致（回归修复验证）。
**AC-3**：Web 端健康 MP4 播放中，把进度拖到未缓冲的大文件尾部区段，播放器按需重拉数据，不无限等待顺序下载。

### 2.2 文件管理「修复损坏媒体」入口（右键/长按菜单）

| 功能 | 说明 |
|------|------|
| 菜单入口 | 三端文件管理中，对视频/音频文件右键（桌面/Web）或长按（移动）菜单新增「修复损坏媒体」 |
| 仅媒体文件可见 | 菜单项仅对视频/音频扩展名文件显示 |
| 健康拒绝 | 目标文件为健康文件时，提示「该文件无需修复」，不创建任务 |
| 损坏可修 | 目标文件判定为损坏/非流式时，创建异步修复任务并入队 |
| 无法修复的提示 | 目标文件探测后确属无法解析（无媒体流）时，提示「该文件无法修复，请下载后查看」 |
| 重复任务拦截 | 同一文件存在未完成（排队/执行中）的修复任务时，不允许重复创建，提示任务已存在 |
| 权限（写+删并存） | 发起修复要求对目标磁盘**同时具备写权限和删除权限**（`can_write` + `can_delete`）：写权限用于产物写入隐藏目录，删除权限用于覆盖时替换原文件。权限不足时菜单入口禁用/请求返回 403 |

**用例**：用户在文件列表右键一个 AVI 视频 →「修复损坏媒体」→ 若健康：toast「该文件无需修复」；若损坏：toast「已加入修复队列」并可在修复中心查看进度。

**AC-4**：健康媒体文件右键修复被拒绝并提示；不创建任务、不产生任何磁盘写入。
**AC-5**：损坏媒体文件右键修复后，任务进入队列，修复中心可见其状态与进度。
**AC-6**：同一文件存在未完成任务时重复发起修复，被拒绝并提示。
**AC-6a**：仅有读权限或仅写/仅删单一权限的用户发起修复，被拒绝（403）；三端修复入口对该用户禁用/隐藏。

### 2.3 异步修复执行与产物管理（服务端）

| 功能 | 说明 |
|------|------|
| 异步执行 | 修复任务在服务端后台队列执行（沿用无损重封装：视频 copy + 音频转 AAC），并发上限沿用现有配置（管理员可调） |
| 产物落盘 | 产物写入原文件同目录 `.jflove-repair/` 下，命名为「原名.扩展名」→「原名.mp4」（统一输出 fMP4） |
| 隐藏目录 | `.jflove-repair/` 在三端文件列表中**不展示**（列入过滤规则） |
| 进度上报 | 任务提供进度信息（排队中/执行中/百分比或阶段/成功/失败/已取消），供修复中心轮询 |
| 可取消 | 排队中/执行中任务可取消；执行中取消时终止 ffmpeg、清理半成品 |
| 失败重试 | 任务失败后可重新发起（重新创建任务）；**重新发起时按最新修复流程执行，并先清理旧任务的残留产物，不留垃圾文件** |
| 服务重启恢复 | 服务重启后未完成任务标记为失败（中断），产物半成品清理；已成功任务与产物保留 |
| 产物验证 | 修复完成后服务端自动对产物做可播性验证（能解析出流/时长即算通过），验证结果记录在任务上 |
| 覆盖执行 | 覆盖 = 修复产物移动到原文件位置并改名为原文件名，**原损坏文件直接删除，不留备份**；覆盖为原子性操作（失败时产物保留、原文件不动） |
| 产物清理 | 用户可删除产物（未覆盖前）；隐藏目录中无有效产物时自动清理空目录 |

**AC-7**：损坏文件修复完成后，`.jflove-repair/` 下存在修复产物，且原文件字节不变。
**AC-8**：修复中心可见任务全生命周期状态；排队中/执行中任务可取消，取消后无半成品残留。
**AC-9**：服务重启后，中断任务标记为失败，产物半成品被清理；已完成任务与产物保留。
**AC-10**：服务端对修复产物完成自动验证（可解析、时长合理），验证不通过的产物不进入「可覆盖」状态。
**AC-10a**：任务失败后重新发起，旧残留产物被清理，最终隐藏目录中仅存在最新一次成功修复的产物。

### 2.4 修复中心（进度管理页面，三端）

| 功能 | 说明 |
|------|------|
| 页面入口 | 三端均提供「修复中心」入口（文件管理页工具栏/侧边入口） |
| 任务列表 | 展示任务：文件名、所属磁盘、状态（排队中/执行中/成功/失败/已取消/已覆盖）、创建时间、耗时/进度 |
| 操作 | 按状态提供操作：取消（排队/执行中）、验证播放（成功）、覆盖原文件（成功且验证通过）、删除产物（成功未覆盖）、重试（失败）、删除记录（任意终态） |
| 验证播放 | 在线播放修复产物（与正常文件播放一致的加密流体验），满意后再覆盖 |
| 覆盖确认 | 覆盖需用户**重点二次确认**（明确警示：修复版将顶替原名，**原损坏文件将被直接删除、不可恢复**），二次确认后才执行；覆盖要求当前磁盘写+删权限 |
| 自动刷新 | 任务进行中页面自动轮询刷新状态 |
| 权限（全平台共享） | 任务列表**全平台共享**，不做账户隔离（避免不同账号重复修复同一文件）；任务记录创建者仅供展示。**只读账号（无写+删权限）可查看全部修复记录，但无任何操作权限**；具备写+删权限的用户可执行全部操作 |

**用例**：用户在修复中心看到任务「损坏视频.ts → 成功」→ 点击「验证播放」预览修复产物 → 满意后点击「覆盖原文件」→ 二次确认弹窗（警示：原损坏文件将被删除、不可恢复）→ 确认后修复版以原文件名出现在原位置，原损坏文件已删除。另一账号打开修复中心，同样能看到这条任务（不会重复发起修复）。

**AC-11**：修复中心可完整查看任务状态并执行对应操作；覆盖操作有重点二次确认。
**AC-12**：覆盖成功后，原位置文件为修复版（以原名命名），原损坏文件已删除（磁盘无备份残留）；之后在线播放该文件即为健康文件正常播放（含 seek）。
**AC-13**：任务列表全平台共享（含只读账号可见）；只读账号（无写+删权限）操作类请求全部被拒（403），三端操作按钮禁用/隐藏；具备写+删权限的任意用户均可操作。

### 2.5 配置项调整

| 功能 | 说明 |
|------|------|
| 移除实时修复开关 | 移除「媒体修复实时开关」（`media_repair_enabled`）相关 UI 与播放路径判断；该配置键保留但不再影响播放（或标记废弃） |
| 保留并发配置 | 修复并发数配置（`media_repair_max_concurrent`）保留，作用于离线修复队列 |
| 保留重编码子开关 | `media_repair_allow_transcode` 保留语义：离线修复 `-c copy` 失败时是否允许降级重编码 |

**AC-14**：移除实时修复开关后，播放行为不再受任何「修复开关」影响；修复并发/重编码配置仅作用于离线修复队列。

## 3. 非功能需求

### 3.1 性能

| 指标 | 目标 |
|------|------|
| 健康文件播放 | 与 v1.4.0 一致（原文件直读 + 加密帧），无 ffmpeg 参与，无额外 CPU |
| 损坏文件播放拒绝 | 判定发生在服务端流式接口内（探测结果短 TTL 缓存复用），首次探测 < 1s 量级 |
| 离线修复吞吐 | 无损重封装 IO 主导；并发上限沿用现有配置 |
| 修复中心轮询 | 轮询间隔 ≥ 2s，避免高频请求 |

### 3.2 安全性

- 严格遵循 `AGENTS.md §9`：无新增明文白名单；修复任务/产物/覆盖接口全部加密 body + JWT；新路由显式标注鉴权与归属校验（任务只能由创建者/管理员操作）。
- 产物/备份文件传输仍走加密帧流（`StreamingResponse + encrypt_stream_chunk`）。
- 覆盖/删除属破坏性操作：服务端校验归属与权限，客户端重点二次确认。
- `.jflove-repair/` 不出现在文件列表 API 响应中（服务端过滤），避免信息暴露。
- 日志不记录文件名/路径明文（截断/哈希）。

### 3.3 兼容性

- 浏览器兼容性同 v1.4.0（Chrome/Firefox/Safari/Edge 90+/15+）。
- v1.4.1 及之前的「实时修复流」客户端逻辑被移除；`/stream` 接口对未携带 `range_start_seconds` 的旧客户端行为不变（byte 流）。

## 6. 已确认的设计决策

1. **产物位置**：原文件同目录隐藏文件夹 `.jflove-repair/`（2026-08-28 用户确认）。
