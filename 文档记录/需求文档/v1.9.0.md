### 0.4 关键澄清（回答用户 U7）

- `.jflove-download` **是离线下载产生的**：任务先把分片/中间产物写到 `<目标目录>/.jflove-download/<task_id>/`，
  成功后 `os.replace` 改名为正式文件；任务结束会删该 `task_id` 子目录，但**父目录 `.jflove-download` 会留成空目录**，
  失败/进程被杀时还可能留下子目录（启动时按 24h 清孤儿）。
- 它之所以「看上去乱」，是两件事叠加：① 临时目录分散在**每个目标目录**；② 文件列表没有过滤它。
- `.jflove-repair` 同理，位于每个源文件目录。这两个目录都不在统一位置。
- 本版目标：**每块磁盘根只保留一个程序专用隐藏临时根**；上传分片收敛到服务端统一临时根；
  用户目录不再出现散落的 `.jflove-download`；列表不展示任何隐藏项。

### 0.5 关于「上传内容堆积在内存」的澄清（回答用户 U10）

- **事实：服务端没有把整个上传文件放在内存。** 分片到达即写盘（E-18）；合并时逐片读盘 → 写临时文件（E-20）。
  进程内存峰值 ≈ 并发请求数 × 单请求几 MB 的解密 / JSON / base64 副本，**与文件总大小无关**（E-19）；
  8GB 内存下 3GB 上传不会因「全量堆内存」而 OOM。
- **「上传时播放卡」的真实原因（按代码）**：
  1. `complete` 仍是在请求内执行，合并的 `sha256.update()` 跑在**事件循环线程**，弱 CPU 上分段占用事件循环；
  2. **没有全局合并并发上限**（E-21）：App 同时 3 个传输任务，可让 2~3 个大文件同时合并，
     N2840 + 机械盘会把 CPU 与磁盘打满；
  3. 播放流式帧与合并**共用同一事件循环与线程池**（E-22），上传请求的解密 / JSON 也走同一线程池；
  4. 1MB 分片 → base64 约 1.4MB + 加密信封，单请求多份副本在弱 CPU 上放大分配 / GC 压力（但**不是 GB 级**）。
- **「先写盘再合并」已经是现状**；能真正缓解瞬时压力的是：
  **合并移入独立线程 + 合并全局并发默认 1 + 上传分片并发限制 + 分片降到 512KB**（见 F56 / D35）。
- **针对 8GB / N2840 的容量建议**：合并并发 1、上传分片并发 2、分片 512KB、每用户未完成会话 4~8、
  磁盘预留 ≥ 2× 单文件大小；播放与上传同时进行时，让合并排队而不是并发。
- **仍需承认的物理上限**：3GB 合并要读 3GB + 写 3GB + SHA256，N2840 的 CPU 与磁盘吞吐是硬约束；
  本版解决「卡死 / 假失败 / 抢占播放」，不承诺合并耗时大幅下降。

### 0.6 被废弃的方案（禁止下游照旧实现）

| 废弃方案 | 废弃原因 | 现行结论 |
|---|---|---|
| `complete` 保留「不传 `async_mode` 走旧同步模式」的兼容分支 | 用户 2026-11-09 明确选择「强制异步，三端同步升级」 | 见 D27 / F47 |

| 临时目录保持分散（每目标目录一个） | 用户明确要求规整 | 见 F49 |

## 1. 版本概述

### 1.1 一句话定位

**v1.9.0 让大文件上传/下载「断了能续、合并不再假失败」，把程序自产临时文件收进统一隐藏临时根并统一清理，同时为弱 CPU 服务器提供资源隔离（合并线程化 + 并发上限 + 分片 512KB）。**

### 1.2 与上一版本（v1.8.4 / v1.8.3）的差异

| 维度 | v1.8.x 现状 | v1.9.0 |
|---|---|---|
| 3GB 上传合并 | `complete` 同步长请求；App 120s 超时判失败 | `complete` 立即返回 `merging`；后台合并；进度轮询 |
| 上传续传 | 服务端会话只在内存；无可查已收分片；App 失败清分片 | 会话持久化 + 内容指纹复用 + 状态查询 + 分片级重试；服务端重启后仍可续 |
| 分片丢失 | 只能从头 | 状态接口如实返回缺失片；缺片补齐；会话没了就安全重开 |
| 下载 | 三端从头下载 | 服务端支持字节 Range；三端支持断点续传（Web 用 IndexedDB/OPFS） |
| 临时目录 | 上传分片在 `build/upload_tmp`；离线下载在每目标目录 `.jflove-download`；修复在源目录 `.jflove-repair`；合并 `.part` 在目标目录 | 统一临时根 + 分类子目录；旧目录迁移；列表不可见 |
| 上传资源占用 | 合并同步跑在事件循环；无全局合并并发；1MB 分片；播放易被抢占 | 合并线程化 + 全局合并并发 1（可配）+ 分片 512KB + 上传并发受限；弱服务端模式预设 |
| 文件列表 | 只过滤 `.jflove-repair`；`.jflove-download` 会显示 | `list` / `scan` 不返回任何 `.` 开头条目；程序保留目录禁止接口访问 |
| 清理 | 24h 硬编码；启动首轮 1h；不可配；无客户端类型维度 | 三端可配：TTL / 开关 / 间隔 / 客户端类型 / 孤儿保留期；与续传 TTL 单一来源 |
| 兼容 | 旧同步 complete | 强制异步，三端同版本升级 |

### 1.3 范围与命名

- 版本号 **1.9.0**（唯一真相 `version.json`，`scripts/sync_version.py` 同步 9 处）。
- 产品术语：
  - **断点续传保障期**：上传会话可续传的最长时间，默认 24 小时。
  - **统一临时根**：每磁盘根下一个程序专用隐藏目录（名称由设计定，建议 `.jflove-tmp`）。
  - **隐藏项**：名称以 `.` 开头的文件或目录。
  - **客户端类型**：app / desktop / web / unknown。

### 1.4 范围边界（明确不做）

| 不做 | 原因 |
|---|---|
| 改加密协议 / 新增加密原语 / 改帧格式 | 安全宪法 §9.5；本版只在加密 body 内新增字段 |
| 新增数据库表或修改既有表结构 | 会话用文件持久化；清理配置走 `config` 键值 |
| 提升合并物理吞吐（sendfile、跳过 SHA256 等） | 本版先把「超时假失败」和「无法续传」解决；性能优化另立候选 |
| 后台同步 / WorkManager（v1.8.4 台账 N4） | 不在本版范围 |
| 全局诊断页（v1.8.4 台账 N1） | 不在本版范围 |
| 离线下载业务能力 / 媒体修复业务能力变更 | 本版只治理其临时目录与清理，不改解析/修复逻辑 |
| 「仅本地构建」以外的发布决策 | Phase 8 由用户再次选择 |

## 2. 目标用户与核心场景

### 2.1 目标用户

- **手机用户**：相册里有 3GB 视频，Wi-Fi 中断/App 被杀/服务端合并慢时，重试不再从头传。
- **多端用户**：同一账号在 App / 桌面 / Web 上传或下载大文件，断网后能继续。
- **管理员**：要能配「临时文件保留多久、多久清一次、哪些客户端的临时文件允许清」，且知道清理不会误删正常文件。
- **普通用户**：文件列表只看到自己的正常文件，不被 `.jflove-download` 等隐藏目录打扰。

### 2.2 核心场景

**场景 A（相册大视频上传中断）**
手机相册选择 3GB 视频 → 上传到 60% 时 Wi-Fi 断开 → 传输任务失败 → 恢复网络后重试 →
App 查询服务端已收分片，只补剩余 40% → 分片补齐后提交合并 → 立即返回「服务端合并中」→
界面显示合并进度 → 合并完成，远端文件大小为 3GB、SHA256 与本地一致。

**场景 B（服务端合并慢，客户端不再假失败）**
3GB 文件合并需要 5 分钟：客户端 `complete` 请求 1 秒内返回；每 2.5 秒轮询进度；
期间其它页面（列表、播放、下载）不卡；合并完成后进度变 `done` 并返回最终路径。

**场景 C（服务端重启后继续）**
上传到一半，服务端重启；客户端重试 → `init` 按内容指纹找回原会话，返回已收分片 →
继续上传剩余分片 → 合并成功。

**场景 D（分片已被清理）**
用户隔了 3 天再重试（超过 24h 保障期，分片已被自动清理）→ 客户端 `init` 得到新会话、
状态提示「原分片已过期，将从第 0 片重新上传」→ 正常上传，不报错。

**场景 E（下载中断续传）**
桌面/App 下载 1GB 文件到 40% 断网 → 重试时从本地 `.part` 的 40% 处续传；
远端文件已变化 → 自动删除 part 从头下载；完成后文件完整。
Web 端刷新页面后从 OPFS/IndexedDB 中已保存的分块继续。

**场景 F（管理员配置清理）**
管理员在 Web/桌面/App 系统设置里把「断点续传保障期」设为 72 小时 →
服务端过期判定、清理保护期、客户端展示的「可续传至」时间同时变为 72 小时；
把「允许自动清理的客户端类型」设为仅 `web` → App/桌面的过期分片不被自动清理。

**场景 G（文件列表干净）**
用户进入文件管理 → 只看到正常文件/目录；看不到 `.jflove-download` / `.jflove-repair` /
统一临时根；对账扫描也不会把它们当作文件差异同步。

**场景 H（升级一致性）**
发布 v1.9.0 时三端与服务端同批次升级；用旧客户端连接新服务端上传会被明确提示升级，
不会出现「看起来成功、其实文件没合并」的静默错误。

## 3. 功能需求

### 3.1 F46 上传断点续传

**F46.1 会话持久化（跨服务端重启）**
上传会话元数据必须持久化到统一临时目录内（与分片同目录），服务端启动后能恢复未过期会话；
恢复时以**磁盘上实际存在的分片文件**为准重建「已收分片」，不信任任何内存计数。

**F46.2 幂等 init（内容指纹复用）**
同一用户、同一磁盘、同一目标路径、同一文件名、同一大小、同一 SHA256 的上传，
在保障期内重复 `init` 必须复用同一上传会话与同一临时目录，返回已收分片列表；
不得每次生成新 upload_id、新目录。

**F46.3 状态查询**
新增「查询上传会话状态」能力（加密请求，归属校验）：
返回会话是否存在、状态、已收分片索引、缺失分片索引、总分片数、过期时间；
分片文件缺失时按实际存在性过滤，客户端据此只补缺失片。

**F46.4 客户端本地续传记录（三端）**
三端都要在本地保存「未完成上传记录」（目标磁盘/目录/文件名/大小/哈希/upload_id/已发分片）；
App 此前没有，本版补齐；桌面已有，按本需求对齐。

**F46.5 失败处理**
- 网络失败、超时、合并失败：**不得主动删除服务端会话与已传分片**（保留供续传）；
- 用户明确取消上传 / 用户明确「放弃」时才允许清理会话；
- 分片上传失败按分片级重试（指数退避，至少 5 次），不得让单个分片失败直接推倒整个文件。

**F46.6 远端已存在判定**
重试时若远端目标文件已存在且大小与源文件一致，可直接判定已上传完成，避免「合并成功但响应丢失」
导致整文件重传；客户端须用远端列表/索引核验，不能只看本地记录。

**F46.7 会话丢失/过期回退**
`init` / `status` 发现会话不存在、已过期、分片目录丢失、状态为失败：
客户端收到明确的「需重新开始」状态后，从第 0 片重新上传；**不得报错卡死**。

**F46.8 并发安全**
同一 upload_id 的合并请求必须串行；多个客户端同时上传同一内容时，允许复用会话，
但不得并发重写同一批分片导致损坏。

### 3.2 F47 合并异步化与进度

**F47.1 立即受理**
`complete` 必须立即返回「合并已受理」（毫秒级到秒级，不等待合并完成），
响应包含状态 `merging` 与轮询建议；合并由服务端后台执行。

**F47.2 进度查询**
客户端轮询「上传进度」接口：
- 合并中：状态、已处理/总分片、百分比、已耗时；
- 完成：状态 `done`，返回最终文件路径；
- 失败：状态 `failed`，返回可展示的中文原因（缺片 / 校验失败 / IO 失败）。
进度记录在会话结束（完成/取消）后仍保留一段时间，客户端可确认最终结果，不得立即变成「未知/无权」。

**F47.3 不阻塞**
合并期间事件循环不得被哈希/磁盘读写阻塞；同一时刻其它上传/下载/列表/播放接口仍可正常响应。

**F47.4 失败语义**
- 缺片：返回缺失片索引，客户端补齐后可再次合并；
- 校验失败：会话标记失败，客户端重试时按「全量重传」处理（分片无独立哈希，无法定位坏片）；
- IO 失败（磁盘满/权限/文件被占用）：返回明确原因，保留会话一段时间供修复后重试。

**F47.5 强制异步（D27）**
服务端**不保留**旧同步模式；三端与同一版本服务端同批次升级。发布说明必须写明该约束。

### 3.3 F48 下载断点续传（三端）

**F48.1 服务端 Range 能力**
下载接口接受「起始字节偏移」，从该偏移开始按既有加密帧格式流式输出；
响应头提供实际起始偏移、文件总大小、远端文件版本标识（用于续传校验）；
偏移越界返回明确错误（416 语义），客户端自动回退从头下载。
服务端**不保存下载临时文件**（续传数据在客户端）。

**F48.2 桌面 / App**
- 下载先写本地 part 文件（隐藏命名，不污染用户可见文件名）与一份元数据（远端大小/版本标识/已下字节）；
- 重试时读取 part 大小作为起始偏移继续；元数据不一致（远端文件变化）则删除 part 从头；
- 完成且校验大小一致后原子改名为目标文件；
- 用户取消/失败默认**保留** part 供续传；用户明确「放弃下载」才删除。

**F48.3 Web**
- 使用 IndexedDB 或 OPFS 按块保存已解密的字节；
- 下载中断/刷新页面后，用已保存字节数作为起始偏移续传（重新建立加密会话不影响续传）；
- 完成后从存储导出为文件并清理临时数据；
- 不支持 OPFS 的浏览器必须回退为普通整文件下载，并明确提示不支持续传（不得静默）。

**F48.4 目标已完整判定**
重试前若本地目标文件已存在且大小与远端一致，可直接判定完成，不重复下载。

**F48.5 本地 part 生命周期**
客户端本地 part 保留 **7 天**（D33）；超期在客户端启动/定时清理时删除；
用户主动清理下载记录不删除已完成文件，但可清理对应 part。

### 3.4 F49 临时文件统一治理

**F49.1 统一临时根**
- **服务端进程级**：上传分片统一收敛到一个服务端临时根，按会话分子目录；
- **磁盘级**：每块虚拟磁盘根下**最多一个**程序专用隐藏临时根，其下按用途分类：
  上传合并临时、离线下载临时、媒体修复产物、旧目录迁移残留等；
- 用户目录中不再出现分散的 `.jflove-download` / `.jflove-repair`。

**F49.2 合并临时文件例外**
为满足「原子替换」，合并临时文件必须与目标文件同目录（同文件系统），
统一使用固定命名 `<目标文件名>.jflove-upload-<upload_id>.part`（隐藏命名、列表不显示）；
清理任务按固定命名精确匹配，绝不删除其它 `.part` 或正常文件。

**F49.3 旧目录迁移**
升级后首次启动/首次访问磁盘时，把旧 `.jflove-download` / `.jflove-repair` 的内容迁移到统一临时根；
- 迁移失败不阻塞服务启动与文件访问；
- 迁移失败的旧残留由清理任务按「程序自产固定命名」规则处理（只清过期项）；
- 迁移完成后旧目录不得再出现在文件列表。

**F49.4 访问隔离**
文件管理接口（列表/下载/预览/删除/移动/重命名/上传目标/对账扫描）不得访问程序保留的隐藏目录：
统一临时根、旧 `.jflove-download`、`.jflove-repair` 等；
路径校验必须按「路径段」拒绝，不能只做字符串包含判断。

**F49.5 修复产物默认保留**
媒体修复产物属于用户可验证的业务产物，**默认不自动删除**；
仅在用户删除对应修复记录时一并清理。离线下载的临时目录在任务结束（成功/失败/取消）后清理该任务子目录。

**F49.6 客户端临时文件**
App/桌面下载 part 存放位置由设计统一（优先应用私有缓存目录，避免用户在文件管理器看到）；
如必须与目标文件同目录，则使用隐藏命名并在完成/放弃后清理；Web 临时数据完成后清除。

### 3.5 F50 文件管理隐藏项过滤

**F50.1 列表过滤**
文件管理列表接口**不返回**任何名称以 `.` 开头的文件或目录（服务端统一过滤，三端无需各自过滤）。

**F50.2 对账过滤**
全量对账扫描 / 变更增量接口同样不返回隐藏项，避免挂载云盘把临时目录当业务文件同步。

**F50.3 兼容访问**
用户自己已存在的 `.` 开头文件（非程序保留目录）不显示在列表；已知精确路径时仍可下载/删除（保持兼容）。
上传/新建/重命名到 `.` 开头名称时，界面必须明确提示「该名称将作为隐藏文件保存，不会显示在列表中」。

**F50.4 修复记录**
因隐藏过滤而无法从列表进入的旧 `.jflove-download` 内容，由迁移/清理任务处理，用户无需手动操作。

### 3.6 F51 服务端自动清理（可配置）

**F51.1 配置项（服务端 `config` 键值，管理员可改、立即生效，无需重启）**

| 配置项 | 默认 | 允许范围 | 语义 |
|---|---|---|---|
| 自动清理总开关 | 开 | 开/关 | 关闭后不自动删任何临时文件 |
| 断点续传保障时长 | 24 小时 | 1 小时 ~ 7 天 | **唯一 TTL 来源**：会话过期、清理保护、客户端展示均用它 |
| 自动清理间隔 | 60 分钟 | 5 分钟 ~ 24 小时 | 后台清理周期 |
| 允许自动清理的客户端类型 | 全部 | app / desktop / web / unknown 子集 | 只清名单内类型；名单外永不自动清理 |
| 孤儿临时文件保留期 | 24 小时 | 1 ~ 168 小时 | 无会话归属的残留（迁移失败/进程被杀）按此清 |
| 每用户未完成上传会话上限 | 8 | 1 ~ 64 | 防止单账号堆满临时分片（达到上限时拒绝新会话并提示） |

**F51.2 单一来源（D32）**
- 会话过期判定、清理跳过阈值、`init/status/progress` 返回的过期时间，全部读**同一个配置值**；
- 启动首轮清理必须遵守同一 TTL，**禁止**「启动时 1 小时就清」的旧行为；
- 保障期内（含正在上传的会话）永不自动清理。

**F51.3 清理范围（只删自产）**
只允许清理：
1. 统一临时根内、目录名严格匹配会话 UUID、文件名为 `<数字>.chunk` 或会话元数据的目录；
2. 目标目录内严格匹配 `.jflove-upload-<UUID>.part` 的合并残留；
3. 统一临时根内按用途分类的离线下载任务子目录 / 旧目录迁移残留（匹配固定命名）；
4. 客户端本地 part（客户端自己的清理逻辑，不影响服务端文件）。

**F51.4 安全硬约束（D31）**
- 删除前用真实路径校验目标仍位于允许的根内，不跟随符号链接；
- 目录内出现任何非预期文件名 → **整个目录跳过并记警告**，不删除；
- 不删除 `.jflove-download` / `.jflove-repair` 中无法确认归属的内容（迁移期由迁移逻辑负责）；
- 绝不递归删除用户目录、绝不按「目录里有文件就清空」的泛化规则执行；
- 清理日志只记数量/类型/跳过数，不记文件名、路径明文。

**F51.5 可观测性**
清理任务记录：最近执行时间、上次清理数量、跳过数量；
管理员系统设置页可查看；保留最近若干次记录（不落用户内容）。

**F51.6 立即清理**
三端系统设置页提供管理员「立即清理」按钮（触发一次与定时任务同规则的安全清理），
显示清理结果；非管理员不可见/不可调用。

### 3.7 F52 三端系统设置页清理配置

**F52.1 展示位置**
App / 桌面 / Web 的「设置 → 系统设置（管理员）」新增「存储与临时文件」卡片。

**F52.2 配置项**
至少包含：总开关、断点续传保障时长、自动清理间隔、允许清理的客户端类型、孤儿保留期、每用户会话上限、立即清理。
每项有默认值、范围校验与中文说明；保存后立即生效，三端同源（任一端修改后其它端刷新可见）。

**F52.3 一致性文案**
「断点续传保障时长」旁必须说明：**该值同时决定断点续传有效期和临时文件清理保护期**；
清理阈值不可单独配置，避免双方不一致。

**F52.4 权限**
仅管理员可读写；普通用户看不到该卡片（或只读展示由管理员设定的值）。

### 3.8 F53 有效期与失效回退

| 对象 | 默认有效期 | 到期行为 |
|---|---|---|
| 上传会话（服务端分片） | 24 小时（可配 1h~7d） | 会话过期、分片被清理；客户端重试时收到「需重新开始」，从头传，不报错 |
| 下载 part（客户端本地） | 7 天 | 客户端清理超期 part；重试时从头下载 |
| 合并残留 `.part` | 跟随保障期（默认 24 小时） | 清理任务删除 |
| 离线下载临时任务目录 | 任务结束后立即清；孤儿 24 小时 | 清理任务删除 |
| 修复产物 | **默认不自动删** | 用户删除修复记录时清理 |

**F53.1** 客户端必须展示「可续传至 <时间>」（来自服务端 `expires_at`），
让用户知道超过后需要重新传，不产生「怎么又要重传」的困惑。

**F53.2** 服务端 `init` / `status` 对已过期会话必须返回明确状态，不返回 500，不静默创建新会话后不告知客户端。

### 3.9 F54 升级与兼容（D27）

- 本版 `complete` 强制异步；服务端不保留同步分支。
- **发布约束**：服务端与 App / 桌面 / Web 必须同批次升级到 1.9.0；发布记录与 UAT 记录必须写明。
- 旧版本客户端连接新服务端时，上传 `complete` 会收到 `merging` 而非最终结果；
  产品要求服务端在 `init` 中识别旧客户端（缺客户端类型/版本字段）并返回明确的中文错误，
  提示「服务端已升级，请升级客户端后重试」，避免静默失败。
- 回滚按「服务端 + 三端一起回滚」执行，不做跨版本兼容层。

### 3.10 F55 变更增量/对账的隐藏项（补充）

`/files/journal` 只返回业务变更，不返回临时目录变更；`/files/scan` 按 F50.2 过滤隐藏项。
挂载云盘对账不得把统一临时根同步到本地/云端。

### 3.11 F56 弱服务端资源隔离与上传内存上限（D35，本版新增）

**F56.1 合并线程化**
合并（逐片读 → 写临时文件 → SHA256 → 原子替换）必须在独立工作线程执行，事件循环只负责进度更新与请求响应；
禁止在事件循环线程做长时哈希 / 同步磁盘 IO。

**F56.2 全局合并并发上限**
服务端对「正在合并的任务」设全局并发上限：默认 **1**，管理员可配 1~4；
超过上限的 complete 进入排队（状态 `queued`），不得并发重写多个大文件；排队不得返回失败，
进度接口显示「排队中 / 排队位置」。

**F56.3 上传分片并发上限**
服务端对「同时处理的分片上传请求」设全局上限：默认按 CPU 推导（≤4 核 = 2，其余 4），可配 1~8；
超限请求短暂排队（超时后返回明确 429），避免瞬时内存 / 线程池 / CPU 峰值叠加。

**F56.4 客户端分片大小**
三端默认分片 **512KB**（可配 256KB ~ 1MB）；`total_chunks` 按客户端分片大小计算，加密帧与接口协议不变；
服务端校验单分片 ≤ 1MB（防内存放大），不一致按 400 拒绝。
> 说明：分片变小会增加请求数，仅作为弱服务端首选；强服务端仍可调回 1MB。

**F56.5 弱服务端模式**
三端系统设置页提供「弱服务端模式」一键预设：合并并发 1、上传并发 2、分片 512KB、
每用户未完成会话上限 4；启用后显示当前参数，可单独再调。
文案必须写清：该模式降低峰值资源占用，但上传 / 合并总耗时会变长（针对 8GB / N2840 级别服务器）。

**F56.6 播放 / 下载优先**
合并排队与上传限流不得阻塞流式接口：合并期间播放 / 下载请求 P95 不出现秒级劣化；
若仍出现，管理员可临时「暂停上传」或将合并并发设为 0（仅排队不执行）——具体开关由设计确定。

**F56.7 可观测**
系统设置页展示：当前合并执行数 / 排队数、当前上传请求并发数、最近一次合并耗时与进度接口延迟；
供弱服务端现场判断是否应启用「弱服务端模式」。

## 4. 非功能需求

### 4.1 体验

- 上传失败后重试必须显示「检测到未完成上传，从第 N 片继续」或「原分片已过期，将从第 0 片重新上传」。
- 合并期间显示进度与「服务端合并中，请勿关闭」；合并失败显示中文原因与下一步。
- 下载续传显示「已从 X% 继续」；远端文件变化时显示「文件已更新，将重新下载」。
- 设置项每项有默认值/范围/说明，保存成功/失败有明确反馈。
- 文件列表为空（全是隐藏项）时显示正常空态，不暴露隐藏目录名称。

### 4.2 性能与可靠性

- `complete` 受理请求 P95 ≤ 1 秒（不含合并本身），不得再因合并耗时导致客户端超时。
- 合并期间事件循环不被阻塞：同一进程的列表/下载/播放接口 P95 不显著劣化。
- 分片级重试为指数退避，不能形成风暴；同一会话的合并请求串行。
- 服务端重启后未过期会话可恢复；恢复失败不得阻塞启动。
- 三端断点续传有效流量不重复（已收分片/已下字节不再重传）。
- 合并期间事件循环不被阻塞；进度接口轮询 P95 ≤ 1 秒。
- **弱服务端（≤4 核 / 8GB）**：默认合并并发 1 时，上传 3GB 同时播放 1080p 不出现 >2 秒卡顿/断流
  （实机录像 + 主观体验证据）。
- **内存不随文件大小增长**：处理 1MB 分片请求的进程 RSS 增量有上限（建议 < 32MB/请求），
  不随 3GB 文件线性增长（RSS 采样 + 代码审查）。

### 4.3 安全（不得降级）

- 所有新字段走既有加密信封；不新增明文白名单；不新增长期密钥。
- 上传会话/状态/进度查询必须校验 `upload_id` 归属；管理员也不能通过换 ID 操作他人会话。
- 响应头不含文件名 / 路径 / 用户标识；下载 Range 响应头只放偏移、总大小、版本标识。
- 清理只删程序自产固定命名文件（F51.4）；日志不记录文件名/路径明文。
- 文件管理接口禁止访问程序保留隐藏目录（F49.4）。

## 5. 交互流程

### 5.1 上传（含中断续传 + 异步合并）

```
选择文件 → 本地哈希 → init（服务端按指纹返回会话/已收分片）
  ├─ 新会话：从第 0 片传
  └─ 续传：跳过已收分片，只补缺失片
分片上传（单片失败指数退避重试 5 次，不删会话）
  → complete（立即返回 merging）
  → 每 2.5s 轮询 progress
      ├─ merging：显示进度
      ├─ done：显示完成，收尾（核验远端大小/hash）
      └─ failed：中文原因 + 重试（缺片补片 / 校验失败全量重传）
```

### 5.2 下载

```
检查本地 part/meta → 与远端大小/版本一致？
  ├─ 是：从 part 大小续传（range_start）
  └─ 否：删除 part，从头下载
流式接收 → 解密 → 追加写 part → 完成后改名为目标文件
中断 → 保留 part → 用户重试自动续传
取消/放弃 → 保留 or 删除（按用户动作）
```

### 5.3 清理配置

```
设置 → 系统设置（管理员）→ 存储与临时文件
  ├─ 总开关
  ├─ 断点续传保障时长（同时说明：= 清理保护期）
  ├─ 自动清理间隔
  ├─ 允许清理的客户端类型（多选）
  ├─ 孤儿保留期 / 每用户会话上限
  └─ 立即清理 → 显示清理结果
```

### 5.4 隐藏项

```
文件管理列表 / 对账扫描 → 服务端过滤所有 `.` 开头条目 → 三端展示一致、无隐藏目录
```

## 6. 关键决策与最终裁决

| 决策点 | 最终结论 | 推翻过程摘要 | 原因 |
|---|---|---|---|
| 版本与流程 | **1.9.0 完整流程** | 初始建议可走快速通道；用户选择完整流程 | 新功能 + 协议变更，需需求/设计/审查/测试 |
| 客户端范围 | **App + 桌面 + Web 全做** | 初稿建议 Web 下载续传后置；用户要求各端都做 | 多客户端体验一致 |
| 续传有效期 | **24 小时，可配 1h~7d** | 初稿建议 24h/72h；用户选 24h | 覆盖绝大多数隔夜/断网重试，控制磁盘占用 |
| complete 兼容 | **强制异步，三端同步升级** | 初稿建议保留旧同步模式；用户明确选「强制异步」 | 避免长期维护两套协议与静默失败 |
| 清理配置入口 | **三端系统设置页都加** | 初稿建议仅服务端 config + Web；用户要求三端 | 管理员在任一端可配 |
| 临时目录 | **统一临时根 + 旧目录迁移** | 现状分散；用户要求规整 | 用户目录干净、清理有单一入口 |
| 隐藏项 | **列表/扫描不返回 `.` 开头** | 现状只过滤 `.jflove-repair` | 用户要求不能查询隐藏文件夹 |
| 清理阈值一致性 | **与续传 TTL 同一配置** | 现状 24h 与启动 1h 冲突；用户要求对齐 | 防止「还没到续传期限就被清」 |
| 清理安全 | **只删程序自产固定命名** | 用户重点强调不得删正常文件 | 临时目录在用户磁盘内，误删不可接受 |
| 弱服务端资源隔离 | **合并线程化 + 全局并发 1（可配）+ 分片 512KB + 上传并发受限** | 用户反馈 8GB / N2840 上传时播放卡；初版只规划异步化，未规划资源隔离 | 弱 CPU 下并发合并会打满 CPU/IO，异步化只解决超时、不解决抢占 |

### 6.1 硬不变量

1. **I-1**：加密协议与帧格式不变；新字段只进加密 body。
2. **I-2**：`complete` 强制异步；发布时三端与服务端同版本，不做旧协议兼容层。
3. **I-3**：清理阈值 = 断点续传保障期（单一来源），启动首轮同样遵守。
4. **I-4**：清理只删程序自产、固定命名、路径在允许根内的文件。
5. **I-5**：上传会话严格按 `owner_user_id` 归属；换 upload_id 不得越权。
6. **I-6**：文件列表/对账不返回隐藏项；程序保留目录禁止接口访问。
7. **I-7**：修复产物默认不自动删除；离线下载临时目录任务结束即清。
8. **I-8**：v1.8.x 的记录按账号隔离（D10）、安全宪法 §9 不降级。
9. **I-9**：合并必须在独立线程 + 全局并发上限内执行；事件循环不得执行长时哈希/同步 IO。
10. **I-10**：客户端分片 ≤ 1MB；服务端校验单分片大小；进程内存峰值不随文件总大小线性增长。

## 7. 验收标准（AC-321 ~ AC-365）

### 7.1 上传断点续传

| AC | 判据 |
|---|---|
| **AC-321** | 上传 ≥1GB 文件到 50% 中断（断网/杀客户端），重试时客户端只发送剩余分片；服务端最终文件 SHA256 与源文件一致 |
| **AC-322** | 上传到 50% 后重启服务端，客户端重试能从已收分片继续（会话恢复），无需从头 |
| **AC-323** | 人工删除会话内若干 `.chunk` 后重试：状态接口返回缺失片；客户端补齐后合并成功 |
| **AC-324** | 把会话目录整体删除后重试：客户端收到「需重新开始」，从 0 片上传成功，界面不报错卡死 |
| **AC-325** | 同一内容在保障期内重复 `init` 返回同一 upload_id 与已收分片列表，不创建新目录 |
| **AC-326** | 分片上传失败时按分片级重试（≥5 次、指数退避）；网络失败不 DELETE 服务端会话；用户主动取消才清理 |

### 7.2 合并异步化

| AC | 判据 |
|---|---|
| **AC-327** | `complete` 请求 P95 ≤ 1 秒返回 `merging`（3GB 或人为慢合并场景） |
| **AC-328** | 合并期间每 2.5 秒轮询 `progress` 可正常返回；完成后返回 `done` + 最终路径；会话删除后不出现 403 |
| **AC-329** | 合并期间同一服务进程的列表/下载/播放接口正常响应（事件循环未被阻塞） |
| **AC-330** | 缺片合并返回缺失片索引；hash 失败返回可展示原因并允许「全量重传」重新开始 |
| **AC-331** | 服务端不保留同步 complete 分支；旧客户端请求收到明确「请升级客户端」错误而非静默成功 |

### 7.3 下载断点续传

| AC | 判据 |
|---|---|
| **AC-332** | 服务端下载支持起始偏移；偏移 0 = 现有行为；越界返回明确错误 |
| **AC-333** | App 下载 ≥500MB 文件到 40% 中断，重试从 40% 续传；最终文件大小与 SHA256 一致 |
| **AC-334** | 桌面端同 AC-333；中断重试不重复下载已下字节 |
| **AC-335** | Web 端下载中断/刷新页面后，从 IndexedDB/OPFS 已保存分块续传；完成后导出文件正确 |
| **AC-336** | 远端文件在下载中断期间被替换：客户端检测版本变化后自动删除 part 从头下载，不产生拼接坏文件 |
| **AC-337** | 客户端本地 part 超过 7 天后被清理；用户主动放弃下载时删除 part |

### 7.4 临时目录与隐藏项

| AC | 判据 |
|---|---|
| **AC-338** | 每块虚拟磁盘根下程序自产临时目录最多一个统一隐藏根；用户目录不再出现散落的 `.jflove-download` / `.jflove-repair` |
| **AC-339** | 升级后旧 `.jflove-download` / `.jflove-repair` 内容迁移/清理完成；迁移失败不阻塞服务启动与文件访问 |
| **AC-340** | 文件管理 `list` 不返回任何 `.` 开头条目（含 `.jflove-download` / `.jflove-repair` / 统一根） |
| **AC-341** | `/files/scan` 与 `/files/journal` 不返回隐藏项；挂载云盘对账不出现临时目录 |
| **AC-342** | 程序保留隐藏目录不可通过下载/预览/删除/移动/重命名/上传目标访问；路径段精确拒绝 |
| **AC-343** | 用户已有 `.` 开头普通文件不显示在列表，但已知精确路径仍可下载/删除；新建 `.` 开头名称有明确「隐藏文件」提示 |

### 7.5 自动清理

| AC | 判据 |
|---|---|
| **AC-344** | 把保障期配成 1 小时：会话最后活动 2 小时前 → 被清理；30 分钟前 → 不清理 |
| **AC-345** | 启动首轮清理遵守同一 TTL，不再出现「启动 1 小时就清」（构造 2 小时前孤儿目录，启动后按配置判定） |
| **AC-346** | 配置「允许清理客户端类型 = web」：App 过期会话不被自动清理，Web 过期会话被清理 |
| **AC-347** | 在临时根放正常文件/非 UUID 目录，在用户目录放普通文件：清理后全部保留；只删固定命名分片/part |
| **AC-348** | 清理日志只含数量/类型/跳过数，无文件名/路径明文；清理结果在系统设置页可见 |
| **AC-349** | 关闭总开关后不删除任何临时文件；修改配置无需重启立即生效 |
| **AC-350** | 每用户未完成会话上限达到时拒绝新 init 并提示，不无限堆积临时目录 |

### 7.6 三端设置页

| AC | 判据 |
|---|---|
| **AC-351** | App/桌面/Web 系统设置页均有「存储与临时文件」卡片；字段符合 F52.2；范围校验与中文说明齐全 |
| **AC-352** | 任一端修改配置后，三端刷新可见同一值，立即生效；普通用户不可写 |
| **AC-353** | 「立即清理」按钮仅管理员可用，执行后显示清理数量与跳过数量 |

### 7.7 兼容、安全与门禁

| AC | 判据 |
|---|---|
| **AC-354** | 服务端/App/桌面/Web 版本均为 1.9.0；`scripts/sync_version.py --check` 退出码 0 |
| **AC-355** | 无数据库结构变更；`scripts/check_db_schema.py` 退出码 0 |
| **AC-356** | 所有新接口在明文白名单之外，请求/响应走加密信封；`upload_id` 换 ID 越权返回 403 |
| **AC-357** | 响应头不含文件名/路径/用户标识；日志不含文件名/路径明文 |
| **AC-358** | 五端证据门禁 `check_verification_report.py --version 1.9.0 --require server,web,desktop,android,windows` 退出码 0 |

### 7.8 弱服务端资源隔离（D35 / F56）

| AC | 判据 |
|---|---|
| **AC-359** | 3GB 上传合并期间播放 1080p：不出现 >2 秒卡顿/断流（录屏或人工体验记录，弱服务端配置下） |
| **AC-360** | 3 个大文件同时提交 complete：默认并发 1，同一时刻最多 1 个合并执行，其余排队；progress 显示排队；无失败 |
| **AC-361** | 合并期间 progress 轮询 P95 ≤ 1 秒；代码审查确认合并在 `asyncio.to_thread`，事件循环无长时哈希/同步 IO |
| **AC-362** | 处理 1MB 分片请求时进程 RSS 增量 ≤ 32MB（psutil 采样）；3GB 上传全程 RSS 不随文件大小线性增长 |
| **AC-363** | 三端默认分片 512KB；3GB 上传成功、`total_chunks = ceil(size/512KB)`；服务端拒绝 >1MB 分片（400） |
| **AC-364** | 「弱服务端模式」一键预设后：合并并发 1、上传并发 2、分片 512KB、每用户会话上限 4 生效；三端一致 |
| **AC-365** | 合并并发 / 上传并发配置在三端设置页可读写、立即生效；非管理员不可改；越界值被拒绝 |

## 8. 安全宪法对齐（`AGENTS.md §9`）

| 条款 | 本版落点 |
|---|---|
| §9.1 加密信封 | init/status/complete/progress/download 新字段全部在加密 body；不新增明文白名单 |

| §9.6 角色约束 | App 走 `http_service.dart`；桌面走 `http_client.py`；Web 走 `http-client.ts`；token/session_key 不进日志 |
| 数据隔离 | 上传会话严格按 owner_user_id；清理配置是全局策略（管理员），不涉及用户内容 |

## 9. 风险与后续

| 风险 | 说明 | 应对 |
|---|---|---|
| R-1 三端同步升级 | 强制异步协议，任一端漏升级会导致上传失败 | 发布/ UAT 记录写明三端同版本；init 对旧客户端明确报错 |
| R-2 统一目录迁移 | 旧 `.jflove-download` / `.jflove-repair` 迁移可能遇到权限/占用 | 失败不阻塞；旧残留按固定命名 TTL 清理；迁移结果记日志 |
| R-3 隐藏过滤影响老用户 | 用户已有的 `.` 文件不再显示 | 保留精确路径访问；新建时提示「隐藏文件」；文档说明 |
| R-4 磁盘占用 | 24h 内未完成会话占一个文件大小；多会话叠加 | 每用户会话上限（默认 8）；管理员可调低 TTL |
| R-5 Web OPFS/IndexedDB 兼容性 | 部分浏览器不支持 | 不支持则回退整文件下载并明确提示；不静默 |
| R-6 清理误删 | 临时目录在用户磁盘内 | F51.4 严格命名/路径校验/跳过告警；专门 AC-347 安全用例 |
| R-7 容器重建丢失分片 | `build/` 未挂载卷时重建容器丢会话 | 属于「分片不存在 → 重新开始」的正常回退；部署文档说明 |
| R-8 合并吞吐 | 3GB 合并仍可能几分钟 | 异步化后不再是客户端失败原因；性能优化另立候选 |
| R-9 弱服务端仍卡 | N2840 物理性能有限，播放与上传/合并同时进行仍可能卡 | 默认弱服务端模式（合并并发 1）；实机录屏判据；允许管理员临时暂停上传 |
| R-10 播放加密开销 | 每 64KB 一帧加解密在弱 CPU 上本身有成本 | 本版不动帧格式；把「增大帧 / 硬件加速评估」列为后续候选 |
