# 桌面端 v1.10.24（SFTP 下载/上传在受限会话服务器上的静默失败）

> 分类：**代码 BUG**（`AGENTS.md §7.5.3` 快速修复通道）
> 来源：用户实测（2026-11-27）——「远程连接里点下载无反应，之前可以；SSH 文件页与批量下载也验证一下」
> 计划：`plans/desktop-sftp-transfer-session-limit-fix.md`
> 影响模块：仅 `jflove-desktop/`（服务端接口 / 数据库 / 加密协议未改）
> 版本：1.10.24（`version.json` 唯一来源，`sync_version.py` 同步 12 处 + versionCode 1010024）

## 1. 结论摘要

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 点「下载」→ 选完保存路径后**无任何反应** | v1.10.13 起传输改为新开一条 SFTP subsystem 通道；受限服务器（`MaxSessions 1` 一类）拒绝第二条通道，旧实现在**启动传输前**同步取 client，异常直接抛回桥；前端 `downloadOne` 没有 `catch` ⇒ Promise 拒绝无人处理 = 无行、无提示 | 通道打开失败自动回退会话级 client；前端失败可见 |
| 行内下载 / SSH「文件」页下载 / 批量「下载所选」全中 | 同上（同一 `sftp_download` 路径） | 同上；批量改为逐文件继续 + 汇总 |
| 上传同样会中（用户未报，但同一根因） | `sftp_upload` 同样用 `open_sftp(cached=False)` | 同一回退逻辑 |

## 2. 根因与复现证据

### 2.1 代码证据

- `src/bridge/remote.py::_open_transfer_sftp()`（v1.10.13 引入）：
  ```python
  client = session.open_sftp(cached=False)   # 新开 subsystem 通道
  ```
- `_h_sftp_download()` 在**启动后台线程之前**调用它；异常直接由桥返回错误。
- `ui/src/components/remote/SftpView.tsx::downloadOne()` 旧实现：
  ```ts
  const transfer = await remoteService.sftpDownload(...);  // 无 try/catch
  trackTransfer(...);
  ```
  ⇒ 拒绝无人处理，传输队列不会出现任何行。

### 2.2 真机复现（本地 sshd `MaxSessions 1`，端口 2222）

```text
# 同一连接：目录浏览正常（用会话级 client），第二条通道被拒
cached client listdir= 110
transfer client FAIL after 0.0s: SshError 无法打开 SFTP 通道：ChannelException(2, 'Connect failed')
Secsh channel 1 open FAILED: open failed: Connect failed
```

服务器日志（`/tmp/jf-sshd/log`）同样记录 `channel 1: open failed: Connect failed`。

### 2.3 为什么「之前可以」

v1.10.2 ~ v1.10.12 的下载/上传复用**会话级** SFTP client，不新开通道；
v1.10.13 为了避免「传大文件时目录刷不出来」改成独立通道——在标准 OpenSSH 上更稳，
但在限制并发会话的网关/堡垒机上直接把传输打掉。受限网关恰好也是本项目
v1.10.14 ~ v1.10.21 反复适配的那类服务器（多因素认证、限制尝试次数）。

## 3. 修复

### 3.1 Python（`src/bridge/remote.py`）

1. **传输启动前移入后台线程**：`sftp_download` / `sftp_upload` 立即返回 `transfer_id`；
   通道打开慢/失败都不再卡住桥响应。
2. **通道回退**（`_open_transfer_sftp`）：
   - 先 `open_sftp(cached=False)`；
   - 失败 → 打 WARNING（含异常类型，便于现场诊断）→ 复用会话级 client，
     并在整笔传输期间持有 `_sftp_lock`（paramiko client 不支持并发同步请求）；
   - 两条路都失败 → 发 `remote.sftp_failed`（带 `name` / `direction` / `bytes_total`）。
3. **共享 client 不关闭**：`_finish_transfer_sftp(..., shared, lock)` 共享路径只释放锁；
   专用路径维持原语义（注销 + 关闭）。
4. **取消目录加载不误伤传输**：新增 `_sftp_shared_transfers` 计数；共享传输进行中
   `sftp_abort` 直接跳过关闭并返回 `{"ok": false}`，保住 v1.10.13 的语义
   （前端相应提示「有文件正在传输，暂不能取消目录加载」）。
5. 事件补充 `name` / `direction` / `bytes_total`，供前端在「事件先于响应」时补建行。
6. `_friendly_sftp_error` 增加 `connect failed` / `channel open failed`
   → 「服务器拒绝打开新的 SFTP 通道（可能限制了并发会话数）」。
7. **审查补强（M1/M2/M3）**：
   - 传输事件带 `session_id`；前端各 `SftpView` 按会话过滤（多标签常驻挂载，避免别的会话事件在本标签建行/刷新）；
   - `sftp_cancel` 增加「取消代次」：开通道窗口与排队等锁阶段点取消，传输线程在读写前检查代次并中止（消息「已取消传输」）；
   - 元操作锁改为 `_sftp_guard` 有上限等待（`SFTP_OP_TIMEOUT=45s`）：共享传输持锁时目录加载不会永久卡死，超时返回「有文件正在传输…」；
   - 完成/失败事件改为**清理后再发**（不再让 `scheduleReload` 等锁），`bytes_total` 取实际总字节；
   - 批量汇总改成「已发起 N 个，M 个启动失败」（不再把「已发起」当成功）。

### 3.2 前端（`ui/src/components/remote/SftpView.tsx`）

- `downloadOne` / `handleUpload` 全链路 `try/catch`：失败立即插入失败传输行，
  不再只依赖后台事件；批量下载逐文件继续，结束后显示「成功 N / 失败 M（原因见传输队列）」。
- `trackTransfer` 改 upsert（同 id 不重复建行）。
- `remote.sftp_progress` / `done` / `failed` 处理器：行不存在时补建；
  完成/失败事件先于 `sftp_download` 响应到达也不会丢状态。
- 未勾选文件点「下载所选」给出明确提示（原实现静默 return）。

### 3.3 安全边界

- 未新增网络出口：传输仍在 Python 侧完成，渲染层只传路径（AGENTS §9.6）。
- 未改加密协议 / 未新增密钥或算法。
- 回退只复用**已认证**的会话级 SFTP client，不新建身份凭据。

## 5. 设计取舍

- **为什么保留独立通道优先**：标准服务器上传输与目录浏览互不阻塞，是最优路径；
  回退只在「服务器确实拒绝第二条通道」时发生。
- **为什么回退时持锁**：paramiko `SFTPClient` 的同步请求共享一条通道的响应流，
  并发会「响应被另一线程读走」。持锁期间的代价是目录加载要等传输结束（UI 显示加载中），
  但比「下载完全不可用」正确；大文件下载时刷新目录会等待，属可接受降级。
- **为什么事件补 `name`**：完成/失败可能在 `sftp_download` 响应之前到达；
  没有文件名就无法建一条可读的失败行。

## 6. 已知边界

- 受限服务器上**传输期间目录浏览会阻塞**（共享 client + 锁）。这是为兼容性付出的代价；
  如后续需要在受限网关上并行传输 + 浏览，需服务端支持多通道或独立的 SFTP 连接。
- 未覆盖 Windows 真机 VM（本机无 `jflove-win10` 域）：回退逻辑与平台无关，
  Windows 侧仍需在发布回验时跑 `windows_vm_e2e.sh` 的既有用例；
  **原生保存/目录对话框在 Windows 的点击路径本次未单独取帧**（Linux Xvnc 已覆盖真实模态）。
- 批量下载到同一目录时同名文件会覆盖（既有语义，未改动）。
