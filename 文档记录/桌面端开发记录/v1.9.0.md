## 1. 一句话结论

桌面端把「上传断点续传 + 合并异步化 + 下载 Range 续传 + 管理员清理配置」全部落地：
上传以**服务端 `received_chunks` 为准**（本地记录仅兜底），分片降到 **512KB**，`complete` **强制异步**
并每 **2.5s** 轮询 `upload/progress`；下载按 `/api/v1/files/download` 的 `range_start` 与
`X-Stream-*` / `X-File-Version` 响应头续传 part；系统设置新增「存储与临时文件」卡片与「立即清理」。
网络 / 合并失败**不再主动 DELETE 服务端会话**，只有用户取消才清理。

## 2. 功能与改动点

### 2.1 上传（`src/services/file_service.py`）

| 需求 | 实现 |
|---|---|
| init 带客户端类型（F46 / D34） | `init` payload 新增 `client_type="desktop"`（`file_service.py:345`） |
| 服务端已收分片为准（F46.2 / F46.4） | 读 `init.received_chunks` 得到 `received`，只补缺失片；本地 `storage/upload_resume.json` 只在**旧服务端没有该字段**时兜底（`file_service.py:399-407`） |
| 幂等 / 已存在 / 会话失效回退（F46.6 / F46.7） | `already_exists` 直接返回 `already_path`；`restart_required` 清空续传点、从 0 片重传；会话丢失（400「上传会话不存在/已过期」）自动重新 init 一次 |
| 分片 512KB（F56.4） | `settings.CHUNK_SIZE = 512 * 1024`（`src/config/settings.py:86`），`total_chunks = ceil(size/512KB)` |
| 单片指数退避重试（F46.5） | 沿用 `_CHUNK_ATTEMPTS=5`，延迟 `1/2/4/8s`（`min(2**attempt,15)`），只重发该片 |
| 失败不删会话（F46.5） | 删除 `_cancel_session` 的非取消调用；网络 / 合并失败只保留本地记录并抛错；**仅 `ValueError`（用户取消）才 DELETE**（`file_service.py:454-469`） |
| complete 异步（F47 / D27） | `POST /files/upload/complete` body 增加 `async_mode=True`（`file_service.py:784`） |
| progress 轮询（F47.1~F47.4） | 每 `2.5s`（服务端 `poll_interval_s` 合法时优先）查询 `upload/progress`；`queued/merging` 回报 `finalizing` 进度，`done` 返回 `path`，`failed` 翻译中文原因并保留会话（`file_service.py:58 / 590-858`） |
| 缺片补齐（F47.4） | progress `failed` 且带 `missing_chunks`：只补传缺失分片后重新 complete 一次；再失败按中文原因上报 |
| 合并超时兜底（沿用） | complete 请求读超时 / 响应丢失：不盲目重发，轮询 progress 并按远端大小核验，命中即成功 |

> **本地续传记录**：`upload_resume.json` 仍按「磁盘+目录+文件名+size+mtime」为键，记录
> `upload_id / sent / updated_at`；每 32 片及结束 / 异常时落盘，**不再用它决定续传点**。

### 2.2 下载（`src/utils/http_client.py` + `src/services/file_service.py`）

| 需求 | 实现 |
|---|---|
| Range 请求（F48.1） | `download_to_file` 新增 `range_start`，每次请求在加密 body 显式携带（0 也携带）；GET 仍走既有加密信封，不走 URL |
| 响应头（F48.1） | 读取 `X-Stream-Offset` / `X-Stream-Total` / `X-File-Version`（`http_client.py:694-696`）；`File-Version` 只用于元数据比对，不写日志 |
| part + meta（F48.2） | `save_path + ".part"` 与 `save_path + ".jflove-part.json"`（`http_client.py:42-44`）；meta 记录 `size / version / offset / updated_at`，每 4MB 原子刷新 |
| 版本不一致重下（F48.2 / AC-336） | 请求偏移 > 0 时校验：本地 part 大小、`X-Stream-Offset`、meta version 与 `X-File-Version`；任一不符 → 删除 part/meta 从头下载（只回退一次）；416 同样回退 |
| 原子替换（F48.2） | 流正常结束且 `X-Stream-Total` 与已写字节一致 → `os.replace(part, target)`，删除 meta |
| 失败保留 / 取消删除（F48.2） | 非取消异常保留 part + meta（meta 记录实际偏移），供下次续传；用户取消删除 part+meta |
| 7 天清理（F48.5 / AC-337） | 下次下载同一文件时若 meta `updated_at` 超过 `DOWNLOAD_PART_TTL_SECONDS = 7 天` → 删除 part/meta 从头下载（`file_service.py:852 / 936`） |
| 进度含续传起点（AC-334） | `progress_callback(offset + 本次写入, X-Stream-Total)` |

`file_service.download_file` 负责读取 part + meta、决定 `range_start`、透传 `expected_meta` / `meta_path`；
本地目标已完整（size == meta.size）时直接收尾、不重复请求；part 已完整（改名前中断）时仍带
`range_start=part_size` 请求一次，用 `X-File-Version` 确认远端未变后再 `os.replace`（防同大小替换，AC-336）。

## 3. 调用的后端接口（按设计 §4 契约）

| 接口 | 桌面端用途 | 新增字段 |
|---|---|---|
| `POST /api/v1/files/upload/init` | 建/复用会话 | 请求 `client_type`；响应 `received_chunks / resumed / expires_at / max_chunk_size / recommended_concurrency / already_exists / already_path / restart_required` |
| `POST /api/v1/files/upload/chunk` | 分片上传 | 不变 |
| `POST /api/v1/files/upload/complete` | 触发合并 | 请求 `async_mode=true`；响应 `state / poll_interval_s / path` |
| `POST /api/v1/files/upload/progress` | 合并进度 / 收尾 | `state / processed / total / file_size / percent / queue_position / path / error / missing_chunks` |
| `DELETE /api/v1/files/upload/{upload_id}` | **仅用户取消** | 不变 |
| `GET /api/v1/files/download` | 下载 / 续传 | 请求 `range_start`；响应头 `X-Encrypted-Stream / X-Stream-Offset / X-Stream-Total / X-File-Version` |
| `GET /api/v1/config` | 设置页读取 | 缺省注入 upload_* 默认值 |
| `PUT /api/v1/config` | 逐项保存 | 不变（服务端对 upload 键做范围校验） |
| `POST /api/v1/config/cleanup` | 立即清理 | 响应 `removed_sessions / removed_dirs / removed_parts / skipped / executed_at` |

兼容旧服务端：`received_chunks` 缺失时本地记录兜底；complete 返回直接 `path` 时按已完成处理；
响应头缺失时按「不支持 Range」回退整文件下载；progress 404 / 网络异常只影响进度展示。

## 5. 与上一版本（v1.8.4）差异

| 维度 | v1.8.4 桌面端 | v1.9.0 桌面端 |
|---|---|---|
| 分片大小 | 1MB | **512KB**（服务端硬上限仍 1MB） |
| 续传点来源 | 本地 `upload_resume.json` 的 sent 列表 | **服务端 `init.received_chunks`**；本地记录仅兜底 |
| init | 无客户端类型 | `client_type="desktop"`（旧客户端由服务端 409 提示升级） |
| complete | 长请求 + `complete` 线程内等待合并 | `async_mode=true` 立即受理；**2.5s 轮询 progress**，按 queued/merging/done/failed 收尾 |
| 合并失败 | 异常后 `_cancel_session` 清会话 | **不删会话**；缺片自动补传一次；hash/IO 失败保留会话供重试 |
| 下载 | 全程从头解密到 `.part`，失败即删 part | `range_start` + `X-Stream-*` / `X-File-Version`，part/meta 续传；失败保留、取消才删；7 天过期 |
| 下载进度 | 仅本次会话已写字节 | **含续传起点**的已写字节 + 远端总字节 |
| 管理员设置 | 离线修复 / 离线下载 | 新增「存储与临时文件」+ 弱服务端预设 + 立即清理 |

## 6. 设计取舍

1. **`received_chunks` 权威、本地仅兜底**：仅凭本地记录会在服务端重启/清理后「以为已传完」而漏片；
   而每次上传都先 `init` 的代价是一次幂等请求，可接受。
2. **complete 仍放子线程等待响应**：虽然服务端已异步受理，但保留「等待 complete 响应期间也轮询 progress」
   可以让旧服务端/慢网下界面同样有进度；响应返回 `merging` 后继续轮询到 done。
3. **失败不删会话**：把「网络失败」与「用户取消」彻底分开，避免一次断网让几十 GB 分片前功尽弃；
   本地记录在异常路径也落盘，重启后可继续。
4. **下载续传以 part 实际大小为准**：meta 的 `offset` 只作参考，避免 meta 刷新滞后导致偏移错位；
   版本校验同时要求「本地 meta version + 服务端 X-File-Version」都存在，缺一即从头重下，宁慢不坏。
5. **7 天 part 清理只做同文件触发**：桌面端没有全目录扫描任务（避免误删用户文件 / 长目录遍历），
   同一目标再次下载时会判定超期并删除；未覆盖「永不再下载同一文件」的孤儿 part（见 §7）。

## 7. 已知限制 / 未决问题

1. **part 命名与设计文档有一处措辞差异**：设计 §3.1 写 `<name>.jflove-part` + `<name>.jflove-part.json`，
   本次按任务书明确要求实现为 `<save_path>.part` + `<save_path>.jflove-part.json`。二者都是客户端本地命名、
   不影响服务端契约；建议 designer 在下一轮把设计文档 §3.1 与三端实现对齐（APP/Web 同步时确认）。
2. **客户端 part 的 7 天清理范围**：仅在同一目标文件再次下载时清理过期 part；没有全目录扫描/启动清扫。
   若产品要求「启动即清全盘 part」，需要先建立 part 登记表或限定扫描根，避免遍历用户目录。
3. **未做真实服务端联调**：服务端 v1.9.0 由并行任务实现，当前工作区尚无 init 的新字段 / progress 扩展 /
   Range 响应头；客户端按设计契约编码并用替身单测。后端落地后需补实机证据（上传 1GB 中断续传、
   下载 500MB 中断续传、设置保存与立即清理 200）。
4. **弱服务端预设的「分片 512KB」**是客户端常量，不在服务端 config 里；预设只写合并/分片并发与会话上限，
