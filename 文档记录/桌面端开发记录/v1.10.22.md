# 桌面端 v1.10.22（终端：粘贴重复 + 输入/粘贴卡顿）

> 分类：**代码 BUG**（`AGENTS.md §7.5.3` 快速修复通道）
> 来源：用户 2026-11-22 反馈 —— Linux 端远程 SSH / 本地终端两处问题：
> ① 按一次 Ctrl+V 会粘贴**两次**；② 输入时有明显**延迟和卡顿**；Windows 一并排查
> 计划：`plans/v1.10.22-desktop-terminal-paste-latency.md`
> 影响模块：仅 `jflove-desktop/`（服务端 / 数据库 / 加密协议不改）

## 1. 结论摘要

| # | 现象 | 根因 | 修复 | 判定方式 |
| --- | --- | --- | --- | --- |
| 1 | 一次 Ctrl+V 贴两遍 | 自定义按键处理器**没 `preventDefault()`**，浏览器默认粘贴又走一遍 | 命中自定义分支即 `event.preventDefault()` | **同机 A/B**：去掉该行 2 条 input 帧，加上后 1 条 |
| 2 | **每次粘贴固定卡约 500ms** | `navigator.clipboard.readText()` 在 QtWebEngine 里**永久 pending**，每次都要等满 `CLIPBOARD_TIMEOUT_MS=500` 才回退桥 | 桌面端（桥就绪）**优先走桥**；浏览器 API 只作无桥时兜底 | 单测断言桥就绪时 `readText` **一次都不被调用**且总耗时 <100ms |
| 3 | 页面被判隐藏/被限流时终端输出断流 | 输出写屏绑在 `requestAnimationFrame` 上；rAF 在隐藏页面**完全停摆** | 换 `MessageChannel` 宏任务合帧（`utils/terminal-schedule.ts`） | 最小复现 A/B：rAF 版滞后 3–16ms 持续积压，MC 版 0.1ms 零积压 |
| 4 | 重复布局浪费 | `applyFit` 每次都重跑整套候选测量（同步布局） | 尺寸/字号/自适应开关未变则直接返回 | 源码级单测断言幂等守卫存在 |
| 5 | Linux 页面被后台化 | 反后台化 flags 原来只注入 Windows | Linux 也注入三个开关（遮挡特性仍限 Windows） | Python 单测锁定 Linux 必含三开关、且不含 Windows 独有特性 |

## 2. 根因详述与实测证据

### 2.1 粘贴两次（BUG-1）

`ui/src/components/remote/TerminalView.tsx` 的 `attachCustomKeyEventHandler`：

```js
if (event.code === 'KeyV') {
  if (mode === 'ctrlShift' && !withShift) return true;
  void pasteClipboard();   // 自己读剪贴板 + term.paste()
  return false;            // ← 只拦 xterm 的 _keyDown
}
```

`return false` 的语义只作用于 xterm 的 `_keyDown`（它是 `keydown` 监听器的返回值），
**Chromium 的默认动作（粘贴）照样执行**。于是同一次按键走两条路：

1. 本处理器 `readClipboardText()` → `term.paste()`；
2. 浏览器默认粘贴 → xterm 在 `element` / `textarea` 上注册的 `paste` 监听 → 再 `triggerDataEvent` 一次。

**同机 A/B 对照**（同一构建、同一按键、同一剪贴板，只差 `preventDefault()` 一行）：

```
去掉 preventDefault：Ctrl+V 产生的 input 消息数: 2   → ["\u001b[200~1f1a0ca56ade\u001b[201~", 同上]
加上 preventDefault：Ctrl+V 产生的 input 消息数: 1   → ["\u001b[200~1f1a0ca56ade\u001b[201~"]
```

### 2.2 粘贴固定卡 500ms（BUG-2，用户"卡顿"的主因之一）

`ui/src/utils/clipboard.ts::readClipboardText()` 旧实现「先试浏览器 API，超时再回退桥」。
而在 QtWebEngine 下这条 API 是**死的**：

```
navigator.clipboard.readText 是否永挂： TIMEOUT@3001ms (总耗时 3001ms)
```

即既不 resolve 也不 reject ⇒ **每一次粘贴都要先白等满 `CLIPBOARD_TIMEOUT_MS`（500ms）**。
用户侧感受正是"粘贴时有毛病/卡"。

修复后（桥就绪时直接走桥，桥是同步 IPC）：

| 路径 | 耗时 |
| --- | --- |
| 修复前桌面端每次读剪贴板 | ≥ 500ms（白等超时） |
| 修复后桌面端 | < 100ms（单测断言，且 `readText` 一次都不被调用） |

### 2.3 输出写屏被 rAF 绑死（BUG-3）

`flushPending` 用 `requestAnimationFrame` 调度。rAF 在两种情况下会被 Chromium 掐住：

**① 页面被判隐藏**（最小化到托盘 / 被完全遮挡）—— 实测 rAF **1 秒 0 帧**：

```
hidden state: {"vis":"hidden","raf":0,"mc":295747}
```

同一时刻 `MessageChannel` 在 2.5 秒里跑了 29 万次 ⇒ 停的正是出帧链路，不是 JS。

窗口藏起来时终端仍在收输出，这些字节全压在待写队列里，涨到 `PENDING_LIMIT`（8MB）
后开始**静默丢最旧的数据**，恢复时再一次性灌进去。

**② 无合成器的 X 服务器**（Xvfb / Xvnc）—— 页面上只要有 xterm 持续 `write()`，
rAF 从 60fps 掉到 1.5fps，按键到画面出现实测 **2~4 秒**；把 xterm 从 DOM 摘掉立刻回到 60fps。

**最小复现的 A/B 对照**（同一页面、同一输出速率，只差调度方式）：

| 时刻 | A（rAF 调度）入队/写入/滞后 | B（MessageChannel）入队/写入/滞后 |
| --- | --- | --- |
| t+0s | 241 / **178** / 16.3ms | 241 / **241** / 0.1ms |
| t+8s | 991 / **928** / 14ms | 991 / **991** / 0.1ms |
| t+14s | 1553 / **1491** / 4ms | 1553 / **1553** / 0.1ms |

A 侧持续 **积压**（写入数始终落后入队数），B 侧零积压。

> ### ⚠ 证据边界（诚实声明）
>
> 上面 1.5fps / 2~4 秒那组数据是在**无合成器的 Xvnc/Xvfb** 上复现的。
> 在用户真实桌面（Wayland + XWayland `:0`，DPR=2）上，同一套探针测得
> **keydown → 画面 6–25ms、rAF 稳定 60fps**，未能复现秒级卡顿。
> 因此：
> - **BUG-1（粘贴两次）与 BUG-2（粘贴 500ms）在真实桌面已直接复现/量化，是用户可感知的主因**；
> - **BUG-3 是"隐藏/限流场景"的确定性缺陷**（页面 hidden 时 rAF=0 已实测），
>   但**不能**把它当成用户桌面卡顿的唯一解释 —— 用户在**最小化到托盘再恢复**后
>   使用终端时才会命中该路径。
> 其余已排除项见 §2.4。

### 2.4 已排除的方向（都有实测，避免重复排查）

| 怀疑方向 | 实测 | 结论 |
| --- | --- | --- |
| 后端/PTY 慢 | 本地 PTY `write → 回显` **0.56–0.68ms** | 排除 |
| JS 主线程忙 | renderer CPU profile 3s：15470 样本中 **15429 是 idle（99.7%）** | 排除 |
| 网络/WebSocket | keydown → `ws.send` **2ms**；下行 → DOM 20ms | 排除 |
| DOM 规模 | 页面总元素 261 个，xterm 节点 52 个 | 排除 |
| 背压丢数据 | 持续 5MB 输出期间无 longtask / 无 LoAF | 排除 |
| 多标签累积 | 6 个终端标签并存时中位 **24.9ms** | 排除 |
| `readTerminalShortcuts()` 每键读 localStorage | 1000 次仅 **0.5ms** | 排除 |

## 7. 设计取舍

1. **为什么 `preventDefault()` 而不是干脆删掉自定义处理器**：`ctrl` / `ctrlShift` / `smart`
   三种模式是产品功能（`terminal-shortcuts.ts`），必须保留"有选区才复制、无选区发 SIGINT"
   的语义；`preventDefault()` 只掐掉浏览器默认动作，不动这套语义。
2. **为什么用 `MessageChannel` 而不是 `setTimeout(0)`**：`MessageChannel` 是宏任务且
   **不受最小定时器精度限制**，也不会被嵌套定时器钳制；`setTimeout` 只作无 `MessageChannel`
   环境的兜底。
3. **为什么 Linux 也注入反后台化 flags**：页面 hidden 时 rAF=0 是跨平台行为，
   只是触发方式（遮挡/最小化）不同；这三个开关对正常前台使用无副作用。
4. **为什么 `applyFit` 用指纹而不是直接把调用方改少**：调用方有 ResizeObserver /
   切标签 / 改字号三处，各自都可能合法触发；在唯一入口做幂等最不容易漏。
