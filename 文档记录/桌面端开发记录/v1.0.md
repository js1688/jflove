## 三、架构设计

### 3.1 整体架构

桌面端采用 MVC 架构：

- **View（视图层）**：`src/ui/` 下所有 QWidget 页面，负责展示与用户交互
- **Service（服务层）**：`src/services/` 下各 service 模块，封装与后端 API 的业务调用
- **Utils（工具层）**：`src/utils/` 下的加密、HTTP、会话、日志、线程工具

### 3.2 加密通信架构

所有 API 通信（密钥交换和管理员检测除外）均经过端到端加密：

```
客户端                          服务端
  │                               │
  │──── POST /auth/key-exchange ──▶│  明文：客户端 X25519 公钥
  │◀─── 返回服务端公钥 ────────────│
  │                               │
  │  ECDH 计算共享密钥             │
  │  HKDF-SHA256(salt=b"jflove-v1")│  两端派生相同的 32 字节会话密钥
  │                               │
  │──── POST/GET/PUT/DELETE ──────▶│  请求体：{"nonce":"…","ciphertext":"…"}
  │◀─── 响应体：同样的加密信封 ────│
```

- **算法**：X25519 ECDH + HKDF-SHA256（派生会话密钥）+ ChaCha20-Poly1305（数据加密）
- **nonce**：每次请求随机生成 12 字节，保证密文唯一性
- **JWT Token**：通过加密 Body 中的 `token` 字段传递，不放明文 Header
- **Session ID**：通过 `X-Session-ID` 请求头传递，服务端用于定位会话密钥

### 3.3 会话管理

`SessionManager`（单例）持有以下内存状态：

| 字段                | 说明                           | 持久化       |
| ------------------- | ------------------------------ | ------------ |
| `server_url`        | 服务端地址                     | QSettings    |
| `session_id`        | 服务端分配的会话 ID            | 内存         |
| `session_key`       | 32 字节对称会话密钥            | 内存         |
| `token`             | JWT 访问令牌                   | QSettings    |
| `user_id`           | 当前用户 ID                    | QSettings    |
| `username`          | 当前用户名                     | QSettings    |
| `role`              | 当前用户角色                   | QSettings    |
| `key_exchange_time` | 最近一次密钥交换时间           | 内存         |
| `token_expires_at`  | JWT 过期时间（Unix 时间戳）    | QSettings    |

登录成功后，`auth_service` 解码 JWT Payload 的 `exp` 字段写入 `token_expires_at`，同时将 token / username / role / user_id / expires_at 持久化到 `QSettings`（`session/` 命名空间）。程序重启时 `try_restore_session()` 检查持久化数据是否有效，有效则重新执行密钥交换并恢复内存状态，实现免登录。

### 3.4 异步线程模式

所有网络请求均通过 `Worker(QThread)` 在子线程执行，避免阻塞 UI：

```python
self._worker = Worker(service_func, arg1, arg2)
self._worker.finished.connect(on_success)
self._worker.error.connect(on_error)
self._worker.start()
```

文件上传使用专用的 `UploadWorker`，额外提供：

- `progress = Signal(int, int)`：已传输字节数 / 总字节数
- `cancel()`：设置取消标志，worker 在下一个分片检查点退出

### 4.2 src/utils/crypto.py

| 函数                   | 说明                                          |
| ---------------------- | --------------------------------------------- |
| `generate_x25519_keypair()` | 生成临时 X25519 密钥对，返回 `(私钥对象, 公钥 Base64)` |
| `derive_session_key(priv, peer_pub_b64)` | ECDH + HKDF-SHA256 派生 32 字节会话密钥 |
| `encrypt(session_key, data)` | dict → JSON → ChaCha20-Poly1305 加密 → `{"nonce":…,"ciphertext":…}` |

### 4.3 src/utils/http_client.py

`HttpClient` 类封装所有 HTTP 通信：

| 方法                   | 说明                                       |
| ---------------------- | ------------------------------------------ |
| `get_plain(path)`      | 不加密的 GET（用于密钥交换、管理员检测）   |
| `post_plain(path, data)` | 不加密的 POST（用于密钥交换）           |
| `post(path, data)`     | 加密 POST                                  |
| `get(path, data)`      | 加密 GET（请求体加密，body 通过 `json=` 传递） |
| `put(path, data)`      | 加密 PUT                                   |

**注意**：GET 请求虽然用 `requests.get(url, json=payload)` 发送 JSON body，后端通过 `await request.body()` 读取，而非 Query String，这是本项目特殊设计。

## 五、UI 页面说明

### 5.1 登录/初始化窗口（LoginWindow）

三页 QStackedWidget + 免登录自动恢复：

```
[启动] QTimer.singleShot(100ms) → try_restore_session()
   ├── 恢复成功 → 发射 login_success(role)（直接进主界面）
   └── 恢复失败 → 显示登录流程

[页面0] 服务端地址输入
   → 点击"连接" → 执行密钥交换 → check_admin_exists()
     ├── 无管理员 → [页面1] 创建管理员
     └── 有管理员 → [页面2] 用户登录
[页面1] 创建管理员
   → init_admin() + login() → 发射 login_success(role)
[页面2] 用户登录
   → login() → 发射 login_success(role)
```

## 六、已知注意事项

### 6.1 Python 3.14 f-string Unicode 引号问题

Python 3.14 对 f-string 中的 Unicode 弯引号（`"` U+201C / `"` U+201D）解析更严格，会触发语法错误：

```
SyntaxError: invalid syntax. Perhaps you forgot a comma?
```

**解决方案**：使用中文书名号 `「」` 替代，例如：

```python
# 错误（Python 3.14 不兼容）
f"确定要删除「{name}」吗？"  # 若误用 " " 弯引号

# 正确
f"确定要删除「{name}」吗？"
```

涉及文件：`file_page.py`、`note_page.py`、`user_page.py`、`disk_page.py`

### 6.2 GET 请求携带加密 Body

后端通过 `await request.body()` 读取 GET 请求体（而非 Query String），客户端使用：

```python
requests.get(url, json=encrypted_payload, headers=headers)
```

这是本项目专有设计，用于统一加密所有请求参数。

### 6.3 文件下载/预览响应不加密

后端下载接口返回 `FileResponse`（原始字节流），**响应体不加密**。`http_client.download_stream()` 专用此场景，直接返回 `response.content`，不走解密流程。

### 6.4 Worker 生命周期管理

每个页面持有 `self._worker` 引用防止 Worker 被 GC 提前回收。若快速连续发起多个请求，旧 Worker 会被新 Worker 替换（旧 Worker 的信号仍可能触发，但因 Python GIL 和 Qt 事件队列不会产生竞态问题）。

### v1.0.3 详细变更（2026-05-04）

#### 背景

用户反馈：

1. 上传文件时几乎看不到进度条 —— 经排查发现是 SHA256 校验阶段没有进度反馈、单分片 1 MB 导致小文件几乎瞬间完成；上传对话框是模态阻塞型的，每次只能上传一个文件，体验差。
2. 上传/下载是单线程串行的，多个文件只能排队执行。
3. 没有集中的"任务管理"视图，传输状态完全依赖弹窗，弹窗关闭后无法回看进度或失败原因。

#### 之前的逻辑

- `file_service.upload_file()`：进度回调签名 `(done_chunks, total_chunks)`，仅在每个分片上传完成后回调一次。SHA256 校验阶段一次性把所有分片读入内存（`chunks_data.append(chunk)`），过程中不上报进度。
- `UploadWorker (QThread)`：文件页面专用，每次上传创建一个 worker + 一个 `UploadProgressDialog`（模态对话框）。dialog.exec() 阻塞主线程，只能单文件上传。
- 下载：`http_client.download_stream()` 把响应整体缓存到 `bytes` 后再写到磁盘，对大文件不友好；下载没有取消机制。
- 文件页面 `_on_upload()` 用 `QFileDialog.getOpenFileName()` 仅支持单选；下载时 `_download_file()` 直接用通用 `Worker` 跑 `download_file`，无进度可见。

#### 本次修改

##### 新增 `src/utils/transfer_manager.py`

实现一个全局的传输任务管理器（QObject 单例）：

- **数据模型**：
  - `TaskKind` 枚举：`UPLOAD` / `DOWNLOAD`
  - `TaskStatus` 枚举：`PENDING / HASHING / RUNNING / COMPLETED / FAILED / CANCELLED`
  - `TransferTask` dataclass：`id / kind / filename / disk_id / rel_path / local_path / file_size / transferred / status / error / created_at / finished_at`，提供 `percent` 属性
- **`_TransferWorker(QThread)`**：单任务工作线程，根据 `task.kind` 调用 `file_service.upload_file` 或 `file_service.download_file`，通过 `progress / completed / failed / cancelled` 信号上报状态
- **`TransferManager(QObject)`**：
  - 信号：`task_added(TransferTask) / task_updated(str) / task_removed(str)`
  - API：`submit_upload / submit_download / cancel / clear_finished / stats / tasks`
  - 调度：`MAX_CONCURRENT = 3`，上传/下载共享配额；`_try_dispatch()` 在每次任务结束或新提交时被调用，从 PENDING 队列中按创建顺序挑选下一个任务启动
  - 取消：进行中任务通过 worker 的 `_cancelled` 标志位优雅中断；等待中任务直接置为 CANCELLED
  - 模块底部导出 `transfer_manager` 单例供全应用共享

##### 新增 `src/ui/pages/transfer_page.py`

  - 已结束的任务取消按钮自动禁用

```python
def _try_dispatch(self) -> None:
    while self._running_count() < self.MAX_CONCURRENT:
        next_task = next(
            (self._tasks[tid] for tid in self._task_order
             if tid in self._tasks and self._tasks[tid].status == TaskStatus.PENDING),
            None,
        )
        if not next_task:
            break
        self._start_task(next_task)
```

### v1.0.6 详细变更（2026-05-04）

#### 背景

用户反馈：

1. 同步过程"卡"，桌面端有明显卡顿
2. 感觉同步似乎"每次都重传/重下所有文件"，没有跳过未变更的文件
3. 希望优化性能，避免耗性能的操作（用户提示可以用 hash 比对等方式）

#### 之前的逻辑（v1.0.5）

存在「永动机式重传」Bug：

1. 客户端上传文件 X → 服务端 `complete_upload` 用 `aiofiles.open(..., 'wb')` 写盘 → 文件 mtime = 当前时间（不再是源 mtime）
2. 下一轮同步：客户端读本地 mtime（源时间，旧）vs 远端 mtime（写盘时间，新）→ 判定远端新 → 触发**下载覆盖本地**
3. 下载完成后本地 mtime 又变成下载时刻（更新） → 又超过远端 → 下次同步又触发**上传覆盖远端**
4. 每个文件每轮同步都被反复重传 → 大量任务进入 `transfer_manager.task_added` 信号风暴 → UI 主线程不停创建 `TransferTaskRow(CardWidget)` → 卡顿

之前的 diff 算法也未充分利用 size 信息，只用 mtime 容差判断"未变更"。

#### 本次修改

##### `src/services/file_service.py`

- `upload_file()` 新增 `preserve_mtime=True` 参数，默认在 init 阶段读取 `os.path.getmtime(local_path)` 并通过 init 请求体携带 `mtime` 字段送给服务端
- `download_file()` 新增 `restore_mtime: float | None = None` 参数。下载完成后若提供，则 `os.utime(local_save_path, (mtime, mtime))` 将本地 mtime 还原到服务端 mtime
- 两端 utime 失败时仅 warning 日志，不影响传输结果（best-effort）

##### `src/utils/transfer_manager.py`

- `TransferTask` dataclass 新增字段 `remote_mtime: float = 0.0`（仅下载使用）
- `TransferManager.submit_download(...)` 新增参数 `remote_mtime: float = 0.0`
- `_TransferWorker._do_download()` 把 `task.remote_mtime` 传给 `file_service.download_file(restore_mtime=...)`
- 文件页手动下载（`file_page._download_file`）虽未填该参数，但默认 `0.0` 等价于 None → 不还原 → 行为不变

##### `src/utils/sync_engine.py`

`_SyncRunWorker.run()` 主 diff 循环改进，命中即停的判断顺序：

```python
if local_meta and not remote_meta:
    UPLOAD
elif remote_meta and not local_meta:
    DOWNLOAD
else:
    local_size, local_mtime = local_meta
    remote_size = remote_meta.get("size", 0)
    remote_mtime = remote_meta.get("modified_at", 0)
    if local_size == remote_size and abs(local_mtime - remote_mtime) <= _MTIME_TOLERANCE:
```

`_submit_download()` 把 `remote_meta["modified_at"]` 通过 `remote_mtime=` 参数贯穿到 `transfer_manager.submit_download()`，让下载完成后客户端能还原本地 mtime。

#### 性能影响（理论分析）

第一次同步（首次配置）：所有文件都需要传输，与之前一致。但服务端会把源 mtime 还原到目标文件 → 第二次同步前两端 mtime 一致。

第二次及以后同步（用户的实际"日常"场景）：
- 未变更文件：size 一致 + mtime 容差内 → 走 `result.skipped`，**不调用 `transfer_manager.submit_*`**
- 由于不进入提交流程，`task_added` 信号不会触发，`TransferTaskRow` 不会被创建 → UI 主线程零额外负载
- 仅真正修改/新增的文件会产生传输任务，UI 上自然只显示新增任务

由此从根本上消除了卡顿。

### v1.0.10 详细变更（2026-05-04）

#### 背景

用户反馈：在 Wayland 桌面下打开应用，**无法切换中文输入法**（fcitx5）。要求兼容 Wayland / X11 / Windows / macOS 四种打包目标。

#### 根因分析

通过 `ls venv/lib*/python*/site-packages/PySide6/Qt/plugins/platforminputcontexts/` 看到 PySide6 自带的 IM 桥接插件**不包含 fcitx**：

```text
libcomposeplatforminputcontextplugin.so      ← X11 Compose key
libibusplatforminputcontextplugin.so          ← IBus（OK）
libqtvirtualkeyboardplugin.so                 ← 虚拟键盘
（没有 fcitx 插件）
```

而用户环境是：

```text
WAYLAND_DISPLAY=wayland-0
XDG_SESSION_TYPE=wayland
QT_IM_MODULE=fcitx
GTK_IM_MODULE=fcitx
XMODIFIERS=@im=fcitx
```

shell 里 `QT_IM_MODULE=fcitx` 被 Qt 读到，但 PySide6 venv 找不到 fcitx 插件 → 退化到无 IM → 中文输入法死活调不出来。

要彻底解决又不依赖系统级 fcitx5-qt6（用户的桌面端要 PyInstaller 自包含分发），最稳的做法是在 Wayland 下切到 `QT_IM_MODULE=wayland`，让 Qt 6 的内置 wayland IM 模块走 `text-input-v3` 协议直接对接 fcitx5 / ibus 的 wayland frontend。Qt 6 内置不需要任何插件，跨平台稳定。

#### 本次修改

##### 新增 `src/utils/input_method.py`

提供 `setup_input_method()` 函数，必须在 `QApplication` 之前调用：

- `_pyside_im_plugins()` 扫描 PySide6 venv 自带的 platforminputcontexts/ 目录，返回插件名称集合（如 `{"ibus", "compose", "qtvirtualkeyboardplugin"}`）。文件名后缀按 Linux/.so / Windows/.dll / macOS/.dylib 三种格式都识别

- `setup_input_method()` 决策路径：
  1. 非 Linux（Windows/macOS）→ 直接 return，使用系统原生 IME
  2. 当前 `QT_IM_MODULE` 在 PySide6 中可用 → 保留不动（含特例：`wayland` 是 Qt 6 内置）

     - Wayland 会话 → 强制设 `QT_IM_MODULE=wayland`
     - X11 + ibus 守护进程在跑 + ibus 插件可用 → 设 `QT_IM_MODULE=ibus`
     - 都不命中 → 仅打 warning 日志，保留用户原值

- **macOS**：原生 IME 不依赖 Qt 插件，无需任何配置；本项目暂未在 macOS 验证，但代码路径已经 `if not sys.platform.startswith("linux"): return` 早早分流
