# v1.5.0 桌面端开发记录：界面迁移到 Web UI（Qt WebEngine）+ 同步 / 传输 / 托盘

> 本版本桌面端**界面层整体重做**：从 Qt Widgets（PySide6 + PySide6-Fluent-Widgets）
> 迁移到 **Web UI**（QtWebEngine 渲染前端工程 `ui/`，与 Web 端同一套界面），
> 同时**保留全部原生能力**（托盘 / 本地解码的媒体预览 / 原生文件对话框 / 拖放上传 / 后台同步与传输引擎）。
>
> 配套文档：`plans/desktop-webui-migration-v1.5.0.md`（逐节点交付与证据）、
> `.claude/skills/LESSONS.md` L34–L40（本次沉淀的 7 条跨模块教训）。

## 一、变更概述

### 1.1 架构：Qt Widgets → 原生外壳 + Web UI

| 层 | v1.4.2 | v1.5.0 |
| --- | --- | --- |
| 界面 | Qt Widgets 页面（`src/ui/pages/*`）+ 自绘 kit | **前端工程 `ui/`**（React + TS + Vite + Tailwind，从 Web 端快照后独立演进） |
| 渲染 | Qt 直接绘制 | **QtWebEngine** 渲染，无边框窗口 + Web 自绘标题栏 |
| 与 Python 通信 | 直接调用服务层 | **桥**（`src/bridge/bridge.py`，白名单分发 + 主线程方法集合） |
| 原生外壳 | `main_window.py` / `login_window.py` | `src/ui/web_shell.py` / `tray.py` / `media_overlay.py` |

**关键不变量（已写入 AGENTS.md §9.6 安全宪法）**：
渲染层（JS）**无网络出口**，一切通信只经白名单桥；**文件字节与密钥严禁进入渲染层** ——
上传/下载/预览都在 Python 侧完成，媒体由 `StreamProxy` 解密后交给 **OS 解码器**。

### 1.2 交付的页面（按菜单粒度逐节点交付）

- **N7 文件管理**：磁盘列表 → 目录浏览（面包屑/排序/搜索/分页）、上传、下载、新建目录、
  重命名、移动、删除、**右键上下文菜单**（含媒体文件的「修复损坏媒体」）、**预览**（文本/Markdown/Mermaid、图片、音视频）
- **N8 笔记管理**：列表 + 编辑器 + 预览（**Mermaid 图表真实渲染**）
- **N9 同步管理**（Web 端为降级说明页，此页按**原桌面端**实现）：规则 CRUD、远端目录选择、立即同步、启停、状态

### 1.3 原生能力的保留方式

| 能力 | 实现 |
| --- | --- |
| 媒体预览（**不使用浏览器解码**） | `StreamProxy`（本地解密 + Range 206）→ `QMediaPlayer`（Windows: Media Foundation / Linux: GStreamer）；图片走 Qt 原生解码 |
| 媒体画面如何进 Web 界面 | **独立顶层原生窗口**（`media_overlay.py`）贴在页面预留矩形上，见 §三.1 |
| 文件上传/下载 | **原生文件对话框** + Python 侧分片/哈希/加密/解密落盘 |
| 拖放上传 | `DropAwareWebView.dropEvent` 读 `QMimeData.urls()`（浏览器安全模型下渲染层拿不到真实路径）→ 桥推 `dnd.files_dropped` |
| 同步 / 传输 | 复用原桌面端 `sync_service` + `sync_engine` / `transfer_manager`，经桥暴露 |

## 三、关键设计取舍

### 3.1 媒体画面用「独立顶层原生窗口」贴在 Web 预留矩形上（P0-4 实测）

**为什么不用 `<video>` / `<img>`**：Chromium 内置解码器格式受限（mkv/avi/HEVC/FLAC 常放不出），
而 OS 解码器兼容性强得多；用户明确要求"解码能力吊起本地解码"。

**实测结论**（`poc/media-overlay/`，12/12 断言）：

| 验证点 | 结果 |
| --- | --- |
| 贴合精度（本机 dpr=**1.25**） | 浮层 `(372,130,480,270)` vs 期望 `(372,129,480,270)` —— 误差 **1px（舍入）** |
| 是否需要 dpr 换算 | **不需要** —— Chromium 的 CSS 像素与 Qt 设备无关像素一一对应 |
| 窗口移动 / 缩放 / 页面滚动 | 全部精确跟随；尺寸恒等于预留矩形 |
| 滚出视口 | 浮层**自动隐藏**，不留残影 |

### 3.2 为什么必须有「GUI 线程方法集合」

`QFileDialog` / `QVideoWidget` / `QMediaPlayer` / `QSystemTrayIcon` **只能在 GUI 线程创建**，
而桥默认把方法派发到工作线程。因此登记 `MAIN_THREAD_METHODS`（`dialogs.*` / `media.*` /
`sync.{run,reload,status}` / `transfer.*`），由桥在主线程内联执行（模态对话框本就阻塞界面）。
**阻塞 I/O 仍留在工作线程**（如 `files.write_temp`），避免卡界面。

### 3.3 前端工程用「一次性快照 + 独立演进」

`jflove-web/src` 的页面（含组件与样式）复制到 `jflove-desktop/ui/src` 后**独立演进**，
`jflove-web` 零改动。由此带来两类必要差异：

1. **`file://` 下的三个坑**：hash 路由（无 SPA fallback）、静态资源相对路径（`base: './'`）、
   mermaid 离线包**必须用相对路径**（原来写死 `/vendor/...` 会解析到文件系统根）
2. **平台差异收敛在服务层/Hook**：`file-service.ts` 重写为薄封装（不在渲染层做加密与字节处理）、
   `use-files.ts` 改用原生对话框与桥上传下载

### 3.4 托盘菜单不使用二级子菜单

PySide6 6.11 实测：`menu.addMenu("主题")` 返回的子菜单**一旦加入 action，其 Python 包装对象即失效**
（`Internal C++ object (QMenu) already deleted`），四种写法全部复现、空子菜单正常 →
主题三项**平铺**在顶层菜单。另：`QSystemTrayIcon.setContextMenu()` **不接管 menu 所有权**，
顶层 `QMenu` 必须由 Python 持有引用。

### 4.2 本版本修复的 BUG（含跨模块）

| # | BUG | 根因 | 影响范围 |
| --- | --- | --- | --- |
| 1 | 「新建目录」点了没反应 | 服务端 `/files/mkdir` 只读 `path`（= 要创建目录的**完整相对路径**），Web 端却发 `{path: 当前目录, dir_name: 名字}` → 服务端把当前目录又建了一遍（静默 200） | **Web 端 + 桌面端**（移动端本来就对） |
| 2 | 右键「删除」请求发出但文件不动 | 服务端路由是 `DELETE /api/v1/files`，Web 端请求 `/api/v1/files/delete`（**404**，被前端当普通响应吞掉） | **Web 端 + 桌面端**（移动端与服务层本来就对） |
| 3 | 视频点击后不播放 | `stream_range(disk_id, path, filename)` 的 `path` 语义是**文件所在目录**，传了文件自身路径 → 拼成 `<file>/<file>` → 服务端 404 → `QMediaPlayer InvalidMedia` | 桌面端 |
| 4 | 从预览返回后列表空白、"滚动一下才出现" | 原生浮层是独立顶层窗口，隐藏后 **Chromium 不会重绘**被遮挡区域（DOM 正常、缺的是像素） | 桌面端 |
| 5 | 上传静默失败 | 服务层 `ProgressCallback = Callable[[int,int,str],None]` 是**三个参数**，回调只写两个 → `TypeError` | 桌面端（我的桥实现） |
| 6 | 免登录恢复后"假装已登录"、随后每个接口都失败 | `try_restore_session()` 只看**本地**过期时间，从不向服务端确认 token 是否仍被接受 | 桌面端 |
| 7 | 媒体页日志被刷屏 | `MediaStage` 每 400ms 无条件上报矩形（即使没变） | 桌面端 |
| 8 | **GitHub Actions Windows 桌面端打包失败**（iscc 编译中止，无安装包 → job 失败） | `build.py` 用 `iscc.parent / "Languages"` 猜中文语言文件位置，CI 上 `iscc` 命中的是 Chocolatey **shim**（`C:\ProgramData\Chocolatey\bin`），与真实编译器目录不同；而 `.iss` 里 `MessagesFile: "compiler:Languages\..."` 的 `compiler:` 由 ISCC 解析为**自身安装目录** → 探测说"在"、编译说"不在" → `[Languages]` 段直接中止 | **构建链路（桌面端打包 / CI）** |

> 第 1、2 条是**照抄另一端的客户端代码时把错误一起继承**的典型 —— 已沉淀为 LESSONS **L34**。
> 两条都已**回修 Web 端**；移动端本来就正确，未改动。

### 4.6 BUG 修复：CI 打包失败（iscc / 简体中文语言文件）〔BUG 修复〕

> 通道：AGENTS.md §7.5.3 快速修复通道（纯代码 BUG，版本号保持 v1.5.0）

**现象**：`build-desktop.yml` 的 Windows job 在 iscc 阶段中止：

```
Error on line 94 in jflove-desktop\packaging\windows\jflove.iss:
Couldn't open include file "c:\program files (x86)\inno setup 6\Languages\ChineseSimplified.isl":
The system cannot find the file specified.   → [build][FATAL] iscc 编译失败，退出码 2
```

**根因（已用本机实验证实）**：

1. `find_chinese_isl()` 只用 `iscc.parent / "Languages" / "ChineseSimplified.isl"` 推断位置；
2. CI 上 `shutil.which("iscc")` 命中的是 Chocolatey **shim**（`C:\ProgramData\Chocolatey\bin\iscc.EXE`），
   于是探测指向 shim 目录下的 `Languages\`——**与真实编译器目录无关**；
3. 探测"看起来命中"就传 `HasChineseIsl=1`，而 `.iss` 当时用
   `MessagesFile: "compiler:Languages\ChineseSimplified.isl"`；
4. **`compiler:` 由 ISCC 解析为其自身安装目录**（本机实验：把 `ISCC.exe` 复制到临时目录后，
   `compiler:Default.isl` 只认该临时目录 → 证明与 PATH/shim 无关）→ 该目录无此文件 → 编译中止。

**修复**：

| 改动 | 内容 |
| --- | --- |
| **内置语言文件** | 新增 `packaging/windows/Languages/ChineseSimplified.isl`（Inno 6.5.0+ 版，UTF-8，SHA256 `E0B0B350…9A8D`）+ `README.md` 说明来源/许可（Inno 许可明确允许再分发，须保留版权头）/升级方式 |
| **探测顺序** | `JFLOVE_CHINESE_ISL` 环境变量 → **仓库内置副本** → 构建机真实编译器目录（Program Files × Inno Setup 6/5）→ 都没有则 `None` |
| **硬不变式** | 返回值要么是 `is_file()` 为真的路径，要么是 `None`：**不允许"探测说找到、iscc 说打不开"的第三种状态** |
| **`.iss` 解耦** | 改为 `#ifndef IslPath`（默认仓库内置副本，供手工编译）+ `#if FileExists(IslPath)` 兜底；`MessagesFile: "{#IslPath}"`，彻底弃用 `compiler:Languages\...` |
| **传参** | `build.py` 以**正斜杠绝对路径**传 `/DIslPath=…`（反斜杠在 Inno 路径参数里是转义字符）；未命中时不传该参数 + 响亮降级告警 |
| **回归测试** | 新增 `tests/test_build_installer_isl.py`（10 例）：内置文件完整性、探测优先级、环境变量覆盖、**shim 目录假命中反例**、`.iss` 结构护栏 |

**验证证据**（本机实跑，非"应该没问题"）：

- `flake8 src/ tests/ build.py --max-line-length=99` → **0 警告**；`pytest tests/` → **78 passed**（含新增 10 例）
- 本机端到端：`python build.py --mode onedir --installer --zip` → 产出
  `JFLove-1.5.0-win64-setup.exe`（171.5 MB）/ `*-portable.zip`（252.0 MB）/ onedir（666.6 MB），
  日志明确显示 **「简体中文语言文件（仓库内置）：packaging\windows\Languages\ChineseSimplified.isl」**
- iscc 编译 A/B 对照（同一 `.iss`、同一载荷）：传内置中文 `.isl` vs 传不存在的路径（English 兜底）
  → 两者产物**哈希/体积不同**，证明语言文件确实被编入且由我们传入的路径决定
- `#if FileExists(IslPath)` 兜底实测：路径不存在时**不再中止**，退回英文并照常产出安装包
