## 2. T-2 根因（实测，含我走过的弯路）

### 2.1 现象

`min-rows` 用例第④步断言失败：

```
恢复窗口后未回到用户字号：
{"dims":"135×26","font":"⌥ 字号 13→13（自适应）","warn":false}
```

v1.10.22 据此记成「`autoShrunk` 没复位 ⇒ 产品缺陷」。

### 2.2 实测数据（推翻原判）

终端区 **894×552**、字号 13 时，`lineHeight` 与行高的真实关系：

| lineHeight | 行高 | 可容纳行数 | 是否够 `TUI_MIN_ROWS=24` |
| --- | --- | --- | --- |
| **1.25（舒适）** | **25.63px** | **20 行** | ❌ 不够 |
| 1.10 | 22.55px | 23 行 | ❌ 不够 |
| **1.00** | **20.50px** | **26 行** | ✅ 够 |

验收（DOM 实测，与计算一致）：

```json
{"containerH":552,"screenH":533,"renderedRowCount":26,
 "rowHeightMeasured":20.5,"rowsFontSize":"13px","impliedRows":26}
```

⇒ **在 1180×760 窗口下，舒适档根本放不下 24 行，压缩是产品按设计的正确行为。**
要在 1.25 档容纳 24 行，终端区需要 **≥ 615px**。

而 `TUI_MIN_ROWS=24` 这条硬约束来自真机事故（dsh TUI 在 ≤21 行会画丢输入框内容行，
`terminal-prefs.ts` 注释有记录）——**保住 24 行优先于观感**。

### 2.3 我走过的弯路（已全部回滚，留档避免复犯）

| 尝试 | 依据 | 结果 |
| --- | --- | --- |
| ① 加"复测一次" | 怀疑首次测量竞态 | 无效（紧挨着测读到同一份度量） |
| ② 改为下一帧后延迟复测 | 同上 | 无效 |
| ③ 加 `document.fonts.ready` 闸门 | 怀疑字体未就绪导致行高偏大 | 无效（`fonts.status` 早已是 `loaded`） |

插桩证据（第①轮）证明"首次测量 23 行"确实是事实：

```
[FITPROBE] {"w":894,"h":552, ..., "probeRows":[
  {"f":13,"l":1.25,"rows":23},   ← 测试环境里更高一点，仍 < 24
  {"f":13,"l":1.1,"rows":26}],
 "picked":{"fontSize":13,"lineHeight":1.1,"rows":26,"compacted":true}}
```

**但这恰好说明产品是对的**：23 < 24，就该往下压。
我把它当成"测量竞态"是**误判**——真正的错误在**用例要求"恢复后不得出现自适应"**。

### 2.4 修复

**产品代码零改动**（`TerminalView.tsx` 已 `git checkout` 回 v1.10.22 状态）。

改 e2e（`scripts/verify/desktop_terminal_e2e.mjs`）：

1. `caseMinRows` 第④步断言改为**只要求行数 ≥24 且不比压缩档更差**，不再要求"不出现自适应"；
   注释里写清 615px 这个阈值的来历，防止后人again 误判；
2. **新增 `caseMinRowsDirection`**：验证**两个方向**——
   - 超高窗口（1200×1100，终端区足够）⇒ **必须**回舒适档（不显示「自适应」）；
   - 压到偏矮（900×620）⇒ 允许压缩，但**行数必须 ≥24**。
   这样既拦住"该恢复不恢复"，也拦住"矮窗口也硬用大行高"。

## 3. T-3 根因与修复

`ui/src/utils/clipboard.ts::copyText` 旧实现：

```js
if (await writeThroughBridge(text)) return true;   // 桥
const api = navigator.clipboard?.writeText?.(text); // 浏览器 API + 500ms 超时
...
```

QtWebEngine 里浏览器剪贴板 API **永久 pending**（`readText` 已实测 3 秒无响应），
所以这条路一旦走到就必然白等 `CLIPBOARD_TIMEOUT_MS=500ms`。

修复（与 `readClipboardText` 同构）：

```js
const bridgeReady = isBridgeReady();
if (bridgeReady && (await writeThroughBridge(text))) return true;   // 桥就绪 ⇒ 先且只用桥
const api = navigator.clipboard?.writeText?.(text);                 // 仅在桥不可用/失败时兜底
if (api) { const r = await withTimeout(api.then(() => true), CLIPBOARD_TIMEOUT_MS); if (r === true) return true; }
// 最后退 textarea + execCommand
```

## 7. 设计取舍

1. **为什么不改产品、只改用例**：`TUI_MIN_ROWS=24` 是硬约束（dsh 会画丢），
   在 552px 的终端区里 1.25 档只能放 20 行，压缩是唯一正确选择。
   把"恢复后必须不出现自适应"写进断言，等于要求产品**违反自己的核心约束**。
2. **为什么新增方向性用例而不是删掉旧断言**：只删会失去覆盖；
   改成"两个方向各自有明确判据"才能既防"该恢复不恢复"、又防"矮窗口硬撑大行高"。
3. **为什么 `copyText` 不干脆删掉浏览器兜底**：`ui/` 也会在普通浏览器（`npm run dev`）里跑，
   那里没有桥，浏览器 API 是**唯一**可用路径，必须保留。
