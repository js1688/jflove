## 一、功能与改动点（逐条对应 issue）

### 1.1 改动 A —— #3 原生媒体浮层生命周期 + 几何同步

**用户现象**（issue #3）：

1. 播放视频时**直接关闭窗体**，视频播放器"还会停留在原地"（画面残留在屏幕上）；
2. **拖拽时**播放框不随主框移动 —— 拖拽后播放内容消失，但**音频继续播放**。

**两处根因**（设计文档 §5.1 的 E10~E12 取证，本角色已逐条复核）：

| # | 根因 | 位置 |
|---|------|------|
| 根因 1 | 浮层是**独立顶层窗口**（`Qt.Tool | FramelessWindowHint`），不随主窗隐藏；`WebShell.hide_to_tray()` 只 `self.hide()`，全仓没有任何地方隐藏浮层 | `src/ui/web_shell.py:407`（改前 `:340`）、`src/ui/media_overlay.py:54` |
| 根因 2 | 浮层几何**只**由渲染层 `setRect()` 驱动；主窗移动时"视口内的 rect"根本没变，渲染层没有"主窗移动"这个事件、不会重新上报；全仓 `moveEvent`/`resizeEvent` **零命中**，无人重算屏幕坐标 | `src/ui/media_overlay.py:143`（`setRect`）、改前 `src/ui/web_shell.py` 无几何事件 |

**修复方式（对照设计文档 §5.2）**：

1. `MediaOverlay` 新增两个**主线程**方法（详 §三）；
2. `WebShell` 新增 `attach_overlay()` / `moveEvent` / `resizeEvent` / `showEvent` /
   `_schedule_overlay_refresh()` / `_on_overlay_refresh()`，并在 `hide_to_tray()` 里联动浮层；
3. `src/main.py` 在创建浮层后加一行 `_shell.attach_overlay(overlay)`。

**关键设计点**：

- **不引入定时轮询**（需求 §3 性能要求）：只在真实几何事件上触发；
- `QTimer.singleShot(0, ...)` + pending 标志把一次拖动产生的**连续事件合并成一次刷新**
  （延迟一帧还顺带解决"拖动中 `mapToGlobal` 拿到未生效坐标"的抖动）；
- **不做 dpr 换算**：复用既有 `_apply_geometry()` 与"CSS 像素 == Qt 逻辑像素"口径
  （`LESSONS.md` L33 的区间口径纪律；浮层模块文档已实测 dpr=1.25 下误差仅 1px 舍入）；
- **依赖方向不反转**：`web_shell` **不 import** `media_overlay`，只用鸭子类型持有引用
  （`main.py` 负责装配）。

### 1.2 改动 B —— #2 删除「允许重编码降级」僵尸开关

**为什么以服务端契约为准**（不改后端、也不给 Web 端加开关）：

服务端 `jflove-server/src/services/media_repair_service.py:11-13` 原文：

> 历史配置键已废弃（media_repair_enabled 实时修复总开关、
> media_repair_allow_transcode 重编码子开关）：键保留在库中不删，
> 但**任何代码不再读取**，播放与修复行为均不受其影响（v1.4.2 hotfix）。

即：桌面端这个开关**拨了没有任何效果**（失效 UI）。issue #2 的字面诉求是"Web 端少了这个开关"，
若照字面在 Web 端补一个 —— 就等于把两端**一起对齐到一个失效交互**上（`LESSONS.md` **L34**：
"抄另一个端的客户端代码前，必须对着服务端契约逐项核对"，客户端之间的不一致会把错误互相传染）。
需求文档 §4 决策 **D2** 与设计文档 §3.1/§3.2 已裁定：**以服务端契约为准，删桌面端开关，Web 端不加**。

**本次收敛结果**：两端系统设置页的可见配置项集合一致 —— **仅「修复并发数」一项**（AC-5）。
服务端配置键 `media_repair_allow_transcode` **保留在库中不删**（本次不动后端，AC-17）。

## 五、设计取舍

### 5.1 为什么复用 `_apply_geometry()` 而不再写一套（#3）

`_apply_geometry()` 已经承载了本项目**唯一**的坐标口径（`view.mapToGlobal(QPoint(x, y))` +
`QSize(w, h)`，不做 dpr 换算，已在 dpr=1.25 实测误差 1px）。再写一套"刷新用"的坐标计算，
就会像 `LESSONS.md` L33 那样出现**两套区间/口径**，表现为"看着对、量着错"。
因此 `refresh_geometry()` 只是"**外部触发的一次 `_apply_geometry()`**"。

### 5.2 关窗后恢复：为什么必须"重新显示"，以及**为什么恢复分支要排在全屏判断之前**

最初实现按设计文档 §5.2.1 的第三条早退写了"`window.isVisible()` 为假则返回"。写回归用例时发现：
`on_shell_hidden()` 把浮层 `hide()` 之后，**从托盘恢复窗口**时 `showEvent` 触发的
`refresh_geometry()` 会被这条早退拦住 ⇒ `_rect` 还在、浮层却**再也不出现**（"只剩音频"的新 BUG）。

第一版修法是把"恢复"分支放在 `_rect` 检查之后、**全屏早退之前** —— 这仍然有洞：
全屏态下 `_fullscreen` 为真，若恢复分支被排在它后面，**全屏 + 关窗 → 恢复**依旧永久不显示。
**Phase 5 前置审查**（编排者读 diff）抓出了这个洞，本角色已修：**恢复分支必须是第一条判断**，
且全屏态要用 `showFullScreen()` 恢复（不得降级成 `_rect` 小矩形）。

修正后的顺序（`refresh_geometry()`，`:262-284`）：

```python
if self._shell_hidden:                      # 0) 恢复分支 —— 必须最先判定
    self._shell_hidden = False
    if self._fullscreen:
        self.window.showFullScreen()        # 全屏态恢复：仍铺满屏幕
        return
    if not self._rect or not self._rect.get("visible", True):
        return
    self._apply_geometry()
    if not self.window.isVisible():
        self.window.show(); self.window.raise_()
    return
if self._fullscreen:                        # 1) 全屏早退（拖动/缩放时不得拉回小矩形）
    return
rect = self._rect                           # 2) 空矩形早退
if not rect:
    return
if not rect.get("visible", True):            # 3) 渲染层声明不可见早退
    return
self._apply_geometry()
```

**顺序即正确性**：这三条早退与"恢复"分支存在**优先级冲突**，写反就会出现"某一条永久路径不显示"。
用例 `test_全屏态关窗后恢复仍以全屏方式显示` / `test_全屏态关窗恢复时不降级为小矩形`
把这条顺序钉死（负向对照 6/7 证明：把它排到全屏早退之后就必红）。

### 5.2.2 该分支与其他状态的交互

- **不引入轮询**：恢复只在"几何事件真的到来时"发生（`showEvent` 或拖动/缩放排队）；
- **"渲染层声明 `visible=false`" 的优先级要分两条路径看**（2026-10-10 编排者核实更正，原文曾写成"`_rect["visible"]` 一律优先"，与代码方向不符）：
  - **非全屏路径**：尊重渲染层 —— `if not self._rect or not self._rect.get("visible", True): return`（保持 `_shell_hidden=True` 等下一次有效上报）；
  - **全屏路径**：**忽略** `visible=false`，直接 `showFullScreen()` —— 口径是"全屏是用户的**显式意图**，布局信号（滚出视口）不得把全屏拉回"。
  - 依据：`media_overlay.py:329-333`（全屏分支，未判 `visible`）vs `:334-337`（非全屏分支，判 `visible`）。该优先级已登记为待用户裁决项（`R5-T3` / AC-14b），若裁定相反，改动仅限 `:329` 前后的一个条件；
- **`open()` 复位 `_shell_hidden`**（`media_overlay.py:109`）：用户显式打开预览时，
  无论主窗此前是否隐藏过，浮层都该正常显示（`open()` 自己会 `show()`），
  避免"关窗期间关掉预览"留下陈旧状态；
- **`close()` 的场景**：`_rect` 被清空 ⇒ 恢复分支第 2 条早退 ⇒ 浮层不会被凭空弹出
  （用例 `test_矩形被清空后不重新显示`）。

### 5.2.3 主窗隐藏期间不得排队几何事件（Phase 5 审查抓出的第二个缺陷）

`hide_to_tray()` 隐藏主窗的过程中，平台仍可能投递 `moveEvent` / `resizeEvent`
（或任何被 `singleShot` 延迟到事件循环之后的几何事件）。若照常排队，回调会走到
`refresh_geometry()` 的"恢复"分支 ⇒ **立刻把刚隐藏的浮层又摆回屏幕上**，
#3 的修复在真机上等于失效（"关窗残留"原样复现）。

护栏（`_schedule_overlay_refresh()`，`web_shell.py:285-291`）：

```python
if (
    self._overlay is None
    or self._overlay_refresh_pending
    or not self.isVisible()      # ← 主窗不可见时不排队
):
    return
```

- `showEvent` 里的那次**直接调用**不受影响 —— 那时主窗已可见，正是"从托盘恢复"的路径；
- 该护栏只拦"排队"这一条路，不改变"主窗可见时同帧合并"的语义（用例双向锁住：
  `test_主窗不可见时几何事件不触发重贴合` 断言 0 次、
  `test_同一帧内多次调度只调用一次_主窗可见` 断言 1 次）。

### 5.3 为什么 `showEvent` 也调一次 `refresh_geometry()`

设计文档 §5.2.2 建议项。理由：托盘"显示窗口"走 `restore_from_tray()`，它只 `showNormal()`；
浮层需要在**窗口真正可见之后**才取得到正确的 `mapToGlobal` 基准。放在 `showEvent` 里正好。

### 5.4 为什么浮层联动挂在 `hide_to_tray()` 一处

标题栏 ✕（`ShellControls.close`）与系统关闭（`closeEvent` 的普通关闭分支）**两条路径最终都走
`hide_to_tray()`**，所以只需在这一处补挂，不必在 3 个地方各写一遍（设计文档 §5.2.2）。
退出应用（托盘「退出」→ `quit_application()`）路径**保持不变**：进程直接退出，无需先隐藏浮层。

### 5.5 为什么 `_schedule_overlay_refresh()` 用 `QTimer.singleShot(0, ...)` 而不是立即刷新

两个理由（都是实测教训驱动）：

1. **性能/观感**：一次拖动会连发几十个 `moveEvent`，逐次刷新会让浮层抖动；
2. **正确性**：Windows 拖动期间 `moveEvent` 可能早于窗口几何真正生效，此时 `mapToGlobal`
   拿到的是**旧坐标**（表现为画面滞后一格）。延迟到当前事件循环之后再取坐标即可拿到最终几何。

> ⚠ 第 2 点的效果**无法在无头环境验证**，列为待人工验证项（§八）。

### 5.6 为什么删开关而不是给 Web 端加开关

见 §1.2。一句话：**服务端契约是唯一真相**，两端 UI 应向契约收敛，而不是互相抄
（设计文档 §3.1 引 `LESSONS.md` L34；需求文档 §4 决策 D2）。

### 5.7 本次刻意**不**做的事

- 不动 `src/bridge/media.py` 的任何桥方法名/参数/事件名 —— 渲染层（JS）**零改动**；
- 不改 `src/components/stream_proxy.py`、不改任何加密/HTTP 代码（`AGENTS.md §9`）；
- 不清理数据库中已废弃的配置键（服务端明确"保留在库中不删"）；
- 不改 `jflove-desktop/ui/src/pages/NoteEditPage.tsx`（同源同步由编排者按字节复制，见 §7）；
- 不删 PoC 里通用的 `switchState()` / `toggleSwitch()` JS 助手（属通用工具，非本开关专属；
  本次只**新增**了一个 `switchCount()` 用于"开关不存在"断言）。

### 12.2 修法（`src/utils/http_client.py`）

1. **新增模块级 `_is_envelope(body) -> bool`**：**只判形状**（`dict` 且同时含 `nonce` 与 `ciphertext`）。
   为什么要独立判形状：把"不是信封"与"是信封但解不开"混为一谈正是缺陷根源。
2. **`_parse_response()`**（判据顺序：先判形状，再看解密结果）：
   - 不是信封 → **明文直返**（`admin-exists` / `health` 等明文白名单照旧）；
   - 是信封且解开了 → 返回解密后的 dict；
   - **是信封但解不开 → 抛 `ApiError(502, "响应解密失败（会话密钥不匹配或响应被篡改）"）`**，
     **绝不**回退成明文外壳。
3. **`_extract_error_detail()` 对齐口径**：是信封但解不开 → 明确文案，
   **不**静默退化成 `resp.text`（否则会把 `{"nonce":…,"ciphertext":…}` 当错误信息展示给用户）。
4. **`_handle_stream_error()` 同步对齐**（同类静默降级点，顺带收敛，避免留第二处同类洞）。
5. **`_decrypt_envelope_or_none()` docstring 补警告**：返回值 `None` 有**两种**含义，
   调用方不能只判 `is not None`。
