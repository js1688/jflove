# v1.4.1 桌面端开发记录：time 修复流时长与 seek 修复

## 一、变更概述

桌面端 time 修复流（服务端 ffmpeg 实时生成的 fMP4）存在两个问题：

| 编号 | 现象 | 根因 | 修复 |
|------|------|------|------|
| BUG-10a | 无总时长、进度条范围 0-0 | empty_moov 流式的 fMP4 mvhd duration=0，QMediaPlayer 拿不到时长 | 服务端改写 mvhd duration（见后端开发记录）；桌面端无需改 UI |
| BUG-10b | 拖拽进度条无效 | time 模式 HEAD 不声明 `Accept-Ranges`，QMediaPlayer 认为不可 seek | HEAD 始终声明 `Accept-Ranges: bytes`，QMediaPlayer seek 发 Range → StreamProxy 线性映射时间 → 服务端 -ss 重拉 |

## 二、详细变更

| 文件 | 变更类型 | 说明 |
|------|---------|------|
| `src/components/stream_proxy.py` | 修改 | `do_HEAD` 对 time 模式也声明 `Accept-Ranges: bytes` |
| `build.py` / `src/config/settings.py` | 修改 | 版本号 1.4.0 → 1.4.1 |

### 2.1 `do_HEAD` 声明 Accept-Ranges

- 原：time 模式不声明 `Accept-Ranges`，让播放器按顺序流式播放（不支持 seek）。
- 现：time 模式也声明 `Accept-Ranges: bytes`，QMediaPlayer 据此认为可 seek，
  拖拽进度条时发字节 Range；`do_GET` 的 time 分支已有线性映射逻辑
  （`range_start / file_size * duration` → `range_start_seconds`），服务端 `-ss` 重拉。

### 2.2 总时长（服务端配合）

- 服务端 `media_probe.patch_mvhd_duration` 改写 fMP4 moov/mvhd 的 duration 字段，
  QMediaPlayer 从容器直接拿到总时长，`durationChanged` 正常触发 → 进度条范围正确。
- 桌面端 UI 无需改动（`_MediaView._on_duration_changed` 已监听 durationChanged）。

## 三、已知限制

- time 修复流 seek 后，服务端 `-ss T` 输出的新流时间戳归零（copy 模式无法保留绝对
  时间戳），QMediaPlayer 的 position 从 0 开始、duration 变为剩余时长。这是 HTTP
  Range seek + 实时转码的固有限制，与 Web 端修复前的表现一致（Web 端用 MSE 的
  `timestampOffset` 解决了，QMediaPlayer 无等价能力）。

### BUG 修复（2026-08-24 发布构建时）

> 标签：BUG 修复（测试用例过时）

- **现象**：发布构建时 pytest 报 1 失败 `test_proxy_url包含token路径`：
  断言 `url.split("/")[-1]` 长度应为 32，实际收到 `{uuid}?v=0`（长度 36）。
- **根因**：v1.4.1 seek 机制给 `proxy.url` 追加了 `?v={_seek_version}` query（用于
  强制 QMediaPlayer 重新拉流），但该测试用例未同步，仍按纯 32 位 token 断言。
- **修复**：`tests/test_stream_proxy.py` 解析 token 时剥离 `?v=` query，并新增断言
  校验 URL 携带 seek 版本号。实现无需改动。
