# 桌面端 v1.10.14（远程连接：旧服务器 SSH 算法兼容）

> 分类：**代码 BUG ×2**（`AGENTS.md §7.5.3` 快速修复通道；用户指定小版本迭代 `v1.10.14`）
> 来源：用户 2026-11-19 实机反馈两条
> 计划：`plans/desktop-remote-legacy-ssh-v1.10.14.md`
> 影响模块：仅 `jflove-desktop/`（服务端 / 数据库 / 加密协议不改）

## 1. 用户现象与根因

### P1：`Incompatible ssh peer (no acceptable host key)`

| 项 | 内容 |
| --- | --- |
| 现象 | 连接 `sfile2.trusted.visa.com` 报「目标 … 连接失败：Incompatible ssh peer (no acceptable host key）」 |
| 根因 | 当前依赖 `paramiko==5.1.0`。paramiko **5.0.0** 移除了 `ssh-rsa` 主机密钥/RSA-SHA1 签名与全部 SHA-1 KEX（上游 changelog 原文警告「旧系统不兼容」）。旧 SFTP 网关只提供 `ssh-rsa` 主机密钥，客户端 `Transport.start_client()` 在 KEXINIT 阶段找不到交集，直接抛该错误（`src/services/ssh_session.py` 原 `open()` 只把英文异常原样拼进 `JumpError`） |
| 修复 | `requirements.txt` 固定 `paramiko==4.0.0`（上游最后保留 `ssh-rsa`/SHA-1 KEX 的版本；4.0 仅移除 DSA，5.0 才移除 SHA-1）；仍支持 Ed25519/ECDSA/rsa-sha2，默认顺序现代在前 |

### P2：`服务器要求密钥认证（服务器允许：publickey），请检查私钥与认证方式`

| 项 | 内容 |
| --- | --- |
| 现象 | 服务器只允许 `publickey` 时认证失败，提示无法区分「认证方式选错」与「私钥被拒」 |
| 根因 A | 旧服务器只接受 `ssh-rsa`（RSA-SHA1）签名，且可能不发 `server-sig-algs`；paramiko 4.x 在没有扩展时默认选 `rsa-sha2-512`，旧服务器拒绝 ⇒ 落到原 `_auth_hint` 的笼统文案 |
| 根因 B | 用户若配置成「密码」认证而服务器只允许 `publickey`，`BadAuthenticationType.allowed_types=["publickey"]` 同样落到该笼统文案，未告诉用户改认证方式 |
| 修复 | ① 增加**旧式 RSA 回退**：仅真实 `paramiko.Transport` + RSA 私钥 + 首次 `publickey` 返回 `failed` + 服务器未声明只支持 SHA-2 时，临时把 `_preferred_pubkeys` 置为 `("ssh-rsa",)` 再试一次，结束恢复；现代服务器首次成功，不触发。② `_auth_hint` 增加 `auth_type` / `key_type` 上下文，区分「认证方式选错」与「私钥被拒」，提示改认证方式或核对 `authorized_keys` / 口令 / RSA 类型。③ `no acceptable host key` / `no acceptable kex algorithm` 翻成中文并说明旧服务器限制 |

## 2. 新旧兼容说明（用户重点关切）

| 服务器类型 | 首次协商算法 | 结果 |
| --- | --- | --- |
| 现代（Ed25519/ECDSA 主机密钥，rsa-sha2 公钥） | 现代算法（优先级未变） | 原行为，首次认证即成功；**不触发回退** |
| 旧式（仅 `ssh-rsa` 主机密钥） | `ssh-rsa` + `diffie-hellman-group14-sha1`（仅当服务器只支持时） | 4.0.0 可正常握手 |
| 旧式（只认 RSA-SHA1 签名，不发 `server-sig-algs`） | 首轮 `rsa-sha2-512` → 失败 → `ssh-rsa` 重试 | 认证成功 |
| 只支持 `ssh-dss`（DSA） | 无 | **仍不支持**（paramiko 4.0 已移除 DSA；需服务器升级到 RSA/Ed25519），错误文案已说明 |

### 真实 paramiko 服务证据（新增用例）

- **旧服务器**（仅 `ssh-rsa` 主机密钥 + 仅 `ssh-rsa` 公钥算法）：`SshSession.open()` 成功，
  `get_remote_server_key().get_name() == "ssh-rsa"`，`is_authenticated() == True`。
- **旧签名回退**（服务端保留算法列表但拒绝 `rsa-sha2` 签名；客户端清空 `server-sig-algs`）：
  首轮失败后 `_attempt_legacy_rsa` 被调用，最终认证成功，调用记录 `["ssh-rsa"]`。
- **现代服务器回归**（ECDSA 主机密钥、默认算法）：认证成功，主机密钥类型
  `ecdsa-sha2-*`，证明现代连接不受影响。

## 5. 已知边界

- 只支持 `ssh-dss`（DSA）的服务器仍不支持（paramiko 4.0 已移除 DSA，上游建议改用 3.x；
  本产品不引入更旧依赖）；错误提示会说明。
- 回退依赖 paramiko 私有属性 `Transport._preferred_pubkeys`；已用依赖 pin + 能力断言测试锁定，
  升级 paramiko 必须先跑 `test_remote_legacy_ssh_v1_10_14.py`。
- 主机密钥 TOFU、跳板链、SFTP 超时、多因素认证状态机均未改动。

## 6. 后续

- 用户需用 v1.10.14 安装包复验 `sfile2.trusted.visa.com`；若仍失败，日志会输出
  `SSH 协商完成：远端=… 主机密钥=… KEX=…` 与认证方法，可据此判断是 DSA-only 还是凭据问题。
