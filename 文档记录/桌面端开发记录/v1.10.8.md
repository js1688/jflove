# v1.10.8 桌面端开发记录：终端底座重建（TUI 输入卡死 / 切标签空白 / 观感重做）

> 版本：v1.10.8　角色：cross-platform-desktop　类型：**代码缺陷 + 体验缺陷**（`AGENTS.md §7.5`）
> 基线：`文档记录/需求文档/v1.10.0.md` §本机终端 / 远程终端、`文档记录/设计文档/v1.10.0.md` §3.4 §3.7
> 触发：用户 Linux 真机（Fedora，桌面端 1.10.7）实测——
> ① 本机终端里跑 `dsh cli`（TUI）后**无法输入、画面像卡住**；
> ② 多标签来回切换，**切回来面板是空的**；
> ③ 终端面板观感差；并要求"复杂命令 / 英文 / 中文输入都要实机验证"。
> 关联计划：`plans/desktop-terminal-base-v1.10.8.md`

## 1. 现象与根因（全部真机复现，非推断）

| # | 用户现象 | 根因 | 取证 |
| --- | --- | --- | --- |
| R1 | `dsh cli` 启动后输入无反应、"卡住" | **xterm.js 6.0.0 生产构建**的 `InputHandler.requestMode()` 里 `const enum` 被编译成 `(k=>…)(void 0\|\|(r={}))`，`r` 未声明 ⇒ 任何 **DECRQM**（`CSI ? m $ p`）都抛 `ReferenceError: r is not defined`。dsh TUI 每帧都发 `\x1b[?1049$p` | CDP 控制台异常栈 `KB.requestMode → FB.parse → GB._innerWrite`；`ui/dist/assets/index-*.js` 全文只有 1 处该坏 IIFE |
| R2 | 抛一次异常后**永久**卡死（不是丢一帧） | xterm `WriteBuffer._innerWrite()` 对解析异常**无兜底**：`_bufferOffset` 不前进，且不会再有新的 `_innerWrite` 被调度；后续 `write()` 见 buffer 非空直接入队 | `ui/node_modules/@xterm/xterm/src/common/input/WriteBuffer.ts` L186-210；日志侧可见 TUI 仍在 `feed()` 输出，但屏幕零变化（像素 diff 只有光标闪烁） |
| R3 | TUI 无配色、界面"土" | 宿主 GUI 会话 `TERM=dumb`，本机终端把 `os.environ` 原样传给 shell | `/proc/<tui pid>/environ` = `TERM=dumb`；显式 `TERM=xterm-256color` 后配色恢复（截图 `11-dsh-term.png`） |
| R4 | 标签切回空白 | `SessionPage` 只渲染 `activeTab` 的 `<TerminalView>`：切走即卸载 → WS 关闭、xterm 销毁；切回重建的新终端没有历史。日志里标签切换成对出现"通道已断开/已连接" | 旧 `ui/src/pages/remote/SessionPage.tsx` L222-241；`/home/tanjun/.local/share/JFLove/logs/app.log` 22:48–22:49 段 |
| R5 | `Ctrl+C` 不产生 SIGINT（隐患，本轮一并修） | POSIX 本机 PTY 只 `preexec_fn=os.setsid`，没 `TIOCSCTTY` ⇒ 子进程没有控制终端、没有前台进程组，行规程不产生 SIGINT/SIGTSTP | 修复前 `stty size` 能用但 `ps -o tpgid` 为 -1；修复后正常（见 §4 用例） |

### 1.1 一个必须记下来的"反直觉"结论

`TERM=dumb` **不是**输入卡死的原因（裸 PTY 里 `TERM=dumb` 也能正常收键）。
真正的输入链路在 R1/R2：**字节一直有写进 PTY**（本轮加了临时 `TERMTRACE` 取证：
`h e l l o` 逐字节写入 fd 124），TUI 也把回显帧写回来了（`TERMOUTTRACE` 可见 44~77B/键），
**是渲染层把帧丢了**。所以"无法输入"其实是"画面永不更新"。

### 1.2 第二个反直觉结论：回放历史输出是错的

为了让"切标签回来不空白"，第一版实现让 Python 侧保留 256KB 输出、重连时回放。
真机验证发现：**回放 TUI 的输出会让终端重新应答 TUI 的能力查询**（DA1 / OSC 10 / OSC 11），
这些应答作为输入进了 shell，被回显成满屏垃圾（截图里成片的
`]R2;276;0c10;rgb:e6e6/…11;rgb:0b0b/…`），并继续污染回放缓冲。

最终方案改为**不销毁实例**：xterm + WebSocket 挂在模块级注册表，路由切换只摘/挂 DOM。
回放路径整条删除（`TerminalHost` 里不再有 `_replay` / `snapshot`）。

### 2.3 关键设计取舍

- **为什么用实例注册表而不是 keep-alive 路由**：不需要改路由架构，且"终端会话的生命周期 = 标签存在的时间"本来就是正确模型。
- **为什么看门狗是"重建 xterm"而不是"重连 WS"**：坏的是渲染端写队列，Python 侧会话与通道都健康。
- **为什么字号/行高改了**：xterm 的单元格高度按字体度量 × `lineHeight` 计算，中文回退字体度量偏大；
  `lineHeight 1.32 → 1.25` + 去掉外层 padding 后，同一窗口从 137×22 变成 135×24。
  **这不只是观感**：dsh TUI 在 21 行及以下会把输入框的内容行画丢（用 tmux 做参照终端复现同样现象），
  24 行才正常——也就是说"多出两行"直接决定 TUI 可用性。

## 5. 已知限制 / 未覆盖

1. **SSH 远程终端未接真机联调**：本机没有可用 SSH 目标与凭据。改动对 SSH 是共用件
   （同一个 `TerminalView`、同一条 WS 通道、同样的 TERM），且 SSH 侧只新增了 `nudge_redraw` 与状态上报；
   未覆盖项按《验证标准》口径显式记录，不冒充已验证。
2. **Windows 未复验**：本轮改动是跨平台的（`nudge_redraw` 在 pywinpty 上走 `set_size`），
   Windows ConPTY 链路仍需 `scripts/verify/windows_vm_e2e.sh` 复跑。
3. dsh TUI 在 **≤21 行**的终端里输入框内容行会丢（TUI 自身问题，tmux 同样复现）；
   默认窗口下现在是 24 行，用户把窗口拉得很矮仍可能遇到——工具条"重绘"与放大窗口可缓解。
4. 终端回放历史已**刻意不做**（见 §1.2）；因此若渲染进程整体崩溃重建，画面只能靠 TUI 自己的 SIGWINCH 重绘。
