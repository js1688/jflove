## 0. 结论速览（TL;DR）

本次把文本编辑器从「**应用内浮动窗格**」改为「**左侧导航里的整页工作区 + 顶部固定标签条**」，并给它加了**登录准入**：

- 未登录时编辑器**零入口、零响应**：导航项不渲染、快捷键运行时首行判门、外部唤起（「打开方式」/命令行/单实例）先在队列里挂起，登录成功后自动补开并切换到编辑器。
- 一个文档一个标签页；切换标签 = 切换编辑面板（非激活面板 `hidden` 但**保持挂载**，切回不丢状态）。
- 浮动窗格的**拖动 / 8 向缩放 / 最小化 / 最大化 / 平铺 / 层叠 / z 序 / 几何** 整体退役。
- 编辑器与远端仍然**零交互**（AC-42 不变）；渲染层仍无网络出口、token 仍只在 Python 侧。

### 3.3 Phase 6 发现的缺陷与回修（2026-10-15，`cross-platform-desktop`）

> 触发：Phase 6 真机探针（`jflove-desktop/poc/editor-probes/`）AC-64 ② 失败 ——
> `out/r15-20261015-164924/r15-run.log` 的 `[FAIL] AC64-2` 一行：`"hash": "#/files"`、
> `"navEditorActive": false`、`"tabCount": 0`；同一行 `"detectAndReadCallsAfterLogin": 1`
> 证明 `flushOpenPaths()` **确实兑现了**（桥方法被调用）⇒ 故障只在「登录后的落点」。

**缺陷 R1：未登录经「打开方式」唤起 → 登录成功后停在 `#/files`（AC-64 ② 失败）**

- **根因（两处导航互相打架，后发起者覆盖先发起者）**
  1. 修复前 `ui/src/utils/scratch/editor-open-paths.ts:118-127`（`useAuthStore.subscribe` 回调）
     在门翻转时执行 `router.navigate('/editor')`，随后 `flushOpenPaths()`；
  2. 修复前 `ui/src/pages/LoginPage.tsx:44-46` 的
     `useEffect(() => { if (isLoggedIn) navigate('/', { replace: true }); }, [isLoggedIn, navigate])`。
  zustand 的 `subscribe` 监听器在 `set()` 时**同步**先跑（队列随即被 flush 清空），React 提交后
  LoginPage 的 effect 才跑；而 React Router 数据路由的 `navigate` 是**异步**的 ⇒ **后发起的 `/`
  覆盖了先发起的 `/editor`** ⇒ 最终落到 `#/files`。设计依据：设计文档 v1.6.1 §2.2.1 时序图
  （`文档记录/设计文档/v1.6.1.md:223-226`）要求「登录成功 → `navigate('/editor')`」；
  验收条目见需求文档 v1.6.1 `:469`（AC-64 ②「完成登录 → 左侧菜单自动切到『文本编辑器』」）。

- **修复方案（收敛成单一「登录后落点」判据，消除两处导航的所有权冲突）**
  1. `ui/src/utils/scratch/editor-open-paths.ts`：
     - `EDITOR_ROUTE` 由私有常量改为**导出**（落点字面量只允许一份）；

> 本批归属：`cross-platform-desktop`（唯一改动模块 `jflove-desktop/`）。用户裁决 = **方案 A**。

### 10.1 真凶（r18 单变量对照矩阵**实测**，非推测）与修复决策

- **真凶 = 剪贴板上的 `UniformResourceLocator`（`CFSTR_INETURL`，Qt 侧即 `text/uri-list`）**：
  **只要它在，QtWebEngine 的 `Ctrl+V` 就贴出 0 字符**。Java/AWT（IDEA 用 `Clipboard.setContents`）
  **必然**写它 ⇒ Win32 格式表固定为
  `HTML Format / CF_UNICODETEXT / CF_TEXT / UniformResourceLocator / CF_LOCALE / CF_OEMTEXT`。
  本次真机复现的实时读数为 `["HTML Format","CF_UNICODETEXT","CF_TEXT","UniformResourceLocator","CF_LOCALE","CF_OEMTEXT"]`
  ⇒ Qt 侧 `["text/html","text/plain","text/uri-list"]`（与上述结论逐项一致）。
- **与 `CF_HTML` 的标记 / 偏移无关**：**不是** QTBUG-118121（已排除）。合成载荷"带 / 不带
  `<!--StartFragment-->`"、四个数字偏移对不对，**都不是变量**；唯一变量是那个 URI 格式。
  单变量矩阵（同一载荷、同一判据、两轮协议、`foregroundIsShell=true`、按键送达自检）：
  裸 Win32 写 `CF_HTML`+文本**不带**该格式 ⇒ 贴出纯文本；随便加一个**自定义**格式 ⇒ **仍**贴出纯文本；
  加 `UniformResourceLocator`（`file:///` 或 `https://`）⇒ **0 字符**；真实 AWT 6 种变体 ⇒ 0 字符；
  真实 AWT **只写纯文本** ⇒ 0 字符；把 AWT 载荷读回**重写成「只有 `CF_HTML` + `CF_UNICODETEXT`」**
  ⇒ **第 1 轮就贴出**。取证工具与证据：`poc/editor-probes/AwtClipHtml.java`、
  `poc/editor-probes/r17-clipboard-cfhtml.py`、`poc/editor-probes/out/.r18-*.jsonl`。
- **渲染层修不了**：QtWebEngine 在该格式存在时**根本没把内容交给渲染层**（正文 0 字符），
  且渲染层 CM6 本来就只读 `text/plain`（离线包实测）⇒ 上一批 C1 的渲染层 paste 接管
  （`pasteHandlerFor`）**对 F6 无效**，却**有真实代价**（抢在 CM6 内置 `paste` 之前，
  破坏"多光标粘贴按行分发"这一 CM6 原生便利）⇒ **本批移除**。
- **方案 A（用户裁决）**：用户在本应用内按 `Ctrl+V` 时，由**原生外壳**把剪贴板从"坏形态"
  重写成"QtWebEngine 能正常粘贴的形态"，然后**让默认粘贴照常发生**（**不**吞键、**不**自插文本、
  **不**改粘贴语义）。
- **为什么是"整体重建成 `CF_HTML` + `CF_UNICODETEXT`"而不是"只删掉一个格式"**：本次真机读数显示
  Qt 眼中真实 AWT 载荷**只有三个**格式（`text/html` / `text/plain` / `text/uri-list`）⇒
  「只剔 `text/uri-list`、保留其余」与「重建成 html + text」**在 Qt 能力面内是同一件事**
  （真要在 Win32 层逐个格式搬运，风险远大于收益）；而后者正是 r18 矩阵里**已被实测有效**的做法。
- **挂钩点为什么是"应用级事件过滤器"**：`QWebEngineView` 的按键落在 **focusProxy（渲染 widget）** 上，
  重写 `QWebEngineView/DropAwareWebView.keyPressEvent` **收不到** `Ctrl+V`（BL-51「配了没反应」的
  前车之鉴）。应用级过滤器经 `QCoreApplication::notify` 分发链到达、对任何接收者都可见，
  且**早于**接收者自己的 `event()`（渲染 widget 的 `keyPressEvent` 才把按键送进 Chromium）。
  真机自证见 10.3 的日志行与 `rewrite_count`。
- **补充安全边界（本次实测新增）**：`QMimeData.text()` 在**没有** `text/plain` 时会**回落到**
  `text/uri-list`。裸 Win32 只写 `CF_HDROP`（= 资源管理器"复制文件"）时，Qt 眼里**只有**
  `text/uri-list`（`hasHtml()=False`、`hasFormat("text/plain")=False`），但 `text()` 会回一段
  `file:///…`。⇒ 判据必须显式看 `text/plain` / `text/html` **存在性**，否则会把用户的**文件复制**
  改写成一段纯文本（之后在资源管理器里粘贴不再是复制文件）。这是本批**必须**有的守卫。

### 11.2 M-15："取走初始正文"与"实例建成"之间的丢正文窗口（`ScratchEditorHost.tsx`）

**选了 (b)：在 cleanup 里对"实例从未建成"补一次写回**（未采用 (a) 把 `takeInitialText` 推迟到实例创建之后）。

```ts
// ScratchEditorHost.tsx:645-647（`pane.id` effect 的 cleanup 内，位于既有 AC-77 双保险快照**之前**）
if (!viewRef.current && initialTextRef.current && !hasInitialText(paneId)) {

}
```

**为什么是 (b) 而不是 (a)**（三条，均可复核）：

1. **(a) 会把"消费初始正文"与"实例存在"的耦合面做大**：`takeInitialText` 的调用点当前在
   effect 体内、**渲染提交期就确定**；挪到 `await loadEditorBundle()` 之后意味着"正文交付时机"
   取决于一次**异步加载的成败** —— 加载失败 / 被取消（本批实测的"挂起"场景）时，
   `initialTexts` 里那份会**永久留着**（既没交付、也没写回），而 `putInitialText` 的语义是
   "未挂载标签的待交付正文" ⇒ 留下一份"幽灵待交付正文"，后续任何一次 `takeInitialText`
   都可能拿到**过期正文**（比"丢一次正文"更难查）。
2. **(b) 与既有架构同形**：本文件已经有**两处**"先交正文、后 destroy"的快照清理
   （callback ref cleanup + `pane.id` effect cleanup），(b) 只是给同一条清理序列补一个
   "实例还没建成"的分支，**不新增第二套生命周期**，也不改 `takeInitialText` 的调用位置。
3. **(b) 的守卫天然挡死标签**：写回仍走 `snapshotInitialText`，其 `tabs.find` 守卫会拒绝
   已关闭标签 ⇒ 不会出现"死标签复活"（AC-59 不受影响，本批专设一条守门用例）。

**三条不能破坏的语义（写进代码注释）**：① 只在**实例从未建成**（`viewRef.current === null`）时走，
实例建成的路径仍由 `snapshotIntoStore` 按 `view` 的**真正文**交付，绝不被旧文本覆盖；
② 只在 `hasInitialText(paneId)` 为**假**时走 ⇒ `takeInitialText` 的"**取走即删 / 交付一次**"
语义**一字未改**（既有断言原样保留）；③ 空串不写回（不是"删除"语义）。

**判据与"修复前是否真红"**（新建 `__tests__/scratch-editor-host-initial-text.test.tsx`，3 条）：

**与设计 §15.6.7 修法原文的**必要偏差**（实测踩坑，已写进源码注释）**：设计建议

**或 ② `hasUrls()` 为真且平台不是 Windows**（非 Windows 上 `text/uri-list` 本就是"复制文件"的载体、
