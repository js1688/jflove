## 4. 关键行为

1. **挂载点默认关闭**：`create_mount` 固定 `enabled=False`；未启用时 `mount.list` 不做状态统计、`mount.refresh` 直接拒绝（AC-101）。
2. **目录隔离**：一个挂载点只对应一个远端子目录；增量与对账都带 `prefix`，服务端二次断言，不在前缀内的变更被丢弃（AC-100 / AC-112）。
3. **状态定义**：
   - `cached`（已缓存）= 本地缓存目录中**存在该文件**；
   - `online`（仅在线）= 索引里有、本地没有。
   状态由文件系统推导，不额外维护状态列，避免"索引说已缓存、磁盘上没有"。
   **系统挂载生效时必须问挂载实例**（`WinCfapiMount.is_cached` / `LinuxFuseMount.is_cached`）：
   FUSE 的 stat 会命中远端索引，所有在线文件也会返回文件类型，`os.path.isfile` 恒为 True。
4. **按需下载**：点「下载」→ `transfer_manager.submit_download`（复用加密流），传完本地出现文件，状态自动变「已缓存」。
5. **释放**：删本地文件并清理空父目录（不越过挂载点根），**不影响远端**（AC-109 / AC-110）。
6. **旧配置迁移**：首次 `mount.list` 时把 `sync_configs_{username}.json` 转成挂载点（`enabled = 旧 auto_sync`），旧文件保留（AC-126）。
7. **索引一致性**：`reset_required=true`（游标过旧）时清空索引并自动走 `reconcile`。
8. **系统级挂载（Windows CfAPI，已实测）**：启用挂载点时注册 sync root 并创建脱水占位；用户打开占位触发 `FETCH_DATA`，驱动经加密下载通道取内容并 `CfExecute(TRANSFER_DATA)` 写回。资源管理器可见云状态。CfAPI 不可用时自动降级为应用内视图并返回 `system_mount=false`。

| 维度 | v1.6.2 | v1.7.0 |

## 7. 已知限制（如实登记）

1. **Linux FUSE 已实现**（见 §8）：Windows 走 CfAPI、Linux 走 FUSE，二者对上层同一契约。
2. **回调内存占用**：`FETCH_DATA` 回调把**整个文件**读入内存再按 `RequiredOffset/Length` 切片。几百 MB 以上的大文件会占用大量内存，后续应改为按范围流式拉取。
3. **挂载路径只读**：下载 / 释放可用，但"在挂载目录里编辑后回传"未做（写入仍走文件管理页）。
4. **降级行为**：CfAPI 注册/连接失败时自动降级为应用内视图，桥返回 `system_mount=false`；界面应据此提示（当前提示文案在页面底部）。
5. **大目录对账**：`reconcile` 全量 walk（设计 R-3），首次对账可能较慢。

## 8. Linux FUSE 系统级挂载（2026-10-18 补充，BL-1）

> 换设备到 Fedora 后补做：Windows 的 CfAPI 在 Linux 不存在，改用 **FUSE（fusepy）** 实现同一套语义。

### 8.1 动机与开工前的真实故障

| 发现 | 说明 |
|---|---|
| **桌面端在 Linux 根本起不来** | `src/utils/mount_vfs.py` 模块顶层 `ctypes.WinDLL("cldapi")` 在 Linux 抛 `AttributeError`；`mount_sync_service` → `bridge` 的 import 链全线崩 |
| dev 库陈旧 | `jflove-dev.db` 缺 `file_changes` 表 ⇒ `check_db_schema.py` 退出码 1；跑 `init_db()` 后为 0 |
| `ui/dist` 陈旧 | 工作区里的前端产物还是「同步管理」旧页面，挂载页看不到；需 `npm install` + 生成 CM6 离线包 + `npm run build` |

### 8.2 模块拆分

| 文件 | 内容 |
|---|---|
| `src/utils/mount_vfs.py` | **门面**：`backend()` / `is_available()` / `create_mount()`，并用 `__getattr__` 惰性导出 `WinCfapiMount` / `LinuxFuseMount`（兼容旧引用，且 Linux 上不会连带 import `ctypes.WinDLL`） |
| `src/utils/mount_cfapi.py` | 原 CfAPI 实现原样迁出（新增 `is_cached`） |
| `src/utils/mount_fuse.py` | 新增 FUSE 实现 |

### 8.3 FUSE 实现要点（踩坑登记）

| # | 坑 | 现象 | 做法 |
|---|---|---|---|
| 1 | 挂载后 `local_path` 被 FUSE 接管 | 用挂载点自身访问缓存目录 ⇒ **无限递归进本文件系统** | 挂载前 `os.open(root, O_DIRECTORY\|O_PATH\|O_CLOEXEC)` 拿底层 fd，之后真实 I/O 全走 `/proc/self/fd/<fd>` |
| 2 | 水合后 `open` 返回 0 | 后续 `read` 去读 **stdin**（0 是合法 fd，`if fh` 还判不出来） | 水合完必须 `os.open` 真实文件并返回其 fd |
| 3 | 挂载点可能已有缓存文件 | 默认 `fusermount` 拒绝挂到非空目录 | `FUSE(..., nonempty=True)` |
| 4 | 索引里只有文件、没有父目录行 | `cd` / `ls` 进不去子目录 | 快照时沿途补隐式目录（`_build_tree`） |
| 5 | **死挂载点**：进程被强杀 | `os.path.ismount` 吞掉 `ENOTCONN` 返回 **False**，随后 `makedirs` 抛 `FileExistsError`，页面直接报错 | 挂载点判定改读 `/proc/self/mounts`（`_is_mountpoint`），先卸载再建目录；`restore_mounts` 逐项 try/except |
| 6 | 已缓存判定 | FUSE 的 stat 命中索引 ⇒ 所有在线文件都被当成"文件"，`cached` 恒 True | `LinuxFuseMount.is_cached()` 走底层目录；`mount_sync_service._is_cached` 优先问挂载实例 |
| 7 | 合成属性缺 uid/gid | `ls -l` 显示 `root root` | 合成 stat 与真实 stat 都显式填 `st_uid/st_gid` |
| 8 | 时间单位 | fusepy 默认浮点秒已弃用 | `_FuseOps.use_ns = True`，getattr 返回 `*_atime_ns`，`utimens` 用 `os.utime(ns=...)` |
| 9 | 并发打开同一未缓存文件 | 重复下载 | 按 rel_path 加锁，同一文件只下一次 |
| 10 | QtWebEngine 接管 `SIGTERM` | `kill` / 关机时 Qt 循环不返回 ⇒ `main()` 的 `finally` 不执行 ⇒ 死挂载点残留 | `main.py::install_termination_hook`：`SIGTERM/SIGINT → app.quit()`，并用 200ms 低频 `QTimer` 把控制权交回解释器 |

### 8.4 接线（上层逻辑未改判据）

`mount_sync_service` 只改三处：

1. `enable_vfs` 改用 `mount_vfs.create_mount(...)` 工厂，并传 `listing=lambda: mount_index.list_files(mid)`
   （FUSE 需要索引来补足"仅在线"文件；CfAPI 忽略该参数）；
2. 新增 `restore_mounts(mounts)`：进入挂载页时把「配置为已启用」的挂载点恢复挂载
   （FUSE 挂载不跨进程存活；CfAPI 注册虽留在系统里但连接同样随进程消失），并顺带清理死挂载点；
3. `list_files` 的 `cached` 判定改走 `_is_cached`（见 8.3 #6）。

`sync_placeholders` / `disable_vfs` / `disable_all_vfs` / 页面**均未改动语义**；
`LinuxFuseMount.add_file` 是 no-op（FUSE 视图由索引动态生成，无需占位）。

`src/bridge/mount.py` 另补两处时序（两种平台都受益）：

- `mount.delete`：**先 `disable_vfs` 再删配置** —— 配置删掉后就没有入口能停用挂载，
  目录会一直被接管；
- `mount.update`：本地目录变化且挂载点已启用时，**先卸载再按新目录重挂**（只改名字不打断挂载）。

### 8.6 已知限制（Linux 侧，与 Windows 对齐）

1. **整文件拉取**：FUSE `open` 触发 `fetch(rel)` 取整个文件后才返回（与 CfAPI 回调同一限制），大文件占内存。
2. **写入不回传**：挂载目录内的新建 / 编辑 / 改名只落本地缓存，不上传也不删除远端。
3. **删除语义**：删除"仅在线"（未缓存）文件会得到 `ENOENT` —— 本地没有实体可删，远端也不会删；
   该条目仍按索引显示（与 CfAPI 占位一致）。
4. **只支持 FUSE 2（fusepy）**：系统需有 `libfuse.so.2` 与 `fusermount`；缺失时降级为应用内视图。

## 9. 挂载点自动同步 + 中文输入修复（2026-10-18 第二轮，用户实测反馈）

> 反馈来源：Fedora 实机使用后提出 4 个问题 —— ①「释放」后文件仍在；② 往挂载目录放文件不上传；
> ③ 界面要手动点下载/释放、「全量对账」这种词看不懂、进度不明显；④ 桌面端无法输入中文。

### 9.1 先澄清「释放」的语义（不是 BUG，但体验误导）

挂载目录里**始终显示全部远端文件**（这正是挂载的意义：未缓存的文件是「仅在线」占位）。
「释放」= 删掉本地缓存实体，文件仍以「仅在线」留在列表里 —— 所以看起来「文件还在」。
旧界面同时给了「下载 / 释放」两个手动按钮，与「自动保持一致」的目标相矛盾。

**处置**：界面**移除下载 / 释放 / 全量对账**三个入口；「释放」等价操作 = 在文件管理器里删除该文件
（本地删除只删缓存，绝不回传远端）。桥方法 `mount.download` / `mount.release` 保留（内部与脚本仍可用）。

### 9.2 自动同步（本轮核心）

| 变化 | 行为 | 实现 |
| --- | --- | --- |
| 本地新增 / 修改 | 自动上传远端 | FUSE 写回调（`begin_write`/`end_write`/`rename`）+ 每 5s 兜底扫描 |
| 本地删除 / 删目录 | **只删本地缓存，绝不回传远端** | FUSE `unlink`/`rmdir` 不触发变更回调 |
| 远端新增 / 修改 | 索引更新；本地缓存过期则丢弃，读取时重新下载 | `_apply_remote_changes`（远端 mtime 更新 ⇒ 删本地缓存） |
| 远端删除 | 本地缓存一并删除 | `_apply_remote_changes` |

关键设计：

- **同步与系统挂载解耦**：`enable_vfs` 先 `start_auto_sync`，CfAPI/FUSE 不可用时自动同步照样运行；
- **启动即恢复**：`main.py::start_mount_supervisor` 每 10s（启动后 2s 先来一次）在线程里
  `ensure_auto_sync()`，**不依赖用户打开挂载页**（否则「放了文件没上传」）；
- **不传半成品**：`.part` / `.jflove-part` 跳过；写入中的句柄（`is_open_for_write`）跳过；
  文件 mtime 需稳定 2s；
- **不重复提交**：`_syncing` 记录进行中的任务；失败后 30s 退避；
- **不做无效扫描**：无变更通知时兜底扫描间隔 5s（`_SCAN_INTERVAL`），避免大目录每 2s walk；
- 上传复用 `transfer_manager.submit_upload`（加密分片上传 + 传输页可见进度）。

### 9.3 界面（`SyncPage.tsx`）

- 副标题改为「本地与远端自动保持一致：改动自动上传，读取时自动下载；本地删除不会影响远端」；
- 顶部只保留 `刷新`（手动立即核对一次）；
- 文件状态三态：**已同步 / 同步中（带百分比）/ 在线**，列表每 2s 轮询刷新；
- 汇总行：`共 N 项 · 已同步 X · 在线 Y · 同步中 Z`。

### 9.4 中文输入（真因 + 修法）

**真因**：`main.py` 强制 `QT_QPA_PLATFORM=xcb`（历史 workaround），而 `input_method.py`
只看 `WAYLAND_DISPLAY` 就把 `QT_IM_MODULE` 设成 `wayland` —— **两者互斥**，等于完全没有输入法。
另外实测：系统 `libfcitx5platforminputcontextplugin.so` **无法**被 PySide6 加载
（`libQt6Gui.so.6: version 'Qt_6.11_PRIVATE_API' not found`，PySide6 不导出 Qt 私有符号），
所以 xcb 下没有可用的 fcitx 路径。

**修法**（`input_method.py`）：

1. 新增 `configure_linux_qt_platform()`，**先定平台再定 IM 模块**：
   - 用户已设 `QT_QPA_PLATFORM` ⇒ 尊重；
   - `JFLOVE_QPA_PLATFORM` 覆盖（遇到显示问题可回退 `xcb`）；
   - Wayland 会话 **且** 检测到 Wayland 输入法前端（fcitx5 的 `libwayland.so` / ibus-daemon）⇒ `wayland`；
   - 否则 ⇒ `xcb`；
2. `setup_input_method()` 以 `QT_QPA_PLATFORM` 为准：wayland 平台设 `wayland` 模块；
   xcb 平台只在 PySide6 自带插件（ibus）可用时才映射，**绝不再设 `wayland`**。

**实测证据**（Fedora 44 / KDE Wayland / PySide6 6.11）：

| 判据 | 结果 |
| --- | --- |
| 启动日志 | `Qt 平台：Wayland 会话且检测到 Wayland 输入法前端，使用 wayland` + `QT_IM_MODULE 由 fcitx 切换为 'wayland'` |

## 10. 同步可见性（2026-10-18 第三轮，用户反馈「不知道在传哪个文件、还有多少没同步」）

### 10.1 之前的断点

1. 挂载页只有「已缓存 / 仅在线」，**没有方向、没有进度、没有待办数量**；
2. 更关键：**本地新建、尚未上传完成的文件根本不在索引里**（索引来自远端 journal），
   所以上传期间界面上完全看不到这个文件 —— 用户以为「没反应」；
3. 读取触发的按需下载（水合）没有任何可见状态。

### 10.2 现在的呈现

**文件级 6 态**（`mount.files[].state`）：

| 状态 | 含义 |
| --- | --- |
| `synced` 已同步 | 本地有实体且与远端一致 |
| `pending` 待上传 | 本地有改动，排队中（已计入列表与统计） |
| `uploading` 上传中 | 带 `progress` 0-100 |
| `downloading` 下载中 | 读取触发的水合 / 手动预取，带 `progress` |
| `failed` 失败 | 带 `error` 原因，30s 后自动重试 |
| `online` 在线 | 本地无实体，读取时自动下载 |

**挂载点级统计**（`mount.status`）：`total / synced / pending / uploading /
downloading / failed / online / active / active_total`。

**界面**：

- 顶部汇总行：`共 N 项 · 已同步 X · 待上传 Y · 上传中 Z · 下载中 W · 失败 F · 在线 O`；
- 「正在同步 N 项」面板：逐条列出**文件名 + 方向（↑上传 / ↓下载）+ 进度%**（最多 8 条，超出提示剩余数量）；
- 文件行徽标同步显示 `上传中 42%` / `下载中` / `待上传` / `失败`（失败悬停显示原因）；
- 刷新节奏：文件列表 **1s**（读本地索引 + stat），挂载点统计 **3s**（需遍历全部文件）。

### 10.3 实现要点

| 位置 | 变化 |
| --- | --- |
| `list_files` | 合并「索引行 + 本地新增但未进索引的行」（`_dirty ∪ _syncing ∪ _failed` 减去索引），否则上传中的新文件不可见 |
| `_dirty` | 本地变更待上传集合（FUSE 回调 / 扫描发现即加入，提交或确认未变时移除） |
| `_hydrating` | 水合（读取触发下载）进行中的集合，`_fetch_content` 进出时维护 |
| `_failed` | 上传失败原因（来自传输任务 `error`），成功后清除 |
| `reconcile_mount(quiet=True)` | 新增**每 15 分钟自动全量核对**，清理「远端被绕过 API 删除 / 本地索引残留」的幽灵条目（原「全量对账」按钮的能力，改为自动） |

## 11. 「进度 100% 但远端找不到文件」的解释与修正（2026-10-18 第四轮）

### 11.1 文件到底在哪（服务端写入时序）

远端**磁盘目录里看不到正在上传的文件**是设计使然（原子写入，避免半成品被读到）：

| 阶段 | 数据位置 | 远端磁盘目录 |
| --- | --- | --- |
| 校验中（SHA256） | 客户端只读本地文件 | 无 |
| 上传中（分片） | **服务端** `UPLOAD_TEMP_DIR/<upload_id>/000000.chunk …` | 无 |
| 服务端处理中（合并） | 目标目录内 `.<文件名>.jflove-upload-<upload_id>.part` | 有 1 个隐藏 `.part` |
| 完成 | `os.replace(.part → 文件)` 原子落盘 | 目标文件出现 |

- 服务端默认 `UPLOAD_TEMP_DIR = jflove-server/build/upload_tmp`（Docker 部署则在容器内）；
  分片按上传会话分目录存放，`cleanup_stale_uploads` 每小时清一次 24 小时前的孤儿目录。
- 因此「上传中在远端目录看不到文件 / 连碎片都没有」是**预期行为**；要看进度应看客户端挂载页。

### 11.2 「100%」为什么骗人（已修）

旧实现把两个阶段都报成同一个百分比：

1. `hashing`：上传前流式计算 SHA256，进度按字节 0→100% —— 此时**一个字节都还没上传**；
2. `uploading`：真正分片上传，进度重新 0→100%；
3. `complete`：服务端把全部分片重写一遍并校验（大文件数十秒），旧实现停在 100% 不动。

**修正**：传输任务新增 `phase`，挂载状态拆成 `hashing` / `uploading` / `finalizing`：

| 状态 | 界面文案 | 含义 |
| --- | --- | --- |
| `hashing` | 校验中 N% | 正在算 SHA256，尚未上传 |
| `uploading` | 上传中 N% | 正在传分片到服务端暂存 |
| `finalizing` | 服务端处理中 | 分片已传完，服务端合并 + 校验 |
| `synced` | 已同步 | 已原子落盘到远端目录 |

界面「正在同步」面板底部新增说明，直接写清「分片暂存 → 合并校验 → 才出现在远端目录」。

### 11.3 实测（本机，真实服务端 + 加密分片上传）

| 文件 | 观察 |
| --- | --- |
| 1 GB | T+0.2s 待上传（暂存 0、远端 0）；T+1.4s 上传中 1%（暂存 28M、远端 0）；T+21.3s 上传中 100%（暂存 1.0G、远端出现 1 个 `.part`）；T+22.5s 暂存清空、远端 1 个文件；T+23.6s 已同步 |
| 2 GB | 状态序列：`校验中 → 上传中 → 处理中 → 已同步`，全程 39.8s，结束后远端文件 2.0 GB |

### 11.4 说明

- 上传吞吐实测约 57 MB/s（1MB 分片 + 加密信封 + Base64），12 GB 文件约需 3–4 分钟，
  期间远端目录始终为空属正常；若需更快可调大 `CHUNK_SIZE`（客户端 `settings.py`）。
- 远端磁盘若空间不足，`os.replace` 前的 `.part` 写盘会失败 → 界面显示「失败」并 30s 后重试，
  悬停可看到服务端返回的原因。

### 11.5 Windows 是否也有同样的问题

**有，而且是同一段代码 ⇒ 已一并修好。** 上传链路的三个阶段（`file_service.upload_file` 的
hashing / uploading / finalizing）、`transfer_manager` 的 `phase`、挂载页状态与文案、
服务端分片暂存与原子落盘，全部与平台无关：

| 项 | Windows | Linux |
| --- | --- | --- |
| 「100% 却看不到文件」 | ✅ 同样是 hashing / finalizing 阶段 | ✅ |
| 文件在服务端 `upload_tmp/<upload_id>/` | ✅ 同一服务端 | ✅ |
| 界面阶段文案（校验中 / 上传中 / 服务端处理中 / 已同步） | ✅ 同一 UI | ✅ |
| 发现本地改动的机制 | CfAPI 无写回调 ⇒ 10s 扫描 | FUSE 写回调 + 30s 兜底 |

**另修一处 Windows 专属隐患**（`_flush_uploads`）：CfAPI 的**脱水占位**在文件系统里也是
「普通文件」，若索引缺失/被重置，扫描会把它当成本地新增文件上传 —— 读取它会先触发水合
（整文件下载）再传回，白费流量。现在上传前会问挂载实例 `is_cached(rel)`，
**未水合的占位一律跳过**（单测 `test_Windows脱水占位不参与上传`）。

> 剩余 Windows-only 差异（不属于缺陷）：合并阶段耗时与文件大小成正比，12GB 约 1–2 分钟，
> 期间界面显示「服务端处理中」，远端目录里只会短暂出现一个隐藏 `.part`。

**Windows 额外修复（陈旧 CfAPI 注册）**：进程被强杀会留下仍有效的 sync root 注册，
旧实现 `CfRegisterSyncRoot` 失败即 `return False` ⇒ 整个挂载点降级为应用内视图。
现在注册失败时**继续尝试 `CfConnectSyncRoot`**（连已有的注册），连接成功后退出时照常注销，
不留陈旧注册。

## 12. 「传一晚上没成功」的根因与修复（2026-10-19，真实 ISO 目录实测）

> 用户实测：挂载 21GB 的 ISO 目录后，界面显示「上传中 100%」，**放了一整晚仍未完成**。

### 12.1 复现（先证明是实现缺陷，不是环境问题）

| 场景 | 结果 |
| --- | --- |
| 本机直连（快盘）上传 21GB（3.0 + 5.7 + 12.2 GB，3 并发） | ✅ 6 分钟全部完成，SHA256 一致 |
| 服务端合并阶段人为延长到 60 秒（模拟慢盘 / 慢网络） | ❌ **31.2s 失败**：`ReadTimeout(read timeout=30)`，随后整文件重传 |

**根因链**：

1. `http_client.post` 的默认超时是 **30 秒**，而 `upload/complete` 期间服务端要把
   全部分片重写一遍并算 SHA256 —— 12GB 在慢盘上远超 30 秒；
2. 超时被当成普通失败 ⇒ `_AutoSync` 30 秒后**重新提交整个文件**；
3. 重传要**重新算一遍 SHA256（几十 GB）+ 从头传全部分片** ⇒ 12GB 每次约 10 分钟；
4. 只要服务端始终慢于 30 秒，就**永远停在「上传 100%」**，一夜也完不成。

### 12.2 修复（客户端，5 处）

| # | 修复 | 说明 |
| --- | --- | --- |
| 1 | `post()` 支持 `timeout` 参数 | `complete` 用 `(30s 连接, 3600s 读取)`；不再把「服务端正在合并」误判为失败 |
| 2 | 合并超时后**核验而非重发** | 轮询远端目录，文件出现且大小一致即视为成功（盲目重发同一 upload_id 会让服务端并发合并同一临时文件） |
| 3 | **分片级重试** | 单个 1MB 分片遇网络抖动只重发该片（最多 5 次，指数退避），不再拖垮整个文件 |
| 4 | **断点续传** | 已发送分片索引落盘 `storage/upload_resume.json`；应用被强杀 / 重启后复用 upload_id 与已传分片 |
| 5 | **SHA256 缓存** | 按「路径 + 大小 + mtime」缓存，重试不再重读几十 GB |

配套：会话失效（服务端重启）时自动重新 `init` 并完整重传一次；续传失败会清记录而不是死循环。

### 12.3 顺带修复的两个数据安全问题（实测中发现）

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| **全量核对误删本地文件** | `reconcile` 把「远端清单里没有」当成「远端已删除」，删掉本地缓存 → 实测把刚准备好的 21GB 测试文件删了 | 核对**只刷新索引**，绝不删本地文件；只有 journal 的显式 delete 才删本地缓存 |
| 远端删除时丢失本地改动 | 本地有未上传改动、远端恰好删了同名文件 | 该文件标记为 dirty 时**保留本地**（下一轮重新上传），数据优先 |

另外：启动挂载时先做一次全量核对（`_need_initial_sync`），避免索引重放出「远端已删除」的幽灵条目、
把真实改动误判为「未变化」而永不上传（实测触发过）。

### 12.4 实测（真实 ISO 目录，21GB）

| 判据 | 结果 |
| --- | --- |
| 全量上传 | ✅ 3 个文件全部「已同步」，21.0 GB |
| 中途强杀（`kill -9`，已传 2016/3115、1664/5815、1024/12533 片） | ✅ 重启后日志「发现未完成的上传，尝试续传」 |
| 续传后完成 | ✅ 剩余 16GB 继续传完，未从头再来 |
| 内容一致性 | ✅ Fedora 3.0GB 与 macOS 12.2GB 的 SHA256 与本地**完全一致** |
| 续传记录清理 | ✅ 成功后 `upload_resume.json` 为 `{}` |
| 本地文件安全 | ✅ 全程 3 个本地文件未被删除 |
| UI | ✅ `共 3 项 · 已同步 3`，逐条显示 3.0/5.7/12.2 GB「已同步」 |
| 单测 | ✅ `tests/test_upload_resume_v1_7_0.py` 6 条（慢合并 / 分片重试 / 会话失效 / 续传 / 哈希缓存） |

### 12.5 仍存在的边界

1. 服务端 `_upload_sessions` 在内存：**服务端重启**后会话失效 ⇒ 客户端会重新 `init` 并重传
   （分片仍要重放，但不会死循环）；临时分片目录服务端会在 24 小时后清理。
2. 远端在应用停机期间被删除的文件，启动核对后会以「本地优先」重新上传（不删本地数据）。
3. 上传吞吐受限于加密单请求链路（实测约 55–70 MB/s，本机直连）。

### 12.6 「只更新客户端、不重启服务端」能否验证（2026-10-19 实测）

**能。** 上传健壮性的四项修复全在客户端，与服务端版本无关：

| 验证 | 服务端 | 结果 |
| --- | --- | --- |
| 合并慢 60 秒（旧服务端 + 新客户端） | **HEAD 旧代码**（worktree 隔离运行） | ✅ 64.6 秒成功；旧客户端同场景 31.2 秒失败 |
| 强杀客户端 → 重启续传（旧服务端） | 同上 | ✅ 日志「发现未完成的上传，尝试续传：已传 160/200 片」，61.2 秒完成 |

**不重启服务端会失去什么**（只影响磁盘，不影响功能）：

| 项 | 旧服务端 | 新服务端 |
| --- | --- | --- |
| 客户端被强杀后的分片目录 | **永不自动清理**（会话永不过期 + 清理跳过会话目录）。实测：200MB 上传中途 `kill -9` 留下 **174MB** 目录 | 空闲 24h 回收；重启后首轮按 1h 阈值清理 |
| 合并被中断留下的 `.part` | 永不清理 | 每小时清理 >24h 的 |
| 并发 `complete` | 无互斥 | 按 upload_id 串行 |

缓解：新客户端的**断点续传会复用**这些目录，上传完成后自动清空 —— 因此只更新客户端时，
只要这些文件最终传完，残留就会被回收；只有「被放弃且不再续传」的任务才会长期占盘。

**结论**：想立刻验证 / 修复卡死问题，只更新客户端即可；建议之后找时间重启一次服务端，
释放历史残留并把清理机制启用。

## 13. 服务端合并进度回传客户端 + 大文件进度信号修复（2026-10-19）

### 13.1 问题

1. 大文件（>2GB）上传到「分片已传完、服务端正在合并」阶段后，界面**停在 100% 不动**，
   用户无法区分「在合并」和「卡死」。合并耗时随文件增大线性增长（本机 2.4 秒/GB，
   弱配置机器更久），没有进度就等于没有反馈。
2. 弱配置服务器上合并耗时可能远超 HTTP 超时：旧逻辑 `complete` 超时后**整文件重传**
   （重算 SHA256 + 从 0 传），这是"传一晚上也传不完"的根因。
3. **新发现（本机实测）**：`_TransferWorker.progress` 声明为 `Signal(str, int, int, str)`，
   Qt 的 `int` 是 32 位，>2GB 文件的字节数在 `emit` 时抛 `OverflowError`（libshiboken）。
   后果是**进度事件全部丢失**（日志里刷了 47898 行 `OverflowError`），
   界面在后台窗口下只能靠定时器轮询，实测出现 60 秒级空档 —— 看起来像卡死。

### 13.2 改动

**服务端（`jflove-server`）**

| 文件 | 改动 |
| --- | --- |
| `src/services/file_service.py` | 新增合并进度注册表 `_merge_progress`（`state`/`processed`/`total`/`file_size`/`started_at`/`elapsed_seconds`），合并循环每 16 片更新并 `await asyncio.sleep(0)` 让出事件循环（否则合并期间进度接口无法响应）；`merge_progress()` 查询；`prune_merge_progress()` 清理 1 小时前的记录；失败标 `failed`；合并结束打印耗时日志 |
| `src/controllers/file_controller.py` | 新增 `POST /api/v1/files/upload/progress`：走加密信封（`decrypt_request_body` + `encrypt_response`）、`_get_user` 取 token、`is_upload_owned_by` 校验归属（他人 → 403） |
| `src/main.py` | 清理循环追加 `prune_merge_progress()`、`cleanup_orphan_partials(db)` |

> 明文白名单未扩大（该接口在加密信封内）；未引入新算法 / 新密钥。

**桌面端（`jflove-desktop`，Windows 与 Linux 共用同一份代码）**

| 文件 | 改动 |
| --- | --- |
| `src/services/file_service.py` | `_finalize()` 把 `complete` 放子线程、主线程每秒轮询服务端合并进度并通过 `progress_callback(processed, file_size, "finalizing")` 回报；`complete` 超时用 `(30s, 3600s)`；超时后**核验远端**而不是重发；`_already_uploaded()` 在续传记录命中时先核对远端 size+mtime（±2s），命中即视为完成 —— **避免慢合并被当成失败而重复上传** |
| `src/utils/transfer_manager.py` | **`progress` 信号改为 `Signal(str, "qint64", "qint64", str)`**（byte 计数不能用 32 位） |
| `src/utils/http_client.py` | `post(..., timeout=)`；`is_transient_error()` 区分可重试错误 |
| `ui/src/pages/SyncPage.tsx` | 订阅 `transfer.added/updated/removed` 事件**即时刷新**（合并突发 300ms 节流）——窗口在后台时 Chromium 会把 `setInterval` 节流到每分钟一次，只靠轮询会让进度"看起来卡住" |

### 13.4 实测（Linux 本机，真实服务端 + 真实挂载）

| 项 | 数据 |
| --- | --- |
| 5.7GB ISO（挂载目录 → 远端） | 上传 137 秒 + 合并 13.7 秒（2.4 秒/GB，5815 片） |
| 3.0GB ISO | 合并 6.2 秒（2.0 秒/GB，3115 片） |

### 13.5 Windows 侧一致性

以上改动**全部与平台无关**（HTTP 客户端、传输管理器、UI 均无平台分支）：

- `Signal("qint64")` 修复对 Windows 同样生效（Windows 上 >2GB 上传同样会 emit 溢出）；
- `_finalize` 轮询合并进度、`_already_uploaded` 防重复、分片重试、断点续传均为纯 Python 逻辑；
- **Windows 待实测清单**：① >2GB 文件上传时界面百分比连续变化；② `finalizing` 阶段显示
  「服务端合并校验中 N% · 已 X 秒」；③ 弱网（或人为调大服务端合并耗时）下不出现整文件重传；
  ④ 强杀应用后重启能续传。

### 13.6 需要重启服务端一次

合并进度接口与清理机制是**新增的服务端能力**。不重启服务端时：

- 客户端不会报错（接口 404 时只影响进度显示，见 `_report_merge_progress` 的兜底），
  上传本身仍能完成，`finalizing` 只显示「已 X 秒」而没有百分比；
- 旧的临时目录泄漏问题（`_upload_sessions` 永不过期）仍然存在。

⇒ 建议重启一次服务端，即可获得百分比与残留回收。

## 14. BUG 修复：Windows 挂载目录「无法打开 / 云操作 60s 超时」（2026-10-19）

### 14.1 现象

Windows 上启用挂载点后，资源管理器能看到挂载根（带云状态图标），但**双击进入报**
「位置不可用 · 无法访问 D:\磁盘云同步 · 云操作未在超时时间结束之前完成。」
（`0x800701AA` = `ERROR_CLOUD_FILE_REQUEST_TIMED_OUT`）。Linux（FUSE）侧同一功能正常。

### 14.2 根因：`cfapi.h` 枚举值写错，目录枚举回调根本没被应答

`src/utils/mount_cfapi.py` 里的回调类型常量与官方枚举**错位**：

| 常量 | 原值（错） | 官方值 |
| --- | --- | --- |
| `CF_CALLBACK_TYPE_FETCH_PLACEHOLDERS` | 2（实为 `CANCEL_FETCH_DATA`） | **3** |
| `CF_CALLBACK_TYPE_NOTIFY_DEHYDRATE` | 6 | 7 |
| `CF_CALLBACK_TYPE_NOTIFY_DELETE` | 8 | 9 |
| `CF_CALLBACK_TYPE_NOTIFY_RENAME` | 10 | 11 |
| `CF_OPERATION_TYPE_TRANSFER_PLACEHOLDERS` | 2（实为 `ACK_DATA`） | **4** |
| `CF_OPERATION_TYPE_ACK_DELETE` / `ACK_RENAME` | 3 / 4 | 6 / 7 |

注册表里没有真正的「目录枚举」回调，`Population=FULL` 的 sync root 被枚举时平台
无人应答 ⇒ 等满 **60s** ⇒ 返回 `0x800701AA`；且该目录随后进入「请求未完成」状态，
再次导航也不再回调（Microsoft Q&A 已记录同类现象）。

### 14.3 证据（本机，Windows，实测）

```text
# 安装版 exe 符号反查（10-18 构建，C:\Program Files\JFLove\JFLove.exe）
FETCH_PLACEHOLDERS : False        # 连回调都没注册
CfUnregisterSyncRoot : False

# 直接枚举真实挂载根（旧实现）

# 跨进程 A/B 探针（jflove-desktop/poc/cfapi/cfapi_crossproc_probe.py，枚举放在子进程 = 模拟资源管理器）
--legacy（只注册 FETCH_DATA）  → CHILD_TIMEOUT >80s
修复后（注册 FETCH_PLACEHOLDERS=3）→ 回调 FETCH_PLACEHOLDERS ×3、CfExecute 全部接受
                                  CHILD_OK 0.00s ['p0.bin', 'p1.bin', 'sub']
```

### 14.4 修复内容（仅 Windows 文件，Linux FUSE 未改动）

`jflove-desktop/src/utils/mount_cfapi.py`：

1. **枚举值按 `cfapi.h` 全部改正**（回调类型 + 操作类型），并注明来源；
2. `_CF_OPERATION_PARAMETERS` 重建为官方布局（`ParamSize` + union），
   **`ParamSize` 按操作取精确值**（`8 + sizeof(该操作结构)`：TRANSFER_DATA/TRANSFER_PLACEHOLDERS=40、
   ACK_DEHYDRATE=32、ACK_DELETE/ACK_RENAME=16），原来一律传整包 96；
3. 各操作独立载荷结构（`AckDelete` / `AckRename` / `AckDehydrate` / `AckData` / `RetrieveData` /
   `RestartHydration`），`ACK_DEHYDRATE` 补齐 `FileIdentity`（「释放空间」才能完成）；
4. 补注册 `CANCEL_FETCH_PLACEHOLDERS`（仅日志），便于区分「平台撤销」与「我们没应答」；
5. `FETCH_DATA` 远端失败时明确回 `STATUS_UNSUCCESSFUL`（0xC0000001），不再回「成功 0 字节」；
6. `CfExecute` 失败统一打印 `mount/type/hr`（原先只打印 hr，无法定位是哪个回调）。
