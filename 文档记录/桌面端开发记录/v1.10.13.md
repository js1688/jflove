## 1. 四条用户现象与根因

### P1 复杂认证「已连接」但目录始终不加载（与 P2 同源）

| 项 | 内容 |
| --- | --- |
| 现象 | 密码 + 密钥（密钥还有口令）的服务器显示「已连接」，SFTP 目录一直转圈；WinSCP 同一账号是「密钥口令 → Further authentication required（账号密码）」两步 |
| 根因 | paramiko 在服务器要求**继续认证**时 `auth_publickey/auth_password` **返回剩余方式列表**（不抛异常）；旧 `_auth_publickey` 忽略返回值直接 return，`_authenticate` 也不校验 `transport.is_authenticated()` ⇒ 未认证却上报 `phase=ready`（`src/services/ssh_session.py`） |
| 测试为何没拦住 | `tests/test_remote_key_auth_v1_10_11.py` 的假 transport 用「抛 `PartialAuthentication`」模拟部分认证，与真实 paramiko「返回列表」语义不一致 |
| 修复 | 认证状态机：按返回列表继续推进（密码 → keyboard-interactive → 再补密钥），支持 `publickey,password` / `password,publickey` / `publickey,keyboard-interactive`；keyboard-interactive 提示含 password/密码用账号密码代答，验证码类提示走 UI；结束硬校验 `is_authenticated()`，未完成绝不发 ready |

### P2 多条 SFTP 连接成功但目录「一直加载中」

| 项 | 内容 |
| --- | --- |
| 根因 A | `open_sftp()` 直接调 `Transport.open_sftp_client()`：`open_session` 默认 channel timeout 3600s；`invoke_subsystem("sftp")` 内部是**无超时** `event.wait()`，服务端不回应即永久阻塞；SFTP channel 默认 `timeout=None`，`listdir` 的 `recv` 同样无界 |
| 根因 B | P1 的假「已连接」也算一类：未认证 transport 去开 SFTP 通道 |
| 根因 C | 桥每个请求独立 Worker 线程；`SftpView` 连接期间每秒探活 + 就绪后首次加载可能同时调 `_sftp()`，旧实现无锁创建/复用同一 client（paramiko SFTPClient 不支持并发同步请求） |
| 修复 | `open_sftp()`：未认证直接报错；`open_session(timeout=CONNECT_TIMEOUT)`；定时器在 `SFTP_OPEN_TIMEOUT`（默认 15s，可 `JFLOVE_SFTP_OPEN_TIMEOUT` 覆盖）到点关闭 channel 让阻塞 wait 失败；`chan.settimeout(SFTP_OP_TIMEOUT)`（默认 45s，可 `JFLOVE_SFTP_OP_TIMEOUT`）；桥侧按会话加锁串行 listdir/mkdir/rename/delete，失败即丢弃坏 client，超时给中文原因并记录耗时 |
| UI | 「加载中…（已用 N 秒）」、超时原因、「取消加载」（关闭 client 中断阻塞读）、失败后「重试」 |

### P3 凭据字段无法清空（留空 = 不修改）

| 项 | 内容 |
| --- | --- |
| 根因 | 服务端已支持 `clear_password` / `clear_private_key`（`jflove-server/src/services/ssh_service.py:224-233`），渲染层类型也声明了，但表单从未发送；口令单独修改/清空没有服务端通道（旧逻辑只在提交新私钥时写 passphrase） |
| 修复 | 密码 / 私钥 / 私钥口令各加「清空」按钮；编辑态保存时发送 `clear_password` / `clear_private_key` / `clear_passphrase`（服务端写空串）；输入新值自动撤销清空标记；新建态仅清本地输入 |
| 服务端 | 新增 `clear_passphrase`；支持「不换私钥、只提交非空 passphrase」的口令单独更新；`clear_private_key` 仍联动清口令 |

### P4 跳板连接下拉「点击后展示框慢慢变大」

| 项 | 内容 |
| --- | --- |
| 现象 | 新建/编辑 SSH/SFTP 时「跳板连接」下拉点击后展示框持续变大；用户两台显示器，跨屏后必现 |
| 根因 | 旧实现是原生 `<select>`（`RemoteConnectionForm.tsx`）：弹出列表是 QtWebEngine/系统级弹层，Windows 多显示器混合 DPI 下跨屏后弹层尺寸/位置不随缩放更新（数据层不重复：store 整体替换、服务端查询无重复） |
| 修复 | 改为页内自绘下拉（DOM 列表 + `max-h-56` 滚动 + 外部点击/Esc 关闭 + 按 id 去重 + 排除会成环的下游连接）；表格/表单不再出现该原生 `<select>`；打开编辑时拉**全量**连接（不受搜索词过滤） |
| 未覆盖 | KVM Windows 靶机是单显示器，无法复现「跨屏 DPI」；已做结构性消除，需用户在真机复验 |

### 真实 SSH/SFTP 证据

- **真实 paramiko 测试服务**（本机 127.0.0.1 随机端口，`AUTH_PARTIALLY_SUCCESSFUL` + `keyboard-interactive`）：
  密钥 → 服务器要求继续认证 → 客户端用账号密码完成 → `is_authenticated()=True`；另一条用例走简单密钥 + 真实 SFTP 子系统并 `listdir` 出 `opt` / `readme.txt`。
- **本机 sshd 冒烟（`scripts/verify/ssh_smoke.py`）未跑通**：临时测试密钥不在 `~/.ssh/authorized_keys`，`ssh -i /tmp/jf-ssh-test/id_ed25519 ...` 返回 `Permission denied (publickey,...)`。
  **未覆盖（原因：本机测试密钥未授权；未擅自改 `~/.ssh/authorized_keys`）**。真实 SFTP 链路由上述 paramiko 测试服务覆盖。

## 4. 已知边界

- Windows 多显示器混合 DPI 的弹层复现依赖真机双屏，KVM 靶机单屏无法证伪；本版做的是**去掉系统弹层**这一结构性修复。
- `JFLOVE_SFTP_OP_TIMEOUT` 默认 45s：超大目录在极高延迟链路上仍可能被判超时；加载中显示已用秒数并可取消，用户可按需调大环境变量。
- keyboard-interactive 的「验证码类」提示按关键词判断（verification/code/OTP/动态/验证码…），非英文/中文提示会落到 UI 输入，不会误用账号密码代答。
- 未删除 `jflove-app/lib/pages/remote/*` 等未接入代码（避免与本次修复混在一起），见 PMO 下个版本候选台账。
