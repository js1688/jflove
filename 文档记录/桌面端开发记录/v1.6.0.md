## 6. 施工面 4：单实例 + 入口（提交 `19e5506`）

### 6.1 与设计 §6.6.1 的一处**已复现**的修订

设计原定「`listen()` 的返回值即唯一仲裁」。**实测在 Windows 上不成立**：

| 探针 | 实测结果（原始产物在仓库内） |
| --- | --- |
| `poc/editor-probes/r2-local-server-arbitration.py` → `out/r2-arbitration.json` | A（首进程）`listen=True` / `isListening=True` / `errorString=""` / `serverError=UnknownSocketError`；**B 在 A 存活期间对同名 `listen()` 同样返回 `True`**，`errorString()` 与 `serverError()` 与成功时**同值** ⇒ `listen()` 无法仲裁 |
| `poc/editor-probes/r3-single-instance-roundtrip.py` → `out/r3-roundtrip.json` | 三进程真实往返：A `is_primary=True`；B `is_primary=False`（自认第二实例）且 `forwarded=True`（收到 `ack`）；A 收到 `[[["D:\资料\往返 测试.txt"], "single_instance"]]` ⇒ **`all_passed=True`**，中文路径逐字符一致 |

⇒ 实现采用「**连接探测优先 + 自探测**」，并以 `ack` 作为"首实例确实收到"的判据
（设计 §6.6.1 的其余口径：`QLocalServer`/`QLocalSocket`、行分隔 JSON、陈旧 socket 兜底、

### 10.2 M-5 UTF-16 换行被误判（提交 `8b3cb6d`）

- **根因**：`text_detect_service.py::_detect_line_end()` 直接数**原始字节**的 `0D 0A`；
  UTF-16LE 的 CRLF 是 `0D 00 0A 00`，永远不含相邻 `0D 0A` ⇒ 判成 `lf`；
  **未编辑直接保存**就把全文换行从 CRLF 改成 LF（违反 AC-20「未编辑保存不改字节」与 AC-S4③）。
- **修法**：新增 `_LINE_END_CODECS`（`utf-16le`/`utf-16be` ↔ BOM 图案），
  `_detect_line_end(sample, encoding)` **先按已判定编码解码再数换行**；已判定编码未知时退回字节计数。
  两处调用点分别传入 B3 救援路径的 `verdict.utf16_pattern` 与主路径的 `encoding`。
- **判据**：新增 `TestUtf16LineEnd` **8 例**（含 `probe → read_text → encode_text` 的**字节级往返相同**）；
  负向对照（`codec=None` 退化为数字节）⇒ **6 failed / 28 passed**，恢复后 34 passed；
  `pytest tests/ -q` ⇒ **438 passed**。
- **附带发现（已登记，未改）**：**无 BOM 的 UTF-16LE `.txt` 仍被判为 `utf-8`** —— 白名单扩展名按 AC-49 跳过嗅探，
  而 NUL 字节是合法 UTF-8 ⇒ B3 救援分支对白名单扩展名**不可达**（对 `.xyz` 一类才走）。属设计取舍，留观察。
