# 桌面端 v1.10.21（远程连接：多步认证共用一条 ssh-userauth 会话）

> 分类：**代码 BUG**（`AGENTS.md §7.5.3` 快速修复通道）
> 来源：用户 2026-11-21 反馈 v1.10.20 仍连不上 `16.162.59.156:6522`（`SSH-2.0-UNLAWFUL ENTRY…` 网关）
> 计划：`plans/v1.10.21-remote-single-userauth-session.md`
> 影响模块：仅 `jflove-desktop/`（服务端 / 数据库 / 加密协议不改）

## 1. 根因（报文级实测，非推测）

### 1.1 症状回顾

用户报错（v1.10.20）：

```text
服务器已接受这把密钥，但**账号密码**没有被接受（本次已发送：publickey→password；
服务器当前的列表：publickey）。私钥本身没有问题…
诊断：…；首轮结果=ok（服务器允许：password）；认证序列=publickey→password；
服务器仍要求：publickey
```

三个版本（v1.10.16 / 1.10.19 / 1.10.20）都在改「发哪个方法」，症状不变。

### 1.2 真凶

`paramiko.Transport.auth_publickey` / `auth_password` / `auth_interactive`
**每调用一次就新建一个 `AuthHandler`，并重发一次 `SSH_MSG_SERVICE_REQUEST("ssh-userauth")`**
（`paramiko/auth_handler.py:185-191` 的 `_request_auth()`；`transport.py:1626/1698` 每次都 `AuthHandler(self)`）。

标准客户端（OpenSSH / JSch / WinSCP）整个认证过程**只发一次**服务请求，
之后在同一会话里连续发多条 `SSH_MSG_USERAUTH_REQUEST`。

用户那台网关把「新的 ssh-userauth 服务请求」当作**认证进度重置**，于是：

```text
发 publickey   → 服务器 partial：允许 password     （公钥这一步过了）
重发服务请求   → 服务器把「公钥已通过」清掉        ← 真凶
发 password    → 服务器认为公钥还没过 ⇒ 拒绝，且只列 publickey
```

### 1.3 三条独立证据

**① 客户端报文级对比**（`/tmp/jf_wire_trace_probe.py`，本地真实 SSH 服务）：

```text
A 当前 JFLove：
  SERVICE_REQUEST[ssh-userauth] → USERAUTH_REQUEST[publickey]
  → SERVICE_REQUEST[ssh-userauth] → USERAUTH_REQUEST[password]     ← 多发一次

B JSch/WinSCP：
  SERVICE_REQUEST[ssh-userauth] → USERAUTH_REQUEST[publickey]
  → USERAUTH_REQUEST[password]                                     ← 只有一次
```

**② 复现型网关 A/B 对比**（`/tmp/jf_reset_gateway_probe.py`，网关规则＝新服务请求即重置）：

```text
A. 当前 JFLove（每步重发）    认证成功 = False
    收到新的 ssh-userauth 服务请求 → 认证进度清零
    publickey 通过 → partial(password)
    收到新的 ssh-userauth 服务请求 → 认证进度清零
    password 被拒（公钥进度已丢 ⇒ 只列 publickey）

B. JSch / WinSCP（一次服务）  认证成功 = True
    publickey 通过 → partial(password)
    password 通过 → Access Granted
```

A 的产物与用户报错**逐字吻合**。`RFC 4252 §4` 的认证模型是「服务器驱动、一条会话内
多步推进」，而 paramiko 的 `auth_*` 便利方法正是按「一次调用＝一条独立 userauth」实现的。

**③ 协议级端到端**（修复后，`/tmp/jf_e2e21.py` + `/tmp/jf_gw21.py` 复刻网关）：

```text
[srv] 服务请求 #1
[srv] publickey 通过 → partial(password)
[srv] password 通过 → Access Granted
```

## 2. 修复

新增 `_AuthChannel`（`ssh_session.py`）：把「一次 userauth 服务会话」封装起来。

| 行为 | 修复前 | 修复后 |
| --- | --- | --- |
| 第一步 | `auth_publickey()` → 内含 SERVICE_REQUEST | 同（首次仍走 `_request_auth`） |
| 后续每一步 | `auth_password()` → **再发一次 SERVICE_REQUEST** | 直接发 `SSH_MSG_USERAUTH_REQUEST`，**不发服务请求** |
| userauth 会话数 | 每个方法一条 | **全程一条** |

实现要点：

- 复用**同一个** `paramiko.auth_handler.AuthHandler` 实例，并挂回 `transport.auth_handler`
  （run 循环靠 `transport.auth_handler._handler_table` 分发 `SERVICE_ACCEPT` / `USERAUTH_*`）；
- 报文组装复用 paramiko 自己的 `_get_key_type_and_bits` / `_finalize_pubkey_algorithm` /
  `_get_session_blob` / `sign_ssh_data`，**不自行实现签名与编码**；
- 只对**真实 `paramiko.Transport`** 生效；测试替身（自定义 `auth_*`）继续走原路径；
- `ssh-rsa`（RSA-SHA1）回退也走同一条会话；
- 会话挂在 `self._active_auth_channel` 上、认证结束置 `None` —— **不改**
  `_attempt_auth` / `_attempt_legacy_rsa` 的签名，既有用例与替身零改动。

同时修正一处**前端与服务端口径不一致**（实机验证时暴露）：
`RemoteConnectionForm.tsx` 的「密码 + 密钥」在新建时拦下了空密码，而服务端
（`ssh_service.normalize`）早已允许「有私钥即可留空」。现按服务端同口径：
`authType === 'password_publickey' && (本次私钥 || keyToken || hasSavedKey)` 才允许留空。

### 4.5 已知未覆盖

  复刻网关在**协议级 + 界面级**双向验证（该规则正是从用户报错反推并逐字复现出来的）。
- Windows 真机 VM（`probe.sh` 报 `windows_vm: 关闭`）：未覆盖安装包行为。
- 复刻网关不实现 SFTP 子系统，界面停在「加载中…」属网关限制（认证已 `Access Granted`）。

## 5. 用户侧复验

装 v1.10.21 后连同一台服务器：认证方式「密码 + 密钥」，**密码栏可以留空**，
连上后在弹框输入账号密码即可。

若仍失败，请把整条 `诊断：…` 发回 —— 关注两点：

1. `认证序列` 是否仍为 `publickey→password`（本版不会再出现多轮重发）；
2. 日志（Windows：`%LOCALAPPDATA%\JFLove\logs\app.log`）里是否出现
   `Error reading SSH protocol banner` / `Socket is closed` 之类的连接层异常。

## 6. 为什么这次能修好（与前几版的区别）

| 版本 | 改的是 | 为什么没解决 |
| --- | --- | --- |
| ≤1.10.16 | 发哪个方法、密钥发几次 | 每步仍重开 userauth ⇒ 网关进度被重置 |
| 1.10.17–1.10.18 | 键盘交互兜底、文案 | 同上 |
| 1.10.19 | 改用严格 authlist + 弹框密码走 `password` | 同上（且加的 `none` 探测吃掉了限次网关的机会） |
| 1.10.20 | 删除 `none` 探测（最小请求） | 请求数对了，但**每步仍重开服务会话** |
| **1.10.21** | **全程共用一条 userauth 会话** | 报文序列与 JSch/WinSCP 完全一致 |
