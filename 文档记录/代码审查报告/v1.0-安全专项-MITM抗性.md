# JFLove v1.0 安全专项审查 — 企业 MITM 抗性

| 审查项 | 内容 |
| ------ | ---- |
| 审查目标 | 验证应用层加密在企业级 MITM 代理（公司根 CA 可解密 HTTPS）下的有效性 |
| 审查日期 | 2026-05-04 |
| 审查范围 | jflove-server / jflove-desktop 全部 HTTP 通信路径 |
| 关联文档 | 设计文档 v1.0 §3.3-3.5（加密机制）、需求文档 v1.0 §5.4（安全与加密） |

---

## 1. 执行摘要（最重要）

> **TL;DR**：现有方案在「**被动 MITM**」（公司只读取流量做 DLP）场景下，**绝大多数请求和响应字段是安全的，但文件下载和文件预览是裸奔的**。在「**主动 MITM**」（公司代理实时改写流量）场景下，整个加密通道可被旁路，**这是设计层面的根本缺口**。

**3-5 句话讲清楚公司能看到什么 / 看不到什么**：

- ✅ **看不到**：登录密码、JWT、笔记内容、文件名（在 `body.path` 里）、目录结构、用户名（业务接口里）、SQL 数据等所有走 `decrypt_request_body / encrypt_response` 的字段
- ❌ **能看到**：**所有文件下载和预览的完整二进制内容**（FileResponse 直发，无应用层加密）；下载时 `Content-Disposition` 头里**裸露原始文件名**；上传/下载文件的字节大小（content-length 头）
- ⚠️ **元信息泄露**：HTTP 方法、URL 路径模板（含 `disk_id` / `user_id` / `upload_id` 等数字 ID）、`X-Session-ID`、Cookie、流量时序与体积模式
- 🔥 **结构性风险**：当前 X25519 密钥交换**没有服务端身份认证**——主动 MITM 代理可以替换密钥交换消息插到中间，使应用层加密失效。这是设计缺口，需要引入服务端公钥固定（pinning）或预共享密钥才能真正防住"公司根 CA"威胁

## 2. 加密体系总评

### 2.1 加密原语选择 — ✅ 合规

[jflove-server/src/utils/crypto.py](jflove-server/src/utils/crypto.py)、[jflove-desktop/src/utils/crypto.py](jflove-desktop/src/utils/crypto.py)：

- 非对称：X25519 ECDH（椭圆曲线 Diffie-Hellman），256 位安全
- 派生：HKDF-SHA256，盐 `b"jflove-v1"` 双端一致
- 对称：ChaCha20-Poly1305 AEAD，12 字节随机 nonce，含认证标签
- nonce 用 `os.urandom(12)`，CSPRNG 来源
- 私钥：服务端 `X25519PrivateKey` 生成后用完即销毁，session_key 仅存内存 (`_session_store: dict`)，不落盘 — 符合"会话密钥不重用 + 不落库"的需求

**结论**：加密原语和参数选择正确，无算法层面问题。

### 2.2 信封格式 — ✅ 合规

请求/响应一律 `{"nonce": <base64>, "ciphertext": <base64>}` 包封，base64 仅用于二进制→文本转换，**不是加密替代品**（chunk_data 字段同理 — 见下文 §4.2 详述）。

### 2.3 客户端 HTTP 客户端 — ✅ 合规

[jflove-desktop/src/utils/http_client.py:137-149](jflove-desktop/src/utils/http_client.py#L137-L149) 的 GET 实现把参数放进**加密 body** 而不是 URL query：

```python
def get(self, endpoint: str, data: dict | None = None) -> dict:
    url = self._base_url() + endpoint
    payload = self._build_payload(data)
    resp = requests.get(url, json=payload, headers=self._auth_headers(), timeout=30)
```

**重要**：这是非常规但正确的设计——绕过 HTTP 标准的 query string 暴露。GET / POST / PUT / DELETE 全部走这条路径，URL 上**没有任何参数值**。

### 2.4 服务端中间件 — ✅ 合规

[jflove-server/src/utils/middleware.py:15-42](jflove-server/src/utils/middleware.py#L15-L42)：所有进入业务接口的请求强制走 `decrypt_request_body`，缺 `X-Session-ID` 直接 401。

## 3. 严重发现：高危

### H-1：文件下载/预览**响应体未加密**（严重）

**位置**：

- [jflove-server/src/controllers/file_controller.py:233](jflove-server/src/controllers/file_controller.py#L233) — `download_file` 返回 `FileResponse(file_path, filename=rel_path.split("/")[-1])`
- [jflove-server/src/controllers/file_controller.py:313](jflove-server/src/controllers/file_controller.py#L313) — `preview_file` 返回 `FileResponse(file_path)`

**问题**：

`FileResponse` 是 Starlette 内置的**原始字节流**响应。整个文件内容直接走 HTTP body，**不经过 `encrypt_response` 加密**。在公司 MITM 场景下：

1. 请求体加密 → 公司看不到 `disk_id` 和 `path`，**看不到你下载的是哪个文件** ✅
2. 但响应体是原始字节 → 公司**完整捕获文件内容**，可以做 DLP / 内容分析 / 备份 ❌

加上 line 233 还把 `filename=rel_path.split("/")[-1]` 设到 `Content-Disposition` 响应头里 → **文件名也明文泄露**。

代码中明确承认了这点（[http_client.py:9-10](jflove-desktop/src/utils/http_client.py#L9-L10) 注释）：

```python
"""
下载文件接口返回原始字节流（服务端使用 FileResponse，不加密响应体）。
"""
```

**严重等级**：🔴 **高**。直接违背用户核心诉求"我连文件内容都不想被公司捕获到"。

**MITM 场景下能看到的**：

| 场景 | 公司能看到 |
| ---- | ---------- |
| 下载 `secret.docx` 1.2 MB | ✅ 完整 1.2 MB Word 文件二进制 + `Content-Disposition: filename="secret.docx"` |
| 预览 `1080P_HD.mp4` | ✅ 完整视频流（实时 DLP 触发） |
| 预览 `password-list.txt` | ✅ 完整文本内容 |

**修复建议（按优先级排序）**：

1. **首选**：把 `download` / `preview` 改为加密 chunked response。复用客户端 `_build_payload` 思路：服务端边读边按固定大小分片，每片 ChaCha20-Poly1305 加密，用相同信封格式流式输出。客户端 `download_to_file` 改为流式解密+落盘。

   ```python
   # 服务端示意
   from fastapi.responses import StreamingResponse
   async def download_file(...):
       ...
       async def encrypted_stream():
           with open(file_path, "rb") as f:
               while True:
                   chunk = f.read(CHUNK_SIZE)
                   if not chunk:
                       break
                   nonce = os.urandom(12)
                   ct = chacha.encrypt(nonce, chunk, None)
                   # 4 字节大端长度前缀 + nonce(12) + ciphertext + tag(16)
                   yield struct.pack(">I", 12 + len(ct)) + nonce + ct
       return StreamingResponse(encrypted_stream(), media_type="application/octet-stream")
   ```

2. **同时**：在响应 header 中**移除 `filename`**（不要再把文件名放 `Content-Disposition` 中），文件名让客户端自己从原始 `path` 取（请求体已经加密，所以本来就在客户端手里）。

3. **同时**：上传方向已经是密的（chunk_data 在加密 body 内），但**响应头里的 `Content-Length` 仍泄露密文长度**。建议在加密分片中加适量随机 padding（如 16 字节随机 padding），让 MITM 无法精确推算文件大小。这是高级强化项，严格 size-blinding 还需要等长流量整形，工程量大，可作为 v2 目标。

### H-2：密钥交换缺乏服务端身份认证（结构性高危）

**位置**：[jflove-desktop/src/services/auth_service.py:120-158](jflove-desktop/src/services/auth_service.py#L120-L158) + [jflove-server/src/services/auth_service.py:59-79](jflove-server/src/services/auth_service.py#L59-L79)

**问题**：

X25519 ECDH 提供机密性 + 前向保密，但**不提供服务端身份认证**。当前流程：

```text
客户端 ----(ECDH 公钥 client_pub)----> 服务端
客户端 <----(ECDH 公钥 server_pub)---- 服务端
两端独立计算 session_key = HKDF(ECDH(client_pub, server_pub))
```

公司根 CA 能让 HTTPS 鉴权失效。在主动 MITM 场景下：

```text
客户端 -- pub_A --> [公司代理] -- pub_B --> 真实服务端
客户端 <-- pub_Y --[公司代理]<-- pub_X --- 真实服务端
客户端与代理共享 K1 = HKDF(ECDH(A, Y))
代理与服务端共享 K2 = HKDF(ECDH(B, X))
代理坐在中间用 K1 解→K2 加密，全程明文可见
```

**严重等级**：🔴 **高**（设计缺陷，不是单点 bug）。

**用户的具体提问**：
> "公司能否通过中间人代理捕获到内容然后解密"

如果公司只是**被动捕获 + 离线解密**：✅ 当前设计安全（ECDH 离散对数难题保证）。

如果公司是**主动改写流量**（典型企业级 DLP 代理就是主动的）：❌ 当前设计**可被旁路**，应用层加密形同虚设。

**修复建议**：

引入**服务端公钥固定（pinning）** —— 客户端硬编码 / 预置一个服务端长期身份公钥，密钥交换时验证服务端给出的临时公钥被该长期密钥签名。两条可行路径：

1. **硬编码服务端公钥指纹**（最简单）

   ```python
   # 客户端 src/config/settings.py 中固定一个值
   SERVER_PUBLIC_KEY_FINGERPRINT = b"\xab\xcd...\x12"  # 32 字节
   ```

   每次 key-exchange 收到 `server_public_key` 后，先用它做 HKDF-SHA256 哈希，与本地 fingerprint 比对，不一致 → 强制断开 + 报警。

2. **服务端长期签名密钥**（更专业）

   服务端启动时加载一个长期 ED25519 签名密钥（作为身份凭证）。Key-exchange 时，服务端把临时公钥用长期密钥签名一并下发。客户端用预置的长期公钥验签。

二者都需要客户端**预置**一个不可变的服务端身份指纹，如果用户能保证安装包从可信渠道下载（如官方 Github Release 下载二进制后用 SHA256 校验），就有了根信任。

> 这是 SSH 防 MITM 的同款套路（"Are you sure you want to continue connecting (yes/no)?" 那一步固定的指纹）。

## 4. 严重发现：中危

### M-1：JWT 通过加密 body 传递 — ✅ 实际正确，但有"后门"代码

**位置**：[jflove-server/src/controllers/file_controller.py:38](jflove-server/src/controllers/file_controller.py#L38)、[note_controller.py:31](jflove-server/src/controllers/note_controller.py#L31)、[sync_controller.py:27](jflove-server/src/controllers/sync_controller.py#L27)、其他 `_get_user` 都有：

```python
token = body.get("token", "") or request.headers.get("Authorization", "").removeprefix("Bearer ")
```

**问题**：

服务端**同时接受**两个来源：
1. 加密 body 中的 `token` 字段（推荐）
2. `Authorization: Bearer xxx` header（明文）

客户端代码确认只用第 1 种 ([http_client.py:62-64](jflove-desktop/src/utils/http_client.py#L62-L64))：

```python
if session_manager.token and "token" not in payload:
    payload["token"] = session_manager.token
```

**所以当前生产路径是安全的**。但代码留了 fallback，一旦未来有人加 `headers={"Authorization": ...}` 或外部脚本调用，**JWT 就会以明文走在 HTTP header 里被 MITM 看到**。

**严重等级**：🟡 中（潜在埋雷）。

**修复建议**：删除所有 `_get_user` 中的 `or request.headers.get("Authorization", "")` 兜底，强制只从加密 body 取 token：

```python
async def _get_user(request: Request, db: aiosqlite.Connection, body: dict) -> dict:
    token = body.get("token", "")
    if not token:
        raise HTTPException(status_code=401, detail="缺少认证令牌")
    try:
        return await auth_service.get_current_user(db, token)
    except ValueError as e:
        raise HTTPException(status_code=401, detail=str(e))
```

### M-2：上传分片 `chunk_data` 实际上是加密的（澄清）

**位置**：[jflove-desktop/src/services/file_service.py:139-147](jflove-desktop/src/services/file_service.py#L139-L147) + [jflove-server/src/controllers/file_controller.py:152-164](jflove-server/src/controllers/file_controller.py#L152-L164)

**问题分析**：

之前担忧的"chunk_data 只是 base64"，**实测是误解**：

```python
# 客户端 file_service.py:142-147
chunk_b64 = base64.b64encode(chunk).decode()
http_client.post("/api/v1/files/upload/chunk", {
    "upload_id": upload_id,
    "chunk_index": i,
    "chunk_data": chunk_b64,
})
```

`http_client.post` 把整个字典（含 `chunk_data` 字段）经过 `_build_payload → encrypt → ChaCha20-Poly1305` 包成加密信封再发 HTTP。base64 只是为了把二进制塞进 JSON，**外层一定是加密的**。

服务端 [file_controller.py:154-158](jflove-server/src/controllers/file_controller.py#L154-L158)：

```python
body = await decrypt_request_body(request)  # ← 解密整个 body
chunk_data = base64.b64decode(body.get("chunk_data", ""))  # ← 解密后才 base64 解码
```

**结论**：上传方向是**完全加密的**。MITM 看到的是加密信封，不是文件字节。

**严重等级**：🟢 无问题，仅记录"已验证安全"。

### M-3：URL 路径中嵌入数字 ID — 🟡 信息量低但可观察

**位置**：

- [permission_controller.py:62](jflove-server/src/controllers/permission_controller.py#L62) — `/users/{user_id}/disks/{disk_id}`
- [sync_controller.py:97-98](jflove-server/src/controllers/sync_controller.py#L97-L98) — `/configs/{config_id}/snapshot`
- [file_controller.py:192](jflove-server/src/controllers/file_controller.py#L192) — `/upload/{upload_id}`
- [virtual_disk_controller.py:90, 120, 144](jflove-server/src/controllers/virtual_disk_controller.py) — `/{disk_id}` 等
- [user_controller.py:87](jflove-server/src/controllers/user_controller.py#L87) — `/{user_id}`

**问题**：

URL 路径模板里有数字 ID（user_id / disk_id / config_id）和一个 UUID（upload_id）。MITM 能看到：

```text
PUT  /api/v1/sync/configs/3
GET  /api/v1/sync/configs/3/snapshot
POST /api/v1/files/upload/chunk
DELETE /api/v1/files/upload/d3f8e2a1-...
```

**能推断的**：
- 用户活动时间和频率（由请求时间戳）
- 用户操作哪些"东西"（无语义的数字 ID）
- 上传了一些文件（但看不到文件名 / 大小 / 内容）
- 同步配置数量（看不到具体目录）

**不能推断的**：
- 文件名 / 文件内容 / 路径
- 用户名 / 密码
- 笔记内容

**严重等级**：🟡 中（**元信息泄露**，但不是核心信息）。

**修复建议**（可选，工程量较大）：

如果元信息也想完全屏蔽，唯一彻底的办法是把所有"识别 ID"以加密 body 传递，URL 永远是 `POST /api/v1/cmd`。这相当于把 REST 退化成 RPC over crypto envelope。**不推荐**——破坏 RESTful 风格、Swagger 文档失去意义、调试困难。

折中方案：维持现状即可，元信息泄露在用户场景下风险可控。

### M-4：HTTP 错误响应可能泄露明文 detail

**位置**：所有 controller 的 `raise HTTPException(status_code=4xx, detail=str(e))` —— 至少 30+ 处

**问题**：

服务端遇到错误时返回类似：

```json
{"detail": "对目标磁盘没有读取权限"}
```

这个 JSON 是 FastAPI 默认行为，**未经过 encrypt_response**。MITM 能看到：

- 接口校验逻辑（"用户名或密码错误" / "用户名长度至少 3 字符" / "管理员账号已存在"）
- 业务异常细节（"目录不存在: foo/bar/secret"）— **会泄露用户提供的 path 字段**！
- SQL 异常（如果未捕获）

特别危险的例子：[note_controller.py:79](jflove-server/src/controllers/note_controller.py#L79) 等很多接口把 `ValueError(str)` 直接转 detail，里面可能含用户传入的文件名。

**严重等级**：🟡 中（条件触发的明文泄露）。

**修复建议**：

1. 给所有受保护接口（即非 key-exchange、非 admin-exists、非 health 的）的错误响应也加密：

   ```python
   # 在 controller 顶层加一个工具函数
   def encrypted_error(session_id: str, status_code: int, message: str):
       resp = encrypt_response(session_id, {"detail": message})
       resp.status_code = status_code
       return resp

   # 用法
   raise from encrypted_error(session_id, 403, "无写入权限")
   # 或者用全局 exception_handler 统一处理 HTTPException
   ```

2. 给敏感细节"消毒"——只返回笼统错误码 + 通用消息，详细信息只写日志：

   ```python
   except ValueError as e:
       logger.warning("note read error: %s", e, exc_info=True)
       raise HTTPException(status_code=404, detail="资源不存在")  # 不带原始消息
   ```

## 5. 严重发现：低危

### L-1：明文接口的信息暴露

**位置**：[main.py:46-48](jflove-server/src/main.py#L46-L48)、[auth_controller.py:84-87](jflove-server/src/controllers/auth_controller.py#L84-L87)、[auth_controller.py:39-48](jflove-server/src/controllers/auth_controller.py#L39-L48)

**问题**：

三个明文接口：

| 接口 | 明文内容 | 暴露评估 |
| ---- | -------- | -------- |
| `GET /health` | `{"status": "ok"}` | 仅服务存活探测，无敏感信息 |
| `GET /api/v1/auth/admin-exists` | `{"exists": true/false}` | 暴露**有/无管理员**这一系统状态。攻击者可知"该 JFLove 实例已初始化" |
| `POST /api/v1/auth/key-exchange` | 客户端公钥 + 服务端公钥 | ECDH 协议本来就要求公钥可见，无密码学风险（前提是有 H-2 的服务端身份认证） |

**严重等级**：🟢 低。

**修复建议**：保持现状即可。如果想极致隐藏，可以把 `/admin-exists` 也包成密钥交换的"piggyback"——key-exchange 响应里直接附带 `admin_exists` 字段，省一个明文请求。

### L-2：日志中可能记录敏感字段

**位置**：

- [file_service.py:243](jflove-desktop/src/services/file_service.py#L243) — `logger.info("文件/目录已删除: disk=%d, path=%s", disk_id, rel_path)`
- [file_service.py:212](jflove-desktop/src/services/file_service.py#L212) — `logger.info("文件下载完成: %s → %s（%d 字节）", rel_path, local_save_path, written)`
- [file_service.py:110](jflove-desktop/src/services/file_service.py#L110) — `logger.info("开始上传文件: %s，大小=%d，分片数=%d", filename, file_size, total_chunks)`
- [auth_service.py 服务端](jflove-server/src/services/auth_service.py)、`note_service.py`、`sync_service.py` 多处类似

**问题**：

这些日志写入本地 `logs/app.log` —— 如果日志被公司端点 DLP 抓取（比如公司有"扫描所有用户日志文件"的策略），**文件名 / 路径 / 用户名都泄露**。但这是 endpoint security 问题，不是 MITM 问题，超出本次审查范围。

**严重等级**：🟢 低（不在 MITM 威胁模型内，但仍是隐患）。

**修复建议**：
- 日志中对路径做哈希化或截断：`path=hash[:8]`
- 或开关化日志详细等级：生产环境仅 ERROR 级，开发环境再开 INFO

### L-3：流量元信息泄露（流量分析）

**MITM 可观察但无解法的元信息**：

| 元信息 | 暴露内容 | 风险 |
| ------ | -------- | ---- |
| TCP 连接时序 | "用户 12:00 开始活跃，每 5 分钟一次同步" | 知道使用习惯 |
| 请求频率 / 方向 | "短期内大量 chunk 上传，10MB 总量" | 推断在传大文件 |
| Content-Length | 加密后的密文长度（≈ 明文 + 28 字节开销） | 推断文件大小（误差 ~28B） |
| 目的 IP / 域名 | 服务端 IP 与端口 | 知道你连了哪台服务器 |

**严重等级**：🟢 低。

**修复建议**：

完全防流量分析需要 padding + 时序混淆 + Tor 级匿名网络。对企业 DLP 场景，建议接受这部分元信息可见，集中精力守护"内容不可见"。

## 6. 暴露点清单（按风险排序）

| 严重 | 位置 | 暴露内容 | 是否阻断"公司分析文件内容" |
| ---- | ---- | -------- | -------------------------- |
| 🔴 H | `GET /api/v1/files/download` 响应 | **完整文件二进制**（任意类型）+ 文件名 | ❌ **直接破** |
| 🔴 H | `GET /api/v1/files/preview` 响应 | **完整文件二进制**（任意类型） | ❌ **直接破** |
| 🔴 H | 主动 MITM 场景下整个 ECDH | 应用层加密被旁路 | ❌ **整体可破** |
| 🟡 M | `Authorization` header 兜底 | 潜在的 JWT 明文泄露 | 当前未触发 |
| 🟡 M | HTTP error `detail` 字段 | 用户提供的 path / filename | 条件触发 |
| 🟡 M | URL 路径模板（含数字 ID / upload_id） | 用户活动元信息 | 不影响内容 |
| 🟢 L | 明文接口（`/health` / `/admin-exists` / `/key-exchange`） | 系统状态 + ECDH 公钥 | 不影响内容 |
| 🟢 L | 客户端日志文件 | 文件名 / 路径 | 不在 MITM 模型内 |
| 🟢 L | 流量元信息 | 请求时序 / 大小 | 不影响内容 |

## 7. 修复优先级（按用户核心诉求"文件内容不能被分析出来"）

### P0 - 必须修

1. **加密文件下载/预览的响应体**（H-1）。这是用户核心诉求，且是**唯一**当前会让公司直接拿到文件内容的路径。无论多忙都要修。
   - 服务端：`download_file` / `preview_file` / `download_stream` 改成 `StreamingResponse`，按固定块加密输出
   - 客户端：`http_client.download_to_file` / `download_stream` 改成边收边解密落盘
   - 同时移除响应头中的 `filename`

2. **删掉 `Authorization` header 兜底**（M-1）。一行删除，预防未来埋雷。

### P1 - 强烈建议修

3. **服务端公钥固定**（H-2）。引入预置的服务端身份指纹，防主动 MITM。否则在公司根 CA 场景下，整套加密都可能被旁路。具体方案见 §3.H-2 修复建议。

4. **错误响应也加密 + 消毒细节**（M-4）。避免用户输入回传到 detail 里被 MITM 截获。

### P2 - 可选强化

5. 加密分片中加 padding（H-1 后续）—— 模糊文件大小
6. 客户端日志截断敏感字段（L-2）
7. 把 `admin-exists` 数据捎带到 key-exchange 响应（L-1）

## 8. 与设计文档的偏差

设计文档 [文档记录/设计文档/v1.0.md](文档记录/设计文档/v1.0.md) §4.2 "数据加密" 主张：

> "所有请求参数与响应内容必须经过加密处理"

**实际偏差**：

- ❌ `download_file` / `preview_file` 响应直接走 `FileResponse`，未加密
- ❌ 4xx/5xx 错误响应 `{"detail": "..."}` 未加密
- ⚠️ 明文接口（key-exchange / admin-exists / health）在设计中已说明例外，但 admin-exists 暴露系统状态这点没在文档体现

设计文档 §4.1 "认证与授权" 暗示 HTTPS 是承担身份验证的层级，但**没有说明在公司根 CA 场景下要怎么补足身份认证**——这是设计层面应该补充的内容。

建议设计文档增加 §4.1.X "防主动 MITM 服务端公钥固定"小节，明确写出服务端长期身份密钥与客户端预置指纹的方案。

## 9. 总结

| 用户的核心问题 | 当前答案 |
| -------------- | -------- |
| "公司能否捕获请求 URL 中的参数？" | ✅ 不能。GET/POST/PUT/DELETE 全部走加密 body，URL 里没有任何参数值 |
| "公司能否捕获请求体？" | ✅ 不能。100% 加密 |
| "公司能否捕获响应体？" | ⚠️ 业务接口响应不能；但**文件下载/预览的响应是明文的** |
| "公司能否解密分片上传的文件流？" | ✅ 不能。chunk_data 在加密 body 里 |
| "公司能否捕获到下载/预览的文件内容？" | ❌ **能，完整内容明文可见** |
| "公司能否分析出文件内容？" | ❌ 下载/预览路径可以；上传路径不可以 |

**核心建议给用户**：

1. **优先修 H-1**（文件下载/预览加密），这是当前唯一让你"文件内容被公司看到"的地方
2. **再修 H-2**（服务端公钥固定），否则面对主动 MITM 代理，所有加密都形同虚设
3. **顺手修 M-1 / M-4**，删除 Authorization 兜底 + 加密错误响应

修完 P0+P1 后，就算公司用最强的企业级 DLP 代理（带根 CA + 主动 MITM），也只能看到：
- 你发了某些 HTTPS 请求到 jflove 服务器
- 大致的请求频率和数据量
- **看不到任何文件内容、文件名、路径、笔记内容、密码、token**

这个收敛程度对绝大多数威胁场景已经足够。
