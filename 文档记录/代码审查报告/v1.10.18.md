## 2. 逐项审查结论

### 2.1 「弹框门槛」去掉 `expects_password`

| 检查项 | 结论 |
| --- | --- |
| 是否会影响纯密码连接 | ✅ 例外分支要求 `key is not None`（有私钥才弹框）；纯密码连接无密钥，不受影响 |
| 是否会在能连的服务器上多弹一次框 | ✅ 只在「服务器要求 password 且本地无密码」时触发；服务器若已接受密码认证则不会走到这里 |
| 是否会无限弹框 | ✅ `MAX_METHOD_ATTEMPTS["keyboard-interactive"] = 1` + `interactive_tried` 双重限制，每连接最多一次 |
| 与 `auth_type` 解耦的副作用 | ⚠️ **中等**（见 §3.1） |

### 2.2 文案修正

| 检查项 | 结论 |
| --- | --- |
| `key_accepted` 判定是否准确 | ✅ 只在该轮 `status == "ok"` 时为真（v1.10.17 已收紧），不会把 `rejected` / `failed` 误当成功 |
| 是否可能把「密钥真的被拒」误报成「密码问题」 | ✅ 不会：`key_accepted` 为假时仍走原「未接受当前密钥」分支 |
| 空输入与密码错误是否区分 | ✅ `_interactive_empty` 只在弹框返回空串时置真；密码填错不会置真 |
| 文案是否泄露凭据 | ✅ 只含方法名与下一步指引；用例断言不含输入值 |

### 2.3 防御性改动

`_attempt_auth` 对 `auth_interactive` 缺失的实现抛 `SSHException`（被统一转成可读错误），
避免测试替身/病态实现触发 `AttributeError` 崩溃。✅ 合理。

## 3. 问题清单

### 3.1 【中等】认证方式与行为解耦后，「密钥」方式也可能要求密码

- **现象**：用户选「密钥」（配置上不该要密码），但若服务器仍要求密码，客户端会弹框询问。
- **影响面**：仅「有私钥 + 本地无密码 + 服务器要求 password」的连接；这正是用户真实网关的形态。
- **评估**：**有意为之**。WinSCP 的实际行为就是「先用密钥，连上后弹框要密码」；旧版直接报
  「请改用密码 + 密钥」把用户挡在门外，导致用户反复改配置碰运气（用户实测四次不同结果）。
- **建议**（不阻塞）：后续版本可在弹框标题里标注「服务器要求账号密码（当前认证方式为「密钥」）」，
  让用户理解为什么会被问密码。
- **本次处理**：保留。

### 3.2 【轻微】`expects_password` 参数被移除

原参数已无用途（门槛改为只看「有没有私钥」），移除后 `_pick_next_method` 签名更简洁。
✅ 无遗留引用（`grep expects_password` 为空）。

### 3.3 【轻微】空输入提示依赖 `OTP_TIMEOUT = 60`

若用户操作较慢（>60 秒）会得到「没有收到你输入的账号密码」。文案已说明超时约 60 秒。
✅ 可接受；后续可考虑放宽到 120 秒。

### 3.4 【轻微】旧用例语义变更

`test_authenticate_key_requires_password_hint` 由「提示改配置」改为「先弹框，失败才提示」。
已在该用例 docstring 写明变更依据与用户证据。✅ 可接受。
