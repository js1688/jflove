## 3. 本轮发现并已修的问题（按严重度）

| 级别 | 问题 | 处置 |
| --- | --- | --- |
| **严重** | X1：xterm 6.0.0 的 DECRQM 处理抛 `ReferenceError`，`WriteBuffer` 无异常兜底 ⇒ 终端永久卡死 | 新增 `xterm-decrqm.ts` 前置接管；另加写队列看门狗自愈 |
| **严重** | X2：卸载 `TerminalView` 时 `send({type:'close'})` ⇒ 路由切一次就把用户 shell 杀掉 | 改为"只关通道不关会话"，会话只由「断开」按钮回收 |
| **严重** | X3：初版用"回放 256KB 输出"补偿切标签 ⇒ 回放触发终端应答 TUI 查询，应答被 shell 回显成垃圾 | 删除回放路径；改为会话级实例注册表（DOM 摘挂不销毁实例） |
| **严重** | X4：xterm 在未入 DOM 的容器上 `open()` ⇒ 单元格量不到、以 80×24 起步，TUI 首帧与 resize 交错后错乱 | 先 `appendChild` 再 `mountTerminal`；自愈路径同样约束 |
| 高 | X5：`navigator.clipboard.readText()` 在 QtWebEngine 里会 `NotAllowedError`/长时间 pending，粘贴"点了没反应" | 浏览器 API 带 500ms 超时 + Python 桥兜底 + 失败 toast |
| 高 | X6：默认快捷键 `ctrl`（Ctrl+C 复制）⇒ 终端里按不住跑飞的进程 | 默认改 `smart`（有选区复制、无选区 SIGINT） |
| 中 | X7：状态回调挂在 `onCursorMove` 上，TUI 高频触发 React setState | 120ms 节流 |
| 中 | X8：输出队列无上限，渲染层异常时可被撑爆 | 8MB 上限，丢最旧并 `console.warn` |
| 中 | X9：Wayland 下浏览器与 Qt 两个剪贴板数据源互相顶掉 | 复制改为"桥优先"，只保留一个数据源 |
| 低 | X10：`cdp_keys.mjs` 用 `keyDown+text` 注入，xterm 收到两遍（`echo helloecho hello`） | 改为 `rawKeyDown→char→keyUp`，并只挑可见终端 |

## 4. 遗留与风险（不阻塞发布）

1. **SSH 远程终端未接真机**（无可用目标/凭据）：改动是共用件，SSH 侧只加了 `nudge_redraw` 与状态上报；
   测试报告按《验证标准》口径记为"未覆盖（原因）"。
2. **Windows 未复验**：`nudge_redraw` 在 pywinpty 上走 `set_size`，逻辑通用，但打包与 ConPTY 链路需 VM 复跑。
3. **Wayland 剪贴板依赖窗口焦点**：这是合成器的安全策略（无人值守注入时窗口无焦点 ⇒ 读写都为空）；
   真机聚焦后实测通过（`/tmp/jf-term-e2e-wl6/`）。已在粘贴失败时给出可操作提示。
4. **dsh TUI 在 ≤21 行终端里会画丢输入框内容行**（tmux 交叉复现，属上位程序缺陷）；
   本轮把默认窗口的终端行数从 22 提到 24，规避了默认场景。
5. 终端会话在 App 退出时结束（无 tmux 级持久化）——与 v1.10.0 设计一致，未改变。
