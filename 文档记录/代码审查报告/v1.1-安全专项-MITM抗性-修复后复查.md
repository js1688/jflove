## 2. 验证：H-1 文件流端到端加密

### 2.1 方案

**帧格式**（大端字节序）：

```text
[4B 帧体长度 L] [12B nonce] [N B 密文 + 16B 认证标签]
其中 L = 12 + N + 16 = 28 + 明文字节数
```

服务端文件按 64KB 明文切片，每片独立 ChaCha20-Poly1305 加密；客户端逐帧读取并解密落盘。**整个 HTTP 响应体均为密文**，没有任何字节是文件原始数据。

### 2.2 服务端改动

**新增** [src/utils/crypto.py](jflove-server/src/utils/crypto.py)：

```python
STREAM_PLAINTEXT_CHUNK_SIZE = 64 * 1024

def encrypt_stream_chunk(session_key: bytes, plaintext: bytes) -> bytes:
    nonce = os.urandom(12)
    chacha = ChaCha20Poly1305(session_key)
    ciphertext = chacha.encrypt(nonce, plaintext, None)
    body = nonce + ciphertext
    return struct.pack(">I", len(body)) + body
```

**修改** [src/controllers/file_controller.py:233-269](jflove-server/src/controllers/file_controller.py#L233-L269) 与 [285-326](jflove-server/src/controllers/file_controller.py#L285-L326)：

- `download_file`：从 `FileResponse(file_path, filename=...)` → `StreamingResponse(_build_encrypted_file_stream(...))`
- `preview_file`：同样改为加密流响应
- **移除** `Content-Disposition: filename="..."` 头（避免文件名泄露）
- 新增 `X-Encrypted-Stream: v1` 响应头作为协议版本标识

### 2.3 客户端改动

**新增** [src/utils/crypto.py](jflove-desktop/src/utils/crypto.py)：

```python
def decrypt_stream_chunk(session_key, frame_body) -> bytes
def read_exact_stream(raw, n) -> bytes  # 处理短读
def parse_stream_frame(raw, session_key) -> bytes | None  # 流结束返 None
```

带安全上限：单帧明文不超过 2 MB，防内存炸弹。

**修改** [src/utils/http_client.py](jflove-desktop/src/utils/http_client.py)：

- `download_to_file`：循环 `parse_stream_frame()` → 解密 → 写入 `xxx.part` → 完成后原子 rename。任意一帧认证失败立即抛错并清理临时文件
- `download_stream`：同样改为帧式解密后拼接（仅小文件预览用）

### 2.4 端到端测试结果

```text
OK ECDH:        服务端 ↔ 客户端派生出相同会话密钥
OK encode:      250000B 明文 → 250128B 密文（128B 开销 = 4 帧 × 32B，0.051%）
OK decode:      还原 250000B，字节级完全一致
OK tamper:      篡改任意一字节 → InvalidTag 拒绝
OK truncate:    截断认证标签 → ValueError 拒绝
OK wrong-key:   错密钥 → InvalidTag 拒绝
OK empty:       空流（0B 文件）正常处理
```

**完整性保证**：每帧都带认证标签，任何中间人代理修改密文 → 客户端立即 `InvalidTag` 异常 → 临时文件清理。**写入磁盘的内容 100% 是已通过完整性校验的明文**。

### 2.5 公司 MITM 视角

修复前 → 修复后对比：

| MITM 能看到 | 修复前 | 修复后 |
| ----------- | ------ | ------ |
| HTTP 方法 + URL 模板 | ✓ | ✓（无变化） |
| 文件内容 | **✓ 完整明文** | **❌ 仅密文帧** |
| 文件名（`Content-Disposition`） | **✓ 明文** | **❌ 头已移除** |
| 文件大小（content-length） | ✓ 精确 | ✓ +0.05% 偏差（密文略大于明文） |
| 文件类型（魔术字节） | **✓ 可识别** | **❌ 不可识别**（密文均匀分布，看似随机） |
| `X-Encrypted-Stream` 响应头 | — | ✓ 仅"v1"协议版本，无信息量 |

DLP 现在拿到一个 250128B 的随机字节流，无法判断它是 PNG 还是 PDF 还是 password.txt。

# init_upload 中记录归属

# 新增校验函数
def is_upload_owned_by(upload_id: str, user_id: int) -> bool:

## 5. 验证：M-4 错误响应加密

### 5.1 修复

[src/main.py](jflove-server/src/main.py) 新增全局 HTTPException 处理器：

```python
_PLAIN_PATHS = (
    "/health",
    "/api/v1/auth/key-exchange",
    "/api/v1/auth/admin-exists",
)

def _maybe_encrypt_error(request, status_code, detail):
    if any(request.url.path.startswith(p) for p in _PLAIN_PATHS):
        return JSONResponse(status_code=status_code, content={"detail": detail})
    session_id = request.headers.get("X-Session-ID")
    if session_id:
        session_key = auth_service.get_session_key(session_id)
        if session_key:
            ciphertext = encrypt(session_key, json.dumps({"detail": detail}, ensure_ascii=False).encode())
            return JSONResponse(status_code=status_code, content=ciphertext)
    return JSONResponse(status_code=status_code, content={"detail": "请求失败"})

@app.exception_handler(HTTPException)
async def encrypted_http_exception_handler(request, exc):
    return _maybe_encrypt_error(request, exc.status_code, str(exc.detail))

@app.exception_handler(Exception)
async def global_exception_handler(request, exc):
    return _maybe_encrypt_error(request, 500, "服务器内部错误")
```

### 5.2 客户端配套

[src/utils/http_client.py](jflove-desktop/src/utils/http_client.py) 的 `_parse_response` 与新增的 `_handle_stream_error` 都识别加密错误信封：

```python
def _decrypt_envelope_or_none(self, body):
    if "nonce" in body and "ciphertext" in body:
        return decrypt(session_key, body["nonce"], body["ciphertext"])
    return None

# 错误处理
err_body = resp.json()
decrypted = self._decrypt_envelope_or_none(err_body)
if decrypted is not None:
    detail = decrypted.get("detail", "请求失败")
elif isinstance(err_body, dict):
    detail = err_body.get("detail", resp.text)
```

### 5.3 行为

- 受保护接口：错误响应体为 `{"nonce":"...", "ciphertext":"..."}`，detail 加密。MITM 看不到「无权浏览该磁盘」「目录不存在: foo/bar」之类的具体信息
- 明文白名单（`/health` / `/auth/key-exchange` / `/auth/admin-exists`）：错误保持明文（这些路径本来就明文工作）
- 无 session 时：返回通用 `{"detail":"请求失败"}`，不泄露细节

### 5.4 自检发现的额外漏洞与修复（v1.1 补充）

用户提出"是否所有错误信息都加密"后，自检发现 v1.1 初版的全局处理器存在两处绕过路径：

#### 5.4.1 Starlette 内部抛出的 HTTPException 未被加密

`fastapi.HTTPException` 是 `starlette.HTTPException` 的**子类**，但 FastAPI 的 `@app.exception_handler(HTTPException)` 注册逻辑只匹配 `fastapi.HTTPException` 实例。Starlette 自己抛出的 HTTPException（如**路径不匹配 404**、**方法不允许 405**）会走 starlette 默认处理器，返回**明文** `{"detail": "Not Found"}` / `{"detail": "Method Not Allowed"}`。

**修复**：在 [main.py](jflove-server/src/main.py) 增加专门的 `StarletteHTTPException` 处理器：

```python
from starlette.exceptions import HTTPException as StarletteHTTPException

@app.exception_handler(StarletteHTTPException)
async def encrypted_starlette_http_exception_handler(request, exc):
    return _maybe_encrypt_error(request, exc.status_code, str(exc.detail))
```

#### 5.4.2 Pydantic 校验错误（422）未被加密

`fastapi.exceptions.RequestValidationError` 同样不是 `HTTPException` 子类。`/api/v1/auth/key-exchange` 用了 `KeyExchangeRequest(BaseModel)`，路径参数（如 `disk_id: int`）也会在类型不匹配时触发。默认返回明文 422 + 字段名详情数组。

**修复**：在 [main.py](jflove-server/src/main.py) 增加 `RequestValidationError` 处理器，把 detail + errors 数组用 session_key 一并加密。明文白名单路径（如 key-exchange）仍保持明文行为。

#### 5.4.3 端到端验证（FastAPI TestClient 实测）

| # | 场景 | 状态 | 是否加密 | 备注 |
| - | ---- | ---- | -------- | ---- |
| A | 404 路径不存在（Starlette） | 404 | ✅ True | 解密后 `{"detail": "Not Found"}` |
| B | 405 方法不允许（Starlette） | 405 | ✅ True | 解密后 `{"detail": "Method Not Allowed"}` |
| C | 422 路径参数类型错（Pydantic） | 422 | ✅ True | 解密后含 `errors` 详细数组 |
| D | 401 无 X-Session-ID（业务） | 401 | ⚠️ False（通用 "请求失败"） | 无密钥可加密，仅通用提示，无内容泄露 |
| E | 400 body 解密失败（业务） | 400 | ✅ True | 解密后 `{"detail": "请求解密失败"}` |
| F | 401 JWT 无效（业务） | 401 | ✅ True | 解密后 `{"detail": "令牌无效或已过期"}` |
| G | key-exchange 422（明文白名单） | 422 | ❌ False | 按预期，明文（白名单路径） |
| H | admin-exists 200（明文白名单） | 200 | ❌ False | 按预期，明文 |
| I | /health/sub 404（明文白名单） | 404 | ❌ False | 按预期，明文（白名单路径） |

**结论**：所有可能含**业务/用户内容**的错误响应（A/B/C/E/F）现在都是加密的；不在白名单内、又确实没有可用 session-key 的极少数场景（D）只回通用「请求失败」字样，不泄露任何用户内容。

## 6.5 密钥交换协议专项复查（用户追问）

> **用户疑问**：「交换密钥的逻辑，是否先从服务端获取公钥，然后使用公钥加密端对端加密的私钥进行交换。我担心交换密钥时密钥没有被加密，被泄漏」

### 6.5.1 直接结论

**用户的担心基于对密钥交换协议的常见误解**：实际代码用的是 **X25519 ECDH 密钥协商**，不是 RSA 风格的密钥封装（即"用对方公钥加密自己的对称密钥再发过去"）。两者的安全模型完全不同：

| 协议 | 工作方式 | 风险 |
| ---- | -------- | ---- |
| RSA 密钥封装（古典） | 客户端用服务端公钥加密一个真正的对称密钥 → 发给服务端 → 服务端用私钥解出 | 服务端长期私钥若泄漏，所有过去录到的流量都能解密（**无前向保密**） |
| **X25519 ECDH（当前）** | 双方各生成临时密钥对 → 互换公钥 → 双方独立计算出相同的共享密钥 → **共享密钥从不在网络上传输** | 即便录到全部公钥流量也算不出 session_key（要解 ECDLP，2¹²⁸ 复杂度）；私钥用完即销毁 → **天然前向保密** |

### 6.5.2 实际网络上传输的全部数据

经审查 [auth_service.py 客户端](jflove-desktop/src/services/auth_service.py#L113-L137) 与 [auth_service.py 服务端](jflove-server/src/services/auth_service.py#L59-L79)，整个 `/api/v1/auth/key-exchange` 接口在网络上能被 MITM 看到的内容只有：

```text
请求体:  {"client_public_key": "<32B base64>", "refresh": false}
响应体:  {"session_id": "<UUID>", "server_public_key": "<32B base64>"}
```

**完全不传输**任何形式的对称密钥、私钥或共享秘密。

### 6.5.3 实测验证

跑了脚本模拟整个流程（模拟 Eve 是公司 MITM，录到全部流量）：

```text
=== Eve 录到的全部数据 ===
Alice public key: m2prSOS9hgiQo9aSHMY/OJZiYi/zgFwbGWD+tgYeuyI=
Bob   public key: VRvtFuaDWHn7OP5aF7oxIp5bPJ1EuqceGIrZRgbnvH8=
  → 总共 64 字节信息（两个 X25519 公钥）

=== Eve 试图重建 session_key ===
Alice 算出:                          77df5200193c944277dff6711547ae5e...
Eve 用自己造的私钥配 Alice 公钥算出:  1eb8ac57186deeae9a3529237e955dae...
Eve 用自己造的私钥配 Bob   公钥算出:  bb963be36d46437282ec0b2ae49c2958...
  → 完全对不上
```

Eve 拿到两个公钥也算不出真正的 session_key。**这是数学上的硬约束（解 Curve25519 ECDLP 约需 2¹²⁸ 次运算）**，不是"目前没人发现漏洞"那种工程级断言。

### 6.5.4 密钥交换 6 项细粒度审查

| # | 审查项 | 状态 | 代码证据 |
| - | ------ | ---- | -------- |
| 1 | 用 ECDH 协商而非 RSA 封装 | ✅ | [crypto.py derive_session_key](jflove-server/src/utils/crypto.py)：`private_key.exchange(peer_pub)` |
| 2 | 私钥是否离开生成方 | ✅ | grep 全仓库零"send private key"路径 |
| 3 | 临时密钥一次性 | ✅ | 每次 `generate_x25519_keypair()`；refresh 时旧 session_key 立即从 `_session_store` 删除（[auth_service.py:92-93](jflove-server/src/services/auth_service.py#L92-L93)） |
| 4 | 公钥反序列化 | ✅ | `X25519PublicKey.from_public_bytes()` —— `cryptography` 库内部已防小子群攻击；X25519 设计本身就有抗小子群保证 |
| 5 | session_key 不落盘 | ✅ | 服务端：`_session_store: dict[str, bytes]`（内存）；客户端：`session_manager.session_key`（内存）。重启即丢 |
| 6 | KDF 选择 | ✅ | `HKDF-SHA256(salt=b"jflove-v1", length=32)` 符合 RFC 5869，业界推荐 |

### 6.5.5 区分两类攻击（重要）

| 攻击类型 | 是否可行 | 原因 |
| -------- | -------- | ---- |
| **被动 MITM**（公司只录流量、解密、做 DLP 审计） | ❌ **完全无效** | ECDH 数学保证，session_key 不在网络上 |
| **主动 MITM**（公司代理实时改写流量、替换公钥） | ⚠️ **可被利用** | ECDH 没有身份认证 → 见 H-2 |

**用户问的是被动 MITM 场景（"密钥被泄漏"）**：✅ 完全没有泄漏路径。

主动 MITM 是另一个独立问题（H-2），需要服务端公钥固定才能彻底防，详见下文 §7。

## 7. 仍未解决：H-2 主动 MITM（设计层面，待决策）

**现状**：当前 X25519 ECDH 没有服务端身份认证。如果公司代理是**主动 MITM**（实时改写流量），它能：
1. 拦截客户端 `client_pub_A` → 发自己的 `client_pub_B` 给真实服务端
2. 拦截服务端 `server_pub_X` → 发自己的 `server_pub_Y` 给客户端
3. 客户端与代理共享 K1 = HKDF(ECDH(A, Y))
4. 代理与服务端共享 K2 = HKDF(ECDH(B, X))
5. 代理坐中间用 K1 解→K2 加密，全程可见

**对你的实际威胁**：

- 如果公司只做**被动捕获 + 离线解密**：当前设计**安全**，公司一无所获
- 如果公司是**主动改写流量**（典型企业级 SSL Inspection 网关，如 Symantec ProxySG / Palo Alto / Forcepoint）：当前设计**可被破**

**为什么没修**：

H-2 的修复需要"客户端预置一个不可变的服务端身份指纹"，涉及：

1. 服务端长期身份密钥的生成、保管、轮换策略（产品决策）
2. 客户端如何预置该指纹（写死代码？config 文件？首次连接 TOFU？）
3. 安装包从哪个可信渠道分发（GitHub Release / 公司内网 / 自建网站？）

这些不是单点代码修改，需要先有产品/部署层面的决策。建议下个迭代专项处理。

**临时缓解**：

- 个人部署场景下，如果你确认你的服务器到客户端这条链路上**没有公司代理**（在家用网络 / 自有 VPN），当前设计就是安全的
- 如果你处于公司网络且必须经过公司代理，那目前**没有完美防御**，所有走公司网络的应用层加密都可能被破。建议直接走 VPN（IKEv2 / WireGuard）绕开公司代理

## 8. 总结

### 8.1 用户核心诉求验收

| 用户原话 | 修复结果 |
| -------- | -------- |
| "上传、下载，包含分片和非分片，响应、参数都必须是端对端加密传输" | ✅ 全覆盖 |
| "URL 中出现 ID 等参数可以不加密" | ✓ 维持现状（数字 ID 无业务语义） |
| "必须保证不会被通过更改 ID 的方式绕过权限" | ✅ 全覆盖（upload 归属 + browse 读权限 + 所有 admin-only 路由都校验） |

### 8.2 修复后的安全边界（被动 MITM 场景）

公司能看到：

- HTTP 方法、URL 路径模板（含无业务语义的数字 ID）
- 流量时序与体积（精度 ±0.05%）
- `X-Session-ID` UUID（不能用它解密任何内容）
- `X-Encrypted-Stream: v1` 响应头（仅协议版本）

公司**看不到**：

- ❌ 任何请求参数（包括 GET/POST/PUT/DELETE 的全部 body 字段）
- ❌ 任何响应体（包括成功响应和错误 detail）
- ❌ **任何文件内容**（下载、预览、上传分片均为密文）
- ❌ 文件名（不在响应头里）
- ❌ JWT、密码、笔记内容、目录路径
