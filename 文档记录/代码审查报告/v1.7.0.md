# JFLove v1.7.0 代码审查报告

> 审查依据：`文档记录/需求文档/v1.7.0.md`、`文档记录/设计文档/v1.7.0.md`、`AGENTS.md §4 / §5 / §9`
> 审查范围：本次全部改动（server / desktop / app / web）
> 审查角色：code-review（Phase 5）

---

## 1. 总体评价

整体实现与设计一致：服务端 journal 语义、范围隔离、鉴权与加密均符合 §9；桌面端桥与渲染层边界守住；移动端上传复用加密通道；Web 删除干净。

**但有两个必须先说清的事实**：

1. **桌面端「系统级挂载」已实现（Windows CfAPI）**，由 `src/utils/mount_vfs.py` 提供：注册 sync root → 创建脱水占位 → 读取触发 `FETCH_DATA` → `CfExecute` 写回。三步判据由 `poc/cfapi_probe.py` 与 `tests/test_mount_vfs_v1_7_0.py` 实测通过。**Linux FUSE 未实现**（用户确认先调 Windows）。
2. **审查发现并已回修 1 个严重缺陷**：移动端相册扫描原先只取最近 200 项，导致更早的照片永远轮不到。已改为分页扫描（`album_backup_service.dart`）。

## 7. 复审：CfAPI 挂载目录「无法打开 / 云操作 60s 超时」修复（2026-10-19）

### 7.1 审查范围

| 文件 | 性质 |
| --- | --- |

| `jflove-desktop/tests/test_mount_autosync_v1_7_0.py` | 仅路径断言改 `Path(...).name`（测试自身平台假设） |
| `poc/cfapi_crossproc_probe.py` | 诊断探针（非交付产物） |

### 7.2 缺陷复述与证据核对

原实现的回调/操作类型常量与 `cfapi.h` 错位（`FETCH_PLACEHOLDERS` 写成 2 而非 3、
`TRANSFER_PLACEHOLDERS` 写成 2 而非 4、`NOTIFY_DELETE` 8→9、`NOTIFY_RENAME` 10→11、
`ACK_DELETE`/`ACK_RENAME` 3/4→6/7），导致 `Population=FULL` 的 sync root 被枚举时
**没有任何应答**，平台等满 60s 返回 `0x800701AA`。

审查员独立复核（本机实测，非引用开发记录）：

```text
# A/B 探针（枚举在子进程执行 = 模拟资源管理器）
--legacy（只注册 FETCH_DATA）        → CHILD_TIMEOUT >80s
修复后（FETCH_PLACEHOLDERS=3）      → 回调 ×3、CfExecute 全接受、CHILD_OK 0.00s

# 真实挂载根（旧实现）
ENUM_FAIL D:\testa cost=60.4s winerror=426 (0x800701AA)
```

结论：**根因成立，修复方向正确**。
