### 3.2 中等

#### M-1 F36.3 缺「时长偏差 ≤1s」校验（AC-271 判据不完整）

- 位置：`jflove-server/src/services/media_fetcher_service.py:636-641`
- 现状：合并后只校验 `audio` / `video` 流存在；`_probe_output` 已返回 `duration`（同文件 `:160-197`）却未使用，也没有探测主轨时长做比较。
- 影响：音轨错配/截断（长度差 >1s）时仍会判 `success`，与需求 F36.3、设计 §2.1「时长与主轨差 >1s ⇒ `merge_failed`」不符；AC-271 的「时长偏差 ≤1s」无实现、无断言。
- 证据：`grep -n "duration" jflove-server/src/services/media_fetcher_service.py` 仅命中 `_probe_output` 内部解析，`_fetch_with_audio` 未引用；新增测试也只断言 streams（`tests/test_offline_media_fetcher_v1_8_0.py:696-728`）。
- 建议：

```python
main_probe = await _probe_output(video_path)
probe = await _probe_output(output)
if "audio" not in streams:
    raise FetchError("merge_failed", "合并产物缺少音轨")
main_d = float(main_probe.get("duration") or 0)
out_d = float(probe.get("duration") or 0)
if main_d > 0 and out_d > 0 and abs(out_d - main_d) > 1.0:
    raise FetchError("merge_failed", "合并产物时长与主轨不一致")
```

#### M-3 部分结果（`level=partial` + warnings）未透出给客户端，超时后静默降级

- 位置：`jflove-server/src/services/media_analyzer_service.py:1230-1247`（生成 `warnings` / `level="partial"`）→ `jflove-server/src/services/offline_download_service.py:849-865`（`_store_analysis` 丢弃 `warnings`）→ `offline_download_service.py:371-475`（`task_to_dict` / `get_detail` 不含 `analysis_level` / `warnings`）
- 现状：分析超时但有已抓取项时，服务端确实落 `ready` + `analysis_level='partial'`，但 `AnalysisResult.warnings` 没有落库字段，`task_to_dict`/`get_detail` 也不返回 `analysis_level`；三端都没有读取（`grep -rn "analysis_level\|warnings" jflove-*/src jflove-desktop/ui/src jflove-app/lib` 除 scratch 无关命中外为空）。
- 影响：用户在「解析超时」后看到的是**完整 ready 任务**，不知道少了内容，也无法得知「部分结果，深度分析未完成」；违反 F37.4「同时返回 warnings」与 AC-279 的 warnings 判据、I-6。
- 建议：`task_to_dict` 增加 `analysis_level`；`offline_download_tasks` 或响应层增加 `warnings`（可由 `analysis_level=='partial'` 派生固定文案，避免 DDL），三端任务详情展示「解析超时，已返回部分结果」。

#### M-4 HLS/DASH 主轨带 aux 音轨时被排除，仍可能静默产出无声文件

- 位置：`jflove-server/src/services/media_fetcher_service.py:451-457`（`needs_aux` 排除 `protocol in ("m3u8","mpd_segments")`）
- 现状：`aux_url` 由分析端在「视频轨无 acodec」时无条件配对（`media_analyzer_service.py:627-633`），但下载端只有**直链主轨**才走 aux 合并；`protocol=="m3u8"` 时直接进 `_fetch_hls`，若该变体是纯视频播放列表，下载结果无音轨且**不报错**（`_fetch_hls` 不校验音频）。同理 `_fetch_with_audio` 内的 m3u8/mpd 分支（`:592-600`）在 `needs_aux` 前提下不可达，是死代码。
- 影响：需求 F36.1「`aux_url` 非空时必须同时获取主轨与音轨」与 F36.4「禁止静默落无音轨文件」对该组合不成立；典型于「HLS 视频变体 + 独立音频 m3u8」站点。
- 证据：`_fetch_with_audio` 的 `protocol == "m3u8"` 分支仅在 `needs_aux` 为真时到达，而 `needs_aux` 恰好排除 m3u8 ⇒ 不可达。
- 建议：`needs_aux` 不再按协议排除；若担心 HLS/DASH 已内嵌音轨，可先 `_probe_output(主轨)`，缺 audio 才合并 aux；同时删除死分支或改为「aux 协议推断」复用。

### 11.2 修复引入的新问题

#### R-1（中等）HLS/DASH 主轨 + HLS aux 时临时文件同名，主轨被覆盖导致合并失败

- 位置：`jflove-server/src/services/media_fetcher_service.py:592-606`（主轨 HLS/DASH 下载）、`:671-677`（aux `.m3u8` 复用 `_fetch_hls`）、`:817` / `:877`（`_fetch_hls`/`_fetch_dash` 输出均为 `<tmp_root>/merged.mp4`）
- 机理：`_fetch_with_audio` 的 `video_path` 在 HLS/DASH 主轨时就是 `<tmp_root>/merged.mp4`；随后 `_fetch_aux_audio` 对 `.m3u8` 音轨再次调用 `_fetch_hls(..., tmp_root, ...)`，把同一个 `merged.mp4`（以及 `local.m3u8`）覆盖成音轨内容 ⇒ ffmpeg 对 `video_path` 执行 `-map 0:v:0` 时无视频流，合并失败（`merge_failed`）。
- 影响：M-4 的目标场景之一（HLS 视频变体 + 独立 HLS 音轨）实际不可用；属**修复引入**，此前该组合是被 `needs_aux` 排除（静默无音轨），现在变为显式失败，但仍未实现「合并成有声音的成片」。
- 证据：`test_main_with_audio_skips_aux` / `test_merge_duration_mismatch_fails` 均只覆盖**直链主轨**（`protocol: "http"`），无 `protocol: "m3u8"/"mpd_segments"` + HLS aux 用例。
- 建议：给 aux 下载独立输出名/子目录（例如 `_fetch_hls(..., output_name="aux.mp4")` 或 `tmp_root/aux/`），并补一条「m3u8 主轨 + m3u8 aux」用例。
