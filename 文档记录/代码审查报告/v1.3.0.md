## 问题列表

### 严重 #1 — CORS `allow_credentials=True` 与 `allow_origins=["*"]` 冲突

- **文件**：`jflove-server/src/main.py:54-59`
- **违反**：CORS 规范 — 当 `Access-Control-Allow-Credentials: true` 时，`Access-Control-Allow-Origin` 不能为 `*`
- **影响**：浏览器**拒绝所有跨域请求**，Web 端完全无法工作
- **修复建议**：

```python
# ❌ 当前
allow_origins=["*"],
allow_credentials=True,

# ✅ 修复：JWT 走加密 body 不依赖 Cookie，无需 credentials
allow_origins=["*"],
allow_credentials=False,
```

---

### 严重 #2 — GET 请求不发送加密 body

- **文件**：`jflove-web/src/utils/http-client.ts:70`
- **违反**：设计文档 §5.2（所有加密请求统一走加密信封）、安全宪法 §9.1.4（GET 请求体也走加密 JSON）
- **影响**：**6 个受保护 GET 端点鉴权失败**（后端 `decrypt_request_body` 取不到 token）

| 端点 | 调用方 |
|------|--------|
| `GET /api/v1/files/disks` | file-service / file-store |
| `GET /api/v1/notes/list` | note-service |
| `GET /api/v1/disks/list` | disk-service |
| `GET /api/v1/users/list` | user-service |
| `GET /api/v1/permissions/list` | permission-service |
| `GET /api/v1/config` | config-service |

- **修复建议**：

```typescript
// ❌ 当前：GET 丢弃加密信封
body: method !== 'GET' ? envelope : undefined,

// ✅ 修复：所有方法均发送加密 body
body: envelope,
```

# 附录 B：方案 B 专项审查（GET 加密参数 URL 传递，2026-08-02）

> 审查角色：code-review | 审查范围：方案 B 变更（后端 middleware 1 处 + Web 端 5 文件 + 测试适配）
> 背景：浏览器禁止 GET 携带 body（fetch/XHR 均丢弃），Web 端只读接口改为真 GET + URL query 传加密信封；后端 `decrypt_request_body` 在请求体为空时从 query 读取信封（用户授权全局通用改动，桌面/移动端 body 方式不受影响）。

## 总体评价

方案 B 设计正确、实现简洁：信封仍为 ChaCha20-Poly1305 密文，URL 不含任何明文业务参数，符合 §9.1.4；后端改动仅 1 处且 body 优先、query 兜底，对旧客户端零影响。整体质量良好，可进入测试阶段。发现 **1 个中等**（需验证）与 **2 个轻微** 问题，均不阻塞发布，建议在测试阶段覆盖验证。

## 问题列表

### 中等 #B1 — GET query 信封存在 URL 长度风险（需测试验证）【已验证通过，风险低】

- **文件**：`jflove-web/src/utils/http-client.ts`（`getQueryEncrypted` / `downloadStream`）
- **描述**：加密信封 Base64 长度随请求体增长（token + 参数），普通场景约 400~600 字符；但深层目录 / 长文件名场景（`/files/list`、`/files/download` 的 `path` 字段较长）信封可能显著变长。多数服务器/反向代理默认限制请求行 8KB（Nginx `large_client_header_buffers` 默认 8k），超限会返回 414。属理论风险。
- **验证结果（Phase 6）**：✅ 服务端实测 4814 字符 path → 信封 query 6816 字符，uvicorn 正常接收、解密并进入业务层（返回业务 400「路径不存在」，非 414/解密失败）；前端单测构造 >4KB path 的 GET query 信封，URL 无明文泄漏、解密完整无截断。**结论：当前 uvicorn 默认配置下 6.8KB query 无问题，风险低**；若未来经 Nginx 反代需注意 `large_client_header_buffers` 配置。

### 轻微 #B2 — `encryptedRequest` 的 `extraHeaders` 为死参数，注释过时

- **文件**：`jflove-web/src/utils/http-client.ts:38-42,77`
- **描述**：`extraHeaders` 参数已无任何调用方传值（`httpClient.post/put/delete` 均未传）；函数体注释"所有方法（含 GET）都发送加密 body"已过时——GET 已改走 `getQueryEncrypted`，不再进入本函数。
- **建议**：删除 `extraHeaders` 参数与相关展开；注释改为"本函数用于 POST/PUT/DELETE（携带 body）；GET 请走 `getQueryEncrypted`"。

### 轻微 #B3 — 服务端访问日志记录完整 URL query（含密文信封）

- **文件**：`jflove-server`（uvicorn access log）
- **描述**：Web 端 GET 请求的完整 URL（含 `?nonce=...&ciphertext=...`）会写入 uvicorn 访问日志。密文不构成明文泄漏，不违反 §9.4.14（日志不记录用户内容明文），但日志体积会增大且便于离线分析密文。
- **建议**：可接受（密文无 key 不可解）；如在意日志体积，可配置访问日志仅记录路径不记录 query（`uvicorn --log-config` 自定义 access 格式），非必须。
