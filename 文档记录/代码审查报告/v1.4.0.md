## 三、问题列表

### 严重

无。

### 中等

**M1｜`/stream` 数值参数无容错 → 异常输入 500**
- `jflove-server/src/controllers/file_controller.py:544-546`
- 描述：`int(body.get("range_start", 0))` / `int(body.get("range_end", -1))` / `float(body.get("range_start_seconds", 0) or 0)` 对非数字字符串无校验，解密 body 由客户端可控，传 `"abc"` 会抛 `ValueError` → 500（虽被全局处理器加密返回，不泄露信息，但健壮性差、可被用于制造错误）。
- 建议：
  ```python
  def _to_int(v, default: int) -> int:
      try:
          return int(v)
      except (TypeError, ValueError):
          return default
  ```
  对三个参数统一容错，非法输入按默认值处理或抛 400。

**M2｜Web MSE seek 重建 buffer 存在竞态**
- `jflove-web/src/utils/media-source-player.ts:271-296`
- 描述：`resetBuffer()` 先 `mediaSource.removeSourceBuffer(sourceBuffer)`（若 SourceBuffer 正在 `updateend` 前被占用会抛错，被 try/catch 吞掉），随后无条件 `addSourceBuffer(codec)`；若 remove 失败而 add 成功，旧 SourceBuffer 残留，新旧缓冲数据时间轴重叠，可能导致播放卡顿/异常。`onSeeked` 在 `seeked` 事件触发，此时前一次 append 可能仍未结束。
- 建议：seek 时若 buffer 正忙，先等待 `updateend`（或 `abort()` 后再 remove）；更稳妥的方案是整体重建 MediaSource（`URL.revokeObjectURL` + 新 `MediaSource`），或用 `sourceBuffer.abort()` 后 remove。至少保证"remove 失败则不 add"，避免双 buffer 并存。

**M3｜修复并发等待无超时 → 弱 CPU 下请求可能长时间挂起**
- `jflove-server/src/services/media_repair_service.py:88-96`
- 描述：`_acquire_slot` 在并发满时 `while True: await asyncio.sleep(0.05)` 无限轮询；若多个 ffmpeg 修复（尤其重编码大文件）长时间不结束，新请求会无限等待、占用连接。
- 建议：轮询加入超时（如 `MEDIA_REPAIR_WAIT_TIMEOUT=30s`），超时抛 `HTTPException(503)` 或返回"修复队列繁忙，请稍后重试"；同时监听 CancelledError 正常中断。

### 轻微

**S1｜健康判定每次请求重复探测（与设计 §5.1 有出入）**
- `jflove-server/src/services/media_repair_service.py:ensure_playable` / `media_probe.probe_media`
- 描述：开关开启时，每次 `/stream` 请求（含 seek 多次 range）都执行一次 `ffmpeg -i` 探测；设计文档 §5.1 提到"探测结果按 mtime+大小短 TTL 缓存"，本次未实现。
- 建议：按 `(mtime, size)` 做进程内短 TTL 缓存（如 60s），减少重复 ffprobe。

**S2｜config 内存缓存与多进程部署**
- `jflove-server/src/services/config_service.py`（模块级 `_cache`）
- 描述：`_cache` 为进程内缓存，若生产以多 worker 运行 uvicorn，管理员写配置仅失效本进程缓存，其他进程延迟感知。
- 建议：单 worker 部署无影响；若多 worker，可改为写后短 TTL 或每次直读（SQLite 毫秒级），并在部署文档注明。

**S3｜time 模式 meta 的 content_type 固定为 video/mp4**
- `jflove-server/src/services/media_repair_service.py`（`stream_repaired_frames` meta 帧）
- 描述：纯音频源修复流也标注 `content_type: "video/mp4"`，不准确；MSE 按实际流判断，影响小。
- 建议：修复流统一 fMP4 容器，`content_type` 可沿用 `video/mp4`（容器为 mp4），或由 probe 区分音视频后标注。

**S4｜Web 开关连续点击无防抖**
- `jflove-web/src/pages/admin/AdminSystemPage.tsx`（`toggleEnabled`/`toggleTranscode`）
- 描述：开关即点即存，快速连点可能并发 `PUT`。
- 建议：`saving` 期间禁用交互（已部分处理并发数按钮），开关也纳入 `disabled={saving}`。

**S5｜桌面端多 Worker 共享 `self._worker`（沿用现有模式）**
- `jflove-desktop/src/ui/pages/settings_page.py`
- 描述：笔记目录/媒体修复加载与保存共用 `self._worker`，页面销毁时未 join，极端场景可能有已退出线程回调访问已销毁控件。
- 建议：沿用现有模式可接受（Qt Worker 线程安全），如需要可加 `isVisible`/`isHidden` 守卫。

**S6｜byte 模式 seek 到未缓冲区域不远程拉取（已知取舍）**
- `jflove-web/src/utils/media-source-player.ts`（byte 模式）
- 描述：健康文件 byte 流走 MSE 原生已缓冲 seek；seek 到未拉取区域时浏览器暂停等待，不触发远程拉取（修复流 time 模式才支持按时间重拉）。
- 建议：属设计文档 §7 注明的取舍，健康文件非主场景；如后续需完整 seek 体验，可将健康文件也统一走修复流（time）或实现字节↔时间映射。
