### 中等（1 条）

#### M-1：`rename` 和 `move` 接口的"路径不存在"场景返回 400 而非设计文档约定的 404

- **位置（服务端 service 层）**：
  - `jflove-server/src/services/file_service.py:446` — `rename_file` 中 `raise ValueError("路径不存在")`
  - `jflove-server/src/services/file_service.py:492` — `move_file` 中 `raise ValueError("源路径不存在")`
  - `jflove-server/src/services/file_service.py:494` — `move_file` 中 `raise ValueError("目标目录不存在")`
- **位置（控制器 catch 层）**：
  - `jflove-server/src/controllers/file_controller.py:323-324` — rename 控制器将所有 `ValueError` 映射为 HTTP 400
  - `jflove-server/src/controllers/file_controller.py:361-362` — move 控制器将所有 `ValueError` 映射为 HTTP 400
- **问题描述**：设计文档 §4.2.4 明确："`path` 指向的文件/目录不存在 → 404"；§4.3.4 明确："源路径不存在 → 404、目标目录不存在 → 404"。但实现中，"不存在"错误通过 `ValueError` 抛出，控制器统一将 `ValueError` 捕获为 HTTP 400，导致 API 语义偏离设计：REST 语义中"资源不存在"对应 404，"请求参数非法"对应 400。两者混用后 API 消费方无法区分"参数错误"与"资源不存在"。测试文件亦以 400 作为期望（与实现一致但与设计文档不符）。
- **影响**：中等。不影响安全，但破坏了 API 语义契约；对未来客户端（如 jflove-app / jflove-web）的开发者有误导风险。
- **修复建议**：在 `file_service.py` 中将"目标不存在"改为抛出 `FileNotFoundError`（Python 标准库），控制器分别捕获并映射为 404：

  **服务端 `file_service.py` 修改**：
  ```python
  # rename_file:
  if not os.path.exists(target):
      raise FileNotFoundError("路径不存在")   # 改为 FileNotFoundError

  # move_file:
  if not os.path.exists(src_abs):
      raise FileNotFoundError("源路径不存在")  # 改为 FileNotFoundError
  if not os.path.isdir(dst_dir_abs):
      raise FileNotFoundError("目标目录不存在")  # 改为 FileNotFoundError
  ```

  **控制器 `file_controller.py` 修改（rename 和 move 均需更新）**：
  ```python
  try:
      await file_service.rename_file(...)
  except PermissionError as e:
      raise HTTPException(status_code=403, detail=str(e))
  except FileExistsError as e:
      raise HTTPException(status_code=409, detail=str(e))
  except FileNotFoundError as e:        # 新增：资源不存在 → 404
      raise HTTPException(status_code=404, detail=str(e))
  except ValueError as e:
      raise HTTPException(status_code=400, detail=str(e))
  ```

### 轻微（2 条）

#### L-1：`rename_file` 服务层缺少对 `new_target` 的 `_safe_join` 验证（设计文档步骤 9 未实现）

- **位置**：`jflove-server/src/services/file_service.py:448-449`
  ```python
  parent_dir = os.path.dirname(target)
  new_target = os.path.join(parent_dir, new_name)
  ```
- **问题描述**：设计文档 §4.2.5 步骤 9 明确要求对 `new_target` 再做 `_safe_join(base, new_name_rel)` 验证。实现中省略了这一调用。从安全性角度分析，**当前实现实际上是安全的**：`parent_dir` 已由 `_safe_join` 保证在 `base` 内，`new_name` 已经过合法性校验（不含 `/`、`\`、`.`、`..`），所以 `os.path.join(parent_dir, new_name)` 的结果一定在 `parent_dir` 内，不存在逃逸风险。但与设计文档存在偏差，且缺少这一层防御深度（defense-in-depth）保护。
- **影响**：轻微。当前无安全风险，属于设计文档约束未完整落地。
- **修复建议**：可补上防御性调用：
  ```python
  parent_dir = os.path.dirname(target)
  new_target = os.path.join(parent_dir, new_name)
  # 防御性验证：确认 new_target 也在磁盘 base 内
  _safe_join(base, os.path.relpath(new_target, base))
  ```
  或简化为：
  ```python
  new_target = _safe_join(base, os.path.join(os.path.relpath(os.path.dirname(target), base), new_name))
  ```

#### L-2：设计文档 §5.2.4 与实现存在方法名错误（设计文档 typo，实现正确）

- **位置**：设计文档 `文档记录/设计文档/v1.1.3.md §5.2.4`
- **问题描述**：
  1. 设计文档 §5.2.4 说"在 `_on_disks_loaded` 中，磁盘切换时" 更新 `_can_write`，但实际磁盘切换事件发生在 `_on_disk_changed` 中（而非 `_on_disks_loaded`）。实现中正确选择了 `_on_disk_changed`（`jflove-desktop/src/ui/pages/file_page.py:238`）。
  2. 设计文档 §5.2.3 将 `MoveTargetDialog` 的返回方法写为 `get_selected_path()`（snake_case），但 AGENTS.md §4.1 要求方法名使用 camelCase。实现正确采用了 `getSelectedPath()`。
- **影响**：轻微。实现是正确的，设计文档有两处 typo 需要更正，以免将来误导。
- **修复建议**：由 designer 角色更正设计文档中对应章节，无需修改代码。
