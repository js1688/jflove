## 四、生产库 DDL（升级 + 回滚）

### 4.1 升级

```bash
sqlite3 jflove-prod.db < jflove-db/migrate-v1.7.0.sql
```

幂等；只新增表与索引，**不触碰业务数据**。内容：

```sql
CREATE TABLE IF NOT EXISTS file_changes (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    disk_id      INTEGER NOT NULL,
    rel_path     TEXT    NOT NULL,
    op           TEXT    NOT NULL,
    is_dir       INTEGER NOT NULL DEFAULT 0,
    size         INTEGER NOT NULL DEFAULT 0,
    mtime        REAL    NOT NULL DEFAULT 0,
    content_hash TEXT    NOT NULL DEFAULT '',
    created_at   TEXT    NOT NULL,
    updated_at   TEXT    NOT NULL,
    deleted_at   TEXT
);
CREATE INDEX IF NOT EXISTS file_changes_disk_id_idx ON file_changes(disk_id);
CREATE INDEX IF NOT EXISTS file_changes_rel_path_idx ON file_changes(rel_path);
```

### 4.2 回滚

```bash
sqlite3 jflove-prod.db < jflove-db/rollback-v1.7.0.sql
```

**回滚前冲突检查**：本表只存变更日志，删除不影响业务文件与用户数据；但会丢弃变更历史，
旧客户端的 `since_rev` 失效后会回退到全量对账（`scan`），功能不受影响、只是变慢。

```sql
-- 可选：确认记录量（不阻断）
SELECT COUNT(*) FROM file_changes;
```

## 七、已知限制（如实登记）

1. **挂载目录的本地删除不会同步到远端**：远端文件只能在「文件管理」里删 —— 刻意的风险规避（避免本地误删被放大到云端）。
2. **「固定到本地」未单独实现**（AC-108 未达）；「释放」= 清本地缓存，挂载视图仍列出远端全部文件（属预期）。
3. **CfAPI 回调整文件读入内存**：大文件（几百 MB 以上）内存占用高，后续改按范围流式（FUSE 侧为按需读取）。
4. **移动端后台保活未接 WorkManager**：App 被杀后不自动备份（BL-4）。
5. **Android 真机未验证**：相册权限、厂商 ROM 后台行为需真机验收。
6. **旧 `sync.*` 桥与 `sync_engine.py` 仍保留**：过渡期兼容，挂载稳定后移除（BL-7）。
7. **服务端 `_upload_sessions` / `_merge_progress` 在内存**：服务端重启后上传会话失效，
   客户端会重新 `init` 并重放分片（有断点续传记录，不会死循环）。
8. **Windows 侧本轮修复待真机复验**：>2GB 进度、`finalizing` 百分比、弱网不重传、强杀续传
   （清单见 `文档记录/桌面端开发记录/v1.7.0.md` §13.5）。

## 十、重新发布（2026-10-19，覆盖 v1.7.0）

### 10.1 为什么覆盖而不是发 1.7.1

2026-10-18 首次发布推的 tag 指向 `f507ed4`。之后在 Fedora 上实测发现两处致命缺陷（均只在真实环境暴露）：

| 缺陷 | 现象 | 根因 |
| --- | --- | --- |
| 桌面端在 Linux 起不来 | import 阶段即崩，挂载页打不开 | `src/utils/mount_vfs.py` 顶层 `ctypes.WinDLL("cldapi")` 在 Linux 抛 `AttributeError`，整个模块导入链失败 |
| 大文件上传永远传不完 | 分片传完卡在 100%，一晚无进展；日志反复重传 | `complete` 用默认 30s 超时，大文件合并远超此值 ⇒ 判失败 ⇒ **整文件重传**（重算 SHA256 + 从 0 传） |

用户裁决：**该次发布不算发布成功，可以把 `v1.7.0` 完全覆盖**（不产生 1.7.1）。
好处是用户侧版本号统一、不需要维护"两个 1.7.0"；代价是 `v1.7.0` 这个 tag 的指向被改变。

### 10.2 覆盖前置条件（推 tag 之前必须先做）

**先删掉 GitHub 上旧的 `v1.7.0` Release（tag 不用删）。**

原因：全部 6 条 workflow 的 release 步骤都是 `softprops/action-gh-release@v3` +
`tag_name: v${{ env.VERSION }}` + **`draft: true`**（`release.yml:38-44`、`build-desktop.yml:95-98/154-158`）。
对"已发布的同名 Release"再置 `draft: true` 可能被 GitHub 拒绝（发布态无法回退为草稿），
release 步骤失败但**不影响** `build-*.yml` 的打包 job —— 它们会按 tag 重新创建 Release 并挂资产。

处置：`Releases → v1.7.0 → Delete` → 再推 tag；若已推完才发现失败，删 Release 后
在 Actions 里 **Re-run failed jobs** 即可补挂资产，不必再动 tag。

### 10.6 服务端升级提示（覆盖后同样适用）

本次服务端新增了**合并进度接口**与**临时目录回收**，属进程内能力：

- **必须重启容器**（只 `docker pull` 不重启不生效）；
- 不重启也能上传，只是客户端 `finalizing` 退化为只显示「已 X 秒」（接口 404 有兜底），
  且旧的 `_upload_sessions` 永不过期导致的临时目录泄漏不会回收；
- 重启后首轮清理按 **1 小时**阈值处理历史残留，之后每小时一次按 24 小时阈值。
