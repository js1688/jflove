## 1. 发布范围

**删除 `none` 认证探测，改为最小请求序列。**

用户那台网关限制了认证尝试次数（实测等价 `MaxAuthTries=2`）：公钥 1 次 + 密码 1 次刚好用完。
v1.10.19 为了「先取方法列表」多发了一次 `none`，导致正确的密码落在第 3 次而被拒：

```text
【1.10.19：发 none】   none#1 → publickey#2 → password#3 → DENIED（超过 MaxAuthTries）
【正确做法：不发】      publickey#1 → password#2 → Access granted
```

本版：

1. **完全删除 `none` 探测**（`grep auth_none` = 0）：有私钥直接发 `publickey`，否则直接发 `password`；
2. 服务器在失败/部分成功响应里返回的 authlist 仍是后续每一步的唯一依据；
3. 弹框收取的密码继续以 `password` 方法发送（v1.10.19 已修，本版保留）；
4. 顺带修复：服务器「部分认证成功但未给下一步方法」时会沿用旧集合反复重打 —— 现在直接终止；
5. 弹框索取次数上限 2→3，保留「输入失误重试」能力。

服务端 / Web / 移动端 **仅版本号同步**；数据库 **无 DDL**。

### 用户可见变化

- 对「限制认证尝试次数」的网关：以前必然失败，现在可正常连接。
- 其他服务器：**行为不变**（只是少一次无用往返）。矩阵验证见 §2。
- 失败文案仍能区分「没收到输入 / 账号密码不对 / 服务器仍要求密钥」。

## 7. 回滚方式

- 桌面端 / App / Web：回退到 `v1.10.19` 的 Release 资产与镜像，数据库无需回滚。
- 服务端：`docker compose` 把镜像 tag 从 `1.10.20` 改回 `1.10.19` 重启。
- 回退到 v1.10.19 后的已知退化：**限次网关（如 MaxAuthTries=2）会因多一次 `none` 探测而连不上**。
