## 六、生产库 DDL（升级 + 回滚）

> 本版本**有表结构变更**：`users.username` 去掉列级 `UNIQUE`（改为「普通索引 +
> 活跃行部分唯一索引」）。变更原因：删除用户是软删除，而列级 `UNIQUE` 不区分是否删除
> ⇒ 被删账号的用户名被永久占用，管理员删号后无法同名重建（报 `UNIQUE constraint failed`）。

### 6.1 交付物

| 交付物 | 内容 |
| --- | --- |
| `jflove-db/migrate-v1.5.0.sql` | 重建 `users`（保留主键 `id` 与全部行含软删除历史行）→ 去 `UNIQUE` → 建 `users_username_idx` + `users_username_active_uidx`；**幂等、不触碰业务数据** |
| `jflove-db/rollback-v1.5.0.sql` | 恢复列级 `UNIQUE`；脚本头部写明**回滚前冲突检查 SQL**：`SELECT username, COUNT(*) AS n FROM users GROUP BY username HAVING n > 1;` |

### 6.2 实际执行与复验（本次发布实测）

用的是**结构对齐路径**（而非手工跑 SQL），因为对齐工具只改结构、自动备份、自动复验：

```powershell
# 关卡①②③ 一条命令全包（含内置的「代码 → dev」前置检查），退出码即判据
jflove-server\venv-win\Scripts\python.exe scripts/check_db_schema.py
```

实测输出（2026-09-21，本轮发布复核）：

```text
前置检查：dev 库 vs 当前程序代码的表结构
dev 库与当前代码一致 ✓
========================================================================
dev / prod 表结构核对
  dev  = D:\github\jflove\jflove-db\jflove-dev.db
  prod = D:\github\jflove\jflove-db\jflove-prod.db
========================================================================
结构一致 ✓（发布前检查通过）

历史遗留表（代码已不再创建，不参与比对、不会复制到 prod）：
  [dev] notes_permissions（—）
```

- **对齐前后差异：无** —— 本版本的结构变更（`users.username` 去 `UNIQUE`）在开发期已
  随 `init_db()` 迁移落到 dev，并已同步到 prod，故本次**未执行 `--align`**（无差异可对齐，
  因此也没有产生 `<prod>.bak-align-<时间戳>` 备份文件）。
- **复验结果**：退出码 **0**，且 CI 侧 `CI Guards（库结构核对）` 同样 **success**（§3.2）。
- **历史遗留表**：`notes_permissions` 在 dev 残留、**未复制进 prod**；本次**未执行**
  `--prune-legacy`（需要时人工确认其为空再清理，不替用户决定删表）。
- **回滚脚本实测**：本版本按"结构已一致"路径发布，**未实际执行 rollback**（会在恢复
  `UNIQUE` 时与同名历史行冲突）。如需回滚，**必须先跑脚本头部的冲突检查**，
  确认命中后再处理历史行（物理删除或改名），否则 `UNIQUE constraint failed` 中止 —— 这一点已写进脚本内。

> ⚠️ 注意 `users` 表 DDL 里带中文注释（`-- 去掉了原来的 UNIQUE`），
> 人工肉眼比对容易把注释当定义；**判据一律以 `check_db_schema.py` 的输出为准**。

## 八、本次发布过程中的故障与处置

### 8.1 Windows 桌面端 job 首次失败（已修复，版本号不变）

| 项 | 内容 |
| --- | --- |
| **现象** | tag `v1.5.0`（`9f380a0`）触发的 `build-desktop` 中 `build-windows` 失败：`Error on line 94 in jflove.iss: Couldn't open include file "c:\program files (x86)\inno setup 6\Languages\ChineseSimplified.isl"` → `[build][FATAL] iscc 编译失败，退出码 2` → 无 `setup.exe` → `if-no-files-found: error` 使 job 失败 |
| **根因** | `build.py` 用 `shutil.which("iscc")` 结果（CI 上是 Chocolatey **shim** `C:\ProgramData\Chocolatey\bin\iscc.EXE`）的父目录去猜中文语言文件位置；而 `.iss` 的 `compiler:Languages\...` 由 ISCC 解析为**其自身安装目录**（本机实验证实：`ISCC.exe` 复制到临时目录后 `compiler:Default.isl` 只认该目录）→ 探测与编译指向两个不同目录 |
| **修复** | 仓库内置 `jflove-desktop/packaging/windows/Languages/ChineseSimplified.isl`；探测顺序 = 环境变量 → 内置副本 → 真实编译器目录；**返回值必须真实存在**；以绝对路径传 `/DIslPath`；`.iss` 用 `FileExists` 兜底（缺失时响亮降级英文，绝不中止）；新增 10 条回归用例 |
| **验证** | `flake8` 0 警告；`pytest` 78 passed；本机端到端出包（setup 171.5 MB / zip 252 MB / onedir）；A/B 对照证明语言文件确被编入；构造"内置副本缺失 + 编译器目录无该文件"的 CI 条件 → 不再中止、照常出包 |
| **提交** | `2cfd646`（已推 main） |

### 8.2 tag 处置：为什么"删 tag 重推"而不是重跑

- tag 已存在时 `git push origin v1.5.0` **不产生 ref 变更事件 ⇒ 不触发任何 workflow**；
- `Re-run failed jobs` 重跑的是**同一个旧提交**（`9f380a0`），修复不在其中 ⇒ 必然再失败；
- 因此走「修复提交 → 推 main → 删远端 tag → 在新提交重建 tag → 推送」，
  重建后 6 个 workflow 全部重新触发并成功（§3.2）；
- 副作用：已发布的 tag 被移动，**其他人/机器需 `git fetch --prune --tags --force`** 才能对齐。
