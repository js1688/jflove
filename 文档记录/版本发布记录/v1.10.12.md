## 1. 发布范围

1. **SFTP 面板不出目录**（用户实测 BUG）：标签在 `session_open` 返回时就建好并挂载 `SftpView`，
   那一刻 Python 侧还在后台建链 ⇒ 旧实现"挂载即请求 + 不重试"，面板红字「会话尚未建立」常驻。
   修复：按 `remote-store` 的会话状态门控（`connecting` 只显示占位、0 次请求；`ready` 自动加载），
   并对"就绪事件早于标签创建"这一同类残余竞态加**兜底探活**（1s × 最多 30 次，自愈后停表）。
2. **选 `.ppk` 毫无反应**：① 私钥对话框过滤器不含 `*.ppk`（原生对话框里灰色不可选）；
   ② 拒绝文案渲染在抽屉最底部（滚动区外看不到）。修复：过滤器补 `*.ppk`/`*.rsa`，
   失败原因**就地**显示在私钥字段并弹一次 toast；`.ppk` 仍不解析（既定口径），给 PuTTYgen/WinSCP 转换指引。
3. 文案：`open_sftp()` 未就绪 → 「会话尚未建立（正在连接中，请稍候）」；`_sftp()` 会话不存在 →
   「可能已断开，请重新打开标签」。

数据库 **无 DDL**（`check_db_schema.py` 退出码 0，dev=代码、dev/prod 一致）；Web / App 仅版本号同步；
服务端与 Web 镜像重建但无行为变更。

## 6. 发布过程异常与处置（留痕）

**推送到 `github.com:443` 被网络中断**（发行过程唯一阻塞项）：

- 现象：`git push` 反复失败——`Failed to connect to github.com port 443 after 135s` /
  `OpenSSL SSL_read: unexpected eof while reading`；同一时刻 `api.github.com`、`codeload.github.com`
  正常（200/301），`git ls-remote` 偶发成功 ⇒ 非凭证问题、非仓库权限问题。
- 实测定位：本机 DNS 把 `github.com` 解析到 `20.6.7.17`，对该地址 TCP 443 **能建连但数据被中断**；
  换 `57.155.223.240`（8.8.8.8 解析结果）曾 0.4s 返回 200，随后同样超时 ⇒ 链路**间歇性丢包**（约 1/6 成功率）。
- 处置（按"不改仓库配置、不留长期凭据"的顺序）：
  1. 本地不加 `origin` 代理/镜像配置（不动用户仓库配置）；
  2. 起了一个临时 HTTP CONNECT 代理做 DNS 覆写（验证用，未生效）；
  3. **临时 deploy key + SSH over 443**（`ssh.github.com:443`，该链路正常）推送
     —— `git push ssh://git@ssh.github.com:443/...`，`main` 与 tag `v1.10.12` 均推送成功；
  4. **推送后立即删除该 deploy key**（API `204`，复查剩余 deploy key 列表为空），本地私钥文件删除。
- 结果校验：远端 `refs/heads/main = 26e9333`（与本地一致）、`refs/tags/v1.10.12 = 42d010f4`（与本地 tag 对象一致）
  ⇒ 无"内容相同但提交对象不同"的分叉（未走 Git Data API 改写提交，正是为了避开这一点）。
- 遗留建议（下个版本候选）：本机把 `github.com` 的 DNS 换成可靠解析，或给 git 配 HTTPS 代理；否则每次发布都要临时处理。

## 7. 回滚方式

- 桌面端 / App / Web：回退到 `v1.10.11` 的 Release 资产与镜像（`ghcr.io/js1688/jflove-{server,web}:1.10.11`），
  数据库无需回滚（本版无 DDL）。
- 服务端：`docker compose` 里把镜像 tag 从 `1.10.12` 改回 `1.10.11` 重启即可。

## 8. 已知边界

- `.ppk` 仍不做解析/自动转换（PPK v3 依赖 Argon2）——选中即给可执行转换指引；自动转换列为下个版本候选。
- 兜底探活上限 30 次（审查报告 M-1）：>30s 的极慢链路若同时丢就绪事件，面板会停在「会话正在连接」，重开标签即可恢复。
- 原生私钥对话框不经 DOM，CDP 无法驱动；其判据由 pytest（过滤器常量与实际传参）+ vitest（提示渲染位置）承担。
