# JFLove v1.4.2 设计文档

> 需求文档：[`文档记录/需求文档/v1.4.2.md`](../需求文档/v1.4.2.md)（已定稿）
> 基线：v1.4.0 设计 + v1.4.1 快速修复
> 类型：架构调整（实时修复 → 手动离线修复 + 播放纯净化）+ seek 回归修复

---

## 0. 版本对齐

- **需求文档**：`文档记录/需求文档/v1.4.2.md`
- **模块范围**：jflove-server、jflove-web、jflove-desktop、jflove-app
- **核心设计约束**：
  1. 加密协议不变：X25519 + ChaCha20-Poly1305；媒体流仍为加密帧；**不新增明文白名单**
  2. 播放路径**零 ffmpeg**：`/stream` 只输出健康文件字节流；损坏文件返回统一错误码 `MEDIA_NEEDS_REPAIR`
  3. 修复产物落盘于原文件同目录 `.jflove-repair/`；覆盖时**直接替换、不留备份**
  4. 修复功能权限门槛 = `can_write` 且 `can_delete`（admin 天然满足）
  5. 失败重试 = 清旧产物后完整重跑；任何路径不留垃圾文件

### 1.2 修复任务生命周期

```
pending(排队) → running(执行中) → verifying(自动验证) → success(成功)
                     │                                        │
                     ├→ failed(失败: ffmpeg错误/验证不通过)      ├→ overridden(已覆盖)
                     └→ canceled(已取消: 半成品已清理)           └→ (用户删除产物→产物清理)
服务重启: startup 扫描表, pending/running/verifying → failed(中断), 半成品清理
```

## 2. 数据库设计

### 2.1 新表 `media_repair_tasks`（遵循 §5 规范）

```sql
CREATE TABLE IF NOT EXISTS media_repair_tasks (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id         INTEGER NOT NULL,              -- 创建者（仅供列表展示，不用于权限隔离：任务全平台共享）
    disk_id         INTEGER NOT NULL,
    rel_path        TEXT    NOT NULL,              -- 原文件所在目录（磁盘内相对路径）
    filename        TEXT    NOT NULL,              -- 原文件名（含扩展名）
    status          TEXT    NOT NULL DEFAULT 'pending',
                    -- pending / running / verifying / success / failed / canceled / overridden
    progress        INTEGER NOT NULL DEFAULT 0,    -- 0~100（按已读字节/原文件大小估算）
    error_message   TEXT    NOT NULL DEFAULT '',   -- 失败原因（不含路径明文）
    source_size     INTEGER NOT NULL DEFAULT 0,    -- 原文件字节大小（进度估算）
    output_name     TEXT    NOT NULL DEFAULT '',   -- 产物文件名（.jflove-repair/ 内，success 后填写）
    started_at      TEXT,                          -- ISO 时间
    finished_at     TEXT,                          -- ISO 时间
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    deleted_at      TEXT
);
CREATE INDEX IF NOT EXISTS media_repair_tasks_user_id_idx ON media_repair_tasks(user_id);
CREATE INDEX IF NOT EXISTS media_repair_tasks_disk_id_idx ON media_repair_tasks(disk_id);
```

- **产物路径推导**：`磁盘根/rel_path/.jflove-repair/{stem}.mp4`（stem 为原文件去扩展名；与原文件同名产物按 stem+ext 唯一，同 stem 不同 ext 的原文件冲突时追加序号）
- **同文件互斥**：创建任务前查 `disk_id+rel_path+filename` 存在 `pending/running/verifying` 即拒绝（不加唯一索引，靠服务层校验+文件锁语义）
- **运行时迁移**：`init_db` 中 `CREATE TABLE IF NOT EXISTS` + startup 状态修正，无破坏性 DDL

### 2.2 config 键变更

| key | v1.4.2 语义 |
|-----|------------|
| `media_repair_enabled` | **废弃**（保留键不删，不再读取；播放与修复均不受影响） |
| `media_repair_allow_transcode` | 离线修复 `-c copy` 失败时是否降级重编码（沿用） |
| `media_repair_max_concurrent` | 离线修复队列并发上限（沿用，1~8） |

## 3. 后端设计

### 3.1 新增 `src/services/repair_task_service.py`

| 职责 | 说明 |
|------|------|
| 任务队列 | 模块级 `asyncio.Queue` + worker 协程池（并发=配置上限）；startup 启动，shutdown 停止 |
| 创建任务 | ① 权限校验（write+delete）② 健康判定（复用 `probe_media` + `is_mse_friendly`，健康→拒绝；无流→无法修复；损坏→入队）③ 互斥校验 ④ 清理该文件旧产物（失败重试不留垃圾） |
| 执行修复 | ffmpeg `-c:v copy -c:a aac` 输出到产物临时名 `*.repairing.mp4` → 完成后 rename 为正式名；进度按管道已读字节/`source_size` 百分比更新 DB（节流 ≥1s） |
| 自动验证 | `probe_media(产物)`：`has_stream && !fatal && duration>0` → success；否则 failed（错误信息「修复产物验证未通过」） |
| 取消 | pending→直接置 canceled；running→取消事件置位，worker 在读管道循环中检测，kill ffmpeg、删 `*.repairing.mp4` |
| 覆盖 | ① 任务 status=success ② 权限 write+delete ③ `os.replace(产物, 原文件路径)`（原子替换=删除原文件+顶替，不留备份）④ 置 overridden；失败抛错、状态不变 |
| 删除产物 | 删除 `.jflove-repair/` 内产物；目录空则删目录 |
| startup 恢复 | 扫表 pending/running/verifying → failed（「服务重启中断」）；清理磁盘上所有 `*.repairing.mp4` 残留 |

### 3.2 `media_repair_service.py` 重构

- **删除**：`stream_repaired_frames`、`ensure_playable` 的 time 分支、`patch_mvhd_duration` 调用链（实时流整体移除）
- **保留/迁移**：`_build_ffmpeg_cmd`（改为输出文件路径而非 pipe）、并发槽逻辑（改为队列 worker 数）、`is_transcode_enabled`/`get_concurrent_limit`
- `media_probe.py`：`patch_mvhd_duration` 删除；其余保留

### 3.3 `file_controller.py` 变更

- `/stream`：删除 `range_start_seconds` time 分支与 `stream_repaired_frames`；播放前判定（探测缓存 TTL 60s 复用）损坏 → 抛 `HTTPException(415, detail)`，**detail 内嵌错误码** `MEDIA_NEEDS_REPAIR`（加密信封包裹）；健康 → 既有 `_build_range_stream_generator`
- 新增产物流复用：`/stream` 请求体可选 `repair_preview: true` + `repair_task_id` → 流式返回该任务产物（同一加密帧管线，仅健康校验跳过）

### 3.4 新增 `src/controllers/repair_controller.py`

| 接口 | 方法 | 说明 | 鉴权 |
|------|------|------|------|
| `/api/v1/files/repair/create` | POST | 创建修复任务（disk_id/path/filename） | JWT + 磁盘 write+delete |
| `/api/v1/files/repair/tasks` | GET | 任务列表（分页，**全平台共享，所有登录用户可见**；body 传 token） | JWT |
| `/api/v1/files/repair/cancel` | POST | 取消任务（task_id） | JWT + 磁盘 write+delete |
| `/api/v1/files/repair/override` | POST | 覆盖原文件（task_id） | JWT + 磁盘 write+delete |
| `/api/v1/files/repair/delete-artifact` | POST | 删除产物（task_id） | JWT + 磁盘 write+delete |

> **权限模型（全平台共享）**：任务不按账户隔离——任务列表对所有登录用户可见（避免多账号重复修复）；操作类接口（create/cancel/override/delete-artifact）统一校验目标磁盘 write+delete 权限，与创建者无关。只读账号可看不可操作。

全部为加密 body JSON（`decrypt_request_body` + `encrypt_response`），无路径参数（task_id 在 body 内），错误走全局加密 handler。

### 3.5 文件列表隐藏

`list_files` 输出过滤 `entry.name == ".jflove-repair"`（服务端过滤，三端零改动即不展示；下载/删除等接口对 `.jflove-repair` 路径段一律 403）。

## 4. 三端设计

### 4.1 共同行为

1. 播放损坏文件 → 收到 `MEDIA_NEEDS_REPAIR` 错误码 → 弹窗「该文件已损坏，无法在线播放」+「立即修复」按钮 → 调 create → toast「已加入修复队列」→ 可跳转修复中心
2. 文件管理右键/长按「修复损坏媒体」（仅视频/音频扩展名；对无 write+delete 权限的磁盘隐藏/禁用）
3. 修复中心：任务列表（文件名/状态/进度/时间/创建者）+ 轮询(2.5s) + 按状态操作（取消/验证播放/覆盖[二次确认]/删除产物/重试/删除记录）；**列表全平台共享**（只读账号可见全部记录，但操作按钮禁用/隐藏——操作接口同时会校验权限返回 403）

## 5. 安全方案（对照 §9 安全宪法）

| 条款 | 落实 |
|------|------|
| §9.1 加密 | 新增 5 个 repair 接口全部加密 body + 加密响应；产物播放走既有 `/stream` 加密帧管线（v2），无新白名单 |
| §9.3 鉴权 | 无路径参数路由；task_id 在加密 body 内；操作类接口统一校验磁盘 write+delete 权限（任务全平台共享、不做账户归属隔离，避免重复修复；只读账号只读列表） |
| §9.4 不暴露 | `.jflove-repair` 不出现在列表 API；日志不记路径/文件名明文（error_message 不含路径）；URL 无业务参数 |
| §9.5 原语 | 复用 `decrypt_request_body`/`encrypt_response`/`encrypt_stream_chunk`，无新算法 |
| §9.7 自查 | 均已勾选：无可枚举 ID（task_id 在加密 body）、body 加密、响应加密、错误走 HTTPException、产物流用 StreamingResponse、无敏感响应头、日志脱敏、无新增密钥 |

**风险与缓解**：

| 风险 | 缓解 |
|------|------|
| ffmpeg 写产物路径越界 | 产物路径由 `_safe_join(base, rel_path)` 派生后再拼 `.jflove-repair/`，不接受客户端传路径 |
| 并发覆盖竞态 | 覆盖前 status 校验 + `os.replace` 原子操作；同一文件互斥任务 |
| 任务表膨胀 | 终态任务提供删除记录；列表分页（默认 50） |
| 重启残留半成品 | startup 全盘清理 `*.repairing.mp4`（按表内记录的目录范围） |

## 6. 与 v1.4.0/v1.4.1 设计差异

| 维度 | v1.4.0/1.4.1 | v1.4.2 |
|------|--------------|--------|
| 播放损坏文件 | time 实时修复流 | 415 + `MEDIA_NEEDS_REPAIR` |
| 修复触发 | 播放自动 | 手动（右键/长按/播放弹窗引导） |
| 修复产物 | 不落盘 | `.jflove-repair/` 落盘，fMP4 |
| 原文件 | 永不动 | 验证+二次确认后 `os.replace` 直接覆盖（无备份） |
| 新增表 | — | `media_repair_tasks` |
| 新增 API | 0 | 5（repair 系列） |
| 客户端 time 逻辑 | 三端 seek 补丁 | 全部删除（顺带修桌面/移动 seek 回归） |
| meta 帧 stream_mode | byte/time 双值 | 恒为 byte（保留字段向后兼容） |

## 7. 已确认项（2026-08-28 用户确认）

1. 产物命名冲突：同 stem 不同扩展名追加序号（`a.1.mp4`），能分清文件归属即可。
2. 播放前健康判定探测开销（首次 0.1~1s、缓存 60s）：可接受。
3. 修复中心轮询 2.5s/次：可接受。
4. **任务全平台共享、不按账户隔离**：任务列表所有登录用户可见（避免重复修复）；任务记录创建者仅供展示；只读账号可查看全部修复记录但不可操作（接口 403、三端按钮禁用/隐藏）。操作权限统一为磁盘 write+delete（与创建者无关）。
