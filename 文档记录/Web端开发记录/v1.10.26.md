## 2. R1：磁盘容量四项

新增 `DiskCapacity.tsx`，导出三件套（Web 与桌面端**逐字节一致**，受 `check_web_desktop_parity.py` 门禁）：

| 导出 | 用途 |
| --- | --- |
| `DiskCapacityLine` | 磁盘卡片单行摘要：`最大 951.6 GB · 已用 242.0 GB · 可用 708.8 GB · btrfs` + 进度条 |
| `DiskCapacityCells` | 管理表格 4 个 `<td>` |
| `DiskCapacityHeaders` | 管理表格 4 个 `<th>`（与 Cells 顺序严格对应） |

**空值策略**（R1 验收判据）：`total_size` / `used_size` / `free_size` 为 `null` 或非法值 → 一律 `—`；
`disk_type` 空串/null → `—`。**绝不渲染成 `0 B`**（会把"读不到"误导成"真的没空间"）。
进度条仅在拿到 `total_size > 0` 时画，避免除零与假进度。

实测（v1.10.26 真机）：

```
test   / 最大 951.6 GB · 已用 242.0 GB · 可用 708.8 GB · btrfs
R1盘   / 最大 15.4 GB  · 已用 2.6 GB   · 可用 12.8 GB  · tmpfs
```

## 3. P3：415 两种语义分开说

服务端 415 的 detail 有两种前缀相同、语义不同的文案：

| 服务端 detail | 真实含义 | 改前文案 | 改后文案 |
| --- | --- | --- | --- |
| `[MEDIA_NEEDS_REPAIR] 该文件无法在线边下边播` | 文件**是好的**，只是容器不适合 Web MSE（普通 MP4 / faststart MP4 / MKV / AVI） | ❌「该文件已损坏，无法在线播放」 | ✅「该格式不支持网页边下边播，可修复为 MP4 后在线播放（桌面端 / 手机端可直接播放）」 |
| `[MEDIA_NEEDS_REPAIR] 该文件已损坏` | ffmpeg 探测到致命错误，真损坏 | 「该文件已损坏」 | 「该文件已损坏」（不变） |

判据：`msg.includes('已损坏')` 分支。两种都仍给「立即修复」入口。

**为什么必须改**：同一个 `good.mp4`（H.264/AAC，ffmpeg 探测 `has_stream=True/fatal=False`）
Web 端说"已损坏"，桌面/移动端用原生播放器正常播放 —— 同一文件三端结论相反，用户会以为文件坏了。

## 4. P6：目录内搜索

`DiskBrowserPage` 排序工具栏右侧加搜索框（`placeholder="搜索本目录…"`，`aria-label` 齐全）：

- **纯客户端过滤**（目录内容已在本地，无需再打服务端）
- 大小写不敏感、子串匹配
- 有输入时显示「清除」按钮
- 空态区分：**有搜索词** → 「没有匹配的文件」+ 提示具体关键词；**无搜索词** → 原「此目录为空」

## 5. P7：网络错误文案 + 不自动消失

**文案**：`http-client.ts` 新增 `humanizeNetworkError()`，替换 4 处 `` `网络错误：${e.message}` ``：

| 原始异常 | 改前 | 改后 |
| --- | --- | --- |
| `TypeError: Failed to fetch` | `网络错误：Failed to fetch` | 「无法连接服务器，请检查服务端地址是否正确、服务是否已启动，以及是否允许当前站点的跨域访问」 |
| `Load failed` | `网络错误：Load failed` | 「无法连接服务器，请检查服务端地址与网络连接」 |
| timeout | `网络错误：…timeout…` | 「请求超时，请检查网络后重试」 |
| CORS / certificate | 原样英文 | 对应中文提示 |

识别不出的保留原文（截断 120 字符），排查时仍有线索但不刷屏。

**可见性**：`ErrorBanner` 的 `duration` 默认值 **5000 → 0**（不自动消失）。
理由：错误提示自动消失会导致用户还没看清原因提示就没了，只能重复点击再猜一次 ——
实测取证时网络错误横幅 5 秒后消失，截图与复现都抓不到原因。需要自动消失的场景仍可显式传 `duration`。
