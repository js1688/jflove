## 二·补充（第四轮）：HTTP 非安全上下文加密回退（crypto.subtle 不可用）

> 用户反馈：部署后经 `http://local.jflove.cn:18080` 访问，连接服务器报
> `Cannot read properties of undefined (reading 'generateKey')`。

### 根因

- Web Crypto API（`crypto.subtle`）**仅在安全上下文可用**：HTTPS，或 `http://localhost` / `127.0.0.1`。
- `http://local.jflove.cn`（HTTP + 局域网域名）被浏览器判定为**非安全上下文**（实测 `isSecureContext=false`、`crypto.subtle=undefined`），X25519 密钥交换直接失败。
- 属浏览器强制安全限制，非代码逻辑 bug。

### 改动

| 文件 | 改动 |
|------|------|
| `package.json` | 新增依赖 `@noble/curves@2.2.0`（X25519）、`@noble/hashes@2.2.0`（HKDF/SHA-256），与 `@noble/ciphers` 同族纯 JS 库 |
| `src/utils/crypto.ts` | 新增 `isWebCryptoAvailable()` 检测与纯 JS 回退：`generateKeyPairJS`（`x25519.keygen`）、`deriveSessionKeyJS`（`x25519.getSharedSecret` + `hkdf(sha256)`）；`generateKeyPair` / `deriveSessionKey` 在 `crypto.subtle` 不可用或私钥为 `Uint8Array` 时自动走纯 JS 路径；**协议不变**（标准 X25519 + HKDF-SHA256，盐 `b"jflove-v1"`，32B） |
| `src/services/file-service.ts` | 上传 SHA256 计算同样回退（`crypto.subtle.digest` 不可用时用 `sha256`） |
| `tests/utils/crypto.test.ts` | 适配私钥联合类型；新增「纯 JS 派生一致」「纯 JS 与 Web Crypto 跨实现互操作一致」2 用例 |

### 验证

- 单测：`tsc` 0 / `eslint` 0 / `vitest` **43** 通过（含纯 JS 回退 + 跨实现互操作）
- **与后端互操作实测**：Node 纯 JS 客户端完整链路（key-exchange → login → 加密 GET query 信封）对本地后端全部成功，证明回退路径与后端 cryptography 完全兼容
- 新镜像 `jflove-web:1.3.1`（manifest `deea9cc9`）容器冒烟：index 200 / SPA fallback 200
- HTTPS / localhost 环境仍走 Web Crypto 原路径，不受影响

> **部署建议（供参考）**：重新部署本镜像后，`http://local.jflove.cn:18080` 即可正常连接；
> 更推荐后续为 Nginx 配置 HTTPS（或 Caddy 自动证书），使 Web Crypto 主路径生效。

## 二·补充（第六轮）：Service Worker 流式代理——视频/音频真边下边播 + seek

### 改动

| 文件 | 改动 |
|------|------|
| `src/sw/index.ts`（新） | SW 流代理：拦截 `/jflove-stream/{token}`、Range 解析（bytes=a-b / a- / -N）、fetch 后端加密流、逐帧解密（`parseStreamFrames` + `decryptStreamChunk`）、首帧 meta → 206 + Content-Range；`skipWaiting`+`clients.claim` 立即接管无需 reload；HEAD 探测 file_size |
| `src/utils/stream-proxy.ts`（新） | 注册 SW（module）、`syncSession` 传会话（postMessage 内存）、`openStreamUrl` 生成一次性 token URL（自动拆分 path→目录+filename）、`closeStreamUrl`；非安全上下文返回不可用 |

## 二·补充（第七轮）：视频/音频「边下边播」真正落地（修复「总是完整下载后再播放」）

> 用户反馈：视频/音频预览总是做不到边下边播；必须先解决「方案是否可行」再改代码；
> 硬性要求：**一定要边下边播，拒绝下载完成后再播放**。

### 方案问题分析（先定方案，再改代码）

浏览器「边下边播」只有三条路，逐一论证：

| 方案 | 原理 | 结论 |
|------|------|------|
| 原生 Range 直放 | `<video src=真实URL>` 浏览器自动发 Range | ❌ 后端只出密文，浏览器解不了密，违反加密宪法 |
| **MSE**（旧 `media-source-player.ts`） | fetch 加密流→解密→append 到 SourceBuffer | ⚠️ 仅 fMP4 / WebM / 简单音频可靠；普通 MP4（moov 在尾部）、MKV/AVI/MOV 会 append 失败；旧实现对 mp3/wav/flac/ogg 用了错误 codec 探测 → 这就是"不可靠"根因 |
| **Service Worker 流式代理**（桌面端 StreamProxy 的 Web 版，采用） | `<video src="/jflove-stream/<token>">` → SW 拦截 → 解析 Range → 后端 `/api/v1/files/stream`（已支持 range_start/range_end）→ 逐帧解密 → `206 Partial Content` → 浏览器原生解码器接管 | ✅ **通用可靠**：mp4/webm/mp3/wav/flac/ogg/m4a/aac/opus 全部真边下边播 + seek。约束：仅安全上下文（HTTPS/localhost） |

**回退链（关键路径可靠）**：① SW 流式代理（安全上下文主路径）→ ② MSE（非安全上下文兜底，对 fMP4/WebM/mp3/flac/ogg 仍边下边播）→ ③ 完整下载 Blob（最后兜底，仅当两者都不可行）。

### 改动

| 文件 | 改动 |
|------|------|
| `src/utils/stream-frame.ts` | 新增 `parseRangeHeader`（RFC 7233 bytes=X-Y/X-/-N + 钳制到 [0,fileSize]）与 `openEncryptedStream`（向后端 /stream 打开加密 Range 流，读首帧 meta 后返回逐帧解密数据帧生成器；页面 MSE 与 SW 共用，会话参数化避免 SW 依赖 localStorage） |
| `src/sw/index.ts`（新） | SW 流式代理：拦截 `/jflove-stream/{token}`，HEAD 探测 / GET Range，`openEncryptedStream` 拉流逐帧解密，`206 + Content-Range + Accept-Ranges` 返回；opaque token 映射流目标（URL 不暴露业务数据）；会话经 postMessage 同步仅存内存；`skipWaiting`+`clients.claim` 立即接管 |
| `src/utils/stream-proxy.ts`（新） | 页面侧：`registerStreamProxy`（dev/prod 均注册 `/sw.js` + `scope:'/'`）、`syncStreamSession`、`openStreamUrl`/`closeStreamUrl`、`clearStreamProxySession`；非安全上下文自动不可用 |

## 二·补充（第八轮）：修复流式预览 404「文件不存在」（path/filename 拼接不一致）

> 用户实测反馈：真实服务器（`server.jflove.cn:8989`）上视频预览，`GET /api/v1/files/stream` 返回 404。
> 要求：到「磁盘(500GB)/叶方」目录下找真实视频验证；禁止访问磁盘(240GB)、禁止删除任何数据。

### 根因（两处，均已修复）

1. **path 语义不一致（404 直接原因）**：
   - 后端 `/api/v1/files/stream` 的接口约定（v1.1.0 起，桌面/移动端一致）：`path`=**文件所在目录**、`filename`=**文件名**；
     `get_stream_range` 内部 `os.path.join(path, filename)` 拼接。
   - Web 端 `FileItem.path`（`file-store.ts`）是**完整路径（含文件名）**，如 `/叶方/IMG_0443.MP4`；
     `FilePreviewPage` 把 `path=完整路径` + `filename=文件名` 同时传给 `/stream`，
     后端拼成 `base/叶方/IMG_0443.MP4/IMG_0443.MP4` → 「文件不存在」404。
   - 修复：`stream-frame.ts` 的 `openEncryptedStream`（SW 与 MSE 唯一共用入口）归一化——
     若 `path` 以 `/${filename}` 结尾则截掉文件名作为目录；两种传法（目录 / 完整路径）均兼容，
     不破坏桌面/移动端传法。
2. **`parseStreamFrames` 单分片丢帧（隐藏缺陷）**：原实现「先 read 再解析」，当 meta 帧与数据帧
   落在同一网络分片（小文件/单分片）时，`initialBuffer` 中的数据帧在遇到 `done` 时被丢弃，
   抛「流结束但缓冲区仍有未解析数据」。修复：先解析缓冲中的完整帧再读取，与新增测试共同暴露并修复。

### 改动

| 文件 | 改动 |
|------|------|
| `src/utils/stream-frame.ts` | `openEncryptedStream` 归一化 `path`：以 `/${filename}` 结尾则截为目录（兼容完整路径/目录两种传法）；`parseStreamFrames` 改为先解析缓冲再读取（修复单分片丢帧） |
| `tests/utils/stream-frame.test.ts` | 新增 2 用例：① 传完整路径时后端收到 path=目录 + filename=文件名（解密 query 信封断言）；② 传目录+文件名保持不变 |
