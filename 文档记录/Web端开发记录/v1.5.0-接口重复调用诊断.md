# v1.5.0 Web 端「接口重复调用 / 进入系统闪动」诊断报告

> 类型：只读诊断（未修改任何生产代码）
> 模块：`jflove-web`（React 18 + Vite 6 + TypeScript + react-router 7 + zustand 5）
> 诊断工具：`设计预览/stub_backend.mjs`、`设计预览/diag_web_dup_requests.mjs`（新增，仅诊断用）
> 实测日期：工具运行于本机 Windows + 无头 Edge（`--headless=new`）+ CDP

---

## 0. 结论速览（TL;DR）

| # | 现象 | 是否生产环境真实存在 | 处置 |
|---|---|---|---|
| 1 | 每个页面首次进入时，业务接口被同一 URL 连发 **2 次** | ❌ **否** —— 仅 dev（StrictMode 双跑 effect） | **不需要修** |
| 2 | `/repair`（修复标签）首次进入时 `files/repair/tasks` **立即连发 2 次**（间隔 19 ms），随后每 2.5 s 轮询 | ✅ **是**，prod 实测复现 | **必须修** |
| 3 | 跨源部署下，**每次业务调用实际产生 2 条 HTTP 请求**（`OPTIONS` 预检 + 实际请求） | ✅ **是**，所有场景 `OPTIONS 数 == 业务请求数` | **必须修**（部署层） |
| 4 | `/files`、`/notes` 首帧渲染 **假的空态**（"暂无可用磁盘" / "共 0 篇"）后才切骨架屏 | ✅ **是** | **必须修** |
| 5 | 进入 `/` 时多出一帧「只有侧边栏、主内容区空白」 | ✅ **是** | 建议修 |
| 6 | `users` / `virtual-disks` 被不同页面各自重复拉取（一次会话内各 2 次） | ✅ **是** | 建议修 |
| 7 | 根节点 `<html>` 的 `dark` class 变两次导致主题闪烁 | ❌ **否** —— 实测仅 **1 次** class 变更 | 不需要修 |

**一句话结论**：用户感觉的「接口调两遍」在生产环境里**主要不是 React 重复调用，而是 (a) 跨源 CORS 预检让每次调用产生 2 条 HTTP 请求、(b) `/repair` 页确有一个 effect 自触发导致的真实重复**。dev 下（`npm run dev`）StrictMode 会把**所有**页面的首个数据请求翻倍，这是用户最容易观察到的「调两遍」，但它是 React 18 开发态特性、不是缺陷。

### 1.2 桩后端为什么必须存在（以及它不影响结论）

页面默认把 API 打到 **绝对地址** `http://localhost:8989`（`src/config/constants.ts:14` `DEFAULT_SERVER_URL = 'http://localhost:8989'`，经 `src/utils/session.ts:79-81` `getServerUrl()` 读取，`src/utils/http-client.ts:32-34` `baseUrl()` 使用）。
`vite.config.ts:19-27` 里的 `/api` 代理**永远不会被走到**（代理只在请求路径为相对 `/api` 时生效），所以：

- 真实后端挂掉 ⇒ 页面停在错误态、`main.tsx:19-21` 的 `resyncSession().catch(() => logout())` 会**清会话并把用户踢回 /login**，无法测量「成功路径下的请求次数」；
- 桩后端按**与 `src/utils/crypto.ts` 完全一致的协议**（X25519 ECDH + HKDF-SHA256 `salt=b"jflove-v1"` + ChaCha20-Poly1305 信封 + `X-Session-ID` 头 + 加密 GET 的 URL query 信封）应答，使页面走成功分支，从而能观察到**完整**的请求集合。

> **重要说明**：本报告统计的是**请求被发起了几次**（`Network.requestWillBeSent`），与响应是否成功无关；桩后端只影响「页面渲染到哪一步」，不影响「同一次挂载里同一 URL 被点了几次」。

## 4. 每条重复调用的根因

### 4.1 【生产真实缺陷】`/repair` 首次进入 `repair/tasks` 立即连发两次

**位置**：`jflove-web/src/pages/RepairCenterPage.tsx:80-88`

```tsx
80:  useEffect(() => {
81:    // 磁盘权限（写+删并存）用于按钮可用性；管理员由服务端放行
82:    if (disks.length === 0) {
83:      loadDisks().catch(() => {});
84:    }
85:    void refresh();
86:    const t = setInterval(() => { void refresh(); }, 2500);
87:    return () => clearInterval(t);
88:  }, [refresh, loadDisks, disks.length]);
```

**根因**：依赖数组里含 **`disks.length`**，而 effect 体内**自己**会调用 `loadDisks()` 去改变它 —— 这是一个**自触发重跑**：

1. 首次挂载时 `disks.length === 0`（`src/stores/file-store.ts:46` `disks: []`）；
2. effect 调 `loadDisks()`（`file-store.ts:58-68` → `GET /api/v1/files/disks`）；同时调 `refresh()`（第 1 次 `repair/tasks`）；
3. 桩后端（=真实后端语义）返回 1 个磁盘 ⇒ `file-store.ts:62` `set({ disks })` ⇒ `disks.length` 由 `0 → 1`；
4. **dep 变化 ⇒ effect 重跑** ⇒ 再次 `void refresh()`（第 2 次 `repair/tasks`，实测 +192ms）+ 清掉旧 interval、重建新 interval。

**注意**：如果账号**一个可访问磁盘都没有**，`disks.length` 恒为 0，就不会重跑；所以这个重复**只在有磁盘权限的账号上出现**，与用户反馈「有时像调两遍」相符。interval 体只调 `refresh()`，**不会**每 2.5 s 重复请求 `files/disks`。

**次要问题（设计如此，但有优化空间）**：`setInterval(..., 2500)` 无「页面不可见时暂停」「连续无变化退避」，用户把标签页挂在后台时仍持续打服务端。

### 4.2 【生产真实，非「重复调用」但会让人误判】每次业务调用实际产生 2 条 HTTP 请求

**位置**：`jflove-web/src/utils/http-client.ts:150-156`（加密 GET）、`:71-81`（加密 POST/PUT/DELETE）

页面 origin 是 `http://localhost:3001`（或 4173 / nginx 的 80），而 API 打到绝对地址 `http://localhost:8989`（`src/config/constants.ts:14`）——**跨源**。请求带自定义头 `X-Session-ID`（`:75` / `:153`）与 `Content-Type: application/json`（`:74`），两者都会触发 CORS 预检。

**实测证据**：全部 32 次场景运行中，`OPTIONS` 预检次数**恒等于业务请求次数**（见 §2.1/2.2 两表最后两列）。例如生产态 `/repair`：业务 9 次 ⇒ 预检 9 次 ⇒ 服务端共收到 **18 条 HTTP 请求**。

在 DevTools Network 面板里，这就是「点一次接口、出现两条请求」。**这极可能就是用户口中「像调接口调两遍一样」的主要来源**，而且它在生产环境同样存在。

**为什么 `vite.config.ts:19-27` 的代理救不了**：`server.proxy` **只在请求走相对路径 `/api` 时生效**，而 `http-client.ts:32-34` 的 `baseUrl()` 返回的是 `localStorage.jflove_server_url || 'http://localhost:8989'`（绝对地址）。同时 `nginx.conf`（全文 34 行）**没有任何 `/api` 反向代理**，生产容器里同样是跨源绝对地址调用。

### 4.3 【跨页面真实重复】`users` / `virtual-disks` 被多个页面各自拉取

| 逻辑数据 | URL | 调用点 |
|---|---|---|
| 用户列表 | `GET /api/v1/users` | `jflove-web/src/pages/admin/AdminUsersPage.tsx:52`（effect `:61`）、`jflove-web/src/pages/admin/AdminPermissionsPage.tsx:48`（effect `:71`） |
| 全部磁盘（admin） | `GET /api/v1/virtual-disks` | `jflove-web/src/pages/admin/AdminDisksPage.tsx:57`（effect `:66`）、`jflove-web/src/pages/admin/AdminPermissionsPage.tsx:49`（effect `:71`）、**`jflove-web/src/pages/SettingsPage.tsx:44`（effect `:43-55`）+ `:178`（点「浏览选择」）** |
| 用户可见磁盘 | `GET /api/v1/files/disks` | `jflove-web/src/stores/file-store.ts:61`（FileListPage）、`jflove-web/src/pages/DiskBrowserPage.tsx:110`、`jflove-web/src/pages/RepairCenterPage.tsx:83` |

**实测**（生产构建，一次会话连续切 4 页）：`users` **2×**、`virtual-disks` **2×**、`files/disks` 1×、`notes/disk-config` 1×。
**根因**：这三类数据**没有任何共享缓存**——`AdminUsersPage` / `AdminDisksPage` / `AdminPermissionsPage` 各自用组件内 `useState` + mount effect 拉取（`AdminUsersPage.tsx:32,61`；`AdminDisksPage.tsx:36,66`；`AdminPermissionsPage.tsx:36,71`），既不复用 zustand store，也不做 TTL 缓存；`SettingsPage` 则直接 `useState`（`:39`）。

**附带问题**：`SettingsPage`（普通用户也会打开）调用的是 **admin 语义的** `/api/v1/virtual-disks`（`disk-service.ts:17-23` 注释即写明「管理员获取全部磁盘列表」），而 `FileListPage` 用的是 `/api/v1/files/disks`。同一逻辑概念两个 URL、权限语义不同，容易导致普通用户看到自己无权限的磁盘。

### 4.4 【同页二次调用，点击触发】`SettingsPage` 重复拉磁盘列表

**位置**：`jflove-web/src/pages/SettingsPage.tsx:43-55`（mount 拉一次，`:44` 是请求）与 `:176-182`（点「浏览选择」再拉一次，`:178` 是请求）

```tsx
173:  <Button size="sm" icon="folder"
176:    onClick={async () => {
178:        const d = await diskService.listAllDisks();   // 与 :44 同一个 URL
179:        setDisks(d);
180:        setShowDirBrowser(true);
```

挂载时已经拉过一次（`:44`），用户每次点「浏览选择」都会 `setDisks(d)` 并**丢弃刚拉到的数据重新请求**——`setDisks` 在这里没有意义（数据已经在了）。

### 4.5 【同页二次调用，写操作后全量重拉】store 透明重取

| 位置 | 行为 |

| `jflove-web/src/stores/file-store.ts:99-102` `createDir` | `POST /files/mkdir` 后 `loadFiles()` 再拉 `GET /files/list` |

### 4.6 【dev 假象】StrictMode 双跑 effect

**位置**：`jflove-web/src/main.tsx:24-28`

### 6.2 根节点 class 是否变两次（问题 4 的直接回答）

**实测：不会。`<html>` 的 `class` 在一次加载中只被写入 1 次（深色）或 0 次（亮色），不存在「变两次」。**

深色模式（`localStorage['jflove.theme'] = 'dark'`，生产构建）实测序列：

```
  13.5ms  <html> class: null → class="dark" colorScheme="dark" bg="rgb(8, 13, 24)"   ← 唯一一次 class 变更
  13.5ms  <html> style: null → class="dark" colorScheme="dark" bg="rgb(8, 13, 24)"   ← style.colorScheme
  13.5ms  <html> style: "color-scheme: dark;" → class="dark" …                        ← style.backgroundColor
  37.7ms  paint  path=/files  #root.innerHTML=0B   html.class="dark" colorScheme="dark"
 116.4ms  paint  path=/files  #root.innerHTML=9220B  html.class="dark" colorScheme="dark"
 149.0ms  paint  path=/files  #root.innerHTML=9845B  html.class="dark" colorScheme="dark"
```
亮色 / 跟随系统（headless 默认亮）实测：**完全没有 `class` 属性变更记录**，只有 2 次 `style` 变更。

**原因**：
1. `jflove-web/index.html:14-29` 的内联同步脚本在 `<head>` 里先跑：`root.classList.toggle('dark', isDark)`（`:22`）。亮色时 `toggle(..., false)` 对**没有该 class** 的元素是**无操作**，不产生属性变更；深色时加上 `dark` —— 这是**唯一**一次 class 变更。
2. React 挂载后 `jflove-web/src/App.tsx:18-21` 调 `useThemeStore.watchSystem()`，最终进 `jflove-web/src/stores/theme-store.ts:46-53` 的 `applyThemeToDom(resolved)`：`root.classList.toggle('dark', resolved === 'dark')`（`:48`）。此时 class 已与内联脚本设的一致，`toggle` 是**幂等无操作**，**不产生第二次变更**。
3. 两条路径的模式来源相同（都是 `readStoredThemeMode()` 读同一个 key `jflove.theme`，`theme-store.ts:17,69-70` vs `index.html:16-20`），所以正常情况下结果**必然一致**，不会出现「先暗后亮」的双闪。

**唯一潜在不一致点**（本次未复现，仅代码审查发现）：内联脚本还写死了 `root.style.backgroundColor = isDark ? '#080d18' : '#f6f7fb'`（`index.html:25`），而 `theme-store.ts:46-53` 的 `applyThemeToDom` **只管 `classList` 与 `colorScheme`，从不清理这个内联背景色**。该值目前恰好等于 tokens 里的画布色，但一旦设计令牌改色，`<html>` 的内联背景会与 `--bg-canvas` 分叉。建议把 `:25` 的写死色值改为 `root.style.removeProperty('background-color')`（由 CSS 接管），或两处改色时强制同步。

**结论：「进入系统闪动好几次」与主题无关，不需要动 `index.html` 的内联脚本或 `theme-store.ts` 的 class 逻辑。**
