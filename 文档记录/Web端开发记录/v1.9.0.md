## 1. 本次实现结论

| # | 能力 | 结论 |
|---|---|---|
| 1 | 上传断点续传（Web） | `init` 带 `client_type:"web"`；按服务端返回的 `received_chunks` 跳过已传分片；分片默认 **512KB**；单片失败**指数退避重试 5 次**（500ms → 1s → 2s → 4s）；网络/合并失败**不** DELETE 会话，仅用户取消才清理 |
| 2 | 合并异步化 | `complete` 带 `async_mode:true` 后，每 **2.5s** POST `/api/v1/files/upload/progress`，处理 `queued / merging / done / failed / unknown`；「旧服务端 complete 响应无 state 字段」时才静默降级为同步完成；本版不依赖同步协议 |
| 3 | 下载 Range 续传 | `range_start` 只进加密 body（URL 无明文）；解析 `X-Stream-Offset / X-Stream-Total / X-File-Version`；本地分块**OPFS 优先 → IndexedDB 回退 → 都不可用回退整文件下载并明确提示**；刷新后从已存偏移续传；完成后拼 Blob 导出并清理临时数据；失败保留、用户「放弃」才清理 |
| 4 | 设置页「存储与临时文件」 | 管理员系统设置新增卡片：总开关 / 保障时长 1~168h / 清理间隔 5~1440min / 客户端类型多选 / 孤儿保留期 1~168h / 每用户会话上限 1~64 / 合并并发 0~4 / 上传分片并发 1~8 / 弱服务端模式一键预设 / 立即清理；走既有加密 `configService`；保存后立即重新 GET 刷新 |
| 5 | 测试 | 新增 **5 个测试文件、43 个用例**（另有 1 个传输 store 用例）：上传续传/重试/取消/异步轮询/远端核验、下载续传/降级/远端变化/失败保留、OPFS 存储实现与选型、设置服务层、设置页交互 |
| 6 | 文档 | 本文件；`jflove-web/README.md` 增补「大文件断点续传」能力与已知限制 |

## 2. 功能与改动点

### 2.1 上传（`src/services/file-service.ts`）

- 新增常量（`jflove-web/src/services/file-service.ts:33` 起）：
  - `UPLOAD_CHUNK_SIZE = 512 * 1024`（D35 / F56.4；3GB = `ceil(size/512KB)` 片，AC-363）
  - `UPLOAD_CHUNK_MAX_ATTEMPTS = 5`、`UPLOAD_CHUNK_RETRY_BASE_DELAY_MS = 500`
  - `UPLOAD_PROGRESS_POLL_INTERVAL_MS = 2500`、`UPLOAD_MERGE_MAX_WAIT_MS = 30min`（防无进度记录无限轮询）
- `uploadFile`（`:483`）：
  0. **上传前**先用 `GET /api/v1/files/list` 核验「远端同名且大小一致」；命中则直接判定完成、不 init 不传片
     （F46.6；服务端实现不自动判定 `already_exists`，由客户端按需求以大小一致为判据；列表读取失败则继续正常上传）。
  1. SHA256 → `POST /api/v1/files/upload/init`，body 新增 `client_type:"web"`（`:506`）。
  2. 响应支持 `received_chunks / resumed / expires_at / already_exists / restart_required / max_chunk_size / recommended_concurrency`：
     - `already_exists` → 直接判定完成，不再创建会话（F46.6）；
     - `received_chunks` → 跳过已收片、初始进度按已收字节计数；提示「检测到未完成上传，从第 N 片继续」；
     - `restart_required` → 提示「原分片已过期或已失败，将从第 0 片重新上传」，从 0 片上传（F46.7）；
     - 响应无这些字段时按新会话（0 片）处理。
  3. 分片上传：`uploadChunkWithRetry`（`:747` 附近）单片失败按指数退避重试（最多 5 次），只抛最后一次错误；**失败不删除会话**。
  4. `complete`（`:591`）：`{upload_id, async_mode: true}`；响应：
     - 无 `state` 字段（旧服务端）→ 静默降级为同步完成（本版唯一允许的兼容分支）；
     - `done` → 完成；`failed` → 抛 `ApiError(400, 中文原因)`（`missing_chunks` / `hash_mismatch` / `io_error` 映射见 `describeMergeError`）；
     - `merging` / `queued` → `pollMergeProgress`（`:784`）：每 2.5s 轮询，`queued` 显示排队位次、`merging` 显示百分比，仅状态变化时回调一次；`done` 返回 `path`；`failed` 抛中文原因；`unknown` 抛「进度记录可能已过期」。
  5. 失败兜底（F46.6）：`complete`/轮询失败后，用 `GET /api/v1/files/list` 核验远端同名同大小文件；命中则判定完成，避免「合并成功但响应丢失」导致整文件重传。
  6. 取消：`signal` 触发且尚未提交 `complete` → 调用 `DELETE /api/v1/files/upload/{upload_id}`（`cancelUpload`，`:650` 附近）清理会话后抛 `AbortError`；已提交合并的取消**不删会话**（服务端继续合并）。

### 2.2 下载（`src/services/file-service.ts` + `src/utils/http-client.ts`）

- `http-client.ts`：
  - 新增 `DownloadStreamHeaders`（`X-Stream-Offset` / `X-Stream-Total` / `X-File-Version` / `X-Encrypted-Stream`，`:365`）与 `DownloadStreamResult`；
  - `downloadStream(path, body, {signal})`（`:408`）返回 `{ stream, headers }`；4xx（含 416）先解密错误信封再抛 `ApiError(status, detail)`；401 续约后重发；用户取消抛 `AbortError`；`range_start` 只在加密 body 内。
- `file-service.ts`：
  - `downloadStream` 新增 `rangeStart` 参数（`:246`）；
  - `downloadResumable`（`:297`）主流程：
    1. `getDownloadPartStore()`：OPFS → IndexedDB → null（不支持时 `onStatus('unsupported')` + 整文件下载，不静默）；
    2. 每次下载前 `cleanupExpired(7 天)`（D33 / AC-337）；
    3. 读 meta → `range_start = offset` 请求；校验 `X-File-Version` / `X-Stream-Total` / 实际 `X-Stream-Offset`；版本/大小变化、服务端忽略 range、416 越界 → 删除本地 part 从头下载并提示（AC-332 / AC-336，不拼坏文件）；
    4. 逐帧解密 → 每 1MB 追加到本地存储并回写 meta（version/size/offset/chunkCount/updatedAt）；
    5. 结束时校验总大小；把本地分块拼 Blob 触发「另存为」，清理本地 part；任一步失败保留 part（`throw` 给页面显示）；
    6. 本地分块被浏览器清理/损坏（读出字节不足）→ 清理残数据并提示重新下载，避免反复续传出坏文件。
  - `abandonDownload(diskId, path)`（`:439`）：仅用户显式「放弃续传」时删除本地 part。
  - `downloadRaw`（预览用）仍走同一 `/files/download` 流，但**不做**续传（MSE 预览路径不变）。

### 2.3 本地续传存储（新增 `src/utils/download-store.ts`）

- 统一接口 `DownloadPartStore`（`:40`）：`readMeta / writeMeta / appendChunk / readAll / remove / cleanupExpired`。
- 选型 `detectDownloadStorageKind()`（`:69`）：`navigator.storage.getDirectory` 可用 → `opfs`；否则 `indexedDB` 存在 → `indexeddb`；否则 `none`。
- OPFS 实现（`:125`）：
  - 根目录 `jflove-downloads/`，每个文件一个子目录（`encodeURIComponent(diskId|path)`）；
  - `meta.json` + `chunk-000000.bin` 逐块文件（避免整文件 read-modify-write）；
  - `index.json` 记录 `updatedAt` 供 7 天清理；索引读改写串行化；
  - OPFS 探测成功但实际不可用（隐私模式/权限拒绝）→ 回退 IndexedDB（`getDownloadPartStore`，`:392`）。
- IndexedDB 实现（`:267`）：DB `jflove-downloads`，`meta`（keyPath `key`）+ `chunks`（keyPath `[key,index]`）两个 object store；`delete` 用 `IDBKeyRange` 删整 key 的分块；`cleanupExpired` 按 meta 时间删。
- 常量 `DOWNLOAD_PART_TTL_MS = 7 天`（`:18`）；`isPartExpired` 纯函数供单测。
- 安全：本地 meta 只存远端 size/version/offset 与文件名，**不存 token / session_key**；存储键不进入 URL。

### 2.4 Hook / 页面接线

- `src/hooks/use-files.ts`：
  - 上传：创建 `AbortController` 并通过 `transfer.registerCancelHandler` 接入「取消」；`onStatus` → Toast（继续上传 / 排队 / 服务端合并中）；失败 `toast.error`；刷新列表失败单独提示。
  - 下载：`downloadResumable` + 进度 → 任务进度；`resume/restart/unsupported` → Toast（「继续下载 / 重新下载 / 无法断点续传」）；失败 `toast.error`；取消保留本地 part。
  - `abandonDownload`：供传输页「放弃续传」按钮调用。
- `src/stores/transfer-store.ts`：新增 `registerCancelHandler`（模块级回调表，不进 Zustand 状态，`:100`）；`cancelTask` 先触发回调中止在途请求，再置 `cancelled`；`removeTask / clearFinished` 同步注销。
- `src/pages/TransferPage.tsx`：下载任务 `failed / cancelled` 时显示「放弃续传」按钮（`:101`），点击调用 `abandonDownload`。

## 3. 调用的后端接口（与设计 §4 对齐）

| 接口 | 方法 | Web 端用法 | 关键字段 |
|---|---|---|---|
| `/api/v1/files/upload/init` | POST | 加密 body | 请求 `client_type:"web"`；响应 `upload_id / received_chunks / resumed / expires_at / already_exists / already_path / restart_required` |
| `/api/v1/files/upload/chunk` | POST | 加密 body，512KB/片，失败重试 5 次 | `upload_id / chunk_index / total_chunks / chunk_data` |
| `/api/v1/files/upload/complete` | POST | 强制异步 | 请求 `async_mode:true`；响应 `state / path / error / missing_chunks / poll_interval_s` |
| `/api/v1/files/upload/progress` | POST | 2.5s 轮询 | 响应 `state / percent / queue_position / path / error / missing_chunks` |
| `/api/v1/files/upload/{upload_id}` | DELETE | **仅用户取消**时调用 | 路径参数 UUID；归属校验由服务端 |
| `/api/v1/files/download` | GET | 加密 query 信封 + `range_start` | 响应头 `X-Stream-Offset / X-Stream-Total / X-File-Version`；帧格式不变（v1） |
| `/api/v1/files/list` | GET | 失败兜底核验远端大小 | `files[]`（隐藏项由服务端过滤） |
| `/api/v1/config` | GET/PUT | 设置页读写（加密） | 上传清理 8 个键（默认值缺省注入） |
| `/api/v1/config/cleanup` | POST | 立即清理（加密） | 响应 `removed_sessions / removed_dirs / removed_parts / skipped / executed_at` |

安全核对（§9）：所有新字段都在加密信封内；`range_start`/`upload_id` 不进 URL 明文（路径参数 UUID 由服务端校验归属）；
响应头只有偏移/总大小/版本标识，无文件名/路径/用户 ID；客户端不新增任何加密原语；token/session_key 不落日志与本地续传数据。

## 4. 与上一版本（v1.8.4 / v1.8.2）的逻辑差异

| 维度 | v1.8.4 现状 | v1.9.0 Web |
|---|---|---|
| 上传分片 | 1MB，`total_chunks = ceil(size/1MB)` | **512KB**，`total_chunks = ceil(size/512KB)` |
| init | 每次新建会话，不带客户端类型 | 带 `client_type:"web"`；按 `received_chunks` 跳过已传片；支持 `already_exists` / `restart_required` |
| 单片失败 | 直接推倒整个上传 | **指数退避重试 5 次**，不推倒整个文件 |
| 失败清理 | 原本也不删除（保持） | 明确「网络/合并失败不 DELETE，仅用户取消 DELETE」；新增可用的取消链路 |
| complete | 同步等待合并（3GB 必超时） | `async_mode:true` 立即返回 + 2.5s 轮询进度；旧服务端无 state 字段才降级 |
| 下载 | 一次性流式下载到内存 → Blob | Range 续传 + OPFS/IDB 分块；刷新后续传；完成后拼 Blob 导出；失败保留 part |
| 下载存储 | 无 | OPFS 优先 / IndexedDB 回退 / 都不可用整文件下载并提示 |
| 本地 part 生命周期 | 无 | 7 天自动清理；用户「放弃续传」显式清理 |
| 传输取消 | 仅改 UI 状态，后台请求继续 | `AbortController` 中止在途请求；上传取消删会话、下载取消保留 part |
| 设置页 | 离线修复 / 离线下载 | 新增「存储与临时文件」卡片（10 项 + 预设 + 立即清理） |
| 兼容策略 | 同步 complete | **强制异步**（D27），仅旧服务端无 state 字段的静默降级 |

## 6. 设计取舍

1. **OPFS 采用「目录 + meta.json + 逐块文件 + index.json」**：OPFS 的 `createWritable()` 不支持随机位置追加，整文件读写会让大文件续传失真；逐块文件写入简单、幂等，索引文件承担 7 天清理所需的更新时间。IndexedDB 用 `meta` / `chunks` 两个 store 避免每次读改写整包。
2. **续传参数只进加密 body**：沿用现有 GET + URL query 信封做法，`range_start` 不进入 URL；响应头只放服务端设计规定的三个元数据头（§9.4）。
3. **旧协议只保留一个静默降级点**：仅当 `complete` 响应**没有** `state` 字段（旧服务端同步协议）时按完成处理；新协议一律异步轮询（D27 不保留同步分支）。
4. **取消语义与失败语义分离**：失败保留会话/分块供续传；只有用户取消（上传）或「放弃续传」（下载）才清理。`registerCancelHandler` 放在 store 模块级 Map 而非 Zustand 状态，避免函数引用进入状态快照。
5. **保存后立即 GET 刷新**：设置页保存先逐项 PUT，再重新拉取配置，确保三端共享值与 UI 一致（AC-352）；越界值由前端前置拦截，最终以服务端 400 为准。
6. **不引入新加密原语**：复用 `encryptEnvelope` / `decryptEnvelope` / `decryptStreamChunk` 与既有帧格式。
7. **不做 F56.7 可观测指标面板**：设计 §4 未给出「合并执行数/排队数/上传并发/合并耗时」的 API 契约，前端不自造接口；已在 §8 列为待后端补契约项。

## 8. 未决问题 / 风险

1. **端到端实机验证移交 Phase 6**：本客户端按设计 §4 契约实现。开发期间后端并行落地了新协议
   （`file_controller.py` 已含 `client_type` 校验、`upload/status`、`async_mode` 分支、下载 `X-Stream-Offset/X-Stream-Total/X-File-Version`、
   `POST /config/cleanup`），并已逐字段静态比对与本客户端请求/响应字段名一致；
   但本轮未启动服务端跑「浏览器上传 → 断网续传 → 下载刷新续传」实证，避免与并行后端开发互相污染环境。
   Phase 6 必须补 `node scripts/verify/web_shot.mjs --click-text '连接服务端'` + 真实上传/下载续传证据。
2. **`init.already_exists` 服务端契约差异**：设计 §2.3 写「服务端返回 already_exists」，但 `file_service.init_upload_ex`
   明确**不**自动判定（注释：同大小不代表同内容），恒返回 `already_exists:false`。
   Web 端已实现两处兜底：① 上传前用远端列表核验同名同大小即判定完成；② 合并/轮询失败后再核验一次。
   客户端仍保留对 `already_exists` / `already_path` 字段的兼容分支（设计型服务端上线即生效）。
   建议 designer/backend 在 P5 统一该口径。
3. **`upload/status` 契约**：设计新增该接口，但 Web 端凭 `init.received_chunks` 即可续传，未调用它；若后端要求客户端主动 `status` 查询/补片，需追加服务方法与用例。
4. **F56.7 可观测**：设计未定义指标 API，设置页暂不展示「合并执行数/排队数/上传并发/合并耗时」；待后端补契约（`/config/cleanup` 已按设计实现）。
5. **IndexedDB 实现只有选型/回退单测**：真实浏览器 IDB 读写与 OPFS 隐私模式行为需在联调时实测（本机 jsdom 无 OPFS/IDB）。
6. **下载续传依赖服务端 Range**：旧服务端忽略 `range_start` 时客户端会检测实际偏移并从头下载（不产生坏文件），但会多一次请求；属于可接受降级。
7. **上传取消为「分片边界中止」**：在途分片请求本身不 abort（避免把服务端写盘打断），最迟当前分片返回后停止；已传分片由 DELETE 清理。
8. **跨版本分片尺寸变更的会话复用风险**：服务端指纹不含 `total_chunks`（`init` 响应也不回传它）。若 24h 内存在
   v1.8.x（1MB 分片）遗留会话，1.9.0 Web（512KB）重传同一文件时可能复用到旧 `total_chunks` 会话，
   客户端无法自检，表现为分片索引越界 400。建议服务端把 `total_chunks` 纳入指纹或 `init` 回传；
   客户端在拿到契约后再补自检（当前不改其他模块）。
