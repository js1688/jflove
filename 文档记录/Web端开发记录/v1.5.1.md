## 5. 设计取舍（含与设计文档的偏差说明）

1. **「大纲」开关放在 PageHeader，而不是 Markdown 工具栏**
   设计文档 §4.1 的布局图把 `[大纲]` 画在 `[编辑|分屏|预览]` 旁边，且 Markdown 工具栏只在
   编辑 / 分屏渲染（`showEditor`）—— 若把开关放进那个工具栏，**预览模式（已有笔记的默认模式）将无法折叠大纲**，
   AC-8「可折叠与展开」就落空了。因此按设计图放在 PageHeader 的 actions 区，用现有
   `IconButton` + `Icon name="list"`，`data-on` 在**折叠时**为真（按任务书写法），并加 `aria-expanded`。
2. **开关只在「有标题的预览 / 分屏」出现**
   与大纲栏的可用条件完全一致：编辑模式或笔记无标题时不渲染按钮，避免出现"点了没反应的死开关"
   （与需求 §1.2「删除看起来能配、实际不生效的界面」同一条原则）。
3. **`outlineAvailable` 里额外加了 `!store.isLoading`**
   加载中会短暂持有**上一篇笔记**的 `currentContent`，不加这个条件会先闪一下旧笔记的大纲。
4. **新增大纲栏条目容器类沿用原实现的 `space-y-1 px-4 pb-3`**，标题行由 `<summary>` 的
   `cursor-pointer px-4 py-2 text-[13px] text-muted hover:bg-hover` 改为不可点击的
   `px-4 py-2 text-[13px] text-muted`（侧栏标题行不再是折叠触发器，折叠职责已交给工具栏按钮）。
5. **`.icon-btn[data-on='true']` 的 CSS 新增（+5 行）**
   既有样式表只有 `.tb[data-on]` / `.tab[data-on]` / `.toggle-box[data-on]` / `.segmented > button[data-on]`，
   没有 `.icon-btn[data-on]`；不加这条，`data-on` 只是一个不产生视觉反馈的属性。
   **跨端提示**：桌面端 `ui/src/styles/components.css` 同样没有这条规则，若桌面端也要有可见激活态，
   需在其样式表补同一条（不在本角色边界内，已上报编排者）。
6. **判定用 ref 而不是 effect 依赖**
   两个 ref 都**按 filename 记账**：`modeResolvedForRef`（该 filename 是否已判定过）+
   `userSwitchedModeForRef`（**哪一篇**笔记被手动切换过，Phase 5 M-4 返工后的口径，见 §11.1），
   判定只发生在 `loadNote(...).then` 里一次；自动保存触发的 `store` 变化**不会**回头改写用户模式。
7. **取 `useNoteStore.getState().currentContent` 而不是闭包里的 `store.currentContent`**
   effect 闭包里的 `store` 是本次渲染的快照，加载完成那一刻它可能还是上一篇笔记的内容。
   任务书里的 `store.currentContent` 语义是"store 的当前内容"，这里按语义取实时值。
8. **不做的事**（与设计文档 §6.3 一致）：不加滚动联动高亮、不引入 `IntersectionObserver`、
   不写 `localStorage`、不改 favicon、不动 `Icon.tsx` 注册表、不夹带重构。

### 11.1 M-4（中等 → 已修复）：`userSwitched` 跨笔记不复位

**缺陷**：返工前用 `useRef<boolean>` 记录"用户是否手动切过模式"，语义是**组件实例级全局** ——
在某篇笔记里手动切过一次后，此后**打开任何有内容的笔记都会停在 `edit`**，违背 AC-9
（"有内容 → 预览"）。审查员核实当前路由只有 `notes/:noteId`、无页内跳转入口，故**当时不可达**，
但属"加个页内跳转就立刻变真缺陷"的隐患。

**修法**（按 filename 记账）：

| 位置 | 返工前 | 返工后 |
| --- | --- | --- |
| ref 声明 | `const userSwitchedModeRef = useRef(false);` | `const userSwitchedModeForRef = useRef<string \| null>(null);` |
| `.then` 守卫 | `if (userSwitchedModeRef.current) return;` | `if (userSwitchedModeForRef.current === filename) return;` |
| 手动切换标记 | `userSwitchedModeRef.current = true;` | `userSwitchedModeForRef.current = filename;` |

**语义**：同一 filename → 手动优先、不再被自动改写（AC-11 不变）；换 filename → 重新按内容判定
（有内容 `preview` / 空 `edit`，AC-9 / AC-10 恢复）。防回退：源码级断言额外锁了
`not.toContain('userSwitchedModeRef')`，防止有人把全局布尔版改回来。

**验证**：新增 3 条用例（§8.3），负向对照 D 组 3 failed → 恢复后 21 passed（§9）。

### 11.3 只读核实：`http-client.ts:99-101` 不存在"解密失败当成明文成功"

**审查疑问**：Web 端是否漏修了 v1.5.0 文档声称修过的同型缺陷（200 响应解密失败被静默当成明文成功）？

**结论：Web 端不存在该静默失败路径。**—— 200 成功路径**无条件**解密，失败必然抛错。

**静态证据（行号）**：

| 位置 | 代码 | 说明 |
| --- | --- | --- |
| `src/utils/http-client.ts:99` | `const respJson: { nonce: string; ciphertext: string } = await response.json();` | 直接取信封字段，**没有任何** `if (respJson.nonce)` 之类的"是否为信封"分支 |
| `src/utils/http-client.ts:100` | `const decrypted = decryptEnvelope(sessionKey, respJson.nonce, respJson.ciphertext);` | **无条件**调用解密；明文 JSON 时 `nonce/ciphertext` 为 `undefined` |
| `src/utils/http-client.ts:101` | `return JSON.parse(new TextDecoder().decode(decrypted)) as T;` | 只有解密成功才会走到"返回业务数据" |
| `src/utils/crypto.ts:151-160` | `decryptEnvelope` 内无 try/catch、无明文兜底：`base64ToUint8Array(nonceB64)` → `chacha20poly1305(key, nonce)` → `chacha.decrypt(...)` | 任一环节失败即抛（`atob` 抛 `InvalidCharacterError`；nonce 长度/认证标签不对由 `@noble/ciphers` 抛） |
| `src/utils/http-client.ts:102-109` | `catch` 把非 `ApiError` 包成 `ApiError(0, '网络错误：…')` 再 **throw** | 是"抛错"，不是"吞掉后返回明文" |
| `src/utils/http-client.ts:169-171` | 加密 GET（URL query 信封）走的是**同一形状**的无条件解密 | POST/PUT/DELETE 与 GET 两条路径都覆盖 |
| `src/utils/http-client.ts:226-240` | `tryDecryptError` 有 `return json as { detail: string }` 兜底 | **仅用于 `!response.ok` 的错误响应**，只取 `detail` 供提示，不可能被当成成功数据 |
