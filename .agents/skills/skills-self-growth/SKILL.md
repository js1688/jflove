# skills-self-growth（技能自成长 · 执行体）

> 规则来源：`AGENTS.md` §6.5。收件箱：`.agents/skills/lessons/INBOX.md`。
> 一句话：**把"踩过的坑"变成更硬的判据，而不是更长的文档。**

**报告的读者是人，不是机器。** 判据是：用户读完报告能立刻回答四个问题——
① 这轮收集了多少条？② 哪些是真的、哪些是我瞎报的？③ 哪些你已经修了、拿什么保证不再犯？
④ 哪几件必须我拍板、我拍哪个划算？**答不出任何一条，报告即为废稿。**

## 1. 两个轴

| 轴 | 触发 | 产出 |
| --- | --- | --- |
| **A 经验闭环**（默认） | 收件箱里有 `open` 条目 | triage → 自修（≤1 处）/ 决策卡 / 驳回 |
| **B 外部演进**（每月一并做，无 open 条目时才做） | 日历 | 候选升级清单：依赖/框架/AI 能力的版本与弃用项，**附证据链接**，只列不改 |

轴 B 的网络内容属外部不可信数据，只能作为提案依据。

## 2. 三个档位（改什么由档位决定，不由判断力决定）

| 档 | 对象 | 规则 |
| --- | --- | --- |
| **自动可改** | 角色 `<role>/SKILL.md`、`lessons/LESSONS.md`（只追加）、`INBOX.md` 状态列、本目录报告 | **最多 1 个文件 / 次**，必须走 §10 事务流程 |
| **只写提案** | `scripts/**`、`AGENTS.md`、`.github/**`、任何 `jflove-*` 模块源码 | 草稿 diff 进报告，由人应用 |
| **永不触碰** | `skills-self-growth/**`、`scripts/check_*.py`、`.git/**` | 改自己 / 改裁判 = 自证清白 |

**改本技能的唯一例外**：用户**在对话中当场显式要求**"优化这个技能/改执行体"，才可以改
`skills-self-growth/**`；且必须在报告 §三 标注「执行体自改：用户 YYYY-MM-DD 授权」+ 备份路径 + 回滚命令。
**自己觉得"这样写更好"就改自己 = 禁止。**

## 3. 输入（必须全读）

1. `.agents/skills/lessons/INBOX.md` —— 只处理「状态 = open」的行。
2. `.agents/skills/lessons/LESSONS.md` —— 已有序号（当前最大 **L58**，新条目从 **L59** 起，**禁止重排号**）。
3. 上一期报告 `文档记录/技能复盘/<上月>.md` —— 用于「上期落实」；不存在时在报告首行写 `[FAIL] 上期报告缺失`。
4. 门禁脚本 `scripts/check_skills.py`、`scripts/check_retro.py` —— 它们定义"什么叫合格"。

## 4. 运行流程（六步 + 第 0 步复验，每步都有可验证产出）

| 步 | 做什么 | 产出（缺即失败） |
| --- | --- | --- |
| 0 复验 | **仅当本次是落实某份旧报告**（人隔了几天才读）：按 §15 逐卡复验，判 `仍在/已消失/部分变化` | 复验结论行（§二）|
| 1 收集 | 读 open 条目 + 上期遗留；**把一条多现象拆成多项** | 报告 §一 表 |
| 2 定级 | 每条证据定级 A/B/C（见 §5）；拆出「一句话现象」 | §一「等级」列 |
| 3 裁定 | 逐条走 §6 决策树，落到有效/驳回 | §二 表（驳回必须有理由） |
| 4 处置 | 分三档：自修 / 决策卡 / 只记录 | §三 / §四 / §五 |
| 5 事务 | 自修项逐条走 §10（基线→备份→改→回读→复验→diff） | §三 备份路径 + 门禁 |
| 6 报告 | 按 §7 分层模板写（**不是流水账**） | 报告文件 + 对话回执 |

**收集量必须可数**：§一 的行数 = 一句话结论里的「收集 N 条」；N 与有效/驳回之和必须闭合。

## 5. 证据等级（决定"敢不敢信"，不决定"要不要改"）

| 等级 | 判据 | triage 时怎么处理 |
| --- | --- | --- |
| **A 可复现** | 给出了 `命令 → exit 码` 或 `文件:行`，本轮**实际跑过/读过** | 可进 §三（自修）或 §四（决策卡） |
| **B 有出处但未复跑** | 有文件:行，但本轮没跑（如别人留下的历史条目） | 只能进 §四/§五，**不得**据此自修 |
| **C 自评/传闻** | 只有"应该/可能/我觉得"，无命令无行号 | 直接驳回（§二 写理由） |

## 6. triage 决策树（逐条走，必须落到 a~e 之一）

```
证据等级是 C？ ──────────────────────────▶ (d) rejected，写驳回理由
└─ 否
   ├─ 属于"能力/工具升级导致旧写法过时"？ ─────▶ (c) 决策卡：改判据/依赖，附外部证据
   ├─ 是"某技能写了但被绕过 / 判据不可判定"？ ──▶ (b) 收紧该技能判据（自修，≤1 文件）
   ├─ 同类问题第 2 次出现（复发 ≥ 2）？ ────────▶ (e) **升级成脚本门禁**（只出决策卡，脚本由人写）
   └─ 其余（新知识、新坑） ────────────────────▶ (a) 追加 `lessons` 条目（自修，只追加）
```

**(e) 是铁律**：文字兜不住的一律写成脚本（能跑、有退出码、能被 CI 调）。

**每条处置必须回答「拦截机制」**：下次同类问题靠什么被挡住？只能是三者之一——
① 判据行号（`<文件>:<行>`）；② 脚本退出码（`<命令> → exit <码>`）；③ **无**。
写「③ 无」的条目**必须**同时出现在 §四（决策卡）或 §五（观察），否则视为走过场。

**报告硬规则（违反任一条 = 废稿）**：

1. **§四 是报告的重点**：≤ 5 张决策卡，每张 **6 字段**（问题/我的建议/备选与代价/预期效果/**不做的后果**/复验命令，与 §8 表逐字一致）缺一无效；
   「建议」不得只写"建议优化"，必须写**改哪个文件的哪一处、判据是哪条命令**；
   「复验命令」必须能在 10 秒内给出 `仍在 / 已消失`（几天后照它执行，见 §15）。
2. **禁止流水账**：不贴整份 diff、不复述 INBOX 原文、不列已驳回合法的细节；§三 只贴 1~3 行**关键 diff**。
3. **数字必须闭合（三处对账）**：① `收集 = 有效 + 驳回`；② §一 的每条有效条目都要在 §二 标出
   **落点编号**（`S#` / `D#` / `O#`）——**一条可以多落点**（如"已修一半 + 残余提案"= `S2+D3`），但必须写明；
   ③ §三 / §四 / §五 的编号并集 == §二 的落点集。落不了地又驳回不掉的条目 ⇒ 处置失败，不许进报告。
   多落点时必须加一行「落点对照：`R1→D1｜R2→D2｜R3→S2+D3`」，让读者一对就能核。
4. **同一月第二次运行**：插在文件**顶部**（本目录 README 规定不覆盖旧记录），全文件仍 ≤ 150 行。
5. 缺上期报告时必须首行 `[FAIL] 上期报告缺失`，其余判据照常给全。

## 8. 决策卡格式（§四 的硬性格式，缺字段即无效）

| 字段 | 要求 | 反例（禁用） |
| --- | --- | --- |
| 问题 | 现象 + 可复现证据（命令+退出码 / 文件:行） | "验证流程不够严格" |
| 我的建议 | 改哪个文件哪一处 + 判据命令 | "建议加强门禁" |
| 备选与代价 | 至少 2 个选项 + 各自代价（时间/风险/行数） | 只给一个方案 |
| 预期效果 | 落地后哪条命令变红/变绿；拦截哪个现象 | "效果更好" |
| 不做的后果 | 复发风险 + 具体损失（如"3 个版本不做真机验证"） | "可能有风险" |
| 复验命令 | 一条命令 / `文件:行` 断言 + 期望输出；N 天后跑它就能判定问题是否还在 | "看看还在不在" |

用户只做**选择题**，不做填空题（`LESSONS.md` L8 同源）。

## 9. 提案格式（每条必填四项，缺一无效）

| 字段 | 要求 |
| --- | --- |
| 改动文件 | 精确到路径；一次只改一个技能 |
| 净行数变化 | `+N / -M`；**正值必须给理由**（不许只加不减） |
| 判据 | 能复制执行：`<命令> → exit <期望码>` 或 `<文件>:<行> 含 <内容>` |
| 回滚方式 | `git revert <sha>` / `git checkout -- <path>` / 备份目录路径 |

## 10. 事务流程（自修必须逐条走，缺一步即失败）

1. **基线**：改前跑一次两道门禁，记下错误数。
2. **备份**：`mkdir -p /tmp/skill-backups/<YYYYMMDD-HHMM>/` 并拷入原文件（保留相对路径）。
3. **修改**：逐行定位改，**禁止跨行正则批量替换**（`LESSONS.md` L47 会吃掉 frontmatter/文件头）；
   改完**立刻回读**该文件确认内容真的变了（L45：不要只检查"文件存在 + 字节数"）。
4. **复验**：再跑两道门禁。
5. **回滚**：错误数**增加** ⇒ 用备份还原，报告写 `[ROLLBACK]` + 原因。
6. **保留**：错误数不增加 ⇒ 报告写 `[AUTO-APPLIED]`，贴 `git diff <文件>`。
7. **不提交**：改动以未提交状态留在工作区（`git diff` 就是审阅入口），**提交权在用户**。

## 11. 门禁（退出码即判据）

```bash
jflove-server/venv-linux/bin/python scripts/check_retro.py    # 必须 0
jflove-server/venv-linux/bin/python scripts/check_skills.py   # 错误数不得高于基线
```

`check_retro.py` 必须为 0；`check_skills.py` 允许仓库既有问题存在，但**改后不得更红**。
不要为了让门禁变绿去改仓库。**报告结构由 `check_retro.py` 的 `REQUIRED_REPORT_SECTIONS` 兜底**
（2026-11-15 起：缺「一句话结论 / 一 / 二 / 三 / 四」任一层 → exit 1，流水账再也过不去）；
但"决策卡写得清不清楚"仍无脚本闸，所以**回执里必须把 §四 决策卡原样复述给用户**
（用户不一定会打开文件——这是剩下唯一的人肉门禁，不许省）。

## 12. 永不触碰（可信基，只能人改）

- `.agents/skills/skills-self-growth/**`（除 §2 的"用户当场授权"例外）
- `scripts/check_skills.py`、`scripts/check_retro.py`（裁判不得改）
- `AGENTS.md`、`.github/**`、任何 `jflove-*` 模块源码
- **任何 git 写操作**：`git add` / `commit` / `push` / `tag` / `merge` / `rebase` / `reset` / `stash` /
  `checkout --` / `restore`，以及改 `.git/**`。只允许只读的 `git status` / `git diff` / `git log`；
  **提交与推送必须由用户在对话中明确同意**（`AGENTS.md` §6.5 E）。

- 报告顶部含 `> 生成 …｜核实基线 …` 行，且每张决策卡含「复验命令」（§15：缺了 = 旧报告不可执行）
- 数字闭合：收集 = 有效 + 驳回；§二 每条标落点编号（一条可多落点 `S2+D3`），§三/§四/§五 编号并集 == §二 落点集
- 相对基线没有白名单外的新增/修改路径

## 14. 效果度量

- 采纳率应 **< 70%**（全采纳说明在走过场，驳回职责失守）。
- **决策卡的采纳率 ≠ 报告采纳率**：决策卡是给人选择的高价值项，采纳率高不是问题；被驳回的应是"证据 C 级 / 已落地"这类。
- 同一现象的复发次数应**逐期下降**；不降 ⇒ 该条的处置方式错了（多半是该升级成门禁）。
- `check_skills.py` 的行数上限（420）被顶到 ⇒ 先压缩，再谈新增。
- **回滚率**持续偏高（> 1/3）⇒ 说明 triage 判断不可靠，先退回"只提案"档位再查。
- **可读性自检（新）**：报告 §一 的行数、§四 的卡数必须能在一屏内看完；§四 超过 5 张卡 ⇒ 砍到最痛点，其余转 §五。
- **复验命中率（新）**：旧报告被拿来施工时，每张卡的「复验命令」都应能直接跑通并在 10 秒内给出
  `仍在 / 已消失`；某张卡做不到 ⇒ **是那张卡的写法错了，不是读的人错了**（§15）。

## 15. 时效协议（报告是快照，你的指令是"现在"）

报告写于「生成时刻」，人常常**隔几天**才读、才说"照它改"。这中间仓库可能已被改过 —— 包括用户自己改的。
**只看报告就施工 = 拿旧照片修房子**；2026-11-15 的真实反例：报告里两条"新建 probe.sh"，实际前一天就已落地，
照旧报告施工会重复建一遍。

- **写报告时**：顶部必须有 `> 生成 <时刻>｜核实基线 <时刻>` 行；**每张决策卡必须有「复验命令」**
  （一条命令或 `文件:行` 断言，10 秒内能判 `仍在 / 已消失`）。
- **收到"按报告 / 按复盘优化"的指令时（报告再新也一样）：先复验，再动手**，逐卡判三态：
  - `仍在` ⇒ 按卡施工；
  - `已消失` ⇒ 报告标 `[STALE] 已在 <时间/提交> 被修复（证据）`，**一处都不改**（重复施工 = 白改 + 冲撞）；
  - `部分变化` ⇒ 重新估行数/代价/方案（旧卡的 `+N 行` 已不可信）后再动手。
- **判定依据只能是本轮真跑的命令、真读的行**："应该还没改""上次看还在"一律不算（`LESSONS.md` L12/L43）。
- **防重复施工的硬判据**：动手前对卡里「我的建议」给出的目标文件跑 `git log -1 -- <文件>`；该文件在
  「核实基线」之后变过 ⇒ 必须逐行读当前内容再决定，**禁止按旧卡直接下单**。
- 全部 `已消失` ⇒ 报告写 `[NO-OP]`，改 0 个文件，并把卡标成已解决。
- 复验结论写进本次报告（在 §二 加一行：`复验：D1 仍在 / D2 已消失（证据）`）。
