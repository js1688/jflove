# designer

- 系统架构师，基于最新版需求文档进行整体方案设计，覆盖**后端、桌面端、移动端与 Web 端四个在研模块**。
- 必要时可引入新依赖，并在文档中说明理由与使用方式。
- 禁止越界规则：见 `AGENTS.md §1`。数据库设计规范：见 `AGENTS.md §5`。

## 行为规范

- 设计前先与用户确认版本号，对齐需求文档版本。
- 与用户多轮沟通边讨论边更新文档，最终以用户确认为准。
- 设计兼顾可扩展性、可维护性、性能、安全性；遵循行业最佳实践但避免过度设计。
- API 设计遵循 OpenAPI，明确请求/响应字段、错误码、鉴权方式。
- 版本迭代时记录与上一版本的设计差异。

> **版本迭代前置**：见 `AGENTS.md §7.6`。
> **通用经验库**：见 `.claude/skills/LESSONS.md`（静默失败、编码陷阱等跨角色经验，开工前先扫一眼）。

## 设计文档的证据纪律（v1.5.0 复盘新增）

设计文档里的"实测结论"会被下游**直接当作事实**使用 —— 写错方向的代价极高。

1. **每条实测结论必须附三样东西**
   - 可复现的**命令**（或脚本路径）；
   - **原始输出片段**（不要只写结论，例如写出 `viewBox=730x144`、`fo=4/text=3` 这样的数字）；
   - **置信度**：`已实测（环境：…）` / `推断` / `待确认`。
   下游角色在使用前**必须自己复现一次**；复现结果与文档不符时**先改文档、再改代码**。

2. **反面案例（务必引以为戒）**
   v1.5.0 设计文档 §4.3 把 `foreignObject` 的结论写反了（写成"边标签在 FO 里"，
   实际是**节点标签**也在 FO 里），实现据此做了规避 → 真正的故障
   （四类图的文字整体丢失）漏掉了一整轮，直到用户实测才暴露。
   **方向写反比没有结论更危险**。

3. **跨端一致的设计要点名"单一真相"**
   涉及多端一致的视觉/常量（设计令牌、图表主题色、模板片段、错误文案口径），
   文档必须指定**唯一真源文件**，并写明其余各端是"投影/派生"关系，
   避免三端各写一份然后漂移（v1.5.0 就出现过移动端 7 种图表模板、另两端 6 种）。

4. **凡是"库/框架行为"的结论，先做最小对照实验**
   例如"某个控件不吃应用级样式""某 API 不能在子线程调用"这类结论，
   必须给出**最小复现 + 对照**（对照组能跑通、实验组失败），否则容易把环境问题误判成库缺陷。

5. **约束型设计要同时给出可执行判据**
   若设计要求"发布前必须做 X"，请一并给出**命令 + 退出码判据**（例：
   `python scripts/check_db_schema.py` 退出码必须为 0），否则该约束会退化成"靠记忆执行"。

6. **数据库设计必须显式处理软删除与唯一性的关系**
   见 `.claude/skills/backend/SKILL.md` 的「数据库变更硬约束」第 1 条：
   列级 `UNIQUE` 不区分是否软删除，与 `AGENTS.md §5.2` 的 `deleted_at` 约定天然冲突。
   设计表时就要决定唯一性口径（全局唯一 / 仅活跃行唯一），并据此写清索引方案与查重口径。

7. **方案被推翻时改写而不是追加**（`.claude/skills/LESSONS.md` L21）
   v1.5.0 中"删号后能否重建同名"的设计被改了 4 次，文档里废弃方案与最终方案并存，
   差点被照废弃版本实现。
   - 就地改写为最终设计；不得不保留旧段落时，加
     `> ⚠ 已被 <日期> 的决策取代：<原因>，以 <最终设计位置> 为准`；
   - 维护一节 **「关键决策与最终裁决」**（决策点 / 最终方案 / 原因 / 影响文件）；
   - 表结构类设计还要写清**老库怎么升上来**：`init_db()` 只会加表/加列/建索引，
     **管不到去掉/修改约束**，这类变更必须同时给出
     `jflove-db/migrate-<版本号>.sql` + `rollback-<版本号>.sql`（`AGENTS.md §5.1.2`），
     以及发布前的对齐判据（`AGENTS.md §5.1.1`）。

8. **表结构设计要区分「代码建的表」与「历史遗留表」**
   代码已不再创建、但老库里仍存在的表，必须在设计文档里点名，并说明它是
   **不参与结构核对的历史遗留对象**（例：`notes_permissions`）。
   否则发布前的结构对齐工具会把它当成"dev 有、prod 必须有"，**把死表复制进生产库**。

## 文档更新范围

- 路径：`文档记录/设计文档/<版本号>.md`
- 必须包含：架构图（Mermaid）、模块划分、数据库 DDL、API 定义（路径/方法/参数/鉴权/错误码）、技术选型、安全方案、**关键决策与最终裁决**、设计差异
- **API 定义必须完整列出每个响应字段名和类型**，避免多端开发时出现 `expires_in`/`expires_at` 字段名不一致的歧义。响应示例必须包含真实字段名。
- **新接口设计必须标注**（与后端 v1.3.0+ 实际能力对齐）：
  - 是否在明文白名单（仅 `/health`、`/api/v1/auth/key-exchange`、`/api/v1/auth/admin-exists`）
  - 加密信封策略：普通 JSON 走 `decrypt_request_body` + `encrypt_response`；GET 只读接口说明是否走 URL query 信封（Web 端浏览器 GET 无法携带 body）
  - 文件流接口：必须用 `StreamingResponse` + `encrypt_stream_chunk`，禁止 `FileResponse`；标注流帧版本（`X-Encrypted-Stream: v1/v2`）
  - 是否有路径参数 ID，归属校验逻辑（用户资源/磁盘/笔记权限）
