# 通用经验库（Lessons）

> 本文件只放**跨角色复用的硬经验**：每条都来自真实故障或真实实测，不是风格建议。
> 各角色技能里只写"与本角色强相关"的条目，通用部分统一引用本文件。
>
> **怎么用**：
> - 开工前扫一眼与本任务场景相关的类别；
> - 修完 bug / 写完功能后，对照「四、交付前自查清单」；
> - **新增条目时**必须写清：现象 → 根因 → 正确做法 → 复现/验证方式。没有实测证据的不要写进来。

## 一、静默失败（最危险的一类：不报错但结果是错的）

这类问题最难查，因为**没有任何异常、日志正常、测试也过**。

### L1. 组件库会覆盖应用级样式
- **现象**：桌面端"UI 看着完全没改"，主操作按钮还是组件库默认的青绿色。
- **根因**：`qfluentwidgets` 的控件在构造时给自己打了 **widget 级样式表**（实测每个控件 7631 字符），优先级高于 `QApplication.setStyleSheet()` 的应用级 QSS。应用级 QSS 里写 `#PrimaryButton { ... }` 对 `PrimaryPushButton` **完全无效**。
- **正确做法**：走组件库自己的 API（`setThemeColor` 设置强调色），而不是试图用 QSS 覆盖；确需定制时用 `setCustomStyleSheet`。
- **验证**：**取像素**断言，不要只看代码。`widget.grab().toImage().pixelColor(...)` 对比期望色值。

### L2. `getBBox()` 在无布局容器里返回 0
- **现象**：甘特图在桌面端/移动端"无法预览"——SVG 被渲染成 `viewBox="0 0 0 144"`、`width="100%"`、`max-width:0px`，整张图不可见。而同一份源码在普通浏览器里 viewBox 宽是 730。
- **根因**：桌面端用的是**无窗口** `QWebEnginePage`，视口是 **0×0**（实测 `window.innerWidth == 0`）。mermaid 渲染时用 `getBBox()` 量图，量到 0 就把它写进了 SVG。只有部分图表类型受影响（甘特图中招、流程图侥幸正常），所以很容易漏掉。
- **正确做法**：**不要相信渲染引擎自己量的尺寸**。渲染完成后重新量一次（内容其实画对了，实测 `getBBox()` 能返回 1296×113），把正确尺寸写回 `viewBox` / `width` / `height`，并删掉内联 `max-width`。
- **验证**：断言产物 SVG 的 `viewBox` 宽高 **> 0**，并对每种图表类型都跑一遍。

### L3. 测到的配置不是生产用的配置
- **现象**：审计脚本报告"全部检查通过"，但真实应用是坏的。
- **根因**：审计脚本自己手写了一份简化配置（漏了顶层 `htmlLabels`），而应用用的是另一份。**审计通过 ≠ 应用正确**。
- **正确做法**：审计脚本必须**导入/复用应用自己的配置模块**（如 Web 端 `await import('/src/utils/mermaid/config.ts')`），而不是抄一份。
- **验证**：在审计输出里显式打印"是否用了应用配置"，例如 `usedAppConfig: true`。

### L4. 缓存键没覆盖"会影响结果"的输入
- **现象**：改了渲染模板，界面毫无变化；修完 bug 复验仍返回旧结果，白排查一轮。
- **根因**：缓存键只含「内容 + 主题 + 引擎版本」，不含**模板本身**。更隐蔽的是：用「文件大小 + mtime」做指纹**不可靠**（脚本改写、批量 checkout、打包解压都可能让内容变了而这两个值没变）。
- **正确做法**：把模板/资源的内容**哈希**并进缓存键；内容哈希才可靠。
- **验证**：改一次模板 → 断言缓存键变了、旧结果不再命中。

### L5. 框架的"隐形兜底"改变语义
- **现象**：错误提示要 30 秒后才出现；期间一直是骨架屏，用户以为页面卡死。
- **根因**：Riverpod 3 默认对失败的 Provider **自动重试**（最多 10 次、退避到 6.4s）。这期间 `AsyncValue` 是「loading + 已有 error」，`AsyncValue.when` 一直走 loading 分支。
- **正确做法**：显式关掉自动重试（`ProviderContainer(retry: (_, _) => null)`），失败立即呈现错误态，由用户点「重试」再请求。
- **验证**：断言失败后立刻是 error 分支、且不会自己重试。

### L6. 异常被"吞"在没人看的地方
- **现象**：Web 端添加重名用户没有任何提示，而安卓端有提示。
- **根因**：页面里的 handler 是**裸 `await`，没有 try/catch**。接口抛错后异常被吞掉，弹窗照关、界面毫无反应。
- **正确做法**：所有会发请求的 handler 必须 try/catch，并把 `e.message` 展示给用户；失败时**不要关闭弹窗**（保留已填内容便于改名重试）。
- **验证**：静态扫描全量源码找"handler 内的裸 await"（这类回归是"新页面又忘了"，只有扫全量才拦得住）。

## 二、平台与环境陷阱

### L7. Windows 控制台/子进程的编码是 GBK
- **现象**：脚本打印 `✓` / `→` 直接 `UnicodeEncodeError` 崩掉；子进程渲染中文图表时报 `'utf-8' codec can't encode character '\udcaf'`。
- **根因**：Windows 上子进程的 `sys.stdin.encoding` 跟随区域设置（实测 **gbk**）。父进程侧写 `encoding="utf-8"` **管不到子进程自己的解码方式**。纯 ASCII 内容正常、含中文必失败——这正是最好的线索。
- **正确做法**：
  - 父进程 spawn 子进程时给环境变量 `PYTHONIOENCODING=utf-8`；
  - 脚本自身 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`（无法重配时退化输出）；
  - **注入型模板**（HTML/JS 模板）保持**纯 ASCII**，中文说明放注释并确保不破坏语法。
- **验证**：故意用**含中文**的输入跑一遍；只测 ASCII 会漏掉。

### L8. 无头/离屏环境的真实边界
- **现象**：`QWebEngineView` 构造即崩（`STACK_BUFFER_OVERRUN`），但 `QWebEnginePage` 完全正常。
- **根因**：**不是** WebEngine 的问题——该会话没有桌面窗口站，`QWidget().show()` 同样崩。用离屏 Page 可以绕开。
- **正确做法**：无法开窗口的环境下，用 `QT_QPA_PLATFORM=offscreen` + 离屏 `Page`；判定"某个库坏了"之前，先用同环境的最小对照（如 `QWidget().show()`）排除环境因素。
- **验证**：先跑最小对照实验，再下结论。

### L9. 组件库不能在任意线程驱动
- **现象**：把离屏 `QWebEnginePage` 渲染放进 `QThread` 直接崩：`Check failed: checker.CalledOnValidBrowserThread(...)` / `Must be called on Chrome_UIThread`。
- **根因**：WebEngine 只能在其**创建线程**驱动。想"用后台线程避免卡界面"这条路**走不通**。
- **正确做法**：要真正不阻塞 GUI，只能用**子进程**（子进程自建 `QGuiApplication` + 自己的 WebEngine，与主进程完全隔离）。**一次进程批量渲染多张图**，摊薄进程启动开销；结果**落盘**回传，不要把大二进制塞进 stdout。
- **验证**：测量 GUI 线程被阻塞的时长（如 `set_markdown` 返回耗时），而不只是"有没有报错"。

## 三、流程与协作

### L10. 设计文档里的 PoC 结论可能是**方向反了**的
- **现象**：设计文档写着「边标签在 `<foreignObject>` 里」，实现按这个结论做了规避，结果真正的故障恰好是"节点标签也在 foreignObject 里"。
- **根因**：PoC 结论写反了方向，而实现方**信任了文档、没有自己复核**。文档错误会被下游无限放大。
- **正确做法**：
  - 设计文档里的每一条"实测结论"必须附**可复现的命令 + 原始输出**，并标注**置信度**；
  - 实现方在使用该结论前**必须自己复现一次**；复现结果与文档不符时，**先改文档再改代码**。
- **验证**：把关键结论做成断言/脚本，让文档结论与代码行为**由同一份证据**支撑。

### L11. 测试不要把"当前的错误行为"锁成期望值
- **现象**：把「清洗会删掉 `<foreignObject>`」「注释里写了占位符导致 bundle 内联两次」写成了断言——等于把 bug 固化。修好 bug 后这些测试反而失败。
- **正确做法**：写测试时先问"**这是期望行为还是现状行为**"。现状是坏的，就写成"已知缺陷"并**显式标注待修**；修完后那个断言必须**反转为期望行为**，而不是删掉。
- **验证**：修复提交里要能看到对应的断言反转。

### L12. 约束要绑定到可执行的检查，否则等于没写
- **现象**：技能里早就写了「生产库表结构同步（升级 DDL + 回滚脚本）」，但没有任何工具或校验；v1.5.0 差点漏掉 prod 库的约束变更。
- **根因**：**只写进文档的约束靠记忆执行**，迟早漏。
- **正确做法**：每条硬约束都要绑定 `命令 + 退出码判据 + 阻塞条件`（例：`python scripts/check_db_schema.py` 退出码必须为 0）。
- **验证**：把该命令故意跑出"失败"一次，确认流程真的会**拦住**你。

### L13. 代码/测试脚手架与生产代码的命名要一致
- **现象**：诊断脚本一直报 `AttributeError: 'MainWindow' object has no attribute 'filePage'`，白折腾一轮。
- **根因**：窗口里的属性是 `self.file_page`（snake_case），而脚本按组件库风格的 `win.filePage`（camelCase）取。
- **正确做法**：写脚手架前先 `grep` 真实属性名；不要把"另一处的命名习惯"套过来。
- **验证**：脚手架第一次运行就要能产出数据，拿不到数据先怀疑命名/路径，而不是怀疑逻辑。

### L14. 改数据库结构前先问：`init_db()` 兜得住吗？
- **事实**：`init_db()` 的运行时迁移只会**加表 / 加列 / 建索引**；**管不到"需要去掉约束"**这类既有结构变更（如去掉列级 `UNIQUE`）。SQLite 也不支持 `DROP CONSTRAINT`，只能重建表。
- **正确做法**：凡涉及"去掉/修改既有约束"，必须写显式迁移脚本 + 回滚脚本，并按 `AGENTS.md §5.1.1` 在发布前核对对齐。
- **不要用的做法**：`PRAGMA writable_schema` 直接改建表语句 —— 实测会留下悬空自动索引，之后任何访问都报 `malformed database schema ... orphan index`，而且**当时不抛异常**、看着像成功了。

### L15. "以 X 为准"里的 X 本身可能是错的（基准的基准）
- **现象**：`dev 库 == prod 库` 核对通过，报"结构一致 ✓"，但**两边都不是当前代码的结构** —— 脚本用 dev 库当基准，而 dev 库是个没跑过迁移的旧文件。同类问题还有反向的：dev 库是长期滚出来的，**含有代码早就不建的死表**，"以 dev 为准"会把死表**复制进生产库**。
- **根因**：只比"两个库是否一致"，没比"库是否等于**当前代码**期望的结构"。基准本身没有受检。
- **正确做法**：基准必须先自证 —— 让**代码的建表 DDL** 在一个内存库里执行一遍，得到"代码期望的结构"，再与 dev 比对。三道关：`代码 ↔ dev ↔ prod`，而不是只看最后一段。
- **验证**：故意拿一个旧结构的 dev 库喂给检查脚本，确认它**拦住**（返回 1）而不是放行。

### L16. 工具会"忠实执行一个错误口径"，破坏力比没有工具更大
- **现象**：对齐工具承诺"不删生产库多出来的列，只报告"，实测却把 prod 自有的一列**连同数据删掉了**，还打印"结构一致 ✓"。
- **根因**：判据用的是**建表语句整串文本比较**。prod 多一列 ⇒ 整串不等 ⇒ 判定 `table_ddl_mismatch` ⇒ 执行"重建表"，而重建只拷贝交集列。于是"报告级"的差异被"阻塞级"的动作顺手清掉了，两条规则互相矛盾。
- **正确做法**：结构比较必须**结构化**（按列名对齐比列定义 + 比表级约束），并且**只判"基准要求而目标不满足"的方向**；目标方多出来的东西永远只报告、不参与触发破坏性动作。
- **验证**：造一个"prod 多一列"的库跑对齐，断言**该列与其数据仍在**。

### L17. 校验脚本必须做**反向验证**（guard 的 guard）
- **现象**：新写的核对脚本第一次跑就报"一致 ✓"，很容易就此收工 —— 但它可能只是**根本没比对上**。
- **正确做法**：任何"检查/校验/门禁"类脚本，交付前都要**喂坏数据**证明它会翻脸，且要覆盖每一类判据：
  少一列 / 多一列 / 缺表 / 缺索引 / 列定义变化（如去掉 `UNIQUE`）→ 必须返回失败；
  纯格式差异（表头 `IF NOT EXISTS`、引号、列顺序、逗号前空白）→ **必须**返回通过。
  两条都要测：只会翻脸的会误报，只会放行的是装饰品。
- **验证**：把"该通过"和"该失败"两类用例写在同一个脚本里，一起跑。

### L18. 静默跳过 = 假通过
- **现象**：检查脚本内部把某些对象（SQLite 内部表、历史遗留死表）排除在比对之外，输出却只写着"结构一致 ✓"。使用者以为"一致"覆盖了全部对象。
- **正确做法**：凡是**被排除/被跳过/降级为警告**的东西，必须在输出里**显式列出来并说明原因**。报告要回答"你没检查什么"，而不只是"你检查了什么"。
- **验证**：输出里必须能看到被忽略对象的清单。

### L19. 跑在临时副本上的验证，基准要在"动作前一刻"取
- **现象**：验证"对齐不丢数据"的脚本一直失败，查下来是**脚本自己**在制造差异时先把数据删了，却拿更早的指纹去比 —— 把自己造的破坏算到了工具头上。
- **根因**：基准取样点错了（在"制造差异"之前）。
- **正确做法**：
  - 基准必须在**被测动作执行前一刻**取；
  - 合法的"加列"会让整行指纹变化，所以要比的是**按原列清单算出的指纹**（先断言原列一个都没少，再比内容）；
  - 别把合法变更当回归。
- **验证**：故意让被测动作"多做一件合法的事"（加列），确认断言仍通过。

### L20. 配置常量不读环境变量时，别用环境变量去隔离测试
- **现象**：验证脚本设了 `JLOVE_DB_PATH=<临时库>` 就以为安全，而 `settings.py` 里 `DB_PATH` 是**硬编码常量**、完全不读该变量 —— 结果脚本**静默地操作了真实的 dev 库**，而"造一个干净库"的断言全错。
- **正确做法**：改路径不要靠猜环境变量。**先 grep 真实取值方式**，然后按方式注入：
  导入顺序是 `from src.config.settings import DB_PATH` ⇒ 要改的是 `src.models.database` 模块命名空间里的 `DB_PATH`，改完 **`finally` 复原**。
- **验证**：断言真实库的 `mtime`/行数在脚本跑完后**没有被改动**。

### L21. 同一个决策被反复推翻时，文档必须留"最终裁决"痕迹
- **现象**：v1.5.0 里"删号后能否重建同名"这一处，方案被来回改了 **4 次**（先改成物理删除 → 再改成允许重复/去唯一索引 → 再改回软删除 → 最终定为"软删除 + 去列级 `UNIQUE` + 活跃行部分唯一索引"）。
  中途写下的需求/设计/开发记录里，**被推翻的方案与最终方案混在一起**，后来读文档的人（包括下一个 AI 会话）极可能按废弃方案实现。
- **根因**：文档是**追加式**的，没人负责"改口"。上一轮结论在物理上仍然存在，读的人无法判断哪条有效。
- **正确做法**：
  - 一个决策被推翻时，**不要只追加新段落** —— 要么就地改写为最终结论，要么给旧段落显式加
    `> ⚠ 已被 <日期/版本> 的决策取代：<一句话原因>，以 <指向最终结论> 为准`；
  - 需求文档出**验收标准（AC）**、设计文档出**接口/表结构**、开发记录出**实现要点**时，
    必须写明采用的是哪一版裁决；
  - 交付前搜一遍被废弃方案的关键词（如"物理删除"、"去掉唯一索引"），
    确认它们只出现在"已废弃"标注里。
- **验证**：让不知道背景的人只读文档，能说出最终方案与原因；做不到就是文档有问题。

### L22. "本地打包给用户试用" ≠ "发布"
- **现象**：用户要的是"打包出来我先体验一下"，流程却顺手写出了发布记录 / PMO 记录 / 打了 tag。
- **根因**：流程里只有"完整发布"这一个动作，没有"只出产物"这一档。
- **正确做法**：把"打包"与"发布"拆成两个动作，并在交付时**明确说清这次做的是哪一个**：
  - **仅本地打包**：只跑构建、给出产物**路径 + 大小 + 校验值**、说明怎么试用；
    **不产出** PMO 记录 / 版本发布记录，**不动 git**（不提交、不打 tag、不建 Release），
    版本号也不封板；
  - **正式发布**：走 `devops` 技能的发布步骤全流程。
  - 用户说"我先验证一下，没问题再发布"时，默认选前者，并把"发布相关动作一件都没做"写进回复里。
- **验证**：回复里能一眼看出这次是"仅打包"还是"已发布"。

### L23. 全局 `!important` 的动效冻结会从**外部**改变第三方引擎的行为
- **现象**：同一份笔记，在部分机器上类图外框只按标题高度画、成员文字跑到框外，
  ER / 流程图 / 状态图的文字被裁掉、导出的图片也不全。换台机器或换个浏览器又正常。
- **根因**：`index.css` 里为无障碍写的
  `@media (prefers-reduced-motion: reduce) { * { animation-duration:.01ms!important; transition-duration:.01ms!important } }`。
  实测**逐条对照**：
  - 两条都留 → 引擎几何错乱；
  - **只留 `transition-duration` → 照样错乱**（就是它）；
  - 只留 `animation-duration` 或整条去掉 → 一切正常。
  即"把过渡时长压到 ~0"会让 mermaid 在**几何尚未落定**时就去测量，
  进而写出错误的 `viewBox` 与节点尺寸。
- **正确做法**：
  - 全局冻结只作用于**我们自己的 HTML UI**，**SVG 子树必须豁免**
    （本次用 `*:not(svg):not(svg *)`）；
  - 更一般地：**不要用 `*` + `!important` 去覆盖第三方渲染库依赖的属性**
    （时长、`transform`、`will-change`、`contain` 都属高危）。
- **验证**：在 `prefers-reduced-motion` 的**两种取值下各测一遍**，比较 `viewBox` 与几何是否一致
  。两种取值结果不一致 ⇒ 就是这类问题。

### L24. 测试环境的默认值会把结论整个翻转
- **现象**：连续几轮把"类图排版错乱"判成 **mermaid 引擎缺陷**（还写了"配置无解、只能换引擎"的
  结论与三条替代路线），实际却是**我们自己 CSS 的一条规则**造成的。
- **根因**：**无头浏览器默认就报告 `prefers-reduced-motion: reduce`**，于是所有实测都在
  "减动效偏好生效"的环境里做的；而那正是唯一会触发该 CSS 的取值。
  同类陷阱还有：
  - 离屏容器里 `getCTM()` 会把元素在页面里的位置也算进去（`left:-99999px` ⇒ 坐标偏 30 万），
    用 `inverse(getCTM)` 换算必然错；
  - 页面级缓存/内存缓存会让"第二次测量"直接复用第一次的结果    一开始就被它骗过）。
- **正确做法**：
  - 凡结论涉及"媒体查询 / 系统偏好 / 视口 / DPR / 字体"，**必须把该维度显式枚举后各测一遍**，
    而不是吃环境默认值；CDP 里用 `Emulation.setEmulatedMedia` 显式指定位。
  - 同一页面里对比多种设置时，**每次都用全新页面**（或显式清缓存），否则拿到的是缓存。
  - 下"这是引擎缺陷 / 无法修复"这种重结论前，先问一句：**"有没有环境变量还没被枚举？"**
- **验证**：把可疑维度都摆成矩阵跑一遍，结论要在每个格子里都成立。

### L25. "源文件里的常量是对的" ≠ "运行时写进去的内容是对的"
- **现象**：用户反馈「点『插入图表』插入的 ER 图必报语法错误」。
  我从源文件里抽出模板常量、用真实引擎渲染 —— **全部正常**，于是判定"模板没问题"，
  把方向转到了别处。再排一轮才发现：**模板常量确实没问题，坏在插入逻辑里**。
- **根因**：`insertMarkdown` 把插入文本里**第一个 `|`** 当光标占位符并无条件吃掉
  （`insert.replace('|', selected)`），而 mermaid 的 ER 关系语法恰好是 `||--o{`。
  用户没选中任何文字时 `selected` 是空串 ⇒ 第一根竖线被删 ⇒ `用户 |--o{ 会话` ⇒ 解析报错。
  7 个模板里**只有 ER 图**的正文含 `|`，所以只它中招。
- **正确做法**：
  - 验证"某功能产出什么"时，**必须走用户真实路径**（点按钮 → 读结果 → 看下游反应），
    不能只把源文件里的常量拿去测。常量正确与运行时正确是两件事。
  - **占位符/转义类约定要"默认不生效"**：默认原样插入，只有显式声明的调用方
    （工具栏按钮）才解析占位符。**把特殊含义默认打开的 API 迟早吃到真实内容。**
  - 占位符字符要挑**不可能出现在正文里**的；`|` 这种在 Markdown / mermaid / 表格里
    到处都是的字符绝对不能当占位符。
- **验证**：新增的端到端用例要做**负向对照** —— 把修复前的行为注入回去，
  确认用例会失败，且失败信息与用户报的现象一致
  （本次负向对照复现出的错误卡文案与用户截图逐字相同）。

### L30. "跑门禁全绿"不能代替"让用户看见效果"
- **现象**：v1.5.0 桌面端改版连做三轮，每轮都"验收通过"——
  `flake8` exit 0、`pytest` **604 passed / 1 skipped**、7 个探针 **7/7 OK**、
  并排对照 light/dark 各 **73/73**、令牌锁测试全绿、新增单测 68 条。
  而用户验收后的原话是「**跟没改一样**」，并追问"桌面端是不是根本做不到好看？做不到就换框架"。
- **根因**：**验证设施的增长被当成了交付**。这段时间绝大部分改动落在探针/守卫/令牌/审计脚本上，
  用户侧**看不到任何变化**；而"数字全绿"恰好让每一轮都显得可以收工，
  于是**方向错了也没人发现**（真正的结论是"用 Qt Widgets 复刻 CSS 这条路天花板低"，
  不是在探针里再加几条断言能解决的事）。
- **正确做法**：
  - 一个批次结束时，**交付物的第一屏必须是"看得见的东西"**（截图 / 并排图 / 真机操作结果），
    **再**给数字；数字用来**支撑**效果，不能**代替**效果；
  - 节奏固定为"一次一批 → 只跑**相关**探针（≤ 2 分钟）→ 立刻出亮/暗并排图"，
    **全量门禁（全部探针 + flake8 + pytest）只在阶段末跑一次**；
  - 每批附一张人力可读的**功能清单勾选表**（哪些能力还在、哪些还没迁移），
    避免"数字漂亮但功能悄悄少了"。
- **验证**：问自己「**用户能不能从这轮回复里看出变化**」——看不出就不算交付，
  哪怕门禁全绿。这条优先于任何探针。

## 四、桌面端自绘与验证（v1.5.0 桌面端改版复盘）

### L26. 组件库**自绘**的控件，连 `setCustomStyleSheet` 都救不了 —— 只能换控件类
- **现象**：用户说「设计稿挺好看，但桌面端做不出这个效果」。上一轮做了"UI 美化"（改应用级 QSS +
  几个组件微调），改完**看上去毫无变化**。
- **根因**：分两层，L1 只覆盖了第一层。
  1. 组件库控件自带 **widget 级**样式表 ⇒ 应用级 QSS 无效（L1）；
  2. 更深一层：侧栏条目 `NavigationPushButton` 是**完全自绘**的 ——
     `navigation_widget.py` 里 `paintEvent` 直接 `QPainter` 画背景/指示条/文字，
     底色是 `QColor(c,c,c,6~10)` 这类**硬编码半透明叠加**。
     **没有任何样式表入口能碰到它**，`setCustomStyleSheet` 也无效。
- **正确做法**：
  - 先**判断目标控件是"QSS 驱动"还是"自绘"**（看它有没有覆写 `paintEvent`）；
  - 自绘控件 → 找组件库的**自定义控件扩展点**（`NavigationInterface.addWidget(routeKey, widget)`
    接受自定义 `NavigationWidget` 子类），自己画；
  - 不要用 monkeypatch，也不要为了一个控件推翻整个窗口壳。
- **验证**：**A/B 取像素反证** —— 同一个窗口、同一主题、同一份应用级 QSS 下同时放
  「组件库控件」和「自绘控件」，取像素对比：本次实测组件库条目选中底色 `#f0f4f9`
  而设计稿要求 `#eef2ff`，自绘件精确命中 `#eef2ff`。
  **这个对照是"为什么改了没效果"最有力的证据**，比任何代码解读都直接。

### L27. 离屏平台**没有字体**：截图里所有中文都是豆腐块
- **现象**：视觉验收截图里中文全变成 `□□□□`，一度怀疑是自己组件的字体栈写错。
- **根因**：本机（Windows Server 2022 + PySide6 6.11）`QT_QPA_PLATFORM=offscreen` 下
  `QFontDatabase.families()` 返回 **0 个字体族**、`QFontMetrics.inFont('中') == False`。
  真实平台下是 169 个族、`inFont('中') == True`。
- **正确做法**：**性能采样可以用 offscreen，视觉验收必须用真实平台。**
  跑截图脚本前 `$env:QT_QPA_PLATFORM="windows"`（脚本里用 `setdefault` 的话，
  外部设成具体值即可覆盖）。
- **验证**：探针里**自检并打印** `platformName` / 字体族数量 / `inFont('中')`，
  让"这张图是不是可信的"这件事有据可查（本次探针第一行就打了这三项）。
- **推论**：字体栈里排前面的字体**本机可能根本没装**（本次 `Inter`、
  `Segoe UI Variable Text` 都没有，实际落到 `Segoe UI` → `Microsoft YaHei UI`）
  —— 所以 `setFamilies(整条栈)` 是必需的，只设第一个名字会静默丢掉落后的中文回退。

### L28. 控件"移出布局"≠"不再显示"；`deleteLater()` 在没有 `app.exec()` 时不派发
- **现象**（一个会话内踩到两次）：
  1. 「先建默认导航条目、再删掉换成自绘条目」⇒ 侧栏里每个条目**出现两次**（10 条 → 20 条）；
  2. 面包屑重建 ⇒ 旧段**累积**，`["a","b","c"]` 之后切到 `["x","y"]` 仍能看到 a/b/c。
- **根因**：
  - `QLayout.takeAt()` 只把控件移出布局，**控件本身仍留在父级上并按原几何继续显示**；
  - 组件库的 `removeWidget()` 虽然调了 `deleteLater()`，但**延迟删除只在 `app.exec()`
    的事件循环里派发**；截图/验证脚本用 `processEvents()` 循环，旧控件永远不消失。
- **正确做法**：清理控件一律 **`setParent(None)` 再 `deleteLater()`**；
  更根本的是 —— **不要让界面正确性依赖"延迟删除的时机"这种微妙行为**
  （导航那条最后改成"显式注册页面 + 自己接框架那 3 行接线"，从源头不产生重复控件）。
- **验证**：写成**单测**而不是靠肉眼。本次"面包屑累积"就是被单测抓到的
  （`test_面包屑重建不会累积旧段`），肉眼在缩略图上完全看不出来。

### L29. 截图的像素是**设备像素**，控件坐标是**逻辑坐标**（不换算会静默采错，甚至"假通过"）
- **现象**：kit 审计脚本一次报 **17 项失败**，且采样值自相矛盾 —— 渐变主按钮的左端采到
  背景色 `#f0f4f9`、success 徽标采到深蓝 `#1d183c`、侧栏选中/未选的颜色被**对调**。
  而同一张截图肉眼可见：所有组件都渲染正确。
- **根因**：**`QWidget.grab()` 返回的 `QImage` 是设备像素图，而 `mapTo()` 返回的是逻辑坐标。**
  本机实测 `devicePixelRatioF() == 1.25`：请求 900×500 的窗口，抓到的图是 **1125×625**。
  于是每个采样点都偏 25%，取回来的是邻居控件/底色的颜色。
- **为什么这条特别危险**：偏差不必然导致断言失败 ——
  它**可能采到另一个控件的同类颜色而偶然通过**，也就是**假通过**。
  假通过把"没验证"伪装成"验证过了"，比直接失败危险得多。
- **正确做法**：
  ```python
  origin = widget.mapTo(win, QPoint(0, 0))          # 逻辑坐标
  dpr = win.devicePixelRatioF()
  image = win.grab().toImage()                      # 设备像素图
  color = image.pixelColor(round((origin.x() + x) * dpr),
                           round((origin.y() + y) * dpr))
  ```
- **验证**：把"换算本身对不对"也变成断言 ——
  断言 `image.width() == round(win.width() * dpr)`，并在探针开头**打印**
  `devicePixelRatioF()` 与实际图像尺寸，让"这张图可不可信"有据可查。
- **配套的采样点纪律**（同一次里三处都导致过误判）：
  - 避开**文字笔画**（会把文字色判成底色）；
  - 避开**图标笔画**（App 徽标的白色图标抗锯齿实测得到 `#eae7fd`，
    一度被误判成"渐变方向反了"）；
  - 避开**圆角外的抗锯齿带**（色块 30×30、圆角 8px，采样 (2,2) 取到的是父级底色
    与色块的混合色）。取「**形状内、笔画外**」的中腰位置最稳。
- **更普遍的推论**：**像素断言的坐标换算必须被验证，否则你根本不知道取到的是谁的像素。**
  宁可在探针里多断言一条"图像尺寸 == 窗口尺寸 × DPR"，也不要相信"看起来对"。

### L31. 用 Qt Widgets 复刻 CSS 有**天花板**，先看官方对比表再决定要不要走这条路
- **现象**：三轮"UI 美化 + 逐页结构对齐 + 行密度对齐"之后，用户看到的仍是"跟没改一样"：
  侧栏/页头/卡片/按钮的**盒模型**都能量到一致（节距、圆角、字号、色值全对），
  但整体的**圆角 + 阴影 + 模糊 + 层次 + 过渡**就是不像 Web。
- **根因（Qt 官方口径）**：Qt 把 UI 分成 **Qt Widgets**（传统桌面）与 **Qt Quick/QML**，
  官方对比表写明 Widgets 的 **动画 = Limited**、**图形效果 = Limited（只有 CPU 基础效果，
  没有 shader 模糊/发光/阴影）**、**软件渲染**（<https://doc.qt.io/qt-6/topics-ui.html>）。
  而 Web 的观感来自 CSS 的圆角/阴影/模糊/flex-grid + GPU 合成 + 一套统一令牌。
  ⇒ 在 Widgets 上"复刻"CSS，只能一格一格自绘对齐，**上限约 90%，成本持续堆在像素上**。
- **正确做法**：
  - 决定"要不要用 Widgets 复刻 Web 观感"之前，**先读官方对比表**（上面那条链接），
    并明确写出"我们要的那几种效果在不在 Widgets 的能力表里"；
  - 如果目标是**CSS 级观感**（阴影/模糊/过渡/Token 化主题），就用**嵌入式 Web 视图承载界面**
    （`QWebEngineView` + 自有前端产物 + `QWebChannel` bridge），
    **把能力留在原生层**（见 L32：媒体必须原生）；
  - **自绘件的 A/B 取像素只能证明"我改的这一层生效了"**（见 L26），
    它证明不了"整体像 Web" —— 别把局部证据当成全局结论。
- **验证**：换轨后判据从"逐像素对齐 Web"改成"**同源设计令牌 + 令牌一致性校验脚本**"；
  观感结论一律以"**亮/暗并排截图**"为准（L30）。
- **依据与留档**：`文档记录/桌面端开发记录/v1.5.0.md` §16.1 / §16.5、
  `plans/desktop-hybrid-shell-v1.5.0.md` §2.1。

### L32. QtWebEngine 预编译包**没有专有编解码** —— 媒体播放必须留在原生层
- **现象**：把界面搬进 `QWebEngineView` 后，`<video>` 播 H.264/MP4 直接失败、MKV 更不行；
  而同一个文件在本机播放器里正常。
- **实测（本机 QtWebEngine 6.11 / 包内 Chromium 140，`canPlayType` + `MediaSource.isTypeSupported`）**：

  | 能力 | QtWebEngine（我们包里的） | 原生 `QMediaPlayer`（Qt Multimedia 6.11） |
  | --- | --- | --- |
  | H.264 / MP4 | ❌ | ✅ |
  | H.265 / HEVC | ❌ | ✅ |
  | AAC 音频 | ❌ | ✅ |
  | MKV / AVI / MOV / WMV | ❌ 全不支持 | ✅（Matroska/AVI/QuickTime/WMV/MPEG4/Ogg/FLAC/MP3/AAC/WAV/WMA） |
  | AV1 / VP8 / VP9 / WebM / MP3 / FLAC / Opus | ✅ | （用得少） |
  | `WebCodecs.VideoDecoder` | ❌ 未暴露 | — |
  | 挂系统/本地解码器 | ❌ **不能**（只用自己的媒体栈，不读 DirectShow/Media Foundation） | ✅ 就是本地解码器（Qt 6.5+ 默认 FFmpeg 后端） |

- **根因（官方）**：MP4/H.264/MP3 属**专有编解码**，**只在编译 Qt 时**加
  `-webengine-proprietary-codecs` 才有，且**分发需自行取得授权**；
  PySide6 预编译包**没有**这个开关 ⇒ **不是配置问题，改不了**
  （<https://doc.qt.io/qt-6.8/qtwebengine-features.html#audio-and-video-codecs>）。
- **正确做法**：
  - **媒体播放留在原生层**（`QMediaPlayer + QVideoWidget + StreamProxy`），
    Web 页面只当"遥控器"（点播放 → bridge → 打开原生窗）；
  - **不要为了"统一成 Web"而接管播放**：浏览器媒体栈严格，损坏/截断流常直接失败，
    没有原生那套"忽略错误继续播"的档位 ⇒ 接管即功能退化；
  - 依赖 Web 视图的功能清单要**逐条按上表核对**（还有哪些能力它天生没有）。
- **验证**：编解码能力必须在**实际发货的那个 QtWebEngine**里测
  （`HTMLVideoElement.canPlayType` / `MediaSource.isTypeSupported`），
  **不能拿系统 Chrome / Edge 的结论代替**（系统浏览器带专有编解码）。
- **依据**：`文档记录/桌面端开发记录/v1.5.0.md` §16.2（探针脚本结论已落盘，**不要重新测**）。

### L33. Qt 几何 API 的**闭区间/半开区间**口径：看着对、量着错
- **现象**：探针断言"选中行胶囊内部一个底色像素都没有"，**8/8 个页面全部失败**，
  而截图里胶囊明明铺满整行；同一份代码换个窗口落点重跑又是绿的（随机假失败）。
- **根因（两层，都是"区间口径"）**：
  1. 扫描区间写成了 `range(ROW_MARGIN_X, viewportW - ROW_MARGIN_X + 1)` —— **上界多含一列**，
     而委托画的 `QRectF` 是**半开区间** `[a, b)`。实测（dpr=2.0、viewportW=1111、窗口 x 偏移 49）：
     `x=1104 → #c7d2fe`（选中描边）、`x=1105 → #f6f7fb`（`bg_canvas`，**胶囊右边界之外的第一个像素**）
     ⇒ 被判成"胶囊内部有底色"。
  2. Qt 的整数几何 `QRect` 用**闭区间**（`right() == left()+width()-1`、`center()` 由 `left()+right()` 取整得来），
     而浮点几何 `QRectF` / `QPainterPath` / 委托绘制用**半开**（`right() == left()+width()`）。
     两者混用时**必然差 1 像素**，而且**是否暴露还取决于窗口在屏幕上的落点**
     （`round((origin + x) * dpr)` 的进位）—— 这正是"看着对、量着错"的典型。
- **正确做法**：
  - 采样 / 遍历区间一律写成**半开** `[a, b)`，并且**跨度用绘制方自己的几何规则算**，
    不要"自己数偏移"；边界那一像素要有**明确期望**（本次：外右 `x=a+b` 必须底色、内右 `x=a+b-1` 必须非底色）；
  - 不要拿**单元格**矩形推**整行**跨度（`visualRect(index(row,0))` 实测只有 70px 宽，
    拿它断言"整行"会得到"右缩 1047px"的**假失败**）；
  - 同理，量"中心点"时先确认 API 是闭还是半开（`QRect.center()` 对偶数宽度不落在几何中点）。
- **验证**：把修复做成**更严不是更松** —— 本次除改半开区间外，另加一条像素断言
  "胶囊两端必须顶到内缩线"（逐格绘制会让两条同时失败）。
  另：**"换个窗口位置就变红变绿"本身就是区间口径错的信号**，别当成偶发。
- **依据**： / check_row_pill_span`（含 2026-09-16 修正说明）。

### L34. 抄另一个端的客户端代码前，必须对着**服务端契约**逐项核对

跨端同源时很自然会"照抄另一端的 service"，但**客户端之间的错误会互相传染**。
本会话（v1.5.0 桌面端）照抄 Web 端后，一次就带进来两处**服务端根本不认**的契约：

- `/files/mkdir` 只读 `path`（语义 = **要创建的目录的完整相对路径**），Web 端却发
  `{path: 当前目录, dir_name: 名字}` → 服务端把**当前目录**又建了一遍：静默 200、新目录从未出现。
- 删除接口服务端是 `DELETE /api/v1/files`（`@router.delete("")`），Web 端请求
  `/api/v1/files/delete` → **404**，前端当成普通响应吞掉 → "请求发了、文件纹丝不动"。

**规则**：抄之前先看**服务端路由与字段名**（各端服务层互相印证：移动端与桌面端服务层当时都是对的），
差一处就是一处静默故障。**"接口 200 但没效果"永远先怀疑契约，而不是前端状态。**

### L35. 测试 harness 必须与**真实入口**逐项对齐，否则假通过/假失败

自动化自建 shell/app 时，很容易漏掉真实入口 `main.py` 做的事。本会话反复踩：

- 漏 `publish_event` 注入 → 拖放事件**根本没发出去**，而断言却"通过"了（样本文件恰好在被服务目录内）
- 漏 `sync_bridge.setup()` / `transfer_bridge.setup()` → 桥方法报"未初始化"，测试里像产品坏了
- 漏 `set_main_window()` → 原生对话框没有父窗口

**规则**：测试的启动路径要与 `main.py` **逐行对照**；新增一个 `setup` 就在测试里同步加一份。
"测试里像坏了、产品里未必"几乎都是这一条。

### L36. 等**原生对象**必须泵 GUI 事件循环（`sleep` 会把它饿死）

`QMediaPlayer` 的解复用/缓冲、`QThread` 的信号投递，都靠 **GUI 线程的事件循环**推进。
用 `time.sleep()` 轮询时事件循环停摆 → 实测：

- 媒体加载从 **<1s 拖到 3 分钟**，最后以 `Demuxing failed` 收场
- 传输任务永远停在 `running`（工作线程的完成信号投递不出去）

**规则**：等待原生对象一律用"**边等边 `app.processEvents()`**"的版本（本仓库：
`poc/login-shell/test_headless.py::_wait_python_pumping`）。

### L37. PyInstaller 6.x 的 onedir：`--add-data` 落在 **`_internal/`** 下

`--add-data "ui/dist;webui"` 之后，产物在 `build/dist/JFlove/_internal/webui/`，
**不是** `build/dist/JFlove/webui/`。运行期解析要用 `sys._MEIPASS`（onedir 下即 `_internal`）。
**校验方法**：打完包直接查 `_internal/webui/index.html` 是否存在 —— 缺了就是白屏。

### L38. "假通过"的两个典型形态：样本在服务目录内 / 断言读的是缓存

- **样本文件放在被服务目录内**：断言"文件已上传到远端"会天然成立（它本来就在列表里）。
  拖放上传测试就这样假通过过一次 → 源文件必须放在**被服务目录之外**。
- **读的时机早于渲染**：面板/列表还没画完就断言样式或状态 → `None` 或恒假。
  典型表现是**同一断言时而通过时而失败**（本会话：设置页下拉的 3 条断言）。
  修法是"等具体目标状态出现"，不是加长 `sleep`。

### L39. PySide6 6.11 的两个坑：托盘菜单所有权、`addMenu` 子菜单包装失效

- `QSystemTrayIcon.setContextMenu()` **不接管 menu 所有权** → 顶层 `QMenu` 必须由 Python 持有引用
  （否则回收后菜单直接失效）。
- `menu.addMenu("主题")` 返回的子菜单**一旦加入 action，其 Python 包装对象即失效**
  （`Internal C++ object (QMenu) already deleted`）；`addMenu(str)` / `addMenu(QMenu)` /
  `QAction.setMenu` / 是否持引用，四种写法全复现，**空子菜单正常**。
  → 托盘菜单**不用二级子菜单**，平铺即可。

### L40. 原生窗口盖在 Web 内容之上：隐藏后 **Chromium 不会重绘**

媒体浮层是**独立顶层窗口**，它遮挡的区域在浮层隐藏后 Chromium 并不知道要重画 →
用户看到"返回后那块是空白/旧画面，**滚动一下才出现**"（DOM 完全正常，缺的是**像素**）。
**规则**：隐藏原生浮层时必须主动触发重绘（`view.update()/repaint()` + 让渲染层派发一次
`resize`）。**诊断要点**：DOM 断言看不出这种问题，只能靠**整屏抓取**看真实像素。
