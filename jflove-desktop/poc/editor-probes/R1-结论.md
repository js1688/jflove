# R-1 结论：QtWebEngine profile 锁在「早退」路径上是否被触发

> 对应设计文档 `文档记录/设计文档/v1.6.0.md` §6.6.1（判定时机）/ §6.6.2（profile 锁 四条判据）/ §13.1 的 R-1 行
> 实测脚本：`jflove-desktop/poc/editor-probes/r1-profile-lock.py`
> 原始输出：`out/r1-stage.log`、`out/r1-stage-quick.log`、`out/r1-orchestrate.log`、`out/r1-summary.json`、
> `out/r1-child-{a,b,c,p1,p2}.log|.err`、`out/r1-chromium-cmdline.txt`、`out/r1-dir-*.json`、`out/r1-timeline.json`
> 本目录所有文件均在 `poc/` 下，**未改动任何项目源码**。

---

## 0. 裁决（一句话）

**设计 §6.6 定的「判定时机在 `build_app()` 之后、`WebShell()` 之前」成立，而且比设计假设的更安全**：

- 实测 **Qt 6.11 的「默认 profile」是 off-the-record（`isOffTheRecord() == True`、`storageName() == ''`、
  `persistentStoragePath()` 指向 `…\QtWebEngine\OffTheRecord`、`cachePath()` 为空、HTTP 缓存为内存缓存）**；
- 从 `import` → `QApplication()` → `QtWebEngineQuick.initialize()` → `defaultProfile()` → `QWebEnginePage()` →
  `QWebEngineView()` → `show()+loadFinished` → 页面写 `localStorage`，**全程 user-data 目录新增文件数 = 0**，
  `…\QtWebEngine\OffTheRecord` **目录从未被创建**；
- 因此**不存在** Chromium 对同一 user-data 目录的 `SingletonLock` / `SingletonCookie` / `SingletonSocket` 争用：
  所有进程输出里搜 `Singleton` / `ProcessSingleton` / `already running` / `profile appears` **0 命中**；
- **反向压力测试**：在进程 A 已持有 WebEngine 的情况下，另起进程 C 真的创建 `QWebEngineView` 并加载页面 ——
  C 退出码 0、目录 0 新增、**A 完全不受影响**（心跳 tick 2 → 7，随后正常退出，`A_EXIT_OK`）。

⇒ **不需要**启用 §6.6.2 的退路（「在 `QApplication` 之前先 `QLocalSocket` 探活」）。
判定时机**必须早于 `WebShell()`** 的理由回到 §6.6.1 原本那两条（不闪窗、不建第二个托盘），与 profile 锁无关。

## 2. 阶段时间线：profile 到底哪一刻落盘？（`out/r1-stage.log` / `out/r1-timeline.json`）

观察根目录：`%APPDATA%\JFLove\{JFLove,}`、`%LOCALAPPDATA%\JFLove\{JFLove,}`、`%TEMP%\QtWebEngine`。

| 阶段 | 动作 | 目录条目总数 | 新增 | 说明 |
|---|---|---|---|---|
| 0 | 未 import PySide6（基线） | 160 | — | 基线里唯一的"锁类"文件是 **我自建具名 profile** 里的 leveldb `LOCK`（见 §5） |
| 1 | `import PySide6.QtWebEngineWidgets` | 160 | **0** | 仅 import 不落盘 |
| 2 | `QApplication()` + `setApplicationName/Organization` | 160 | **0** | `QApplication` 本身不建 profile |
| 3 | `QWebEngineProfile.defaultProfile()`（触碰） | 160 | **0** | 打印：`storageName=''`、`offTheRecord=True`、`persistent=…\QtWebEngine\OffTheRecord`、`cache=''` |
| 4 | `QWebEnginePage()` | 160 | **0** | |
| 5 | `QWebEngineView()`（未 show） | 160 | **0** | |
| 6 | `show()` + `loadFinished`（`file://` 页面） | 160 | **0** | 只出现 Chromium 的 GPU GLES3 报错（与 profile 无关） |
| 7 | 页面 `localStorage.setItem()`（返回 `ok`） | 160 | **0** | **OTR profile 连 localStorage 都不落盘** |
| 8 | **对照组**：具名持久化 profile（`QWebEngineProfile("jflove-r1-probe")`）+ view + load | 162 | **4** | 新增 `Local Storage\leveldb\LOG.old`、`blob_storage\<uuid>`，`LOG` 315→356 B；`persistent=…\QtWebEngine\jflove-r1-probe`、`cache=%LOCALAPPDATA%\…\cache\QtWebEngine\jflove-r1-probe` |

**`QtWebEngineQuick.initialize()` 单测（`out/r1-stage-quick.log`）**：`QApplication` → `import QtWebEngineQuick`
→ `QtWebEngineQuick.initialize()` 三阶段合计新增 **0**。

**路径事实核对**：`Test-Path "$env:APPDATA\JFLove\JFLove\QtWebEngine\OffTheRecord"` → **False**（该目录根本没被创建）；
`%LOCALAPPDATA%\JFLove\JFLove\QtWebEngine\Default\` 也**不存在**（该目录下只有 Qt 自己的 `cache\qtpipelinecache-*`）。

> 也就是说：**默认 profile 的 user-data 目录在本版本上没有任何磁盘足迹**。
> `%TEMP%` 下也没有任何 Chromium 残留（30 分钟内只看到本任务的探测目录）。
> 唯一未取到的证据：`QtWebEngineProcess.exe` 命令行里只有 `--type=renderer`（无 `--user-data-dir`）——
> QtWebEngine 的"浏览器进程"就在宿主进程内，`--user-data-dir` 不经过子进程命令行，故 **`--user-data-dir` 的精确取值未测出**
> （文件系统层面已证明它不落盘）。

## 3. 多进程实测（`out/r1-orchestrate.log` / `out/r1-summary.json`）

各进程都复刻真实启动路径、都带上与 `main.py` 相同的 app 名/组织名。

| 进程 | 做了什么 | 退出码 | 耗时 | 新增目录条目 | 关键 stderr | 对 A 的影响 |
|---|---|---|---|---|---|---|
| **A** | `QApplication` + `QWebEngineView` + 加载页面，**保持 40 s**（2 s 心跳） | 0 | 40 s（19 tick，`A_EXIT_OK`） | **0** | 仅 `Failed to create GLES3 context` ×6（GPU，与 profile 无关） | —（基准持有者） |
| **B** | **只建 `QApplication`**（不建 view/page），1.2 s 后退出 | 0 | 2.23 s | **0** | 仅 sandbox 提示 + GLES3 ×2 | 无（A 心跳继续） |
| **C** | A 运行期间 **创建 `QWebEngineView`** 并加载页面，8 s 后退出 | 0 | 9.17 s | **0** | 仅 GLES3 ×6 | **无**：A tick 数 2 → 7，A 之后正常退出 |
| **P1** | 具名**持久化** profile + view，保持 25 s | 0 | 25 s（12 tick） | —（该 profile 目录在 stage 8 已建） | GLES3 | — |
| **P2** | P1 运行期间用**同一具名持久化 profile** 再建 view | 0 | 7.14 s | **+2**（`blob_storage\<uuid>`） | **`Unable to move the cache: 拒绝访问。 (0x5)` ×3**（`net/disk_cache/cache_util_win.cc:25`） | **无**：P1 tick 3 → 12，P1 正常退出 |

**全文关键字命中统计**：`Singleton` 0、`ProcessSingleton` 0、`already running` 0、`profile appears` 0；
唯一的锁命名文件是 **我自建具名 profile** 里的 `Local Storage\leveldb\LOCK` 与 `Session Storage\LOCK`（LevelDB 锁，非 Chromium 进程单例）。

**逐条回答任务里的三问**

1. **profile（user-data 目录）在什么时刻被创建/加锁？**
   → **在本项目当前配置下，任何时候都不落盘**：默认 profile 是 OTR，`QApplication`、`QtWebEngineQuick.initialize()`、
   `defaultProfile()`、`QWebEnginePage()`、`QWebEngineView()`、`show()`+加载、页面写 `localStorage` 都不产生文件，
   **不存在锁文件**。对照：一旦改用**具名持久化 profile**，磁盘目录立刻出现（stage 8），
   且双进程同用时出现 `disk_cache` 目录争用（P2 的 `Unable to move the cache: 拒绝访问 (0x5)`）。
2. **双进程实验** → 见表（A/B/C 与 P1/P2）。
3. **「判定时机早于 `WebShell()`」是否足够？** → **足够（且当前根本用不到这条防线）**；
   若将来改成持久化 profile，P1/P2 证明"早退不建 view"这条防线**仍然够用**（争用只发生在真正建 view 的进程之间）。

## 4. 设计 §6.6.2 四条判据的逐条状态

| # | 设计里的判据 | 本次状态 | 依据 / 说明 |
|---|---|---|---|
| 1 | 双击两次 exe（间隔 200 ms）→ `Get-Process JFLove` 计数 **= 1** | **未测出** | 属单实例功能本身的验收（`SingleInstanceGuard` 还没实现，§6.6 是"从零做"）；R-1 的判据是 profile 锁，不是进程计数 |
| 2 | 第二实例路径上断言**未创建** `QWebEngineProfile` | **已实测（成立）** | 进程 B：只建 `QApplication`，profile 目录 0 新增；且 `defaultProfile()` 触碰本身也不落盘 |
| 3 | 检查 `%LOCALAPPDATA%\JFLove\QtWebEngine\Default\` 下**不出现**新增 `Singleton*` 残留 | **已实测（成立，但判据写错路径）** | 该目录**不存在**（真实 OTR 路径在 `%APPDATA%\JFLove\JFLove\QtWebEngine\OffTheRecord`，且该目录也从未创建）；全程 `Singleton*` 0 命中 ⇒ 判据成立但描述与事实不符，建议改写 |
| 4 | 反向对照：判定时机挪到 `WebShell()` 之后 → 断言进程数 2 + 出现第二个托盘 | **未测出** | 需要单实例功能存在后才能做（同上） |

**另外两条结论性的实测事实**（可直接回填 §6.6.2）：

- 「QtWebEngine 对同一 user-data 目录持有 profile 锁（`SingletonLock`/`SingletonCookie`/`SingletonSocket`）」
  这一**推测在本项目当前配置下不适用**（Windows 上 Chromium 的单例机制本来就不走这三个文件，且 OTR profile 不落盘）。
- 真正的风险点是 **持久化 profile 的缓存/存储目录争用**（P2 的 `Unable to move the cache: 拒绝访问 (0x5)`），
  表现为**非致命**（退出码 0、第一实例不受影响），但会污染日志、可能让第二实例退回临时缓存。

## 6. 附带发现（**超出 R-1 判据，需另行确认，勿当作结论**）

1. **默认 profile 为 off-the-record ⇒ 渲染层 `localStorage` 不跨重启**。
   `ui/src` 里 `utils/session.ts`（`jflove_server_url` / `jflove_session_max_seconds` / `jflove_notes_disk_id` / `jflove_notes_path`）、
   `stores/theme-store.ts` 都写 `localStorage`。项目已有 Python 侧兜底（`session.json`、`preferences.json`、`server_history.json`、`theme.json`），
   但 **`notesDiskId` / `notesPath` / `localSessionMaxSeconds` 是否另有落盘，本次未查证** ⇒ 标记为**待确认**，
   建议由设计/桌面端确认一遍（这属于 v1.6.0 之外的历史行为，不是 R-1 的判据）。
2. **§6.6.2 的路径描述需修正**：`%LOCALAPPDATA%\JFLove\QtWebEngine\Default\` → 实测不存在；
   当前真实行为是 OTR（`%APPDATA%\…\QtWebEngine\OffTheRecord`，且不落盘）。
3. `Release of profile requested but WebEnginePage still not deleted. Expect troubles !`：
   出现在**探测脚本**（未给具名 profile 设 parent / 未删除 page 就退出）里，属探测脚本自身的清理顺序问题，
   **不代表应用有该问题**（应用的 profile 生命周期由 `WebShell` 持有）。

## 7. 未测出 / 存疑清单（不得当作已证实）

1. **判据 1 / 4**（进程数 = 1、反向对照）—— 需要先实现 `SingleInstanceGuard` 才能测（Phase 4a）。
2. **`--user-data-dir` 的精确取值** —— QtWebEngine 浏览器侧在宿主进程内，子进程命令行只有 renderer，未取到；
   文件系统层面已证明默认 profile 不落盘，但"Chromium 内部把 OTR 数据放在哪"（内存/临时）**未测出**。
3. **非 Windows 平台**：`SingletonLock`/`SingletonCookie`/`SingletonSocket` 是 POSIX 侧命名，
   本次**只在 Windows 实测**；Linux/macOS 上 OTR profile 是否同样零落盘 **未测**（推断相似，但未验证）。
4. **持久化 profile 的争用是否会造成数据损坏**：本次只观察到 `Unable to move the cache` 警告与非致命退出（P2 退出码 0），
   **没有**做长时间/多轮/异常退出的压力测试 ⇒ 「不损坏 profile」这一说法**未证实**。
5. 外部文档核对不可用（`web_search` 无 API Key、`doc.qt.io` 抓取受限）⇒ 全部结论依据本机原始输出。
