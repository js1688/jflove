# R-9 结论：二进制嗅探阈值 `0.30` 的标定（实测）

> 任务：验证设计文档 v1.6.0 §5.2.2 的「前 8 KB 中，非文本字节比例 > `0.30` 判为二进制」是否
> **不误杀中文（GBK / UTF-8）**、**不漏放二进制**。
>
> 证据文件（同目录）：`r9-sniff-threshold.py`（探针）、`r9-report.md`（原始表格）、
> `r9-results.json`（结构化结果）、样本目录 `%TEMP%\jflove-r9-probe\`（15 个样本文件）。
> 环境：`jflove-desktop/venv-win/Scripts/python.exe` = Python 3.13.14，纯标准库，**未安装任何新依赖**。

## 0. 结论摘要（先说结果）

| 问题 | 实测结论 |
|---|---|
| `0.30` 是否成立？ | ❌ **不成立**。按 §5.2.2 自己给的 `non_text` 定义，**GBK 中文正文的实测比例为 0.5443 ~ 0.5830，全部 > 0.30 ⇒ 被误判为二进制**（15 类样本中 03 / 10 / 11 三类失败）。 |
| 设计文档"0.30 是保守上界（避免误杀 GBK/UTF-16 文本）"这句话 | ❌ **被实测推翻**。GBK 不用 0.30 救；UTF-16 也不是 0.30 救的（见下）。 |
| 另一处独立缺陷 | ❌ **B3（交替 NUL 指纹，≥ 90%）对中文 UTF-16 从不触发**：实测奇偶两侧 NUL 占比仅 0.0420 / 0.1257。⇒ **无 BOM 的中文 UTF-16 会掉到 B4（含 NUL）被误判为二进制**（样本 14 失败）。 |
| 有没有能全部正确分类的替代判据？ | ⚠ **部分有**。**「BOM / NUL 检查 + 严格解码优先」**（本文算法 C）**修掉了 3 个 GBK 误杀**（样本 03/10/11），但**样本 14（UTF-16 无 BOM 中文）仍判二进制** ⇒ 实际 **14/15**（**不是** 15/15）。对 2000 次"无 NUL 随机二进制"的误放率为 0。**⚠ 编排者复核更正（2026-10-12）**：算法 C 的实现里交替 NUL 门槛**仍是 0.9**（见探针 `r9-sniff-threshold.py:202`），而样本 14 实测 0.1257 ⇒ 不触发、落到"含 NUL ⇒ 二进制"。**样本 14 的处理需额外决策**（见 §6 末尾「B3 门槛」）。 |

## 1. 我实际使用的「非文本字节」判定算法

### 算法 A —— **设计文档 §5.2.2 B5 的原文口径**（基准，必须原样复现才算公平）

```
non_text = 满足以下全部条件的字节：
    ① 不在 {0x09, 0x0A, 0x0D} ∪ {0x20..0x7E}
    ② 不是「合法 UTF-8 多字节序列」的一部分
ratio = non_text / n      （n = len(sample[:8192])）
判为二进制 ⟺ ratio > 0.30
```

> 注意 ② 只认 **UTF-8**。GBK 的双字节序列在 UTF-8 眼里绝大多数非法，因此**两个字节都会被计入 `non_text`** —— 这正是误杀的根因。GBK 双字节的第二字节常落在 `0x40-0x7E`（ASCII 可打印区）或 `0x80-0xFE`；前者侥幸算"文本"，后者算"非文本"，所以比例落在 0.54 左右而不是 1.0。

### 算法 B —— GB18030 感知（对照：只把 ② 扩展为"或属于合法 GB18030 多字节序列"）

### 算法 C —— **解码优先**（本文推荐的替代判据）

```
C1  n == 0                                   → 文本（空）
C2  前 2/4 字节是 UTF-16/32 BOM               → 文本（跳过 C4/C5）
C3  含 NUL 且奇偶两侧"恰有一侧" NUL 占比 ≥90%  → 文本（无 BOM 的 UTF-16）
C4  含 NUL（其余情形）                        → 二进制
C5  sample[:8192].decode('utf-8', strict) 成功 → 文本
C6  否则 .decode('gb18030', strict) 成功且含多字节序列(任一字节 ∈0x81..0xFE) → 文本（gbk）
C7  其它                                      → 二进制
```

> 算法 C **取消了 `0.30` 这个魔数**，且与设计文档 §5.2.3「编码判定」第 4/5 步**同源**
> （同一套 `utf-8 strict` / `gb18030 strict` 判据），两项判定天然一致，不引入新依赖、不新增 I/O。

### 折算成用户可见的后果

- **GBK 用户打开任何中文 `.txt`/`.log`（扩展名不在白名单时）会被拒绝**，提示"不是可识别的文本文件"。这与 AC-51（未知扩展名 + 文本内容 → 按 txt 打开）**直接冲突**。
- "零 ASCII 的纯中文 GBK"是最坏情形（0.5830），**无论把阈值调到多高都不安全**：只要文档是中文为主、ASCII 极少，比例就在 0.55 以上；而一个**不含 NUL 的二进制**（样本 13）比例是 0.5438 —— **两类样本的比例区间重叠**（见下），说明"比例阈值"这条路本身不可靠。

| 分类 | 比例 |
|---|---|
| GBK 中文（应判文本） | 0.5443 / 0.5443 / 0.5830 |
| 无 NUL 随机二进制（应判二进制） | 0.5438 |

> **这是本项最关键的发现**：两类必须分开的样本，比例**几乎完全重合**（0.5438 vs 0.5443）。因此
> **不存在**能同时分开它们的比例阈值 —— 不是 0.30 太大或太小的问题，而是**这个特征本身没有区分度**。

## 3. 关于 `0.30` 是否"保守上界"的两条反证

1. **GBK**：0.30 把 GBK 判成二进制 ⇒ 它不是"偏保守"，而是**方向性错误**（对 GBK 来说，0.30 相当于"只要有一半以上字节非 ASCII 就拒绝"，而 GBK 中文天然如此）。
2. **UTF-16 带 BOM**（样本 04）：A 比例 0.3860 也 > 0.30。它只有靠 **B2 排在 B5 之前**才活下来。也就是说 **B5 的阈值在所有 UTF-16 样本上都是"误杀线"，全靠前面的 B2 兜住** —— B5 阈值"避免误杀 UTF-16"的说明与实测不符。
3. **UTF-16 无 BOM**（样本 14）：B3 的 90% 交替 NUL 门槛**实测只到 0.1257**（另一侧 0.0420），**从未触发**，于是掉进 B4 被判二进制。设计文档 §5.2.3 硬约束 3 说"无 BOM 的 UTF-16 由 B3 判为文本，编码不可推断 ⇒ 提示用户选编码"，**这条在中文 UTF-16 上无法实现**（只有 ASCII 占 ≥ 90% 的 UTF-16 才可能满足 90% 门槛）。

## 4. 误放率扫描（2000 次"无 NUL 随机二进制"，每字节 0x01-0xFF 均匀）

| 判据 | 误放（判成文本）次数 | 误放率 |
|---|---|---|
| 算法 A（设计原文口径 + 0.30） | 0 / 2000 | **0.0000** |
| 算法 B（GB18030 感知 + 0.30） | **2000 / 2000** | **1.0000** |
| 算法 C（解码优先，无比例阈值） | 0 / 2000 | **0.0000** |

> ⚠ **算法 B 被这条扫描一票否决**：把 `non_text` 的定义"放宽到认 GB18030"之后，随机二进制里大量字节对都能凑成合法 GB18030 双字节，比例掉到 ~0.20，于是**任何阈值都拦不住**（实测 100% 误放）。
> 这说明：**修 B5 不能靠"把非文本定义放宽"，必须换判据**（即算法 C）。

## 5. 两个"不是阈值问题"的边界（一并记录，避免误算到 R-9 头上）

1. **样本 07（二进制改名 `.log`）**：按 §5.3 类型表，`log`/`txt`/无扩展名**在白名单内**，AC-49 规定白名单命中**跳过嗅探**。所以它被判为文本**不是嗅探错误**，而是 §5.2.2 结尾已声明的**有意取舍（残余风险）**。实测的嗅探判定其实是正确的（B4 → binary）。
2. **样本 12（前 8 KB 全 ASCII，第 8192 字节后才是二进制）**：判为文本是"**只嗅探前 8 KB**"的固有边界，**换任何阈值都不会变**。若产品不接受，只能加大窗口或改为流式校验（超出本版本范围）。

## 6. 替代判据（推荐，已实测）

**推荐：用算法 C 整体替换 §5.2.2 的 B5，删除 `0.30` 魔数。**

| 项 | 内容 |
|---|---|
| 新流水线 | B1 空文件 → B2 UTF-16/32 BOM → B3 交替 NUL（**门槛需下调**，见下）→ B4 含 NUL → **B5' utf-8 strict 解码成功 ⇒ 文本** → **B6' gb18030 strict 解码成功且含多字节序列 ⇒ gbk 文本** → B7' 其它 ⇒ 二进制 |
| 实测表现 | **14/15**（⚠ **编排者复核更正**：原文写 15/15 有误）—— 修掉 3 个 GBK 误杀（03/10/11），但**样本 14（UTF-16 无 BOM 中文）仍判二进制**（原因：交替 NUL 门槛 0.9 未被下调，实测 0.1257 < 0.9）；无 NUL 随机二进制误放 **0/2000** |
| 代价 | 每份文件对前 8 KB 做 1~2 次 `decode(strict)`；8192 字节的解码是**微秒级**，相对已发生的 64 KB 读取可忽略；**不新增依赖**（标准库 `bytes.decode`），符合 §5.2.3 硬约束 1 |
| 额外收益 | 嗅探与 §5.2.3 编码判定**同源**，不再有两套彼此不兼容的口径；`reason` 可直接复用（`binary` / `unknown_encoding`） |
| 取舍 / 残余风险 | ① GB18030 很宽松，理论上存在"恰好全部是合法 GB18030 的二进制"，但实测 2000 次随机二进制 0 例；且 B4（NUL）已拦下 exe/dll/png/jpg/随机二进制全部样本。② **本项未实测**真实世界的"无 NUL 且非 UTF-8/GB18030"小二进制（例如某些加密容器）——**标为推测**。 |

### 若坚持保留比例阈值，**最小值**（不推荐，仅作退路）

- 必须 **≥ 0.60**（样本 11 = 0.5830 是最坏 GBK 情形），但这会**同时放走**样本 13（0.5438）之外的更多无 NUL 二进制 —— 实测已证明两类区间重叠，**任何单值阈值都不安全**，故本条只作为"万不得已"备案。

### B3 门槛的修正建议（若采用算法 C）

- 现状"恰有一侧 NUL 占比 ≥ 90%"对中文 UTF-16 **不触发**（实测 0.1257 / 0.0420）。
- 建议改为"**一侧 NUL 占比 ≥ 0.40 且另一侧 NUL 占比 ≤ 0.02**"（中文 UTF-16 的典型形态），或干脆**去掉 B3**：让无 BOM 的中文 UTF-16 落到 C5/C6 解码失败 ⇒ 报 `unknown_encoding` 并**提示用户选编码**（与 §5.2.3 硬约束 3 的意图一致，且不会误判为二进制）。
  - ⚠ 该修正门槛值**未做大规模标定**（只测了 1 个样本）⇒ **标为待补测**。
