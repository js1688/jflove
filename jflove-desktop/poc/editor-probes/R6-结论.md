# R-6 结论：`xml-formatter@3` 与 `sql-formatter@15` 的行为核对（实测）

> 任务：核对两个格式化库能否满足 v1.6.0「文本编辑器」工具箱 #9（SQL 美化）/ #10（XML 格式化·压缩）
> 的需求口径 —— 设计文档 §4.1.5 要求 **XML 必须保留注释与 CDATA 语义、压缩只删元素间空白、
> 不触碰文本节点内空白**；R-6 的风险等级是「**静默损坏用户文件（最严重）**」。
>
> 实测版本：**`xml-formatter` 3.7.0**、**`sql-formatter` 15.9.0**、Node **v24.18.0**（Windows）。
> 依赖装在系统临时目录 `%TEMP%\jflove-fmt-probe\`（`npm install --no-save`），
> **未修改任何项目源码 / package.json**。

## 1. 结论摘要

| 问题 | 实测结论 |
|---|---|
| XML **格式化**能否保留注释与 CDATA？ | ✅ **能**（默认即保留；`x1` / `x2` / `x2b` / `x6e` 四例互证） |
| XML **压缩**"只删元素间空白、不触碰文本节点内空白"？ | ❌ **不能**，坏在**两类**：<br>① **"元素唯一内容为纯空白文本"**（`<a> </a>`）会被吃成 `<a></a>`；**任何选项组合都关不掉**（`collapseContent` / `filter` 均无效），只有 `xml:space="preserve"` 能保住（`m1`~`m10`）。<br>② **`collapseContent:true` 在压缩模式 + 多行输入下会"粘词"**：`This is <b>some</b> content.` → `This is<b>some</b>content.`（`c2`，**单词被粘在一起**）。<br>另：**格式化模式同样会吃纯空白文本节点**（`<b> </b>` → `<b>\n    </b>`） |
| 其它必须知道的 XML 行为 | ⚠ **BOM 被丢弃**；⚠ **默认行分隔符是 `\r\n`**；⚠ 非法 XML（缺闭合标签）**默认不报错、静默自动补全**（须开 `strictMode`）；⚠ 单引号属性**一律改写成双引号** |
| SQL 是否够用？ | ✅ **常规 SQL 够用**（语法/大小写/缩进/注释/字符串/多语句/20 方言全部符合预期）。❌ 三个明确不达标项：**MySQL `DELIMITER` 存储过程被改坏**、**`:name` 命名参数默认方言下抛错**、**非 SQL 文本被静默改写成乱码**。⚠ **1000 层括号嵌套耗时 12.9 s**（同步阻塞） |
| 是否"静默损坏"？ | ⚠ **是，且已复现三类**：① XML 压缩吃"纯空白文本节点"；② XML 压缩 + `collapseContent:true` **粘词**（多行输入）；③ XML 非法输入静默补全。三者都会在用户"保存"后写回文件 |

## 2. XML 逐用例判定

判定口径：`OK` = 满足需求；`风险` = 会改动文件但语义基本等价或有规避手段；`不可用` = 直接违反 AC-33。

### 2.1 格式化（`xmlFormat(xml, opts)`）

| # | 用例 | 输入 → 输出（摘要，完整原文见 `r6-out/`） | 注释/CDATA/文本节点空白 | 判定 |
|---|---|---|---|---|
| X1 | **注释** | `<root><!--keep-me--><a>1</a><!-- second comment --><b>2</b></root>` → 两个注释**都在**，各自独占一行 | 保住 | **OK** |
| X2 | **CDATA + 内部空白** | `<root><a><![CDATA[  x < y\n   \t spaced  ]]></a></root>` → CDATA **逐字符不变**（首尾双空格、内嵌换行与制表符全部保留） | 保住 | **OK** |
| X2b | **AC-33 原文样例** | `<root><!--c--><a><![CDATA[ x < y ]]></a></root>` → 注释与 CDATA 都在 | ⚠ 默认格式化把 CDATA **换行缩进到独占一行**，`<a>` 的文本值由 `' x < y '` 变成 `'\n         x < y \n    '`（ElementTree `itertext` 口径，见 `r6-ac33-check.json`） | **风险**（用 `collapseContent:true` 可消除） |
| X3 | **自闭合标签** | `<r><br/><img src="x" /><hr /></r>` → `<br/>` `<img src="x"/>` `<hr/>`，**没有**变成 `<br></br>`；仅 `<img src="x" />` 的空格被去掉 | 保住 | **OK** |
| X3b | **空元素** | `<r><a></a><b> </b><c/></r>` → `<a></a>` 保持；**`<b> </b>` → `<b>\n    </b>`** | ⚠ 单个空格文本节点被换成换行+缩进（值变了） | **风险** |
| X4 | **单引号属性** | `<r a='1' b='two words'>` → `<r a="1" b="two words">` | 语义等价，但**一律改写为双引号**（库无 `'preserve'` 选项，只有 `double`/`single`） | **风险** |
| X4b | **无引号属性**（非法 XML） | `<r a=2 b=x><c/></r>` → `<r a="2" b="x">` | ⚠ **不报错**，静默"修正"成合法 XML | **风险** |
| X4c | 属性内实体与引号 | `b='it"quote'` → `b="it&quot;quote"` | 语义等价 | **OK** |
| X5 | **文本节点内空白** | `<a>hello   world</a>` → `hello   world` **保住**；但 `<b>  lead and trail  </b>` → `lead and trail`：**首尾空白被裁掉** | ⚠ 纯文本元素的**首尾**空白丢失 | **风险** |
| X5b | `xml:space="preserve"` | `<p xml:space="preserve">This is <b>some</b> content.</p>` → **原样**（内容保持同行） | 保住 | **OK**（官方声明的逃生阀，实测有效） |
| X5c | `collapseContent:true` | `<a>hello   world</a>`、`<b>  lead  </b>` → **两者都原样同行** | 保住 | **OK** ← **推荐参数的关键** |
| X8 | **XML 声明** | `<?xml version="1.0" encoding="UTF-8"?>` → **保留** | 保住 | **OK** |
| X8b | **BOM** | 输入首字符 `U+FEFF` → 输出首个字节 `3c3f786d`(`<?xm`)，`charCodeAt(0) !== 0xFEFF` | ❌ **BOM 被丢弃**（`r6-verify.json` 字节级证据） | **风险**（调用方必须补回） |
| X8c | 无声明 | `<r><a>1</a></r>` → **不添加**声明 | — | **OK** |
| X10 | **默认行分隔符** | 输出字节 `3c723e0d0a...`：`\r\n` 计数 7、裸 `\n` 计数 0 | ⚠ **默认 `\r\n`**（与 README 一致），跨平台必须显式传 `lineSeparator` | **风险** |

### 2.2 压缩（`xmlFormat.minify(xml, opts)`）

| # | 用例 | 输入 → 输出 | 判定 |
|---|---|---|---|
| X6 | 元素间空白 | `<r>\n  <a>1</a>\n  <b>2</b>\n</r>` → `<r><a>1</a><b>2</b></r>` | **OK** |
| **X6b** | **`<a> </a>`（有意义的一个空格文本节点）** | `<r>\n  <a> </a>\n  <b>x</b>\n</r>` → **`<r><a></a><b>x</b></r>`** | **不可用** ← AC-33 直接违反 |
| X6c | 文本节点**内部**空白 | `<a>hello   world</a>` → `hello   world` **保住** | **OK** |
| X6d | 混合内容（**单行**输入）+ `collapseContent:true` | `<r><p>This is <b>some</b> content.</p></r>` → **原样**（行内空格保住） | **OK（仅限单行）** |
| X6e | AC-33 样例压缩 | `<root><!--c--><a><![CDATA[ x < y ]]></a><b>hello   world</b></root>` → **原样**，注释/CDATA/三连空格全在；ElementTree 解析通过且文本节点完全相等 | **OK** |
| X7 | **非法 XML（缺闭合标签）** | `<root><a>1</root>` → **不抛异常**，静默输出 `<root>\n <a>\n 1\n </a>\n</root>`（**自动补全闭合标签**） | **风险**（"静默修复"用户文件） |
| X7b | `throwOnFailure:false` | 同上（因默认 `strictMode:false`，解析本就"成功"，`throwOnFailure` 无用武之地） | **风险** |
| X7c | `strictMode:true` | **抛 `Failed to parse XML`** | **OK**（唯一能拦住非法 XML 的开关） |
| X7d | 纯文本非 XML | `hello world\nnot xml at all` → **抛错** | **OK** |

### 2.3 压缩矩阵：能否用选项保住 `<a> </a>`（10 组，`r6-minify-matrix.json`）

| 配置 | `<root><a> </a><b>x</b></root>` 的输出 | 空格保住？ |
|---|---|---|
| 默认 | `<root><a></a><b>x</b></root>` | ❌ |
| `collapseContent:true` | `<root><a></a><b>x</b></root>` | ❌ |
| `collapseContent:false` | `<root><a></a><b>x</b></root>` | ❌ |
| `filter: () => true` | `<root><a></a><b>x</b></root>` | ❌ |
| `<a xml:space="preserve">` | `<root><a xml:space="preserve"> </a><b>x</b></root>` | ✅ |
| 根上 `xml:space="preserve"` | `<root xml:space="preserve"><a> </a><b>x</b></root>` | ✅ |
| `<a>&#160;</a>`（NBSP 实体） | 原样（**NBSP 不算"空白"**） | ✅ |
| `<b>y</b> <c>z</c>`（元素间） | `<root><b>y</b><c>z</c></root>` | ❌（按 AC-33 措辞"元素之间"属**允许删除**） |

> **结论**：`<a> </a>` 这类"元素唯一内容为纯空白文本"的节点**无法用任何选项保住**，只有 `xml:space="preserve"` 例外。

### 2.3b ⚠ `collapseContent:true` 在**压缩**模式下会"粘词"（最严重的一类静默损坏）

`r6-collapse-content.mjs` / `r6-collapse-content.json` 实测（同一份**多行**输入）：

```xml
<root>
  <content>
    <p>
        This is <b>some</b> content.
    </p>
  </content>
</root>
```

| # | 模式 | 选项 | 输出（`<p>` 部分） | 行内空格 |
|---|---|---|---|---|
| c1 | minify | `{}`（默认） | `<p>\n        This is <b>some</b> content.\n    </p>` | ✅ **保住**（`This is some content.`） |
| **c2** | **minify** | **`{collapseContent:true}`** | **`<p>This is<b>some</b>content.</p>`** | ❌ **被删——单词粘在一起** |
| c3 | minify | `{collapseContent:false}` | 同 c1 | ✅ 保住 |
| c4 | format | `{}`（默认） | `This is` / `<b>` / `some` / `</b>` / `content.` 各占一行 | 文本节点值被换行重排（语义仍可读） |
| c5 | format | `{collapseContent:true}` | `<b>some</b>` 与 `This is`、`content.` **各占一行且空格保留** | ✅ 保住 |
| c6 | minify | `{}`（**单行**输入） | `This is <b>some</b> content.` | ✅ 保住 |
| **c7** | **minify** | **`{collapseContent:true}`（单行输入）** | `This is <b>some</b> content.` | ✅ 保住（**所以单行测试会漏掉这个坑**） |

> **⚠ 这是 README 示例的真实行为，不是文档笔误**：README 的 minify 示例用的正是 `collapseContent:true`，其展示输出 `This is<b>some</b>content.` 与实测一致。
> **触发条件**：**minify + `collapseContent:true` + 文本节点内含换行**（即真实用户文件最常见的形态）。
> **后果**：对 `svg` / 类 HTML 内容（§5.3 类型表把 `xml`/`html`/`svg` 都交给同一个格式化器），
> `Hello <tspan>world</tspan>!` 会变成 `Hello<tspan>world</tspan>!` —— **渲染结果直接不同**。
> **规避**：压缩**一律不要传 `collapseContent`**。

### 2.4 用 AC-33 给定判据复核（`r6-xml-ac33-check.py`）

| 产物 | ET 解析 | 文本节点完全相等 | 注释 | CDATA |
|---|---|---|---|---|
| **推荐参数·压缩**（AC-33 原样样例） | ✅ OK | ✅ **是** | 有 | 有 |
| **推荐参数·格式化**（AC-33 原样样例） | ✅ OK | ⚠ 否（新增了元素间缩进空白节点；**原有文本节点 `' x < y '`、`'hello   world'` 均逐字符保留**） | 有 | 有 |
| 库默认·格式化（未包装） | ✅ OK | ❌ 否（`' x < y '` → `'\n         x < y \n    '`） | 有 | 有 |
| 库默认·压缩 含 `<a> </a>` | ✅ OK | ❌ 否（`['\n  ',' ','\n  ','x','\n']` → `['x']`） | — | — |
| 库默认·格式化 含 `<b> </b>` | ✅ OK | ❌ 否（`[' ']` → `['\n    ',…]`） | — | — |
| 推荐参数·`xml:space="preserve"` | ✅ OK | ✅ 是 | — | — |

> ⚠ **对 AC-33 判据本身的一条修正建议**：AC-33 说"压缩后…**文本节点内容不变**"。但对**任何**压缩器而言，删除元素间缩进空白**必然**改动文本节点（元素内容文档里那些缩进本身就是文本节点）。因此该判据若按字面执行，会在"正常缩进文档"上产生**假阳性失败**（`r6-ac33-check.json` 里的"正常缩进 · 推荐参数压缩"一行：输入 `['\n  ','1','\n  ','2','\n']` → 输出 `['1','2']`，这是**正确**的压缩行为，却会被判为"内容变了"）。
> 建议把口径改为：**"非纯空白文本节点的值不变"**（压缩）／**"原有文本节点的值不变，允许新增元素间缩进空白"**（格式化）。

## 3. SQL 逐用例判定

### 3.1 方言枚举（`s1-dialects`，来自 `node_modules/sql-formatter/dist/cjs/languages/`）

**20 个**（与 `allDialects.d.ts` 的 20 个 export 逐一对应）：

```
bigquery, clickhouse, db2, db2i, duckdb, hive, mariadb, mysql, n1ql, plsql,
postgresql, redshift, singlestoredb, snowflake, spark, sql, sqlite, tidb,
transactsql, trino
```

`select a, b from t where a = 1 order by b limit 10;` 在 **20/20 方言**下均成功格式化（无异常）。
非法取值 `not-a-dialect` → **`Error: Unsupported SQL dialect: not-a-dialect`**（明确）。

### 3.2 逐用例

| 组 | 用例 | 实测结果 | 判定 |
|---|---|---|---|
| 大小写 | `keywordCase:'upper'/'lower'/'preserve'` | 三者均按预期生效 | **OK** |
| 大小写 | 是否误改标识符/字符串/函数名 | `select Foo, 'Select Bar' as Lit, count(*)…` → `SELECT Foo, 'Select Bar' AS Lit, count(*)`；`Foo`、字符串、`count` **均未被改** | **OK** |
| 大小写 | `identifierCase`/`dataTypeCase`/`functionCase` | 可独立生效（`identifierCase:'lower'` → `foo`、`mytable` 变小写） | **OK** |
| **注释** | 行注释 / 块注释 / 行内注释 | **全部保留**，但**位置漂移**：`/* 块注释 */ b` 被拆成两行；跨行块注释被重新缩进；末尾 `-- 末尾行注释` 被移到一个空行之后 | **OK（有漂移）** |
| 注释 | 优化器提示 `/*+ INDEX(t idx1) */` | 保留（移到 `SELECT` 下一行，行首） | **OK** |
| 注释 | 仅含注释、无语句 | **原样返回，不报错** | **OK** |
| 缩进 | `tabWidth:2` / `tabWidth:8` | 分别产生 2 / 8 空格缩进 | **OK** |
| 缩进 | `useTabs:true` | 输出中确为 `\t` 字符 | **OK** |
| 缩进 | `indentStyle:'tabularLeft'` | 生效（`select    a,` / `from      t` 对齐式） | **OK** |
| 缩进 | `linesBetweenQueries:3` | 多语句之间产生 3 个空行 | **OK** |
| 字符串 | `SELECT 'a;b' AS c FROM t` | `'a;b'` **未被分号拆分** | **OK** |
| 字符串 | `'select -- not a comment /* neither */ ; from'` | 字符串内容**完全未被误解析** | **OK** |
| 标识符 | `"from"` / `` `where` `` | 引号标识符内的关键字**未被改写** | **OK** |
| 字符串 | PG 美元引用 `$$a;b select$$` | 内容保留（`'a;b'` 未被拆分） | **OK** |
| **参数** | `:name` / `@p` / `?` | ❌ **`'sql'` 方言下 `:name` 抛 `Parse error: Unexpected ":name and "`**，并提示"请选更具体的方言" | **不可用（默认配置）** |
| **多语句** | `select 1; select 2; delete…` | 三条语句全部正确格式化，用空行分隔 | **OK** |
| 存储过程 | PG `$$…$$` 函数体 | 整体保留；但 `add_one(x int)` → **`add_one (x int)`**（函数名后多一个空格，属改写） | **风险** |
| **存储过程** | **MySQL `DELIMITER //`** | ❌ **被改坏**：`DELIMITER //` → `DELIMITER / /`；`END //` + `DELIMITER ;` → `END / / DELIMITER;` | **不可用** |
| 批处理 | T-SQL `GO` | `GO` 保留 | **OK** |
| 非法 | 缺结尾分号 | 正常格式化 | **OK** |
| **非法** | `select from where;` | ⚠ **不报错**，输出 `select\nfrom\nwhere;`（把非法语句"格式化"了） | **风险** |
| 非法 | 未闭合括号/引号 | **抛 `Parse error`** | **OK** |
| **非法** | 非 SQL 文本（XML 片段） | ❌ **静默改写**：`<root><a>1</a></root>` → `< root > < a > 1 < / a > < / root >` | **风险（会损坏文件）** |
| 非法 | 中文散文 | **抛 `Parse error`** | **OK** |
| 非法 | 非法 `keywordCase` | 抛 `TypeError: Cannot read properties of undefined`（**能抛但信息不可读**，运行时无选项校验） | **风险（轻微）** |

### 3.3 超深嵌套 / 超长输入（`r6-deep-nesting.json`）

| 用例 | 耗时 | 输出长度 | 结果 |
|---|---|---|---|
| SQL 50 层括号 | 46 ms | 1.5 KB | OK |
| SQL **200 层**括号 | 412 ms | 62.7 KB | OK |
| **SQL 1000 层括号** | ⚠ **12 888 ms** | **1.9 MB**（2 KB 输入） | **同步阻塞 12.9 s**（未崩溃，但 UI 会卡死） |
| SQL 单行 20000 个 IN 元素 | 756 ms | 208.9 KB | OK |
| XML 200 层嵌套（格式化） | 7 ms | 161.8 KB | OK |
| XML 1000 层嵌套（格式化） | 21 ms | **4.0 MB** | OK（输出体积二次增长） |
| **XML 5000 层嵌套（格式化）** | 11 ms | — | ⚠ **`RangeError: Maximum call stack size exceeded`**（**抛错，不是卡死**；能用 try/catch 兜住） |
| XML 200 层嵌套（压缩） | 1 ms | 1.4 KB | OK |
| XML 20000 个兄弟节点（宽输入） | 48 ms | 540.0 KB | OK |

> **判定**：两个库**都不会卡死**（XML 深嵌套抛栈溢出、可捕获），但 **SQL 1000 层嵌套 12.9 s 同步执行**是真实的冻结风险，且二者都有**输出体积爆炸**（输入 2 KB → 输出 1.9 MB；输入 6 KB → 输出 4 MB）。

## 4. 最终回答

### 4.1 `xml-formatter` 能否满足需求？

| 需求口径 | 结论 |
|---|---|
| 「格式化保留注释与 CDATA」 | ✅ **能满足**（默认行为，无需配置） |
| 「压缩只删元素间空白，**不触碰文本节点内空白**」 | ❌ **不能满足**，**坏在两类**：<br>**① "元素的全部子节点都是纯空白文本节点"**（`<a> </a>`、`<a>  </a>`、`<b> </b>`）→ 被压缩成 `<a></a>`；**无法用选项关闭**（`collapseContent` true/false、`filter` 全部无效），唯一逃生阀是 `xml:space="preserve"`。同类的改写**在格式化模式下也会发生**。<br>**② 压缩 + `collapseContent:true` + 多行输入 ⇒ 粘词**：`This is <b>some</b> content.` → `This is<b>some</b>content.`（单词粘连，对 `svg`/`html` 会改变渲染结果）。**规避办法：压缩一律不传 `collapseContent`**。<br>附带：`<b>y</b> <c>z</c>` 之间的空格也会被删 —— 按 AC-33 措辞属"元素之间"、可以接受，但需产品确认这是预期。 |

**推荐调用参数（格式化）**

```js
import xmlFormat from 'xml-formatter';

// ① BOM 必须由调用方负责（库会丢）
const hadBom = text.charCodeAt(0) === 0xfeff;
const body = hadBom ? text.slice(1) : text;

const out = xmlFormat(body, {
  indentation: '  ',
  lineSeparator: '\n',      // ⚠ 库默认是 '\r\n'，跨平台必须显式指定
  attributeQuotes: 'double',// 库只有 double/single，无 preserve
  collapseContent: true,    // ★关键：保住已存在的文本节点（CDATA/纯文本元素不被换行包住）
  strictMode: true,         // ★关键：非法 XML 抛错，而不是静默补全
  throwOnFailure: true,
});

return hadBom ? '\uFEFF' + out : out;  // ② 补回 BOM（否则 utf-8-bom 文件被降级成 utf-8）
```

**推荐调用参数（压缩）+ 必须加的前置预检**

```js
// ⚠ 绝对不要传 collapseContent —— 它在多行输入上会粘词（实测 c2）
// 默认选项（c1）反而安全：行内空白保留，只删元素间的缩进空白
xmlFormat.minify(body, {
  strictMode: true,       // ★关键：非法 XML 抛错，而不是静默补全
  throwOnFailure: true,
});
```

> 若产品确实要"更彻底地压缩混合内容"，**不能**靠 `collapseContent:true`（会粘词），
> 必须走方案 ② 自研最小压缩（见 §4.3），且要有"粘词"回归用例。

预检实现见 **`xml-safe-minify.mjs`**（原型，9/9 用例行为正确）：

- 用 **`xml-parser-xo`**（`xml-formatter` 自己的传递依赖，**不新增第三方包**）解析出 AST；
- 递归找"**元素除纯空白文本节点外没有任何子节点**"的位置（`xml:space="preserve"` 子树跳过）；
- **找到 ⇒ 拒绝压缩**并给出精确路径（例：`/root/sp`，内容 `" "`）；
- 没找到 ⇒ 才调用 `xmlFormat.minify`（**且不传 `collapseContent`**）。
- 实测：AC-33 样例（`<sp> </sp>`）**被正确拒绝**；正常缩进 XML **正常压缩**；**多行混合内容（`a9`）行内空格完整保留、不粘词**；`xml:space="preserve"` **放行且内容不变**；非法 XML **抛错**；BOM **正确补回**。

> 这条路把 R-6 最严重的「静默损坏」变成了「**显式告知 + 拒绝执行**」，与设计文档 §13.1 R-6 行的退路
> （"「格式化前预览」+ 压缩只删元素间空白；不达标则换库或自研最小实现"）一致，且**不需要换库**。

### 4.2 `sql-formatter` 是否够用？

**常规 SQL 够用**（语法、关键字大小写、缩进、注释、字符串/标识符、多语句、20 方言全部符合预期）。
**推荐参数组合**：

```js
sqlFormat(text, {
  language: dialect,        // 默认 'sql'；由扩展名/用户选择给出，中文项目常见 'mysql' | 'postgresql' | 'sqlite'
  keywordCase: 'upper',     // 'upper' | 'lower' | 'preserve'（即时生效，UI 三选一即可）
  tabWidth: 2,              // 2 或 4
  useTabs: false,           // 与 tabWidth 二选一
  linesBetweenQueries: 1,   // 多语句之间的空行数（默认 1）
  // indentStyle: 'standard',  // 可选 'standard' | 'tabularLeft' | 'tabularRight'
});
```

**不达标 / 必须规避的 4 项**：

| 不达标项 | 现象 | 建议规避 |
|---|---|---|
| **MySQL `DELIMITER` 存储过程** | `DELIMITER //` → `DELIMITER / /`，脚本被改坏 | 检测到 `DELIMITER` 或 `BEGIN…END` 例程时**禁用格式化**并提示 |
| **命名参数 `:name`** | `'sql'` 方言下抛 `Parse error` | 传 `paramTypes` 显式声明（`[':name']`/`['@name']`/`['?']`），或对含 `:name` 的文本**捕获异常后原样返回 + 提示**（绝不留半成品） |
| **非 SQL 文本被静默改写** | `<root>…</root>` → `< root > < a > 1 < / a > < / root >` | 只在"语言 = SQL"时允许格式化；**必须保留设计已要求的「格式化前预览」**；失败/可疑输出不写回 |
| **1000 层嵌套阻塞 12.9 s** | 同步执行期间 UI 冻结 | 加**输入长度 / 括号深度预检**（如深度 > 200 或长度 > 100 KB 直接拒绝 + 提示），并把格式化放到 Web Worker / `requestIdleCallback` |

### 4.3 若某项不达标，替代方案建议

| 不达标项 | 替代方案（按推荐度） |
|---|---|
| XML 压缩吃纯空白文本节点 | **① 加"压缩前置预检"封装**（本文 `xml-safe-minify.mjs`，**零新依赖**、9/9 用例已验证）→ 最省事、风险最低；**② 自研最小压缩**（基于同一 AST，按"父元素只含元素/注释/CDATA 时才删空白"重写序列化器）→ 能真正做到 AC-33 字面要求，但要自行处理实体/属性引号，工作量与回归面更大；**③ 换库**：`vkbeautify` 等同样有空白语义问题，**不推荐** |
| XML 压缩"粘词"（`collapseContent:true` + 多行） | **不传 `collapseContent` 即可规避**（默认 minify 实测安全）。若产品要更彻底的压缩 → 只能走方案 ② 自研，且**必须补一条"多行混合内容不粘词"的回归用例** |
| XML BOM 丢失 | 调用方**记下 BOM 再补回**（原型已验证）—— 与设计 §5.2.3 硬约束 5（`utf-8-bom` 写回必须补 `EF BB BF`）**本来就要求**这件事，不额外增加负担 |
| XML 非法输入静默补全 | 统一传 `strictMode:true` + `throwOnFailure:true`，把异常转成**编辑器内提示**（不弹阻塞窗） |
| SQL MySQL `DELIMITER` | 检测 + 禁用（不自己实现 MySQL 例程解析） |
| SQL 命名参数 | `paramTypes` 配置；配置后仍失败则**原样返回 + 提示** |

## 5. 「已实测」与「推测 / 未测出」的边界

**已实测**

- XML 注释保留（4 例）、CDATA 内容逐字符保留（2 例）、自闭合标签不变形、`xml:space="preserve"` 生效
- XML 压缩吃掉 `<a> </a>` / `<a>  </a>` / `<b> </b>`（3 例 + 矩阵 10 组），且 `collapseContent`/`filter` **无效**
- XML **压缩 + `collapseContent:true` + 多行输入 ⇒ 粘词**（`This is<b>some</b>content.`，`c2`）；同输入默认选项安全（`c1`）；单行输入不会触发（`c7`，故单行测试会漏检）
- XML **格式化 + `collapseContent:true` 不粘词**（`c5`/`c8`，空格保留，仅换行重排）
- XML 格式化裁掉纯文本元素**首尾**空白（`<b>  lead  </b>` → `lead`）、把 CDATA 换行缩进（改变父元素文本值）
- XML **BOM 丢失**（字符 + 字节双重核对）、**默认 `lineSeparator` = `\r\n`**（字节 `0d0a`）
- XML **非法输入默认静默补全**；`strictMode:true` 才抛错；纯文本抛错
- 单引号属性一律改写为双引号；无引号属性不报错
- SQL 20 方言枚举 + 全部可用；`keywordCase` 不误伤标识符/字符串/函数；注释保留但漂移；`tabWidth`/`useTabs`/`indentStyle`/`linesBetweenQueries` 生效
- SQL 字符串内分号/关键字不误解析；`$$` 美元引用保留；多语句可用
- SQL **MySQL `DELIMITER` 被改坏**、**`:name` 抛错**、**非 SQL 文本被静默改写**、截断语句不报错
- SQL 1000 层括号 **12.9 s**；XML 5000 层 **RangeError**
- 替代原型 `xml-safe-minify.mjs` 的 9 个用例行为

**推测 / 未测出**

- **未测出**：`sql-formatter` 在 QtWebEngine / 桥层的**端到端时延**（本项只在 Node 侧测算法耗时；"12.9 s 会冻结 UI"是按主线程同步执行**推断**）
- **未测出**：XML 深嵌套在多大深度处从"正常"转为"栈溢出"（只测了 200 / 1000 / 5000 三点）
- **推测**：`xml-parser-xo` 作为传递依赖被直接 import 的**版本稳定性**（当前 4.1.6 由 `xml-formatter@3.7.0` 锁定；若上游改版本可能在 npm 去重时变化，落地时应把它写进 `ui/package.json` 的依赖或锁定版本）
- **推测**：自研最小压缩（方案 ②）能 100% 满足 AC-33 字面要求 —— **未实现、未实测**
- **未测出**：其他 XML 库（如 `vkbeautify`）的行为对比 —— 未安装、未实测
- **未测出**：`sql-formatter` 对**真实项目里的巨型 SQL 文件**（MB 级）的表现（只测了嵌套与超长单行）
