# R-5 结论：`QWebEnginePage.actions()` 的实际条目 + `setShortcuts([])` 的有效性

> 对应设计文档 `文档记录/设计文档/v1.6.0.md` §4.2.3 / §13.1 的 R-5 行 / AC-10
> 实测脚本：`jflove-desktop/poc/editor-probes/r5-webengine-actions.py`
> 原始输出：`out/r5-windows.log`、`out/r5-windows.json`、`out/r5-offscreen.log`、`out/r5-offscreen.json`
> 本目录所有文件均在 `poc/` 下，**未改动任何项目源码**。

## 0. 一句话结论

在 **PySide6/Qt 6.11.0**（Python 3.13.14，Windows）上，`QWebEnginePage` **已经没有 `actions()` 方法**，
只能按枚举逐个取 `page.action(WebAction)`（48 个真实动作 + 1 个计数哨兵）；
**这 49 项里没有任何一项带默认快捷键，也没有任何一项被注册进 `QWebEngineView.actions()`**
⇒ 设计文档 §4.2.3 假设的「WebEngine 默认把 `Ctrl+S` 映射为保存网页」**在 Qt 6.11 上不成立**，
AC-10「配了但按了没反应」在 **Ctrl+S / Ctrl+P / Ctrl+Shift+S / Ctrl+O / Ctrl+F / Ctrl+G / Ctrl+= / Ctrl+- / Ctrl+0 / F6 / F12**
这些键上**没有宿主来源**（`Ctrl+P` 打印、`Ctrl+O` 打开文件在 Qt 6.11 的 `WebAction` 枚举里**根本不存在**）。
`setShortcuts([])` **实测有效**（先手工绑上 `Ctrl+S` 再清空 → 动作不再被触发），
但**它不是本版本的必要操作**；建议保留为幂等防御 + 版本变化兜底。

## 4. `Ctrl+S` 等组合键到底会不会被抢？（默认状态实测）

**静态判据**：37 个候选组合键与宿主动作的冲突矩阵**全部为空**（`out/r5-windows.log:67-103`）——
`Ctrl+S`、`Ctrl+Shift+S`、`Ctrl+P`、`Ctrl+O`、`Ctrl+F`、`Ctrl+G`、`Ctrl+=`、`Ctrl+-`、`Ctrl+0`、`F6`、`F12`
以及 `Ctrl+U / Ctrl+R / F5 / F11 / Ctrl+D / Ctrl+L / Ctrl+T / Ctrl+Tab / Ctrl+A / Ctrl+C / Ctrl+V / Ctrl+X / Ctrl+Z /
Ctrl+/ / Alt+Z / Ctrl+Alt+* / Ctrl+Shift+V / Ctrl+W / Ctrl+N` **没有任何一个**被宿主动作占用。

**动态判据**（默认状态、真实按键、窗口已激活、敏感性对照已通过）：

| 结果维度 | 实测值（37 个键全部） |
|---|---|
| `action_triggered` | `{}`（无任何动作被触发） |
| 新顶层窗口（保存 / 打印对话框等） | `[]` |
| `zoomFactor` 变化 | 无（`1.0 → 1.0`） |
| `loadStarted`（重载） | 0 |
| view `Close` 事件（`Ctrl+W`） | 0 |
| 渲染层 `keydown` | `[]`（原因见 §6，**这是环境限制，不是结论**） |

**结论**：在 Qt 6.11 + 本项目的 profile 配置下，**宿主（WebEngine）本身不会抢 `Ctrl+S`**；
设计里「`Ctrl+S` 必须从「保存网页」手里抢回来」这一前提**不成立**。

**顺带实测清楚了 `SavePage` 的真实执行路径**（`out/r5-windows.log`，两平台一致）：
给 `SavePage` 绑上 `Ctrl+S` 后按键 → `triggered` 计数 +1 **且** `QWebEngineProfile.downloadRequested`
收到 `{'suggested_file_name': 'r5 probe.mhtml', 'state': 'DownloadState.DownloadRequested'}`；
**不弹 `QFileDialog`**。⇒ 如果要为 AC-10 设一个"能看见"的判据，**不能用"弹不弹保存对话框"**，
应该用「渲染层是否收到该键」或「`downloadRequested` 是否被触发」。
（本项目当前 **没有** 连接 `downloadRequested`（`grep downloadRequested src/` 0 命中），
所以现版本即使真被触发也只会静默丢弃下载请求；但一旦将来补上下载处理，误触就是"悄悄存出一个 `.mhtml`"。）

## 5. `setShortcuts([])` 是否有效？（三种关闭手段 + 直接触发）

对照方法：先 `save.setShortcut(QKeySequence("Ctrl+S"))` + `view.addAction(save)`，
确认**不清空就会触发**（`triggered={'SavePage': 1}`），再分别施加手段：

| 手段 | 施加后读回 | 按下 `Ctrl+S` 的动作触发 | 实测有效性 |
|---|---|---|---|
| **A. `action.setShortcuts([])`** | `shortcuts() == []`（读回确认为空） | `{}`（不再触发） | ✅ **有效** |
| **B. `action.setEnabled(False)`**（快捷键仍绑着） | `isEnabled() == False` | `{}` | ✅ **有效** |
| **C. `view.removeAction(action)`**（快捷键仍绑着） | `in_view_actions == False` | `{}` | ✅ **有效**（但动作从控件动作表被摘掉，恢复需 `view.addAction`） |
| **D. `page.triggerAction(SavePage)`（绕过键盘）** | — | `triggered` 增量 **0**，但 `downloadRequested` +1 | ⚠️ **动作照常执行**，只是**不发出 `triggered` 信号** |

> 两个重要推论：
> 1. 「用 `triggered` 信号计数」**测不到**由宿主自己发起的动作（手段 D 的 0 就是证据）⇒ 判据要用可观效果（下载请求 / 渲染层收键）。
> 2. 手段 A/B/C 都是"清了才生效"，即 **`setShortcuts([])` 这一类调用本身没被 Qt 忽略**（读回也是空）。

**"把 action 从 `page.actions()` 里移除"这条路不存在** —— 因为 `page.actions()` 本身不存在；
控件级移除接口 `QWebEngineView.removeAction()`（继承自 `QWidget`）存在且实测有效，但**默认无可移除之物**（`view.actions()` = 0）。

## 6. 未测出项：渲染层到底收不收得到注入的按键（**环境限制，如实记录**）

**未测出**：无法用注入方式证明「JS 的 `window` 捕获阶段监听能拿到 `Ctrl+S`」（即 §4.2.3 规则 1/2 的前半段）。

证据链（两个平台、两种注入通道都一致）：

| 观测 | 结果 |
|---|---|
| 渲染层 JS 记录器是否装好 | ✅ `runJavaScript` 回调正常（`1+1 → 2`，`install → ok`） |
| **鼠标**点击能否到达渲染层 | ✅ `window.__probeClicks: 0 → 1`（说明 JS 通道与页面事件本身没问题） |
| `QTest.keyClick`（`view` / `focusProxy` 都试过）能否到达渲染层 | ❌ 渲染层 `keydown` 始终为空 |
| Win32 `keybd_event`（OS 级真实按键，`GetForegroundWindow()==窗口` 已断言）能否到达渲染层 | ❌ 渲染层 `keydown` 始终为空 |
| 同一时刻 Qt 侧能否派发 QAction 快捷键 | ✅ 绑上 `Ctrl+S` 就触发（敏感性对照通过）⇒ **Qt 收到了键，Chromium 渲染层没收到** |
| 附加尝试（均无效） | `hide()+show()` 重建焦点（确认收到 `WindowActivate/FocusIn`）、`clearFocus()+setFocus()`、`QApplication.setActiveWindow(view)`、JS 先 `input.focus()` 再点鼠标、去掉 `--disable-gpu` |

⇒ **结论：本机（该 Windows 会话）下 QtWebEngine 渲染层收不到任何注入键盘事件（鼠标正常）**。
因此以下两点列为**未测出、需人工 GUI 复核**：
1. 「睡眠/正常环境下，`Ctrl+S` 在窗格内按下时 JS 能否拿到并 `preventDefault`」；
2. 「Qt 侧某个 `QAction` 持有该快捷键时，渲染层是否真的收不到」（**推测**：收不到 —— 因为
   Qt 的快捷键派发在 GUI 线程、先于控件事件投递到 delegate；但本轮**无法**用差分实验证实，
   因为基线状态下渲染层本来就收不到注入键）。

> 说明：设计 §4.2.3 的退路写着「若某条动作无法通过 `actions()` 拿到，退路是叠 `eventFilter` 或在渲染层用捕获阶段 + `preventDefault` 兜住」。
> **该退路对"宿主 QAction 抢键"这一类冲突很可能无效**（推测，理由同上）；真正能兜住的只有 Python 侧
> （`eventFilter` / 不绑快捷键 / `setEnabled(False)`）。若 Phase 4a 手工验收发现宿主确实抢键，
> **不要指望渲染层 `preventDefault`**。

## 8. 桌面端「窗格内 `Ctrl+S` 归编辑器」的具体做法（可执行 + 退路）

**主方案（最小改动，且与实测一致）**

1. **不要照抄 §4.2.3 的 `page.actions()` 伪代码**（Qt 6.11 无此 API）。改用按枚举取动作：

```python
# web_shell.py（示意；本任务未改动源码）
from PySide6.QtWebEngineCore import QWebEnginePage

#: 只清"宿主外壳类"动作。编辑类（Cut/Copy/Paste/Undo/Redo/SelectAll）不动，
#: 否则可能影响页面内输入控件。
_HOST_CHROME_ACTIONS = (
    QWebEnginePage.WebAction.SavePage,
    QWebEnginePage.WebAction.ViewSource,
    QWebEnginePage.WebAction.RequestClose,
    QWebEnginePage.WebAction.InspectElement,
    QWebEnginePage.WebAction.ExitFullScreen,
    QWebEnginePage.WebAction.Reload,
    QWebEnginePage.WebAction.ReloadAndBypassCache,
    QWebEnginePage.WebAction.Back,
    QWebEnginePage.WebAction.Forward,
    QWebEnginePage.WebAction.Stop,
)

def _disable_host_actions(self) -> None:
    """清掉宿主外壳动作的快捷键/可用性（Qt 6.11 实测：默认本就无快捷键，这里是幂等防御）"""
    page = self.view.page()
    for wa in _HOST_CHROME_ACTIONS:
        action = self.view.pageAction(wa)      # 等价 page.action(wa)；勿用 page.actions()
        if action is None:
            continue
        action.setShortcuts([])                # 实测有效（读回为空）
        action.setEnabled(False)               # 实测有效（双保险）
    # 注意：绝对不要对 WebAction.WebActionCount 调 action()（实测 0xC0000005 崩溃）
```

2. **`Ctrl+S` / `Ctrl+Shift+S` 的归属由渲染层决定**：在 `ui/src` 的应用级 `window` 捕获阶段监听里，
   当 `event.target` 位于 `[data-scratch-pane]` 内时 `preventDefault() + stopPropagation()`（§4.2.3 规则 2 照旧）。
   实测支持这一设计：**宿主没有占这两个键**，按键本来就会进入渲染层（未被宿主消费）。
3. **验收判据（改掉"看弹不弹对话框"）**：AC-10 的判据建议改成可观测的两条：
   ① 窗格内按下绑定键时，渲染层应用级监听命中并 `preventDefault`（用一次手工 GUI 验收）；
   ② Python 侧 `downloadRequested` **不被触发**、且 48 个动作的 `triggered` 计数为 0。

**退路（按成本从低到高）**

| 退路 | 做法 | 实测状态 |
|---|---|---|
| 1 | `action.setShortcuts([])` | ✅ 有效（首选；副作用最小） |
| 2 | 再加 `action.setEnabled(False)` | ✅ 有效（会连带禁用该动作本身） |
| 3 | `view.removeAction(action)`（把动作从控件动作表摘掉） | ✅ 有效；恢复需 `view.addAction` |
| 4 | Python 侧 `QApplication.installNativeEventFilter` / `self.view.installEventFilter` 拦 `Ctrl+S` | 未测（本轮未做；是本项目唯一能兜住"宿主 QAction 抢键"的层次） |
| 5 | 渲染层捕获阶段 + `preventDefault` | ⚠️ 对"宿主 QAction 抢键"**推测无效**（见 §6 说明），不能作为该类冲突的兜底 |

## 10. 未测出 / 存疑清单（不得当作已证实）

1. **渲染层键盘可达性**（§6）：本机注入通道下渲染层收不到键盘事件 ⇒ 「JS 拿到 `Ctrl+S` 并 `preventDefault`」**未实测**，
   需真实桌面手工验收（本机鼠标可达、Qt 侧可派发，说明页面与派发链路本身没问题）。
2. **"QAction 抢键 ⇒ 渲染层收不到" 的差分证据**：**未实测**（基线本来就收不到键，无法做差分），列为**推测**。
3. **Qt 版本敏感性**：结论是 **Qt 6.11.0 特有值**；Qt 6.2–6.10、Qt 5.15 的 `actions()`/快捷键行为**未测**。
   实现里的幂等清理正是为此保留。
4. **真实窗口 vs offscreen**：本次两者结果一致；不排除其它平台插件组合下激活失败（首轮 windows 运行就出现过
   `isActiveWindow=False`，导致整轮按键无效）⇒ 验收脚本**必须**保留"敏感性对照"门禁，否则会把"按键没送到"误判成"宿主没反应"。
5. 外部文档核对：本机 `web_search` 不可用（无 API Key），`doc.qt.io` 抓取遇到跨域重定向限制 ⇒
   **本结论未引用 Qt 官方文档**，全部依据本机实测原始输出。
